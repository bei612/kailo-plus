## 附录：从仓库反推出的 CI 服务契约（2026-11-07 只读调研结果）
行号以分支 `feat/ci-service-rebuild` 上的仓库为准。下文"手册"指 `/volumes/kailo/CI-CD部署测试手册.md`。

### A. CLI（`orchestrator.py` 第 95–126 行的 CI 类）
- **`submit <commit40> <stage> [targets...]`**：stdout 最后一行必须是 32 位十六进制的 job ID。
  - 调用处：`submit SRC build <unit>`（:711）、`submit PIN check`（:869）。
- **`status <job>`**：输出 JSON；退出码 0 只代表成功读到状态。
- **`wait <job> --timeout 300`**：输出状态 JSON。
  - 退出码 0 表示 SUCCEEDED；1 表示 FAILED、CANCELLED 或 UNKNOWN；124 表示等待超时但任务仍在跑（调用方会接着再 wait）。
- **`logs <job> --tail N`**：纯文本。调用方用 grep 匹配 `FAIL|error|错误|^== |EXIT `。
- **状态 JSON 字段**：
  - `state`：QUEUED、RUNNING、DEPLOYING、SUCCEEDED、FAILED、CANCELLED、UNKNOWN 之一
  - `exit_code`、`reason`、`artifacts_path`
  - `generated_metadata_diff`：上游构建时需要
  - `waiting_for`：因内存不足排队时给出所需和可用的内存
  - `postgres`：image_id、version、cleaned_up
  - `artifact.sha256`：gen 任务需要
- **`node.py` 直接读取的队列文件**：`<queue>/jobs/<id>/status.json`，其中有 `stage`、`state`、`commit`（node.py:406-416、1000-1008；`hot-retention.py` 第 144–160 行）。
- **各子命令（手册 231–332）**：
  - `submit C fetch`：只从 GitHub 取源，准备 `<sources>/<C>/apps`、design 树和 `ready.json`。
  - `submit C docs`：执行 `tools/check-docs.sh`。
  - `submit C check`：执行 `check.sh --full`，带临时 PG；生成回执 `<sources>/<C>/check.json`，内容为 `{commit, job, diff}`，`diff` 为空表示 clean。
  - `check-step C lint|verify`（等价于 `submit C check-step …`）：带临时 PG；verify 会先跑 migrate。**这次改为接受分支上的 commit**（旧版不在 main 上就返回 128）。
  - `gen C`（等价于 `submit C gen`）。
  - `submit C build <target>`：只接受已登记的 target；未登记的直接拒绝，不建 job。
  - `submit C deploy buzz-web`：要求 full 回执、干净的源树、镜像按 digest 固定；执行期间状态为 DEPLOYING，此时拒绝 cancel；只允许 buzz-web。
  - `artifact <job>`：只用于 SUCCEEDED 的 gen 任务；先复核 sha256，再把 tar.gz 输出到 stdout。
  - `list`：列出活跃任务和 UNKNOWN 任务；`--all` 连已归档的也列出。
  - `cancel`：可重复执行。排队中的直接移除；运行中的杀掉进程组并清理临时容器；清理失败则标为 UNKNOWN。
  - `retry`：只用于 FAILED 或 CANCELLED 的非 deploy 任务，输出新的 job ID；UNKNOWN 拒绝重试。
  - `clean`：只预览；`clean --apply` 执行归档，保留 status、logs 和 artifacts，归档后的 ID 仍可查 status 和 logs。
  - `handoff`：输出结构化的待办，字段为负责人、状态、证据 job、下一步、完成条件。
- **通用规则**：
  - job ID 可以用 8 位以上的唯一前缀；有歧义或找不到时拒绝。
  - commit、stage、targets 完全相同时，复用已有的活跃 job。
  - 两条 lane，各自同时只跑 1 个：feedback（fetch、docs、check、check-step、gen）和 release（build、deploy）。
  - worker 重启时，正在跑的 job 标为 UNKNOWN，不重放。
  - root 执行时切换到 kailo-dev。

### C. 构建目标
- **`core-worker`**：执行 `tools/release.sh`。

- **上游产物**：执行 `tools/build-upstream.sh <name>`。
  - 内部流程：`upstream_manifest.py plan/stage` → `buildx build --push $REGISTRY/<name>:<base12>`，digest 取 buildx metadata；bundle 类产物输出到 `dist/<name>/`；最后 `upstream_manifest.py record`，改写 `<x>/fork/upstream.yaml`。
  - 退出码：3 表示缺 secret，2 表示缺 build arg。
  - 产物名单：agent-runtime、data-query-{ui,ai-service,engine,ibis}、document-editor、metering、model-gateway、file-storage-{adapter,service}、knowledge-{adapter,service,native-ui,document-reader}、collaboration-relay、web-client；其中 desktop-client 和 mobile-client 是 bundle。
- **record 阶段**：要求 `status.generated_metadata_diff` 是构建副本中 record 文件的 git diff。
  - 新增行必须匹配 `^\+\s+(source_digest|artifact_digest|build_config_digest):\s*sha256:<64hex>$`。
  - 日志要打印 `BUILD WORKTREE STATUS` 和 `GENERATED METADATA DIFF`。
  - 每次构建都在 task TMPDIR 里用固定 commit 新建一份 git 副本。
  - orchestrator 不通过 `kailo-ci artifact` 取构建产物。

### E. check.sh 的运行方式
- 在宿主机上只做启动器：没有 `/.dockerenv` 时调用 `run_in_check_container`（check.sh:1748）。
- 需要的环境：hot `TMPDIR`、`CHECK_CPUS`、`CHECK_MEMORY`、`CHECK_NETWORK`、`CHECK_CACHE_ROOT`。镜像 `local/kailo-check:<sha256(tools/check.Dockerfile)>` 不存在时，还要 `BUILDX_BUILDER`。
- 设置 `CHECK_SOURCE_REF` 时，会 git archive 这个 ref；design 树取自 `.github/workflows/check.yml` 里的 `DESIGN_COMMIT`。
- 步骤顺序：`status lint contract migrate verify replay trace supply seam security docs`。`DATABASE_URL` 没设时 migrate 会 SKIP。
- worker 要自己提供临时 PG：
  - 镜像与生产 core-db 相同；
  - 随机密码、私有网络、不发布端口、tmpfs 不超过 1G；
  - 用完销毁，并把结果写进 status 的 `postgres` 字段；
  - 只用于 check 和 check-step。
