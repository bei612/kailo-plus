# Wren isolated conformance provider

This is the missing Wren-side developer environment from `.design/07` section
8A (REQ-22, DD-76). It is not a replacement for Core/Worker's existing suite
runner, a production PEP, or a source of successful query/deployment results.
It serves explicitly delivered `data_query.v2` query and protocol PEP contexts
for the original native consumers. Core still freezes and runs all required
protocol and capability cases; this provider does not claim the full suite.

Run `node data-query/docker/conformance/provider.mjs` from the fixed source
candidate in the existing constrained Node SDK. Set
`WREN_CONFORMANCE_CONFIG_FILE` to an absolute, owner-only regular JSON file.
Keep the source and its existing `client-kit/adapter/protocol.mjs` together;
the installed Wren Knex dependency is resolved from `data-query/wren-ui`.
No dependency installation, signing-key generation or database migration is
performed by this command. No configuration is defaulted from a production
binding, platform browser session or another component.

The operator configuration contains exactly:

- `mode`: `CONFORMANCE_ONLY`;
- `listenHost`, `listenPort`: the explicitly delivered isolated network listener;
- `productionActionAudience`: the production audience which the isolated
  identity must not reuse;
- `environmentFile`, `identityFile`: the existing
  `ComponentConformanceEnvironment` and `ComponentConformanceIdentity` inputs;
- `queryFile`, `bindingFile`: the original Wren query/binding delivery files,
  pinned to that isolated instance and the same candidate artifact;
- `registrationFile`: the actual `data_query.v2` registration (V2 vectors;
  `data_query.v1` is refused, see the DD-124 section below);
- `databaseUrlFile`: the isolated native PostgreSQL connection, owner-only;
- `nativeFixtureFile`: the retained original deployment input and actual IDs,
  with exactly `projectId`, `deploymentId`, `modelId`, and `manifest`;
- `preparationGeneration`: the explicit positive safe-integer isolated generation,
  frozen with the other delivery files, never copied from production state.

For the explicit preparation operation, also supply `preparationFile`, another
owner-only JSON file containing exactly `graphqlUrl`, `publicOrigin`,
`humanTokenFile`, `projectId`, `modelId`, and `manifest`. The project/model must
already exist in the isolated native database through the original Wren setup;
the manifest is the original MDL input for that same model, not a passing result
or invented hash. `graphqlUrl` is `/api/graphql` on the existing environment's
adapter origin. `publicOrigin` is its actual native CSRF origin. The token file
contains a current independently delivered native HUMAN token for that instance;
it is not a platform Cookie, service token or credential generated by this tool.
The original middleware and resolver still authenticate and authorize every call.
Supply the same existing `WREN_NATIVE_IDENTITY_JSON` deployment value to this
command as to the native UI. `publicOrigin` must equal that verifier's actual
CSRF origin, not merely be a well-formed URL. Before each GraphQL request the
provider reads the complete native project set: this dedicated fixture requires
exactly its configured project. Both the original first-project selection and
the bound project selection therefore have the same target. The original
bound resolver remains the in-request authorization fence; these local reads
are not a replacement for it or an atomic permission transaction.

Preparation accepts the original physical-table MDL representation, including
the Rust engine's omission of null `refSql`. Its `tableReference` must exactly
match the native model's catalog/schema/table properties, and cannot coexist
with SQL. SQL-backed models must instead retain the exact nonempty native
`ref_sql` and no table reference. Missing or changed sources refuse preparation;
normalizing an absent SQL field does not authorize a different physical table.

Using the same existing provider command and configuration:

```sh
node data-query/docker/conformance/provider.mjs prepare
node data-query/docker/conformance/provider.mjs observe
```

`prepare` calls the original GraphQL `deploy(force: false)` only when this
isolated project has no deployment intent. With an existing intent it observes
`modelSync`, as does the explicit `observe` operation. No forced redeploy, retry
loop or second deployment ledger is introduced. The original DeployService
generates the MDL hash, commits its native intent and calls real AI pipelines;
observation remains in the original service. A timeout, GraphQL refusal, missing
identity/config, hash mismatch or lost acknowledgement cannot publish a fixture.
IN_PROGRESS and FAILED return their actual native status without publishing.
Only an actual SUCCESS row with the same manifest, captured model and connection
can produce `nativeFixtureFile`; its deployment ID is read from the native row,
never selected in configuration. Publication is owner-only and create-only;
same-byte re-observation is idempotent, but another fixture is never overwritten.
The command reads the native database and writes only this fixture file. It does
not create a project/model, activate a binding, produce SQL rows/types, choose
expected vectors, or run Core/Worker's suite. SQL and column expectations still
require the real original Ibis/query consumers before the first v1 registration.

Preparation starts a temporary listener from the same `listenHost`/`listenPort`
and original query `serviceTokenUrl`. Supply `preparationGeneration` explicitly
in this isolated operator configuration; it is not a production binding version
or a new wire field. Its only authenticated response is the existing native
HUMAN `authorizeScope` request (`discover`/`manage`). It never accepts a query
Action, returns an ActionToken, or treats an absent deployment as successful.
The configured native issuer and public JWKS endpoint must share this isolated
listener origin. A separately signed HUMAN token must have exactly the native
audience, the delivered instance claim and an unexpired bounded lifetime; the
provider pins that exact private token file and independently verifies it with
the conformance public JWKS. Do not use production SSO cookies or service tokens.
Service authentication, key files, generation/configuration and actual native
project/model facts are checked for each request. The returned conformance
revision is explicitly simulated and cannot authorize production access.
The listener closes after prepare/observe, including failure. Concurrent local
preparation cannot bind the same port twice; original native deployment row-lock
and observation semantics remain authoritative after a lost acknowledgement.

This isolation does not require a production PLATFORM_LLM_ROUTE binding. Under
design section 8A and the SELF_MANAGED_MODEL boundary in section 8.3, its real
AI providers may consume explicitly delivered, actually discovered model
services for synthetic fixture data. Do not fabricate a Gateway production key
or a model dimension. This does not approve a production release's model modes,
prove production usage metering, or exempt its later binding from those gates.

All input files and the existing query service-secret/JWKS files must be
absolute owner-only regular files, not symlinks. Identity contexts include the
three vector steps and their existing `permission-denied:` counterparts. The
Core signer still obtains its independent private key from its configured
OpenBao SecretRef. This provider loads public JWKS only. The original Wren
service-token client authenticates using its component-isolated delivered
credential; transport tokens live only in this provider's process and expire
using the existing identity `tokenSeconds`. No token or secret is logged.

Prepare the native fixture through the original Wren project/model/MDL and
DeployService consumers in an isolated instance. Retain the original manifest
submitted to DeployService and the IDs actually returned. Wait for its actual
SUCCESS observation; do not insert a SUCCESS row or pick placeholder IDs/hash.
The provider is read-only: it checks that project, captured model, columns,
successful deployment and connection fingerprint still match the original
query delivery and registration vector. It hashes the retained input using
the original `DeployService.createMDLHash` byte algorithm, and compares the
stored manifest structurally because PostgreSQL JSONB can reorder keys.

## data_query@2: Wren-generated identifiers are captured, not vector literals (DD-124)

Authority: design 02 DD-124(1)(2)(3)(5), 08 section 6, 16 V-SCN-152/153.
`data_query@1` wrote the deployment ID `1` and hash `b686…` that Wren's
original DeployService generated into its vectors, and typed them as an
integer and a 40-hex string, so no V2 placeholder could stand in their place.
`contracts/adapter/data_query.v2/registration.json` makes `deploymentId`,
`deploymentHash` and the ContentReference `nativeRevision` opaque non-empty
strings and keeps every other schema and declaration of @1. Its V2 case
`native_query` lets describe self-capture `deploymentId`/`deploymentHash`
(GENERATED_REF) and its typed ContentReference; dry_run and query send that
captured reference and expect the captured deployment identifiers. Core
captures them from this candidate's own SUCCEEDED describe response; neither
this provider nor any fixture supplies or predicts them.

The provider therefore accepts only a `data_query` contract version 2 with
`V2` vectors whose deployment fields are bound `{{CAPTURE:…}}` placeholders on
every step and whose dry_run/query inputs bind the captured
`nativeObjectRef`/`nativeRevision`; a V1 registration with literal deployment
values is refused (`preparation.test.mjs` checks both). The native fixture is
the deployment this isolated instance's DeployService actually committed:
`nativeFixtureFile.deploymentId` must be a positive safe integer, and the
SUCCESS row with that ID must match the retained manifest by the original
`createMDLHash` algorithm. Only the literal describe model metadata (name and
column types) is compared with the native model. The Wren adapter returns
`deploymentId` as the decimal string of its native deploy row and accepts only
that canonical form on the SQL input branch.

Terminal native status (DD-124(5)): `observe`/`execute` map the governed
`api_history` row's persisted state through the fixed release mapping
`SUCCEEDED`/`FAILED`; only those carry `nativeStatus` (the raw value) and
`terminalAt`. Every other state, including a missing one, is `UNKNOWN`
without native status. Nothing here has been run on the dev box; the Node
checks and the isolated run belong on the CI node.
