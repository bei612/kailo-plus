# WeKnora adapter native read increment

This is implementation evidence for `DD-94/98/108`, `SF-WEK-14` and the
knowledge capability contract, not a release approval or a statement that all
five knowledge keys are integrated. Source is present; no adapter image,
deployment, active binding or live AgentGateway invocation is certified here.

## Authority and actual consumers

The fixed readonly WeKnora commit is
`2be7bd40631dda1dd485306038f07a62e9ee287e`. Verified native symbols are
`internal/mcpserver/server.go::NewServer`,
`internal/mcpserver/tools_retrieve.go::Server.handleReadDocument`,
`internal/agent/tools/read_document.go::ReadDocumentTool.readPage` and
`internal/application/service/knowledge.go::knowledgeService.GetKnowledgeFile`.
The native MCP server, document/chunk repository, Editor/Viewer grants and
processing states remain authoritative. The adapter does not implement search,
store document bodies in Core or create another MCP registry/server.

The existing Cells adapter's ES256/JWKS verification, bounded HTTP/JSON,
SecretRef-file reading and original Core PEP callback now live in
`client-kit/adapter/protocol.mjs`. Both real adapters consume that same module.
Cells retains its original HUMAN file-launch and Agent revision-only policy;
the common verifier deliberately grants no business permission. Its existing
exports remain available to the original document launch/lifecycle consumers.
No existing Cells artifact is declared rebuilt by this source extraction.

The knowledge adapter consumes the already-selected official MCP SDK `1.26.0`
(`Client` and `StreamableHTTPClientTransport`), also pinned by the Wren UI.
Original initialization, notifications and JSON/SSE handling are left to that
SDK. Only endpoint configuration, delivered credential headers, bounded
response bytes and the configured overall deadline are supplied by this
adapter. There is no handwritten JSON-RPC transport or OAuth fallback identity.
Its lockfile was generated by npm in the existing limited SDK.

## Implemented boundary

The actual HTTP consumer implements `query_revision` and the read/export
branches of `execute`. The frozen binding supplies native MCP URL, credential
file, native KB, platform tenant/workspace, issuer/audience and the Core PEP
client identity. Request fields cannot choose another server, bearer or KB.
All three paths verify the original ActionToken and perform fresh Core PEP
checks before native access and again before releasing the result. Human
execution additionally checks the signed original EE and idempotency key;
Agent delegation and ResultExposure claims are not dropped. Missing or unknown
scope/claims/revision, unavailable PEP and post-read revocation return refusal,
not an empty successful result.

Original `read_document` now supports `metadata_only` without touching chunk
content. Document and KB summaries expose the precise native `UpdatedAt` as
`native_revision`; old `updated_at` and other native fields remain intact.
The adapter's query returns only `nativeObjectRef` and `nativeRevision`, and
requires the signed authorization root to equal the configured native KB.

`knowledge.read@v1` consumes the signed complete `ContentReference`, checks
that native document/KB/revision, then reads original MCP pages to completion.
It rejects pending native parsing, inconsistent page totals, duplicate or
foreign chunks and truncated pages instead of declaring a partial body done.
`knowledge.export@v1` consumes the same reference and the preceding native
`export_document` implementation, which reads original file bytes under the
original Editor requirement. Both re-read precise native metadata after the
operation, then reauthorize before returning the original typed reference and
the protocol's terminal read receipt. No write, re-index or deletion is started
by those paths. Empty native results are accepted only when their actual
complete native evidence proves them; a missing response is never success.

The five-key seed's earlier empty read/export/delete input schemas were found
not to match the existing HUMAN `ComponentActionInput.inputReference` consumer.
That schema/typed-suite correction is a separate Core batch; this adapter
expects the same complete typed reference, not caller-provided native IDs or
business text hidden in Core parameters. No active binding exists for this
unfinished release. Ingest/search/delete execution, native write observation,
usage extraction, lifecycle/conformance and live deployment are not accepted
by this increment. In particular native `deleted=true`, parse queued, missing
rows or lost replies must not be mapped to a fabricated completed operation.

## Native conditional deletion prerequisite (2026-10-06)

Authority remains DD-94/98 and SF-WEK-14: the adapter cannot delete a different
revision from its admitted ContentReference. Fixed upstream
WeKnora `2be7bd40631dda1dd485306038f07a62e9ee287e` provides
`WeKnora/internal/mcpserver/tools_ingest.go::Server.handleDeleteDocument`,
`WeKnora/internal/application/service/knowledge_delete.go::knowledgeService.DeleteKnowledge/executeKnowledgeDelete`,
and `WeKnora/internal/application/repository/knowledge_transfer.go::knowledgeRepository.UpdateKnowledgeForTransfer`.
The latter already fences the exact tenant, KB, status and updated timestamp
before native deletion touches indexes, chunks or files; this implementation
reuses that CAS rather than introducing an adapter deletion store.

The native MCP `delete_document` optional `expected_revision` now reaches
`KnowledgeService.DeleteKnowledgeAtRevision`. The service validates its own
authorized deletion plan, not merely the earlier MCP metadata read. Empty or
non-string supplied revisions refuse rather than falling back to unconditional
deletion. Existing independent native callers that omit the optional field keep
their original semantics. No platform contract, migration or generated type
changes in this increment. Concurrent edits between planning and the original
checkpoint fail the existing CAS; stale or missing revisions fail before any
cleanup. The original KB editor grant remains mandatory.

This does **not** certify the full platform deletion operation: the native
`deleted: true` return remains an acknowledgement, not a new platform terminal
receipt. Original Wiki retract, physical-file cleanup and accounting include
best-effort paths, and the existing Asynq deletion handler does not yet provide
the adapter's durable idempotent observation. Adapter deletion execution remains
absent; no row-missing inference, fake success or new lifecycle authority was
introduced.

Implementation-after evidence used the existing native Go SDK with inspected
4 CPU / 8 GiB limits and its existing Data caches. Command:

```sh
GOCACHE=/cache/build GOMODCACHE=/cache/mod GOPROXY=off go test \
  ./internal/mcpserver ./internal/application/service \
  -run 'Test(DeleteDocumentPasses|DeleteKnowledgeAtRevision|DocumentAndChunkWritesRequireOperationGrant|ExportDocument|ReadDocumentMetadata|AddDocumentRetryKey|ManualCreation)' -count=1
```

Both packages passed, exit 0. In the private SDK only, reversing the native
revision comparison produced actual failures for current/stale/concurrent-edit
cases, exit 1; notably stale deletion incorrectly succeeded. Restoring the exact
formal bytes (`cmp` exit 0) and repeating the command passed both packages, exit
0. The existing service fixture exercises real SQLite rows/CAS; native MCP
checks confirm exact forwarding, foreign-scope refusal and no empty-value
fallback. Raw logs next to the prior adapter logs are
`native-delete-revision.log`, `native-delete-revision-mutation.log`, and
`native-delete-revision-restored.log`. No image build, full check, deployment or
live deletion ran.
