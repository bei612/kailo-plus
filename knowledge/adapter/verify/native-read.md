# WeKnora adapter native read increment

This is implementation evidence for `DD-94/98/108`, `SF-WEK-14` and the
knowledge capability contract, not a release approval or a statement that all
five knowledge keys are integrated. Source is present; no adapter image,
deployment, active binding or live AgentGateway invocation is certified here.

## Authority and actual consumers

The fixed readonly WeKnora commit is
`2be7bd40631dda1dd485306038f07a62e9ee287e`. Verified native symbols are
`internal/mcpserver/server.go::NewServer`,
`internal/mcpserver/tools_retrieve.go::Server.handleReadDocument`,

The native MCP server, document/chunk repository, Editor/Viewer grants and

The existing Cells adapter's ES256/JWKS verification, bounded HTTP/JSON,

Cells retains its original HUMAN file-launch and Agent revision-only policy;
the common verifier deliberately grants no business permission. Its existing
exports remain available to the original document launch/lifecycle consumers.
No existing Cells artifact is declared rebuilt by this source extraction.

The knowledge adapter consumes the already-selected official MCP SDK `1.26.0`
(`Client` and `StreamableHTTPClientTransport`), also pinned by the Wren UI.
Original initialization, notifications and JSON/SSE handling are left to that
SDK. Only endpoint configuration, delivered credential headers, bounded
response bytes and the configured overall deadline are supplied by this
adapter. There is no handwritten JSON-RPC transport or OAuth fallback identity.
Its lockfile was generated by npm in the existing limited SDK.

## Implemented boundary

The actual HTTP consumer implements `query_revision` and the read/export
branches of `execute`. The frozen binding supplies native MCP URL, credential
file, native KB, platform tenant/workspace, issuer/audience and the Core PEP
client identity. Request fields cannot choose another server, bearer or KB.
All three paths verify the original ActionToken and perform fresh Core PEP
checks before native access and again before releasing the result. Human
execution additionally checks the signed original EE and idempotency key;
Agent delegation and ResultExposure claims are not dropped. Missing or unknown
scope/claims/revision, unavailable PEP and post-read revocation return refusal,
not an empty successful result.

Original `read_document` now supports `metadata_only` without touching chunk
content. Document and KB summaries expose the precise native `UpdatedAt` as
`native_revision`; old `updated_at` and other native fields remain intact.
The adapter's query returns only `nativeObjectRef` and `nativeRevision`, and
requires the signed authorization root to equal the configured native KB.

`knowledge.read@v1` consumes the signed complete `ContentReference`, checks
that native document/KB/revision, then reads original MCP pages to completion.
It rejects pending native parsing, inconsistent page totals, duplicate or
foreign chunks and truncated pages instead of declaring a partial body done.
`knowledge.export@v1` consumes the same reference and the preceding native
`export_document` implementation, which reads original file bytes under the
original Editor requirement. Both re-read precise native metadata after the
operation, then reauthorize before returning the original typed reference and
the protocol's terminal read receipt. No write, re-index or deletion is started
by those paths. Empty native results are accepted only when their actual
complete native evidence proves them; a missing response is never success.

The five-key seed's earlier empty read/export/delete input schemas were found
not to match the existing HUMAN `ComponentActionInput.inputReference` consumer.
That schema/typed-suite correction is a separate Core batch; this adapter
expects the same complete typed reference, not caller-provided native IDs or
business text hidden in Core parameters. No active binding exists for this
unfinished release. Ingest/search/delete execution, native write observation,
usage extraction, lifecycle/conformance and live deployment are not accepted
by this increment. In particular native `deleted=true`, parse queued, missing
rows or lost replies must not be mapped to a fabricated completed operation.

## Native conditional deletion prerequisite (2026-10-06)

Authority remains DD-94/98 and SF-WEK-14: the adapter cannot delete a different
revision from its admitted ContentReference. Fixed upstream
WeKnora `2be7bd40631dda1dd485306038f07a62e9ee287e` provides
`WeKnora/internal/mcpserver/tools_ingest.go::Server.handleDeleteDocument`,
`WeKnora/internal/application/service/knowledge_delete.go::knowledgeService.DeleteKnowledge/executeKnowledgeDelete`,
and `WeKnora/internal/application/repository/knowledge_transfer.go::knowledgeRepository.UpdateKnowledgeForTransfer`.
The latter already fences the exact tenant, KB, status and updated timestamp
before native deletion touches indexes, chunks or files; this implementation
reuses that CAS rather than introducing an adapter deletion store.

The native MCP `delete_document` optional `expected_revision` now reaches
`KnowledgeService.DeleteKnowledgeAtRevision`. The service validates its own
authorized deletion plan, not merely the earlier MCP metadata read. Empty or
non-string supplied revisions refuse rather than falling back to unconditional
deletion. Existing independent native callers that omit the optional field keep
their original semantics. No platform contract, migration or generated type
changes in this increment. Concurrent edits between planning and the original
checkpoint fail the existing CAS; stale or missing revisions fail before any
cleanup. The original KB editor grant remains mandatory.

This does **not** certify the full platform deletion operation: the native
`deleted: true` return remains an acknowledgement, not a new platform terminal
receipt. Original Wiki retract, physical-file cleanup and accounting include
best-effort paths, and the existing Asynq deletion handler does not yet provide
the adapter's durable idempotent observation. Adapter deletion execution remains
absent; no row-missing inference, fake success or new lifecycle authority was
introduced.

4 CPU / 8 GiB limits and its existing Data caches. Command:

## Retained native conditional deletion task (2026-10-07)

This increment follows DD-94/98/108 and SF-WEK-14. It adds the real
`knowledge.delete@v1` execute/observe consumer, not another native lifecycle or
Core deletion table. Upstream commit remains
`2be7bd40631dda1dd485306038f07a62e9ee287e`; the exact original seams are
`WeKnora/internal/handler/knowledge.go::KnowledgeHandler.enqueueKnowledgeListDelete`,
`WeKnora/internal/application/service/knowledge_clone_move.go::knowledgeService.enqueueMovedKnowledgeProcessing`,
`WeKnora/internal/router/task_inspector.go::asynqTaskInspector.GetRuntimeTask`, and
`WeKnora/internal/application/service/knowledge_delete.go::knowledgeService.ProcessKnowledgeListDelete`.
The first already dispatches Asynq maintenance work; the second already uses
stable TaskID and retained results, and the inspector reads that same original
queue. No new queue engine, generic executor or operation database is added.

The native MCP `delete_document` consumes the existing admitted KB and precise
document revision plus a stable idempotency key. It reuses original editor/write
authorization, native deletion planning and repository CAS. The task payload
pins tenant, KB, document, revision and its original initiator. A duplicate key
reads the retained task; observation never calls enqueue, and does not need a
document row that a completed deletion has already removed. A mismatched scope,
malformed receipt or expired/missing task refuses instead of inferring success.
The result lives in the original Asynq ResultWriter and is written only after
conditional cleanup has no observed failure. Redelivery with that exact receipt
does not repeat cleanup; without one, the original revision CAS prevents a
partially executed deletion from being replayed. Cleanup failure skips automatic
write retries and remains UNKNOWN for reconciliation, not fabricated FAILED.

Source review caught and fixed queued Wiki-state drift: KB settings can change
after admission. The receipt now obtains its Wiki flag from the actual deletion
plan used by the original CAS/cleanup, not an admission-time payload flag. The
obsolete payload flag was removed. Independent conditional deletion and the
task share that same implementation. An implementation-after native regression
enables Wiki after enqueue, requires the retained receipt to say Wiki, and
requires UNKNOWN while no retract success receipt exists; this new Go case is
initially remained unexecuted because native compilation stopped on disk limits;
its later actual execution is recorded below.

Independent original native callers that omit the conditional/idempotency
arguments keep their native best-effort semantics. Conditional callers now also
retain Wiki-reference, tag, file/image and storage-accounting failures that were
previously only logged. In particular, a row removed before a later cleanup
failure is not a terminal receipt, and a missing row on a conditional retry is
not success. The configured `knowledge_base.delete_receipt_retention` supplies
the original queue retention; expiry loses the evidence and stays UNKNOWN.
This is an additive native task payload/configuration change, with no new
platform schema, migration, business-body copy or generated client model.

Wiki-enabled deletion is deliberately **not certified complete** by this
increment. Original `task_pending_ops` removes successful retract work and
original dead letters can be removed by operators, so zero rows in both is not
durable terminal evidence. The observer reads those existing scoped repositories:
pending retract remains RUNNING, failure or absence of a durable success remains
UNKNOWN. A Wiki success receipt from the original retract consumer is still a
real remaining integration gap; no second timer/store or absence-as-success
shortcut is introduced. Non-Wiki cleanup can return SUCCEEDED only with the
matching retained native receipt and its actual completion time.

Adapter execute and observe both verify the original token/wire hash and fresh
Core PEP before and after native access. Only the existing configured native KB,
server and credential are used. The observer takes the Core's existing
ExternalExecution reference and stable key; it does not re-run the execute path.
The normal typed input remains the full ContentReference. Queue acknowledgements,
unknown states, foreign scope, missing timestamps and post-call revocation cannot
produce an asserted completed operation.

### Receiver read batch and original single-file import

This increment implements DD-89 / component standard §8.2 for an already
governed `knowledge.ingest` call. It does not register an incomplete binding or
claim that an automatic Cells data-source synchronization is available.

The authority is the existing SERVICE principal, Resource permission,
ActionExecution, quota decision and audit. The receiver's admitted ingest is
provenance, not a HUMAN execution parent: the source read creates its own root
SERVICE ActionExecution and operation. The existing parent-context constraint
correctly rejects borrowing a HUMAN's actor/operation. Migration
`20261007060000_service_read_scope` extends the original definition-freeze
function only for this authenticated receiver/source relationship; it adds no
table, workflow, body store or permission authority. A Tenant-level receiver
can read an explicitly granted Workspace resource. Other scope rules remain
unchanged. Receiver generation, source definition/release/generation and source
resource version are frozen; retries retain the same read token stamp and do
not renew an expired token.

The affected path is the original receiver adapter → Core
`/service/v1/adapter/request_read_grant` → source adapter → native Cells
versioned bytes → original WeKnora `add_document` and parse queue. The source
checks its actual authorized root/UUID/version and trusted download origin,
then exact length and SHA-256; a second current PEP check precedes disclosure.
The receiver checks its own write permission again before importing. The
source operation is carried in the binary receipt and retained in the native
Knowledge metadata. Core receives references/hashes only, not file bytes.
