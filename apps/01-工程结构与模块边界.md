## 2. Contract package

`contracts/` 是设计合同的可执行投影，不是新权威。它至少覆盖：

- 强类型 ID、scope 与 `NONE` 语义；
- `.design/03` 的封闭枚举、状态与 reason code；
- BFF query/semantic command/stream schema；
- Governed Action、ActionToken、ExecutionContext 与 ResultExposure；
- Component manifest、Host API、Adapter Protocol 与 handshake；
- 各能力类别的版本化能力契约（`contracts/adapter/<category>.vN`）：契约键、参数/结果 schema、permission 映射、ContentReference 语义与能力声明；
- Workflow input、Update/Signal、projection 与 ExternalExecution schema；
- Audit/Usage/CloudEvent envelope；
- 兼容版本、digest 与 schema canonicalization 规则。

每个语言绑定由同一 schema 生成，或以其他方式证明双向一致。Rust、Go、TypeScript、Dart 和 adapter 语言不得各自维护同名但不同义的枚举。

## 3. Core/BFF 模块

Core 保持一个部署单元和一个业务事务边界，内部使用深模块隔离：

| 模块 | 公开接口 | 隐藏内容 |
|---|---|---|
| Identity/Scope | session 解析、scope guard、principal context | OIDC header 细节、session 存储 |
| Catalog | immutable release/version、binding、Agent/Skill/Tool 查询与命令 | schema canonicalization、projection bookkeeping |
| Admission | preview、admit、recheck、revoke | SpiceDB 组合、approval/quota 判定顺序 |
| Workflow Port | start/update/signal/cancel/query | Temporal client、ID/reuse policy、投影修复 |
| Platform Port Router | 已知 port 的 typed call | provider generation、认证、read-back hash |
| Application Dispatcher | Adapter Protocol 调用 | endpoint、token、native scope、error mapping |
| Projection | Buzz/SpiceDB/Gateway/Web/Task 投影 | generation 与 reconcile 状态 |
| Reservation | CapacityLease、QuotaReservation | 并发锁、过期与 UNKNOWN 回收 |
| Audit/Usage Outbox | append、publish、reconcile | outbox 事务、redaction、retry cursor |
| BFF | typed query、semantic command、受权 stream | Relay 签名、native credential、内部 refs |
| Runtime Supervisor | Codex process lifecycle | CODEX_HOME、IPC、secret env、restart/drain |

模块之间传递 `ExecutionContext` 和稳定引用，不传 Browser header、原始 token 或任意 JSON context。跨模块内部调用不递归创建 Governed Action；只有用户、Agent、Schedule、callback 或 Workflow 可达入口建立 Action。

## 4. Application Worker

Worker 是独立 Go 进程，但与 Core 同仓、同 release train、共享 versioned contracts。它只承担：

- `ApprovalWorkflow`、`AgentTaskWorkflow`、`ComponentTaskWorkflow`；
- `.design/06` 的封闭 ComponentTaskWorkflow kind；
- Activity heartbeat、retry、cancel、continue-as-new 与 replay compatibility；
- 通过 Core service API 执行 fresh admission、状态投影、audit/usage 写入；
- 通过 adapter 执行 native dispatch、observe、cancel、reconcile。

Worker 不直写 Core 数据库，不复制 Core authorization，不把 Search Attribute 当隔离边界。Workflow 只保存冻结 ID、版本、hash、状态和受限 reference。

## 5. Web 与 Component Host

`web/buzz-web` 保存 Web 端受控上游基线与 Kailo patch；`desktop/` 保存 Buzz Desktop 基线与 patch。Web 与 Desktop 的上游 UI 主体是两个代码库（hardy4yooz/buzz-web 与 block/buzz 的 `desktop/`），各自保留、各自以补丁改造；两端共用的是 Kailo 自有的 TypeScript 主体（`web/packages/platform`：BFF 客户端、平台页、原生端登录引导与文案，经 `vendor_files` 放入两端，只在传输上分 Web fetch 与 Desktop `kailo_api` 两个实现）与同一份 Component Host 契约（ADR-09）；`mobile/` 保存 Buzz Mobile 的 Dart 基线与 patch，不共用前端运行时（`SF-MOB-02`）。`component-host` 是一次性主体二开，由 Web 与 Desktop 两端共同实现同一契约。客户端层固定规则：

- Browser 只连接同源公开入口；AgentGateway 组合 `/app/*`、`/api/*` 与 `/component-artifacts/*` 路由；
- Buzz Web 的 Relay query/subscribe/publish/media 全部经 BFF transport，浏览器不持有 signer；Buzz Desktop 与 Buzz Mobile 本机持钥并直连 Relay，其协作数据平面准入由 Relay 执行（`DD-75`）。三端的管理平面一律经 BFF，不因持钥方式放宽；
- Host-native 页面优先覆盖首批管理面；
- Remote module 只加载 Catalog 已批准、内容寻址、同源的 artifact；
- module 只能注册固定 slot，使用窄 Host API；BFF 对每个请求重做准入；
- theme 与 locale 使用订阅式 presentation context；module catalog 按 namespace 校验；
- `DOCUMENT_EDITING` 实现只经通用 `SOURCE_BOUND_PROTOCOL` surface 打开（内置参考实现为 ONLYOFFICE 的 WOPI launch），承载端不按实现产品分支渲染，也不把 iframe 当通用组件机制。

## 6. Adapter、Driver 与 Protocol Peer

| 形态 | 代码位置 | 使用规则 |
|---|---|---|
| Platform Port Client | `core` 内部 | 仅连接 `.design/07` 已知 platform port |
| Remote Adapter | `adapters/<category>/<implementation>` | 业务能力服务的默认形态：独立部署，固定 binding/native scope，执行 Adapter Protocol 与所实现能力契约 |
| Embedded Driver | Core/Worker 编译边界 | 只限平台自身已编译的 driver，新增或升级即重发 Core/Worker；ApplicationBinding 不得选择，业务能力服务不以此形态接入（`DD-64`、`DD-87`） |
| Protocol Peer | 对应 integration 模块 | 按协议定义：只用于平台与一个业务能力服务之间、经 binding 配置的标准协议端点（如 MCP endpoint、`SOURCE_BOUND_PROTOCOL` launch）。两个业务能力服务之间的协议是同一能力组件的内部集成，不是 Protocol Peer，也不由平台配置数据面直连（`DD-58`） |
| Upstream Patch | `upstream-patches/<project>` | 对应具名 `SS-*`，产出独立可追溯 artifact；业务能力参考实现的 patch 只是该实现的 release 前置 |

Adapter 不拥有 Tenant、Workspace、owner、permission、Workflow 或账本。它只把平台固定上下文映射到 native API，并返回标准化 observation/evidence。

业务能力服务的工程规则：

- 可替换业务服务不得成为平台发布前置：Core、Worker、三端与平台必需上游的构建、测试、部署前置校验与发布不依赖任何业务能力服务、其 adapter、其 upstream patch 或其镜像；零业务能力 binding 的部署必须能完整构建、启动并通过平台门禁（`DD-87`、`DD-91`）。
- 能力契约 schema 位于 `contracts/adapter/<category>.vN`，是参数、结果、错误映射与一致性套件的唯一权威；契约键的新增、删除或语义变化只以新版本目录发布（`DD-88`）。
- Core、Worker 与承载端代码只按能力类别与契约键分支，不出现实现产品名的分支、实体、Workflow kind 或 reason code；`component_type_key` 只记实现来源。
- 数据隔离（`DD-93`）：平台核心每个服务与每个业务能力实现各自使用独立数据库实例或至少独立 database、独立凭据与独立私有数据网络，禁止共用 schema 与跨库访问；Core 迁移只作用于 Core 自己的数据库，Core 不持有任何业务能力服务的数据库凭据；组件状态目录不放在 Core/Worker 运行体内；业务能力服务的密钥只经 release `secret_schema` 声明，由 Core 按通用 schema 校验并经 OpenBao 投递。

## 7. 持久化与事务边界

Core 的具体数据库由 Stage 0 ADR 固定，但必须提供：

- Action/Operation/ExternalExecution/Audit/Outbox 的原子写入；
- immutable version 与乐观并发控制；
- Tenant+subject+meter 串行化的严格 reservation；
- stable idempotency key 与唯一约束；
- projection generation 的原子切换；
- 可审计迁移与 point-in-time recovery；
- 管理列表的 Core 自有分页，再经 SpiceDB bulk check 过滤。

不得以跨服务分布式事务替代设计中的 outbox、idempotency、observe 与 reconcile。

## 8. 部署与网络边界

实施不预设 Kubernetes。任何部署形态都必须维持：

- Browser 只能到达公开 AgentGateway；
- BFF 只接受 Gateway 内网身份投影，缺 issuer/subject 的请求全部拒绝；
- SpiceDB、Temporal、OpenMeter、OpenBao、AgentGateway admin 和 native 管理 API 不公开给 Browser/Agent；
- Core/Worker/adapter 各自使用最小 service identity 与独立 secret audience；
- 每个服务的数据库只在自己的私有数据网络内可达；业务能力服务与 Core、Worker 不共用数据网络，两个业务能力服务之间没有平台配置的数据面连通（`DD-93`）；
- 每个 Tenant/binding/runtime 的 native isolation 与 endpoint 由 Catalog 固定，不从请求 payload 推断；
- 网络隔离是纵深防御，不替代应用层认证、fresh authorization 与 scope guard。

## 9. 禁止的结构漂移

- 新建第二套 Agent Registry、Workflow、Quota、Audit、Memory 或 Observability 权威；
- 让 application adapter 变成共享业务数据库或万能代理；
- 由 Gateway、Buzz roster、Temporal Search Attribute 或组件原生角色反推 Kailo membership；
- 将 Remote module、iframe、前端 route visibility 当作授权边界；
- 为每种业务资源复制一套 Workflow 类型；
- 直接写业务能力服务的数据库或其内部状态（如参考实现内部的 CocoIndex state）、Temporal history 或 OpenMeter ledger；
- 由平台以 Schedule、Workflow 或端口编排业务能力服务之间的数据同步（`DD-89`）；
- 让 Core 复制消息、文件、chunk、SQL row、prompt/response 或文档正文，或持有业务能力服务的数据模型（`DD-90`）。
