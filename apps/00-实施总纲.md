# Kailo 一期实施总纲

## 1. 目标

把 `.design` 中已经闭合的产品合同实现为一期三端交付的企业级多人、多 Agent 协作平台，并保持以下核心性质：

- Buzz Client Surface（Web、Desktop、Mobile）是仅有的交互入口，数据面与管理面位于同一产品壳层；三端能力按 `REQ-21` 分级，分级不改变任何治理结论（`DD-74`）；
- Buzz 协议身份的密钥托管按端确定：Web 为 `SERVER`，Desktop 与 Mobile 为 `CLIENT`；协作数据平面的准入执行点是 Relay，管理平面三端一律经 BFF（`DD-75`）；
- Tenant、Workspace、审批、Workflow、授权、容量与计费、操作审计、业务可观测性贯穿 Core 与每个组件；
- 主题与 i18n 贯穿每个用户可达前端 surface；
- 成熟上游保持独立权威，Kailo 通过有版本的 port、adapter、driver 或协议接缝组合它们；
- 长时任务、审批、取消、重试与结果不明对账统一使用 Temporal；
- 上游更新可以被差异化吸收，但不会自动扩大产品能力或权限。

## 3. 实施原则

### 3.1 先纵向闭环，后扩大资源类型

每个阶段必须交付一条从该阶段所含客户端到权威后端、再回到用户可见状态的完整链，包含身份、授权、审计、失败语义和恢复。不得先批量搭建互不连通的服务，再集中补治理。

### 3.2 设计状态直接控制发布

| 设计状态 | 工程动作 |
|---|---|
| `UPSTREAM_SUPPORTED` | 固定版本与配置前提，留下该行为在固定版本上成立的证据 |
| `DESIGN_DEFINED` | 在 Kailo 代码中实现领域合同与验证场景 |
| `ADAPTER_REQUIRED: SS-*` | 实现指定接缝并取得接缝成立的证据后才开放能力 |
| `BLOCKED: GAP-*` | 不生成入口、路由、Tool、Action、Workflow 或开关 |
| `EXCLUDED` | 不进入一期依赖、镜像、运行拓扑和产品导航 |

### 3.3 权威数据不复制正文

Core 保存 scope、owner、binding、准入、reservation、projection、audit/outbox 与外部引用。Buzz 消息、Cells 文件、WeKnora 索引、Wren 模型、Temporal history、OpenMeter 账本和 Codex thread 留在各自权威系统。跨系统读取使用稳定引用和受权联合视图。

### 3.4 失败优先于降级

认证、scope、权限、binding、secret、projection、usage correlation 或终态证据缺失时 fail closed。不得回退到默认 Tenant、默认实例、共享身份、弱认证、重复执行或“成功但不可核验”。

## 4. 一期运行单元

| 运行单元 | 语言/形态 | 责任 |
|---|---|---|
| Buzz Web + Component Host | TypeScript（浏览器） | UI、主题/i18n、语义命令、受控动态组件 |
| Buzz Desktop + Component Host | TypeScript（Tauri 壳）+ Rust `src-tauri` | 与 Web 同一 TypeScript 主体；本机持钥、直连 Relay（`SF-DSK-01`） |
| Buzz Mobile | Dart/Flutter | 独立主体；非组件宿主、不承载 editor surface；本机持钥、直连 Relay（`SF-MOB-01`、`SF-MOB-02`） |
| Platform Core/BFF | Rust 模块化服务 | 领域权威、BFF、Admission、Catalog、Projection、Reservation、Audit/Outbox、port/adapter dispatch |
| Application Worker | Go 独立进程 | Temporal Workflow/Activity、审批、长任务、对账与投影 |
| Codex Runtime | 每 Installation 的受监督进程 | Agent turn 与 thread；无本地 environment |
| Application Adapters | 独立服务 | Cells、WeKnora、Wren 等 native API 到 Adapter Protocol 的窄映射 |
| CocoIndex Runner | Rust library/runner | 在 Temporal Activity 驱动下执行跨 Resource 增量物化 |
| 上游权威服务 | 独立部署 | Buzz Relay、AgentGateway、SpiceDB、OpenBao、Temporal、OpenMeter、Cells、DocumentServer、WeKnora、Wren |

该清单不引入新的 control plane。部署进程数量不改变 `.design/04` 与 `.design/15` 的权威边界。

## 5. Stage 0：工程基线

Stage 0 在任何业务能力编码前完成，产物包括：

1. 建立单仓目录、统一格式化与静态检查入口、版本锁和可重复开发环境。验证手段由实现者选择，本目录只要求结果可复核。
2. 从 `.design/03` 生成或维护一个语言无关的 contract package：标识符、枚举、错误码、Action/Workflow/Adapter/Host 协议 schema；生成物不得成为第二权威。
3. 按 `06-工程基线规范.md` §1 建立设计追溯清单，并以 `05-设计覆盖矩阵.md` 的归属为完备性判据。
4. 按 `06-工程基线规范.md` §4、§5 冻结错误分类与 reason code、API 兼容规则、数据库迁移规则、Workflow 版本规则和事件/outbox 幂等规则。
5. 按 `06-工程基线规范.md` §6 完成 ADR-01 至 ADR-07；ADR 必须保持现有服务边界和权威划分。
6. 建立测试环境所需的上游固定版本清单；实现工程引用 artifact 或镜像，不从 `.references` 工作树构建。
7. 建立 secret 扫描、依赖与许可证清单、SBOM、artifact digest 与来源证明流程。
8. 建立最小发布单元：Core/BFF、Worker、Web、每个 adapter/runner 各自可版本化、可回退。

Stage 0 退出条件逐项可勾选，任一未达成即不进入 Stage 1：

- [ ] 统一检查命令在空系统上通过格式、静态检查、contract compatibility、迁移演练与产物来源验证；
- [ ] 所有语言绑定通过 schema round-trip 与兼容检查，不存在同名异义枚举；
- [ ] 空迁移可前进、可回滚、可安全停止；
- [ ] 空 Workflow history 可 replay；
- [ ] 追溯清单不存在无设计来源的能力，且每条记录的 `stage` 与 `05-设计覆盖矩阵.md` 一致；
- [ ] 能力注册表能拒绝含非空 `blockers` 的能力与 `.design` 判为 `EXCLUDED` 的能力；
- [ ] 部署前置不变式的校验机制已建立：`07-运行与运维基线.md` §1 中属于本 Stage 已接入组件的每一条都已实现校验，且校验失败会阻止启动或激活；尚未接入的组件在其接入 Stage 的退出门禁中补齐，机制本身不得在后续 Stage 重建；
- [ ] baseline manifest 机制已建立：进入本 Stage 运行拓扑的每个上游都有一份，且 `evidence_commit` 与 `implementation_base_commit` 的关系已显式声明；后续 Stage 引入新上游时同步新增；
- [x] ADR-01 至 ADR-07 全部处于"已接受"状态（见 `06-工程基线规范.md` §6 与 `docs/adr/`）；
- [ ] 每个发布单元可独立版本化、可回退，并可追溯到源码 commit、依赖锁与 digest。

## 6. 工程决策门禁

以下选择在 Stage 0 通过 ADR 固定，未固定前不进入业务代码：

- Core 持久化数据库与事务/outbox/锁语义；
- Core 内部模块通信与 API schema 工具；
- Core 与 Worker 的 contract 生成策略；
- 本地开发和部署编排方式；
- 可观测数据的具体存储与查询后端；
- artifact registry、签名、SBOM 与 provenance 工具；
- CI 执行环境与受保护分支规则。

ADR 的验收标准是满足 `.design` 合同，而不是改变合同以迎合工具。

## 7. 完成定义

一期完成同时满足：

- `02-纵向交付路线.md` 的所有非排除阶段通过退出门禁；
- `03-验证发布与验收门禁.md` 的发布门禁全部通过；
- `.design/15` 的一期生产总门禁所列 `SS-*` 均已闭合并可追溯到构建产物；
- `GAP-LCM-01` 对应 Tenant 销毁入口仍不可见，除非设计权威先以新源码证据解除阻断；
- 每个 active release/binding/runtime 都能追溯到源码、配置、secret version、schema、artifact digest 和验证报告；
- 所有关键操作可从 `operation_id` 受权关联 Action、Workflow、ExternalExecution、Audit、Usage 与 native evidence；
- 灾难恢复、回滚、撤权和结果不明对账均完成演练。
