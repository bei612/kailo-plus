# 工程基线规范

本文件固定 Stage 0 必须产出的机器可读工件的确切形状，以及未被 `.design` 固定的工程决策的记录方式。其他实施文档引用这些格式，不重复定义。

格式是工程约定，不是产品语义。字段含义冲突时以 `.design` 为准。

## 1. 能力追溯记录

`03-验证发布与验收门禁.md` 的追溯检查读取这一格式。每个进入实现的能力一条记录，存放于 `tools/traceability/`，随代码提交一起演进。

```yaml
capability_id: file_storage.open_edit         # 稳定、全局唯一、小写点分；不含实现产品名
title: 在承载端（Web/Desktop）中以编辑模式打开文件存储中的文档
stage: EXT-FILE                                 # S0–S5 | PC | EXT-BASE | EXT-FILE | EXT-KNOW | EXT-DATA
status: planned | in_progress | shipped | withdrawn
exposure: none | internal | tenant_admin | end_user

design:
  requirements: [V-REQ-16]
  decisions: [DD-30, DD-31, DD-32, DD-103, DD-104]
  facts: [SF-CEL-05, SF-CEL-12, SF-OFF-03]     # 内置参考实现的证据；外部实现以一致性套件结果为证据
  seams: [SS-DSK-EDITOR-WINDOW, SS-CEL-WOPI, SS-OFF-WOPI]  # 前者属 EXT-FILE 能力契约段，后两者是参考实现的 binding 激活门禁；都不是平台门禁
  blockers: []                                  # 非空即禁止 exposure 超过 none
  entities: [ProtocolSession]

validation:
  scenarios: [V-SCN-24, V-SCN-25, V-SCN-26]
  evidence:                                     # 形式不限：自动化、脚本化演练或可复现的核验记录
    - dimension: 上游接缝                        # 取自 03-验证发布与验收门禁.md §3
      ref: adapters/file_storage/cells-onlyoffice/verify/wopi_pep.md
    - dimension: 端到端场景
      ref: web/verify/document_edit.md

implementation:
  owners: [team-capabilities]
  paths: [core/crates/capability, adapters/file_storage/cells-onlyoffice, web-client/web/src/features/document, collaboration/desktop/src/features/document]
  surfaces: [web, desktop]                       # 该能力实际开放的端；取值来自 web|desktop|mobile
  schemas: [contracts/adapter/file_storage.v1, contracts/api/document.v1.json]
  migrations: [core/migrations/0042_protocol_session.sql]

release:
  artifacts:
    - name: core
      digest: sha256:...
  gate: blocked_until_seams_closed | ready | shipped
```

检查器的硬规则：

- 每个 `design.*` ID 必须在 `.design` 中解析；解析不到即失败。
- `status` 非 `withdrawn` 时 `design` 至少有一个 `requirements`、`decisions` 或 `seams` 条目。
- `blockers` 非空时 `exposure` 必须是 `none`。
- `seams` 非空时每个接缝必须有一条 `dimension: 上游接缝` 的证据；证据的形式不限，但必须指向可复核的记录。
- `stage` 必须与 `05-设计覆盖矩阵.md` 对该能力所含实体与决策的归属一致；不一致时要么改矩阵要么改记录，不得两边并存。
- `exposure` 高于 `none` 时 `release.artifacts` 必须有 digest。
- `capability_id`、`action_key`、Tool 名与 `type_key` 不得含实现产品名：业务能力只用能力契约键（如 `file_storage.write@v1`）与 `<category>.<kind>` 命名空间，实现来源只记在 `component_type_key`，不进入标识符（`DD-88`）。
- `stage` 取 `02-纵向交付路线.md` §1.0 的归属单元：`S0`–`S5`、`PC`（平台一期收口）、`EXT-BASE`（组件与能力契约底座）、`EXT-FILE`、`EXT-KNOW`、`EXT-DATA`。平台核心链的记录不得在 `design` 中引用仅属能力扩展的实体或接缝作为前提（`DD-91`）。

## 2. 上游来源记录（baseline manifest）

`04-上游适配与升级.md` §2 的记录落到这一格式。需要修改或自行构建的上游是二开项目：固定 commit 的完整源码放在按功能命名的目录（`collaboration/`、`web-client/`、`model-gateway/`、`agent-runtime/`，以后如 `metering/`、`file-storage/`），一个上游仓库一个目录，目录内保持上游原样的结构与包名，改动直接在树里（ADR-15、ADR-16）。来源记录存放于项目的 `fork/upstream.yaml`；同一目录下 `fork/verify/` 放接缝证据，`fork/packaging/` 放上游没有而由本仓库维护的构建文件（`agent-runtime` 的固定运行配置在 `fork/runtime-config/`）。只以 Go module 引用、不改也不自建的上游不设目录，来源记录归引用方所有（工作流 SDK 为 `worker/fork/upstream.yaml`），以 `module` 登记，且不得登记 `artifacts` 与 `remove_paths`。原样使用的上游以按 digest 固定的官方镜像引入，不建来源记录。

记录中的路径除 `remove_paths` 外一律相对 `apps/`：

```yaml
project: model-gateway                                       # 项目名
reference_tree: agentgateway                                 # 必填：.references 下对应的上游目录名
upstream_url: https://github.com/agentgateway/agentgateway
evidence_commit: 1f7ebbf87cbdbe9517f6f181221879d04dc50692   # 与 .design/02 §1 一致
implementation_base_commit: 1f7ebbf87cbdbe9517f6f181221879d04dc50692   # 二开树的上游基准
base_divergence: none                                        # 两者不同时必须写明已复核的差异
remove_paths: [ui/src/features/example]                     # 树中整块删除的上游路径（相对项目目录）
artifacts:
  - name: model-gateway                                      # 产物名：小写短横线，全局不重复
    kind: image                                              # image 或 bundle（安装包）
    build_context: model-gateway                             # 必填，相对 apps/；引用 client-kit 的产物为 .
    build_dockerfile: model-gateway/Dockerfile               # 必填，相对 apps/，必须落在 inputs 内
    inputs: [model-gateway/]                                 # 必填：输入范围，至少含本项目目录下的路径
    exclude: []                                              # 可选：从 inputs 中排除的路径前缀
    build_secrets: []                                        # 可选：构建所需的 BuildKit secret 名
    build_args: []                                           # 可选：发布配置注入的非密构建参数名（例如 PLATFORM_DISPLAY_NAME）
    blocked: ""                                              # 可选：登记为阻断的原因
    source_digest: sha256:...
    artifact_digest: sha256:...
source_facts: [SF-AGW-10, SF-AGW-11, SF-AGW-16]
source_seams: [SS-AGW-OIDC, SS-AGW-PEP, SS-AGW-ADMIN, SS-AGW-USAGE]
compatibility_evidence: [model-gateway/fork/verify/oidc-header-projection.md]
owner: team-platform
last_reverified: 2026-09-29
```

`evidence_commit` 与 `implementation_base_commit` 不同且 `base_divergence` 为 `none` 时门禁失败——这条规则防止"设计证据自动覆盖更高版本"。两个 commit 都必须是 40 位十六进制，`implementation_base_commit` 必须能在 `.references/<reference_tree>` 的对象库或 `upstream_url` 中解析，取不到即失败。缺 `reference_tree` 门禁失败。

**本仓库改了什么**：与上游原样的差异不作为文件保存。`tools/upstream_manifest.py diff <项目>`（可加 `--stat`、`--name-status`）以只读方式借用 `.references/<reference_tree>` 的对象库（没有时按 `upstream_url` 浅取基准 commit 到本机缓存），把二开树与基准 commit 比较，输出本仓库的改动，`fork/` 不在其中。`remove_paths` 登记树中整块删除的上游路径（一期不交付的功能目录），`diff <项目> --check` 核对登记与实际整块删除的路径一致；登记的路径仍在树里、重复或越出树外，门禁失败。

**上游变了什么**：`tools/upstream_manifest.py status [<项目>]` 只读取 `.references/<reference_tree>` 的 HEAD、`.references/UPDATE_TASKS.json` 与 `.references/<reference_tree>更新记录.md`，对每个二开项目列出基准 commit 之后的上游新提交与涉及文件，并标出其中哪些文件在二开树里被本仓库改过；它只提示，恒以 0 退出。`tools/check.sh` 的第一步 `status` 运行它，不计入门禁；是否升级由 `04` §4.2 的影响分类决定。`tools/upstream_manifest.py sync <项目> [--to <commit>] [--into <目录>]` 按 `04` §4.4 把上游变化三方合并进二开树（`--into` 时写进该目录里的一份树副本，用于先行演练），冲突按 git 标准标记留在文件里；它不提交，也不改来源记录。两者都不在 `.references` 中写入、检出或构建。

**共用代码不复制**：本仓库自有的共用代码在 `client-kit/`，二开项目以本地路径依赖直接引用——`web-client`（npm）与 `collaboration/desktop`（pnpm）经 `file:`/`link:` 引用 `client-kit/ts`（`platform` 与 `contracts`），`collaboration/mobile` 经 Flutter `path:` 引用 `client-kit/dart`（ADR-09、ADR-16）。没有构建时拷贝；`vendor_files` 已废弃，记录中再出现即门禁失败。上游自带的依赖补丁机制（例如 pnpm `patchedDependencies`）属于上游原样，保留。

`artifacts` 的每一项是一个产物。`inputs`/`exclude` 声明它的输入范围：`inputs` 必须含本项目目录下的路径，引用 `client-kit` 的产物还要列出所引用的 `client-kit` 路径，并以 `build_context: .`（即 `apps/`）构建；`build_dockerfile` 必须落在 `inputs` 内，否则改它不会让产物失效。例如 Relay 镜像 `inputs: [collaboration/]`、`exclude` 排除 `collaboration/desktop/`、`collaboration/mobile/` 与 `collaboration/fork/packaging/`；Mobile 安装包只取 `collaboration/mobile/`、`client-kit/dart/` 与其构建文件。`source_digest` 覆盖范围内每个文件的路径、类型与字节（按本仓库的忽略规则可见的文件，`fork/upstream.yaml` 与 `fork/verify/` 除外），以及 `kind`、`build_context`、`build_dockerfile`、`inputs` 与 `exclude`。范围内任一改动——包括 contracts 重新生成、共用包改动——而未重建，`check.sh seam` 重算不符即失败，判定为「产物不是由当前源码构建」；范围外的改动不要求重建该产物。两个摘要只由 `tools/build-upstream.sh <产物>` 在构建成功后一次写回，尚未构建的产物两者同为 `none`。

每个产物都登记 `build_dockerfile`：上游自带合用的构建文件时直接指向它、需要改就在树里改（例如 `collaboration/Dockerfile`、`model-gateway/Dockerfile`、`web-client/web/Dockerfile`）；上游没有时指向 `fork/packaging/` 下由本仓库维护的构建文件。`kind: bundle`（Desktop 安装包、Mobile release APK）的构建文件最后一个阶段只含安装包，`artifact_digest` 记安装包字节的 SHA-256。`build_secrets` 列出构建所需的 secret，以 BuildKit secret 交出、不进镜像层与构建日志；缺任一 secret 时构建以阻断退出，不以降级构建（debug 证书、无签名）顶替发布产物。`build_args` 列出按部署取值的非密构建参数（例如安装包显示名 `PLATFORM_DISPLAY_NAME`，`DD-111`），由调用方环境给出并以 `--build-arg` 交出；缺任一项或只含空白即拒绝构建，不回退默认值；它们进入产物，因此不得登记凭据。登记了 `blocked` 的产物在门禁中如实列为阻断。

来源记录的解析、结构校验、差异、上游变化、同步与摘要算法只有一份实现：`tools/upstream_manifest.py`。`build-upstream.sh` 构建前以它校验并取字段、以 `stage` 把 `inputs` 内可见的文件按 `apps/` 相对路径放进临时目录后构建、构建后以它写回摘要；`check.sh seam` 以它复核结构、基准可解析与源码摘要，`check.sh supply` 以它取出本仓库在树里新增或改写的行做凭据扫描，`check.sh status` 以它提示上游变化；设计追溯（SF/SS 引用、证据路径）只在门禁里。`patch_series`、`patch_series_digest` 与 `vendor_files` 已废弃（ADR-15、ADR-16），相应的 `vendor` 命令已删除。

## 3. 能力注册表与 exposure 闸门

运行时只认注册表，不认代码里的分支。注册表由追溯记录生成，是路由、菜单、Action、Tool、Workflow kind 与 manifest 的唯一准入来源。

```yaml
# 生成物，不手工编辑
capabilities:
  - id: file_storage.open_edit
    exposure: end_user
    routes: ["/app/content/:resourceId/edit"]
    actions: [file_storage.open_edit@v1]
    tools: []
    workflow_kinds: [PROTOCOL_SESSION_RECONCILE]
```

构建期拒绝条件：注册表出现 `blockers` 非空的能力；出现 `.design` 判为 `EXCLUDED` 的能力；出现未在 `.design/06` 封闭 kind 列表中的 `workflow_kinds`；出现未在 `05-设计覆盖矩阵.md` 归属的 `id`。

硬规则：注册表中的能力 `id`、`actions`、`tools` 与任何 `type_key` 不得含实现产品名；业务能力的 `actions` 与 `tools` 只列能力契约键（`<category>.<verb>@vN`），同一契约键由当前 active binding 的实现承接，替换实现不改注册表条目（`DD-88`）。

## 4. 错误分类与 reason code

`03-验证发布与验收门禁.md` 要求 dashboards、alerts 与 runbooks 使用稳定业务 reason code。分类固定为六类，每个 API 错误、Workflow 失败与 UI 状态都必须落在其中之一：

| 类 | 语义 | 可重试 | 典型 reason code |
|---|---|---|---|
| `DENIED` | 认证、scope、permission、delegation、exposure 不满足 | 否 | `SCOPE_GUARD_FAILED`、`PERMISSION_DENIED`、`DELEGATION_EXPIRED` |
| `BLOCKED` | 设计阻断或能力未开放 | 否 | `CAPABILITY_BLOCKED`、`TENANT_DELETE_NOT_AVAILABLE` |
| `PRECONDITION` | binding、secret、projection、generation、readiness 不成立 | 修复后是 | `BINDING_NOT_ACTIVE`、`SECRET_UNREADABLE`、`RUNTIME_NOT_READY` |
| `LIMIT` | capacity、quota、entitlement、rate limit、大小上界 | 视策略 | `QUOTA_EXHAUSTED`、`CAPACITY_UNAVAILABLE`、`PAYLOAD_TOO_LARGE` |
| `CONFLICT` | 版本、revision、head、幂等键或并发冲突 | 需用户或对账介入 | `REVISION_CONFLICT`、`DUPLICATE_DECISION` |
| `UNKNOWN` | 外部副作用结果不明，等待对账 | 禁止盲目重放 | `EXTERNAL_RESULT_UNKNOWN`、`PROJECTION_DELAYED`、`BILLING_UNAVAILABLE` |

规则：

- reason code 是稳定标识符，进入 audit、UI 与告警；文案可本地化，code 不变。
- `UNKNOWN` 永远不得在 UI 上被渲染成成功或失败，必须显示为待对账并给出 evidence 入口。
- 新增 reason code 与新增 API 字段同等对待，走兼容检查。
- 错误体不携带业务正文、secret、原始 SQL、文件内容或完整 prompt/response。

## 5. 兼容与版本规则

`00-实施总纲.md` Stage 0 第 4 项所指的规则在此固定。

**API / contract**：向后兼容变更（加可选字段、加枚举值的接收端容忍、加新端点）可直接发布；破坏性变更必须新版本号并与旧版本并行到所有客户端迁移完成。枚举值的新增对读取端是破坏性的，除非读取端已实现未知值降级。

**数据库迁移**：每个迁移必须能被上一个已发布版本安全读取（expand-migrate-contract 三步）。删除列或表是独立发布，且必须在其读路径移除后至少一个版本。不可逆迁移单独审批并记录恢复方案。

**Workflow**：已注册 kind 的行为变化用 `GetVersion` changeID 门控，不改 kind 名。Activity 签名变化是新 Activity 类型。任何变更都必须通过录制 history 的 replay 回归。

**Adapter Protocol / Host API**：以 range 声明兼容区间，`05-设计覆盖矩阵.md` 中 `PlatformBuildInfo` 所记录的已部署版本是判定"当前一侧"的唯一来源。

## 6. ADR

未被 `.design` 固定的工程选择必须先有 ADR。模板：

```markdown
# ADR-<序号>：<决策标题>

- 状态：提议 | 已接受 | 已弃用 | 被 ADR-<n> 取代
- 日期：
- 决策者：

## 背景
要解决什么问题，受哪些 `.design` 合同约束（列出具体 DD/SS/实体）。

## 候选方案
每个方案的正确性、事务语义、故障恢复、运维成本、替换边界。

## 决策
选了什么，为什么。

## 后果
正面与负面，以及它锁定了什么、放弃了什么。

## 替换边界
什么条件下需要重新评估；更换该选择要改动哪些模块。

## 不改变的事
明确声明本 ADR 不改变 `.design` 的任何权威划分与能力状态。
```

ADR 存放于 `docs/adr/`，文件名为 `ADR-<序号>-<英文短名>.md`。序号一经分配不重用；被取代的 ADR 保留原文并在状态栏标注取代者。
