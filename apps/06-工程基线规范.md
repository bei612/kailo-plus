# 工程基线规范

本文件固定 Stage 0 必须产出的机器可读工件的确切形状，以及未被 `.design` 固定的工程决策的记录方式。其他实施文档引用这些格式，不重复定义。

格式是工程约定，不是产品语义。字段含义冲突时以 `.design` 为准。

## 1. 能力追溯记录

`03-验证发布与验收门禁.md` 的追溯检查读取这一格式。每个进入实现的能力一条记录，存放于 `tools/traceability/`，随代码提交一起演进。

```yaml
capability_id: drive.file.open_for_edit        # 稳定、全局唯一、小写点分
title: 在承载端（Web/Desktop）中以编辑模式打开 Cells 文件
stage: S6
status: planned | in_progress | shipped | withdrawn
exposure: none | internal | tenant_admin | end_user

design:
  requirements: [V-REQ-16]
  decisions: [DD-30, DD-31, DD-32]
  facts: [SF-CEL-05, SF-CEL-12, SF-OFF-03]
  seams: [SS-CEL-WOPI, SS-OFF-WOPI]
  blockers: []                                  # 非空即禁止 exposure 超过 none
  entities: [FileReference, DocumentSession]

validation:
  scenarios: [V-SCN-24, V-SCN-25, V-SCN-26]
  evidence:                                     # 形式不限：自动化、脚本化演练或可复现的核验记录
    - dimension: 上游接缝                        # 取自 03-验证发布与验收门禁.md §3
      ref: adapters/cells/verify/wopi_pep.md
    - dimension: 端到端场景
      ref: web/verify/office_edit.md

implementation:
  owners: [team-drive]
  paths: [core/crates/drive, adapters/cells, web/buzz-web/src/features/drive, desktop/src/features/drive]
  surfaces: [web, desktop]                       # 该能力实际开放的端；取值来自 web|desktop|mobile
  schemas: [contracts/api/drive.v1.json]
  migrations: [core/migrations/0042_document_session.sql]

release:
  artifacts:
    - name: kailo-core
      digest: sha256:...
  gate: blocked_until_seams_closed | ready | shipped
```

检查器的硬规则：

- 每个 `design.*` ID 必须在 `.design` 中解析；解析不到即失败。
- `status` 非 `withdrawn` 时 `design` 至少有一个 `requirements`、`decisions` 或 `seams` 条目。
- `blockers` 非空时 `exposure` 必须是 `none`。
- `seams` 非空时每个接缝必须有一条 `dimension: 上游接缝` 的证据；证据的形式不限，但必须指向可复核的记录。
- `stage` 必须与 `05-设计覆盖矩阵.md` 对该能力所含实体与决策的归属一致；不一致时要么改矩阵要么改记录，不得两边并存。
- `exposure` 高于 `none` 时 `release.artifacts` 必须有 digest。

## 2. 上游 baseline manifest

`04-上游适配与升级.md` §2 的记录落到这一格式，每个进入运行拓扑的上游一份，存放于 `upstream-patches/<project>/baseline.yaml`。

```yaml
project: agentgateway
upstream_url: https://github.com/agentgateway/agentgateway
evidence_commit: 1f7ebbf87cbdbe9517f6f181221879d04dc50692   # 与 .design/02 §1 一致
implementation_base_commit: 1f7ebbf87cbdbe9517f6f181221879d04dc50692
base_divergence: none                                        # 两者不同时必须写明已复核的差异
patch_series:
  - id: ss-agw-oidc-header-projection
    seam: SS-AGW-OIDC
    files: [crates/agentgateway/src/http/transformation_cel.rs]
    rationale: 固定内部身份 header 的单条 set 写入与 fail-closed 语义
remove_paths: [ui/src/features/example]                     # 构建时整块删除的上游路径，先删后打补丁
vendor_files: [web/packages/contracts/src/generated/contracts.ts:web/src/platform/contracts.gen.ts]  # 本仓库相对源:源树相对目标
patch_series_digest: sha256:...
artifact_digest: sha256:...
source_facts: [SF-AGW-10, SF-AGW-11, SF-AGW-16]
source_seams: [SS-AGW-OIDC, SS-AGW-PEP, SS-AGW-ADMIN, SS-AGW-USAGE]
compatibility_evidence: [upstream-patches/agentgateway/verify/oidc_header.md]
owner: team-platform
last_reverified: 2026-09-21
```

`evidence_commit` 与 `implementation_base_commit` 不同且 `base_divergence` 为 `none` 时构建失败——这条规则防止"设计证据自动覆盖更高版本"。

`remove_paths` 登记裁剪掉的整块上游代码（一期不交付的功能目录）。它不做成删除补丁：删除补丁携带被删文件的全部正文，会淹没需要审阅的改动。构建先删除这些路径、再按 `patch_series` 打补丁；登记的路径在源树里不存在即构建失败。`vendor_files` 登记打完补丁后放进源树的本仓库文件，用于让上游代码引用 `contracts/` 的生成物（ADR-02/03）与 Kailo 自有的共用 TypeScript 包 `web/packages/platform`（ADR-09）：补丁只引用该路径、不携带副本，副本会与本仓库分叉。目标路径在源树里已存在即构建失败。放置只有一个实现（`tools/upstream_manifest.py vendor`）：构建用它；开发中的上游工作树用 `vendor --refresh`，它只覆盖该树 `.gitignore` 已忽略的目标，从而保证那棵树不会把副本提交进补丁。

`patch_series_digest` 覆盖补丁字节、删除清单与 `vendor_files`（目标路径与源文件字节）三者，任一改动而未重建——包括 contracts 重新生成——`check.sh seam` 失败。

清单的解析、结构校验与摘要算法只有一份实现：`tools/upstream_manifest.py`。`build-upstream.sh` 构建前以它校验并取字段、构建后以它写回摘要，`check.sh seam` 以它复核；设计追溯（SF/SS 引用、证据路径）只在门禁里。

`build_dockerfile` 用于产物不是镜像的上游（Desktop 安装包）：指向 Kailo 维护的构建文件，其最后一个阶段只含安装包，`artifact_digest` 记安装包字节的 SHA-256。

## 3. 能力注册表与 exposure 闸门

运行时只认注册表，不认代码里的分支。注册表由追溯记录生成，是路由、菜单、Action、Tool、Workflow kind 与 manifest 的唯一准入来源。

```yaml
# 生成物，不手工编辑
capabilities:
  - id: drive.file.open_for_edit
    exposure: end_user
    routes: ["/app/drive/:resourceId/edit"]
    actions: [cells.file.edit]
    tools: []
    workflow_kinds: [DOCUMENT_RECONCILE]
```

构建期拒绝条件：注册表出现 `blockers` 非空的能力；出现 `.design` 判为 `EXCLUDED` 的能力；出现未在 `.design/06` 封闭 kind 列表中的 `workflow_kinds`；出现未在 `05-设计覆盖矩阵.md` 归属的 `id`。

## 4. 错误分类与 reason code

`03-验证发布与验收门禁.md` 要求 dashboards、alerts 与 runbooks 使用稳定业务 reason code。分类固定为六类，每个 API 错误、Workflow 失败与 UI 状态都必须落在其中之一：

| 类 | 语义 | 可重试 | 典型 reason code |
|---|---|---|---|
| `DENIED` | 认证、scope、permission、delegation、exposure 不满足 | 否 | `SCOPE_GUARD_FAILED`、`PERMISSION_DENIED`、`DELEGATION_EXPIRED` |
| `BLOCKED` | 设计阻断或能力未开放 | 否 | `CAPABILITY_BLOCKED`、`TENANT_DELETE_NOT_AVAILABLE` |
| `PRECONDITION` | binding、secret、projection、generation、readiness 不成立 | 修复后是 | `BINDING_NOT_ACTIVE`、`SECRET_UNREADABLE`、`RUNTIME_NOT_READY` |
| `LIMIT` | capacity、quota、entitlement、rate limit、大小上界 | 视策略 | `QUOTA_EXHAUSTED`、`CAPACITY_UNAVAILABLE`、`PAYLOAD_TOO_LARGE` |
| `CONFLICT` | 版本、revision、head、幂等键或并发冲突 | 需用户或对账介入 | `REVISION_CONFLICT`、`DUPLICATE_DECISION` |
| `UNKNOWN` | 外部副作用结果不明，等待对账 | 禁止盲目重放 | `EXTERNAL_RESULT_UNKNOWN`、`PROJECTION_DELAYED`、`BILLING_UNAVAILABLE` |

规则：

- reason code 是稳定标识符，进入 audit、UI 与告警；文案可本地化，code 不变。
- `UNKNOWN` 永远不得在 UI 上被渲染成成功或失败，必须显示为待对账并给出 evidence 入口。
- 新增 reason code 与新增 API 字段同等对待，走兼容检查。
- 错误体不携带业务正文、secret、原始 SQL、文件内容或完整 prompt/response。

## 5. 兼容与版本规则

`00-实施总纲.md` Stage 0 第 4 项所指的规则在此固定。

**API / contract**：向后兼容变更（加可选字段、加枚举值的接收端容忍、加新端点）可直接发布；破坏性变更必须新版本号并与旧版本并行到所有客户端迁移完成。枚举值的新增对读取端是破坏性的，除非读取端已实现未知值降级。

**数据库迁移**：每个迁移必须能被上一个已发布版本安全读取（expand-migrate-contract 三步）。删除列或表是独立发布，且必须在其读路径移除后至少一个版本。不可逆迁移单独审批并记录恢复方案。

**Workflow**：已注册 kind 的行为变化用 `GetVersion` changeID 门控，不改 kind 名。Activity 签名变化是新 Activity 类型。任何变更都必须通过录制 history 的 replay 回归。

**Adapter Protocol / Host API**：以 range 声明兼容区间，`05-设计覆盖矩阵.md` 中 `PlatformBuildInfo` 所记录的已部署版本是判定"当前一侧"的唯一来源。

## 6. ADR

未被 `.design` 固定的工程选择必须先有 ADR。模板：

```markdown
# ADR-<序号>：<决策标题>

- 状态：提议 | 已接受 | 已弃用 | 被 ADR-<n> 取代
- 日期：
- 决策者：

## 背景
要解决什么问题，受哪些 `.design` 合同约束（列出具体 DD/SS/实体）。

## 候选方案
每个方案的正确性、事务语义、故障恢复、运维成本、替换边界。

## 决策
选了什么，为什么。

## 后果
正面与负面，以及它锁定了什么、放弃了什么。

## 替换边界
什么条件下需要重新评估；更换该选择要改动哪些模块。

## 不改变的事
明确声明本 ADR 不改变 `.design` 的任何权威划分与能力状态。
```

ADR 存放于 `docs/adr/`，文件名为 `ADR-<序号>-<英文短名>.md`。序号一经分配不重用；被取代的 ADR 保留原文并在状态栏标注取代者。

Stage 0 必须完成的 ADR：

| ADR | 决策 | 状态 | 关键约束来源 |
|---|---|---|---|
| [ADR-01](docs/adr/ADR-01-core-persistence.md) | Core 持久化数据库与事务、outbox、锁语义 | 已接受 | `01` §7 的七项持久化要求；严格 reservation 的串行化 |
| [ADR-02](docs/adr/ADR-02-module-communication-and-schema.md) | Core 内部模块通信与 API schema 工具 | 已接受 | `01` §3 的模块边界；contract package 单一来源 |
| [ADR-03](docs/adr/ADR-03-contract-generation.md) | Core 与 Worker 的 contract 生成策略 | 已接受 | 同一 schema 生成或其他一致性证明，禁止同名异义枚举 |
| [ADR-04](docs/adr/ADR-04-orchestration.md) | 本地开发与部署编排 | 已接受 | `01` §8 的网络边界；不预设 Kubernetes |
| [ADR-05](docs/adr/ADR-05-observability-backend.md) | 可观测数据的存储与查询后端 | 已接受 | `.design/14` 的联合只读视图；不复制正文 |
| [ADR-06](docs/adr/ADR-06-artifact-supply-chain.md) | artifact registry、签名、SBOM 与 provenance | 已接受 | `03` §6 的发布门禁；每个产物可追溯 |
| [ADR-07](docs/adr/ADR-07-ci-and-branch-protection.md) | CI 执行环境与受保护分支规则 | 已接受 | `03` §5 的十项合并门禁 |
| [ADR-09](docs/adr/ADR-09-shared-kailo-typescript.md) | Web 与 Desktop 共用的 Kailo TypeScript 只有一份，经 `vendor_files` 进入两端 | 已接受 | `01` §5；`AGENTS.md` 第 12 条的同源要求；`SF-WEB-09`、`DD-74` |

以上七份按「最省事的默认值、后续按替换边界改造」的原则确定：单库 PostgreSQL、进程内模块调用加手写 JSON Schema、生成物入库、Docker Compose、OpenTelemetry 加 Grafana 套件、OCI registry 加 cosign/syft/SLSA、统一入口脚本加 GitHub Actions。每份的「替换边界」一节写明重新评估的触发条件与改动范围。

ADR 的验收标准是满足 `.design` 合同，不是改变合同以迎合工具。任何 ADR 若需要放宽 `.design` 的权威划分，先走设计变更流程。
