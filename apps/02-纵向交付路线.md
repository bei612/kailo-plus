# 纵向交付路线

## 1. 交付方法

每个 Stage 是可运行的纵向切片，不是按技术层分工的瀑布。切片必须同时包含：

1. 本 Stage 所声明各端的用户入口（见 §1.1）；
2. BFF typed query 或 semantic command；
3. Core 领域状态与事务；
4. scope guard 与 fresh authorization；
5. 所需 Approval/Workflow；
6. Capacity/Quota/Usage 的明确策略；
7. Audit、operation correlation 与用户可见状态；
8. native system 的真实终态和失败语义；
9. 主题、i18n、可访问性与权限裁剪；
10. 自动化验证、回滚与设计追溯。

允许并行实现内部模块，不允许绕过入口 Stage 将未治理能力直接暴露给用户或 Agent。

## 1.0 路线结构：平台核心链与能力扩展

路线按 `.design` 的两层架构（`DD-87`）与门禁分层（`DD-91`）分为两部分，与 `.design/15` §5、`.design/16` §4 的「平台门禁 / 各业务能力实现的 binding 激活门禁」一一对应。平台核心链只含 Agent 与协作所需的平台本体：平台可以只有 Agent 与协作、没有任何业务能力服务；组件模型、宿主与能力契约本身也是可选的扩展底座（ADR-13）。

| 部分 | 组成 | 依赖规则 | 门禁层 |
|---|---|---|---|
| 平台核心链 | Stage 0–5，终点为「平台一期收口」 | 严格按序：前一环的退出门禁是后一环的依赖；平台一期收口只依赖 Stage 5，不依赖任何能力扩展 | 平台门禁；一期生产总门禁只在平台一期收口判定 |
| 能力扩展 | `EXT-BASE` 组件与能力契约底座；`EXT-FILE` 文件存储（含在线编辑条件能力）、`EXT-KNOW` 知识、`EXT-DATA` 数据查询 | 全部可选。`EXT-BASE` 依赖 Stage 4 与 Stage 5 的退出门禁；`EXT-FILE`、`EXT-KNOW`、`EXT-DATA` 互不依赖，每个只依赖 `EXT-BASE` 的退出门禁。平台一期收口不依赖任何能力扩展，能力扩展也不依赖平台一期收口 | `EXT-BASE`：组件模型、宿主、Adapter Protocol 与示例组件的门禁；其余：该能力类别的一致性套件与各实现的 binding 激活门禁，只阻断对应 ComponentRelease `APPROVED` 与 ApplicationBinding `ACTIVE` |

每个能力类别扩展分三段交付：能力契约 + 一致性套件（平台侧通用部分）→ 内置参考实现 → 可替换外部实现。产品专有的检查只作为「参考实现验收」，不是平台门禁。「零业务能力 binding」部署必须通过平台核心链的全部门禁（`V-SCN-71`）；未交付 `EXT-BASE` 的部署即是这种部署，平台端口按部署配置解析（`DD-108`）。

新旧编号对应：

| 旧编号 | 新位置 |
|---|---|
| Stage 0–2 | 不变 |
| Stage 3：Component Catalog、运行时 Host、Adapter Protocol 与能力契约 | Tenant 删除、受限会话与 TenantLifecycleSnapshot 为新 Stage 3（§5）；平台核心 ResourceType 的 Resource/Asset、owner 转移与多 owner 审批随首个产出方进入 Stage 5（§7）；其余全部进入 `EXT-BASE`（§10.1） |
| Stage 4 | Quota、Usage 与观测；服务读取边的 Quota 与第三方接入验收移入 `EXT-BASE` |
| Stage 5 | Agent 核心，另含 `PLATFORM_NATIVE` 工具传输、自动化与平台 Resource/owner 链；示例组件的 Tool 路径移入 `EXT-BASE` |
| Stage 6：Cells 云盘与 ONLYOFFICE | 能力扩展 `EXT-FILE`（§10.2）；Cells 与 ONLYOFFICE 是其内置参考实现 |
| Stage 7：WeKnora 知识库与 CocoIndex 增量物化 | 能力扩展 `EXT-KNOW`（§10.3）；平台编排的物化链按 `DD-89` 撤销，改为接收方经授权自拉 |
| Stage 8：Wren 智能问数与一期收口 | 问数部分为能力扩展 `EXT-DATA`（§10.4）；全平台演练与一期生产总门禁移入平台一期收口（§8） |

追溯记录的 `stage` 取值相应为 `S0`–`S5`、`PC`（平台一期收口）、`EXT-BASE`、`EXT-FILE`、`EXT-KNOW`、`EXT-DATA`（`06-工程基线规范.md` §1）。

## 1.1 端交付规则

一期交付 Buzz Web、Buzz Desktop、Buzz Mobile 三端（`REQ-01`、`DD-74`）。本节固定每个 Stage 的端归属，消除「三端同时交付」在排期上的歧义：它指一期结束时三端都可用，不指每个 Stage 的每条能力在三端同时落地。

| 端 | 参与范围 | 依据 |
|---|---|---|
| Buzz Web | 全部 Stage 与能力扩展的完整能力面 | 基线最薄，是设计验证的第一现场 |
| Buzz Desktop | 与 Web 同步的完整能力面；主体是 `block/buzz` 的 `desktop/`（Tauri），与 Web 的 buzz-web 不是同一代码库（`DD-74`），协作面本机持钥直连 Relay、管理面经原生 listener 进 BFF（`DD-75`、`DD-78`）；两端只共享 Kailo 自有 TypeScript 平台包与契约生成物；Component Host 与 Web 共用同一份契约，随 `EXT-BASE` 经 `SS-DSK-COMPONENT-HOST` 接入（`REQ-11`）；主窗口 CSP 编译在签名包内，不执行 `REMOTE_MODULE`，对应入口显示确定状态并指向 Web（`SF-DSK-03`）；在线编辑在独立 editor 窗口中打开，许可集合由 BFF 运行时下发（`DD-104`） | `DD-74`、`DD-75`、`DD-78`、`DD-104`、`REQ-11`、`SF-DSK-03` |
| Buzz Mobile | Stage 1–2 交付协作数据平面与登录、成员视图；Stage 3 起的管理面能力（含自动化）与能力扩展以受权只读视图交付；组件宿主与在线编辑 surface 不交付 | `REQ-21`、`DD-74` |

硬规则：

- 每个 Stage 与能力扩展的退出门禁必须在其声明的**每个**端上各自成立，不允许以 Web 通过代替其余端。
- Buzz Mobile 上未交付的能力按 `V-SCN-65` 不渲染入口；经深链接进入时返回稳定 reason code 并指向 Web/Desktop，不得以内嵌 WebView 绕过。
- 三端对同一 Governed Action 的准入、审批、额度与审计结论必须相同；端差异只体现为入口有无，不体现为治理结论不同（`REQ-21`）。
- 原生端的协作数据平面走本机签名直连 Relay，管理平面经 BFF（`DD-75`）。任一 Stage 的退出门禁在原生端验收时必须同时覆盖这两条路径。

## 2. Stage 0：工程与合同基线

### 交付

- 建立 `01-工程结构与模块边界.md` 的最小目录与发布单元；
- 固定 contract schema、生成策略、兼容规则与追溯清单；
- 完成 Core 持久化、部署、CI、artifact/provenance 等 ADR；
- 建立 migration、outbox、idempotency、error taxonomy 和 feature exposure 基础库；
- 建立上游 baseline/patch manifest，记录固定 commit 与 `SS-*`；
- 建立一条从提交到可验证 artifact 的供应链。

### 退出门禁

- 所有语言绑定通过 schema round-trip 与 compatibility 检查；
- 空迁移可前进、回滚或安全停止；
- 空 Workflow history 可 replay；
- artifact 可追溯到源码 commit、依赖锁和 digest；
- 设计追溯检查能拒绝无来源能力和 `BLOCKED` exposure。

## 3. Stage 1：身份、Tenant/Workspace 与三端协作

### 目标链

```text
OIDC login
→ AgentGateway verified issuer/subject
→ Core PlatformSession/HumanIdentity
→ Tenant/Workspace membership
→ SpiceDB relationship + Buzz Community/Channel roster projection
→ Buzz Web 经 BFF 读写频道；Desktop/Mobile 本机签名直连 Relay
→ Audit/operation timeline
```

### 实施内容

身份与协作面：

- 闭合 `SS-AGW-OIDC`：固定内部身份 header、cookie 前缀/大小、logout 协同和 CORS fail-closed；
- 闭合 `SS-WEB-RELAY`：替换 Browser 直连 Relay 的 query/subscribe/publish/media/user-state 路径；
- 闭合 `SS-BUZ-SERVER-CLIENT`：把上游单身份 harness 扩展为 BFF 的多身份连接与查询面，按 `(principal, active session)` 复用 NIP-42 会话，写入与历史查询走无状态 NIP-98，并固定 NIP-11 上界与限流预算；
- 闭合 `SS-WEB-01`：在 buzz-web 构建期静态 route/navigation 中加入登录、Tenant/Workspace 选择、频道、成员与基础审计页；Buzz Desktop 在其 Tauri 主体中、Buzz Mobile 在其 Dart 主体中分别提供同一组页面（Mobile 为只读或协作子集），两端经原生 listener 取数（`DD-78`）；
- 原生设备公钥登记与撤销（`DD-77`、`DD-79`）：设备以绑定会话的持钥证明登记 CLIENT pubkey，`BUZZ_IDENTITY_PROJECTION` 投入与移出 roster；成员投影与撤权覆盖此人全部 pubkey；
- 托管身份的轮换（`.design/09` 的 key revoke/rotate 与 RelayOperatorIdentity rotate 两行）：Web 托管 HUMAN 身份经两条 `BUZZ_IDENTITY_PROJECTION` 先撤后建，operator 身份以 allow-list 重叠窗口在引导路径上切换；CONTROL 受 `GAP-BUZ-01` 阻断；
- 闭合 `SS-BUZ-OPERATOR`：Community 创建凭据链与 NIP-98 目标约束；
- 闭合 `SS-WEB-PRESENTATION`：全部内置页面复用 Buzz ThemeProvider/CSS variables 与 `AppLocale/messages/t`，Desktop 与 Mobile 以同源的主题语义与 message key 渲染（`REQ-08`）；
- 实现 PlatformSession、Tenant/Workspace、membership、BuzzIdentityBinding 与 RelayOperatorIdentity；
- 实现完整 snapshot + generation 的 BFF stream 恢复；
- 扩展 `SS-BUZ-GOVERNANCE` 关闭 Buzz 自带 workflow（`DD-106`、`SF-BUZ-45`）：治理开关设定时 Relay 不构造 WorkflowEngine、不挂接 `RelayActionSink`、不启动 cron 循环，持久化事件不调用 `on_event`；ingest 拒绝 30620、46020、46030、46031 与指向 30620 的 kind:5，Community owner 也不例外；不注册 `/workflows/*` 与 `/hooks/{id}`；Relay 启动自检三项任一不成立即拒绝启动；Desktop 与 Mobile 的 workflow 界面保持删除。

本 Stage 自带的承重底座（不下放到 Stage 2，否则本 Stage 无法收口）：

- OpenBao 最小面：namespace 划分、KV v2 写入与版本、`SecretRef` 状态机、Core service token 与引导凭据、audit device 前置校验。Human 独立 Nostr key 的托管与 Core 代签直接建立在它之上；
- Temporal 最小面：client、Worker 骨架、`ComponentTaskWorkflow` 的 `TENANT_LIFECYCLE`/`WORKSPACE_LIFECYCLE`/`MEMBERSHIP_PROJECTION`/`MEMBERSHIP_REVOCATION` 四个 kind、`WorkflowRef` 与固定 workflow ID、Start 的 reuse/conflict policy、`ProjectTaskState` 投影 Activity、Activity 超时与重试纪律。

底座只覆盖本 Stage 生命周期链所需的范围。ActionDefinition/Execution 全模型、Approval 全链与任务工作台 UI 属 Stage 2，Tenant 删除属 Stage 3，Quota 属 Stage 4，Resource/Asset 与 CapacityLease 属 Stage 5，ExternalExecution 属 `EXT-BASE`。

### 明确限制

- 不启用 Agent、Component remote module 或任何业务能力 binding；
- Tenant delete 与 Workspace delete 不注册（Tenant delete 在 Stage 3 交付，Workspace delete 一期不注册，`DD-46`）；
- Tenant CONTROL 身份的 key revoke/rotate 不注册（`GAP-BUZ-01`），入口对 CONTROL 回 `409`；
- Browser 不获得 Relay URL、Nostr 私钥或任意 Relay filter；
- 收藏、静音、已读使用 Core `CollaborationUserState`，不复用 Browser NIP-44 权威。

### 验收映射

`V-SCN-01`、`02`、`03`、`13`、`28`、`29`、`32`、`34`、`35`、`43`、`63`、`64`、`70`、`84`。其中 `V-SCN-34`、`35` 在本 Stage 验证成员撤权链与 `REVOKING` 立即拒绝，依赖 Resource owner 的部分在 Stage 5；`V-SCN-43` 在本 Stage 验证 pre-Tenant 认证审计边界，EvidenceRef 按当前权限解析在 Stage 2。

### 退出门禁

- `SS-AGW-OIDC`、`SS-WEB-RELAY`、`SS-BUZ-SERVER-CLIENT`、`SS-WEB-01`、`SS-WEB-PRESENTATION`、`SS-BUZ-OPERATOR`、`SS-BUZ-GOVERNANCE` 各有接缝成立的可复核证据；
- 登录、logout、断线恢复端到端通过；
- 成员建立与撤权经 `MEMBERSHIP_PROJECTION`/`MEMBERSHIP_REVOCATION` 完成 SpiceDB 与 Channel roster 对账，Core `REVOKING` 在对账完成前即拒绝新动作；
- Workflow Start 响应不明时按固定 workflow ID 收敛，不产生第二个业务 workflow ID；
- 外来身份 header、缺失 header、跨 scope stream 和 Browser 直连全部被拒绝；
- 每次消息动作可关联 actor、scope、operation、Buzz event 与 AuditEvent；
- Kailo 部署的 Relay 不装配 Buzz 自带 workflow：workflow 命令 kind 对任何签名者被拒，`/workflows/*` 与 `/hooks/{id}` 不可达，成员消息不触发 workflow run，启动自检不成立时 Relay 不启动（`V-SCN-84`）。

## 4. Stage 2：统一治理内核、Temporal 与任务工作台

### 目标链

```text
Client Surface semantic command
→ Action preview/admission
→ SpiceDB fresh Check
→ ApprovalWorkflow 或 ComponentTaskWorkflow
→ TaskProjection + Audit
→ 三端 Tasks/Approvals（Mobile 只读）
```

### 实施内容

- 实现 ActionDefinition/Execution、Operation、ApprovalPolicy/Projection、WorkflowRef、TaskProjection；ExternalExecution 属于组件 binding，随 `EXT-BASE` 首个带真实 native 副作用的 binding/action（示例组件，`DD-101`）在同一交付切片建立，不能在 dispatch 后补写，也不在无产出方时预建；
- 在 Stage 1 底座上补齐 `ApprovalWorkflow` 与 `SECRET_REF_REHOME`；其余 kind 随各自首个产出方交付，不预建：Tenant 删除分支随 Stage 3，`AGENT_INSTALLATION` 与 `AgentTaskWorkflow` 随 Stage 5，`COMPONENT_RELEASE`、`COMPONENT_BINDING`、`COMPONENT_DISABLE` 与 `RESOURCE_PROVISION` 随 `EXT-BASE`，`PROTOCOL_SESSION_RECONCILE` 与 `CAPABILITY_VERSION_PUBLISH` 分别随 EXT-FILE、EXT-DATA 的能力契约段，`RESOURCE_EXPORT`/`RESOURCE_IMPORT` 一期不注册（§11）；
- 固定 Update ID、Validator 的确定性边界、retry、heartbeat、continue-as-new 与 UNKNOWN 语义；Approval 决定、撤回及参数确认走 Update，运行中 Workflow 取消走 `RequestCancelWorkflowExecution`，RPC 前冻结首次 run 与 UNKNOWN 意图；RPC 成功仍会是 no-op，只有同一链 history 中匹配控制 ID 的事件才证明本次请求已记录，仍须等待 Worker 收尾与 Temporal 终态（`DD-69/84`、`SF-TMP-01/11`）；
- 把 `ProjectTaskState` 扩展到全部 kind；以 Core 预写 WorkflowRef 为有界轮转清单、按固定 workflow ID Describe/History 修补投影。只有未预写引用的 Schedule run 才按 Search Attribute 列表回填（`.design/06` §3.1、`SF-TMP-12`）；
- 实现 owner、fresh approval admission、职责分离和 consumed/invalidated；
- 把 Stage 1 的 OpenBao 最小面扩展为完整 SecretRef 生命周期：audience、version、lease、轮换顺序与各消费端投递；业务 Tenant 遗留 `platform/` 身份 ref 按 DD-85 用受治理 `SECRET_REF_REHOME` 归位，不以换钥或数据库直改替代；
- 实现 Tasks、Approvals、详情、取消、重试和 evidence 导航（EvidenceRef 每次解引用以当前 `audit` 权限 fresh Check）；Web 与 Desktop 完整，Mobile 为受权只读视图；
- 实现 Tenant 与 Workspace 的 `SUSPENDING/SUSPENDED` 与恢复：Workspace 的暂停/恢复从 Tenant scope 发起，Tenant 的暂停/恢复从平台 Catalog scope 发起（`DD-96`）；暂停先在 Core fail closed（新动作、stream 与 scope 解析；Tenant 暂停时该 Tenant 全部成员的请求在身份解析即被拒），再由生命周期 Workflow archive Workspace 的 Channel 或 Tenant 的 Buzz Community（SF-BUZ-15/43）；恢复经新 Governed Action 完整对账 membership、SpiceDB、Buzz roster 与 Channel 后才重新开放。TenantLifecycleSnapshot 是销毁的不可变清单，随 Stage 3 的 Tenant delete 交付，在删除准入时从已停写的 `SUSPENDED` Tenant 冻结。

### 验收映射

`V-SCN-07`、`31`、`32`、`34`–`38`、`43`、`67`、`68`、`69`。按首个真实产出方拆分：`V-SCN-07` 在本 Stage 验证批准后撤权的 fresh Check 拒绝，旧会话 bearer 与在途连接部分在 Stage 5，adapter 侧旧 ActionToken 部分在 `EXT-BASE`；`V-SCN-31` 在本 Stage 只验证暂停与恢复，删除的平台事实部分在 Stage 3，平台核心 ResourceType 的销毁在 Stage 5，组件 binding 子流程在 `EXT-BASE`；`V-SCN-34`、`35`、`37` 在本 Stage 验证成员撤权链、`REVOKING` 立即拒绝与逐角色不可变审批，其中依赖 Resource owner 的 owner 转移、owner 关系不可绕过与多 owner 审批在 Stage 5（首个平台核心 ResourceType）；`V-SCN-38` 在本 Stage 验证 Temporal Start 响应不明按固定 ID 收敛，native dispatch 的 ExternalExecution 部分在 `EXT-BASE`。

### 退出门禁

- 录制 history 在同版本和升级版本 Worker 上 replay 通过；
- 审批不能由 Core 直接改状态，批准后 dispatch 前会重新准入；
- Workflow Start 响应不明不会生成第二个业务 workflow ID；
- 任务投影落后显示 `PROJECTION_DELAYED`，不伪造 terminal；
- Tenant delete Action 在 Stage 3 交付前不可见；本 Stage 只交付 `SUSPENDING/SUSPENDED` 与恢复；
- 暂停先 fail closed、再 archive Workspace 的 Channel 或 Tenant 的 Buzz Community 并回读确认，暂停期间 Resource/Asset/owner、relationship 与 roster 保留；Tenant 暂停/恢复只能由 Catalog scope 的 platform admin 发起，暂停中 Tenant 的成员请求在身份解析即被拒；恢复只在全部投影对账一致后重新开放；
- EvidenceRef 每次解引用都以 AuditEvent scope 与当前 `audit` permission fresh 授权，无权或原证据不存在时只显示不可用；
- 遗留 SecretRef 归位的写入结果不明保持 UNKNOWN 并只查证目标 locator，不自动重写。

## 5. Stage 3：平台事实与 Tenant 生命周期

### 目标链

```text
SUSPENDED Tenant
→ LIFECYCLE_RESTRICTED 会话发起 tenant.delete
→ 准入时冻结 TenantLifecycleSnapshot（平台事实类别清单）
→ ApprovalWorkflow（Tenant admin + snapshot 中全部不同 HUMAN owner）
→ TENANT_LIFECYCLE：PLATFORM_CORE_CHAIN 按类别执行销毁处理器
→ DELETED + 审计保留
```

### 实施内容

- 实现 TenantLifecycleSnapshot 与 TenantDeleteSubprocess：本 Stage 每次删除只建立 `subject=PLATFORM_CORE`、`mode=PLATFORM_CORE_CHAIN` 一条子流程；snapshot 在删除准入时从已停写的 `SUSPENDED` Tenant 冻结，销毁审批与 Workflow 恢复都以它为准（`DD-43`）；
- 按平台事实增量注册 `tenant.delete`（`DD-99`）：本 Stage 登记 Core 事实、SpiceDB relationship、Buzz Community 与 roster、OpenBao Tenant namespace 四类销毁处理器；Stage 4 的 OpenMeter Customer 数据、Stage 5 的平台核心 ResourceType 与 AgentGateway 投影、`EXT-BASE` 的 ApplicationBinding native 删除子流程随各自处理器同一构建登记；snapshot 出现当前构建没有处理器的类别时准入拒绝，Tenant 保持 `SUSPENDED`；
- 动作键与策略按 `.design/05` §2.8 的 `tenant.delete`（`DD-100`）：`TENANT_ADMIN`×1 且 `owner_requirement=ALL_AFFECTED_OWNERS`；本 Stage 的 Tenant 还没有 Resource/Asset，受影响 owner 集合为空，Stage 5 起随平台核心 ResourceType 自动纳入；
- 受限会话（`access_mode=LIFECYCLE_RESTRICTED`，`DD-96`）与 `tenant.delete` 同时注册：Tenant admin 查看与决定生命周期审批、从 `SUSPENDED` 发起删除、在第一个不可逆删除调用前撤回；`tenant_delete.retain_by_decision` 只作用于 `NATIVE_DELETE` 子流程，随 `EXT-BASE` 注册；
- 第一个不可逆删除调用前可撤回到 `SUSPENDED`；`irreversible_dispatch_started=TRUE` 后只允许 rerun/reconcile；`DELETED` 后 AuditEvent、UsageEvent 与 WorkflowRef 保留（`.design/06` §7.2）；
- Tenant 删除不被任何业务能力实现阻断（`DD-91`）。

平台核心 ResourceType 的 Resource/Asset、owner 转移与多 owner 审批不在本 Stage：这些 ResourceType（Agent、Skill、Tool、`llm_route`、`automation`）全部随 Stage 5 首次出现，本 Stage 没有 Resource 的产出方；按 §4「不在无产出方时预建」的规则，它们随首个平台核心 ResourceType 在 Stage 5 交付（ADR-13）。

### 验收映射

`V-SCN-31`。其中 `V-SCN-31` 在本 Stage 验证删除的平台事实部分：增量注册、四类平台事实销毁处理器、缺处理器时准入拒绝与准入后 `UNKNOWN`；平台核心 ResourceType 的销毁在 Stage 5，组件 binding 子流程在 `EXT-BASE`。

### 退出门禁

- 零业务能力 binding 的 Tenant 从 `SUSPENDED` 删除可达 `DELETED`，四类平台事实由各自处理器删除并复验；
- snapshot 出现当前构建没有销毁处理器的平台事实类别时 delete 准入拒绝，Tenant 保持 `SUSPENDED`；准入后才出现缺失时 `PLATFORM_CORE_CHAIN` 停在 `UNKNOWN` 并 fail closed，Tenant 不进入 `DELETED`；
- 受限会话只被生命周期审批、删除发起与撤回入口接受，其余入口一律拒绝；暂停中 Tenant 在本 Stage 之前不开放任何入口；
- 删除只能由 Tenant admin 经受限会话从 `SUSPENDED` 发起，Tenant admin 批准前不进入 `DELETING`；
- 第一个不可逆删除调用之后不提供恢复动作，`DELETED` 之后审计与用量事实仍可按权限查询。

## 9. 能力扩展总则

- `EXT-BASE` 依赖 Stage 4 与 Stage 5 的退出门禁；`EXT-FILE`、`EXT-KNOW`、`EXT-DATA` 可选、互不依赖，每个只依赖 `EXT-BASE`；平台一期收口不以任何能力扩展为前提。
- 每个能力类别扩展分三段：**能力契约 + 一致性套件**——以 `EXT-BASE` 登记的该类别 `ACTIVE` 契约（预置种子的权威是 `contracts/adapter/<category>.v1`）与一致性套件为准，交付该类别在平台侧的通用部分；**内置参考实现**——以 `.design/02` 的 SF/SS 证据加一致性套件准入；**可替换外部实现**——以一致性套件、平台管理员批准、隔离模式与数据位置声明准入，不改 Core/Worker/契约（`DD-88`）。
- 能力类别是 Catalog 运行时数据（`DD-102`）：只使用固定 permission 与通用 Resource/Action/Tool 语义的新类别在 `EXT-BASE` 交付后经受审批的 Governed Action 登记，不需要新的能力扩展或平台发版；需要新平台语义的类别才随 Core 发版。
- 某 Tenant 或 Workspace 启用一个能力类别，即为该类别建立一个 active ApplicationBinding；未启用时该类别不产生导航、页面或残留入口，其契约键工具为 `NO_PROVIDER`。
- 退出门禁以该类别的一致性套件与各实现的 binding 激活门禁（`.design/15` §5 的实现表）为准；「参考实现验收」只决定对应内置实现的 ComponentRelease `APPROVED` 与 ApplicationBinding `ACTIVE`，不阻断平台，也不阻断其他实现。
- 需要另一类别数据的场景（接收方经服务读取边自拉，如 V-SCN-19/21，以及 V-SCN-78 的来源端部分：撤销 `reader` 后来源 PEP 对已签发未过期令牌的后续读取 fresh 拒绝）是**联合验收**：只在来源类别与接收类别的能力扩展都已启用、双方 release 都声明了对应的 `read_edge` 时执行，对端是已通过其类别一致性套件并处于 `ACTIVE` 的真实实现；任一条件不成立时该场景不适用，不阻断另一扩展的退出门禁，双方各自仍完整可用（`DD-89`）。不为此另建对端替身。
- 能力扩展交付的平台侧通用部分（通用 surface、ProtocolSession、通用 Workflow kind、按类别渲染的 `HOST_NATIVE` 页面）不含实现产品名，平台核心链的门禁不引用它们。

## 10. 能力扩展

### 10.1 能力扩展 EXT-BASE：组件与能力契约底座

可选；依赖 Stage 4 与 Stage 5 的退出门禁，不阻断平台一期收口。它把平台从「只有 Agent 与协作」扩展到可经配置与协议接入业务能力服务。

#### 目标链

```text
部署引导 0→1：平台端口首个 PlatformProviderBinding 与预置能力契约
→ Platform admin 登记 immutable release / 能力契约
→ artifact/schema/digest/治理合同验证
→ ApprovalWorkflow
→ exact binding generation 对账
→ Host snapshot 或 Adapter dispatch
→ disable/revoke/rollback
```

#### 实施内容

- 实现部署引导（`DD-108`）：启用 Catalog 时，每个已报告端口的首个 PlatformProviderBinding 与预置能力契约由 Core 容器内的一次性引导写入，只在该端口没有 active binding 时执行，把当前部署配置原样登记为 `APPROVED` 的 PLATFORM release 与 active binding，建立 ActionExecution 与 AuditEvent；此后的 `platform_provider_binding.create` 与 `upgrade` 由另一位 Catalog Tenant admin 批准；Stage 1–5 以部署配置直连平台服务的调用改经 Platform Port Router 解析 active generation；
- 固定 `PlatformBuildInfo.platform_port_keys` 为 `CORE_INTERNAL`、`IDENTITY_EDGE`、`AUTHORIZATION`、`APPROVAL_WORKFLOW`、`SECRET_STORE`、`COLLABORATION_RELAY`、`METERING_BILLING`、`AI_GATEWAY`：只报告本构建已编译 provider 适配代码且其认证接缝已闭合的端口（`METERING_BILLING` 依 Stage 4 的 `SS-OMT-AUTH`，`AI_GATEWAY` 依 Stage 5 的 `SS-AGW-ADMIN`）；`CORE_INTERNAL` 的 target 为 `CORE_INTERNAL`，其余是独立服务，target 为指向当前部署实例的 `REMOTE_SERVICE`，不以 `CORE_INTERNAL` 冒充；
- 实现 ComponentDefinition/Release/Package、PlatformProviderBinding、ApplicationBinding 与 RuntimeProjection；`class=APPLICATION` 的 connector 只能是 `REMOTE_ADAPTER` 或 `PROTOCOL_PEER`，binding 的 `call_identity_mode` 不含 `INTERNAL`（`.design/03` §3）；
- 实现能力模型（`DD-88`、`DD-102`）：CapabilityCategory 与 CapabilityContract 是 Catalog 运行时数据，`FILE_STORAGE`、`KNOWLEDGE`、`DATA_QUERY` 是预置种子；平台管理员经 `capability_contract.register/approve/deprecate` 与 `capability_category.retire` 登记与维护（`.design/05` §2.8）；运行时登记的契约只使用固定 permission 与通用语义，schema 与测试向量以 digest 固定在 Catalog，由通用一致性套件运行器执行；ComponentRelease 以 `implements[category@version]` 声明实现，必须实现该版本全部必选键以及其已声明 `SUPPORTED` 能力（如 `versioned_model`、`online_editing`）对应的条件键；同一 Tenant 或 Workspace 的同一类别只允许一个 active ApplicationBinding；
- `action_key`、ToolDefinition、DelegationScope、ApprovalPolicy 只引用契约键，`component_type_key` 只记实现来源，不进入任何授权、审批或能力判定；
- 实现应用 Resource 的首次创建（`DD-98`）：只经 `resource.create`，Core 先写 `PROVISIONING` Resource，`ComponentTaskWorkflow(kind=RESOURCE_PROVISION)` 写 SpiceDB relationship 后以 Resource ID 为幂等键调用 `resolve_native_scope(mode=CREATE)`；结果不明 fail closed，只以同一 Resource ref 调 `mode=LOOKUP` 对账，`ABSENT_FENCED` 转 `FAILED`；实现 `resource.grant_read` 与 `resource.revoke_read`；
- 实现 Platform Port Router 和 Application Adapter Dispatcher；
- 实现 Adapter Protocol handshake/validate/resolve/execute/observe/cancel/reconcile/usage/error mapping，线协议与两个方向的认证按 ADR-12；实现 Core/Worker→adapter 与服务读取边的 ActionToken（`ActionTokenClaims`）；
- 首个带真实 native 副作用的 binding/action 是示例组件（`DD-101`）：它以 `implements=[]` 登记、自带独立 database，ResourceType、Action 与 Tool 固定在 `component.<component_type_key>` 命名空间；其可取消异步 native task、`resource.create` 与 Tenant 删除子流程必须同时交付写前 ExternalExecution、稳定幂等键、结果不明对账及其受权任务投影；binding 配置 `refuse_create_type_keys[]` 是确定拒绝分支的注入点；无 native 副作用的宿主样例不制造空执行记录；示例组件只在验证部署登记，零业务能力 binding 部署不含它；其 Tool 经 AgentGateway ExtMcp PEP 以 ActionToken 与 fresh SpiceDB Check 调用，不能被 AgentVersion 作为能力需求引用；

- 实现内容寻址 artifact route、静态 import 边界扫描、pending load、generation、dispose 和错误归因；
- 实现 release 登记、批准、撤销，binding 建立/升级/回滚/停用 Workflow，动作键与审批策略按 `.design/05` §2.8（`DD-100`），binding 与 `resource.create` 的 scope 以 `workspace_rule=DECLARED_WORKSPACE` 解析；release 批准由另一位 Catalog Tenant admin 经 ApprovalWorkflow 决定；

- 交付 `REQ-22` 的六件第三方接入面（`DD-76`）：由 `contracts/` 派生的 TypeScript Component SDK、manifest schema 与本地校验器、脚手架、可脱离真实平台运行的本地开发环境、语言无关的 Adapter Protocol 一致性测试套件（线协议与传输按 ADR-12）、端到端示例组件（`DD-101`）；一名未参与平台开发的工程师仅凭接入面完成一个组件、通过一致性套件并成功登记 binding，过程中不读 `.design` 全文、不接触平台源码；

- 实现 `SOURCE_BOUND_PROTOCOL` 的平台侧通用部分（`DD-95`）：release 登记 `editor_origins[]`，部署级许可集合等于已批准 release 所登记集合的并集并由 BFF 运行时下发，Tenant 与 binding 不能扩大；Core 只在 `editor_origin` 属于该 release 登记集合且等于该 binding 固定的实例 origin、`action_url` 的 origin 等于 `editor_origin`、字段均为字符串且未过期时原样下发 DocumentLaunchDescriptor；Web 由同一份部署配置投影静态服务 CSP 与 BFF 读取值，Desktop 的有效集合就是运行时下发的许可集合（`DD-104`）；零业务能力 binding 时该集合为空，CSP 与固定基线一致；
- 实现可空的 `WorkspaceCapabilityDefault` 与通用 `ContentReference`（`DD-90`）：Workspace `ACTIVE` 不依赖前者；审批附件、任务产物与聊天引用只用 ContentReference 或 Relay media，无文件能力 binding 时退回 Relay media；
- 实现服务读取边（`DD-89`）：它是 release 以 `read_edge` 声明的可选能力；经 Governed Action（含审批）为接收方 binding 的 ServicePrincipal 写入或撤销来源 Resource 的 `reader` 关系，接收方每批经 Adapter Protocol `request_read_grant` 申请，Core 以 SERVICE actor 准入（含 Quota）并签发短期 ActionToken；平台不经手数据、不持有同步状态，不以 Schedule 或 Workflow 编排跨服务同步；
- 实现数据与密钥隔离的准入校验（`DD-93`）：`class=APPLICATION` release 缺数据存储隔离、数据位置或 `secret_schema` 即不得 `APPROVED`；Core 按通用 `secret_schema` 校验并经 OpenBao 投递，`DATA_KEY` 轮换在服务回报重加密完成前保留旧版本；
- 实现业务能力服务的模型调用模式（`DD-92`）：binding 在 release 允许集合内选定 `PLATFORM_LLM_ROUTE` 或 `SELF_MANAGED_MODEL`，切换经 `application_binding.switch_model_call_mode` 审批；
- 实现 ApplicationBinding 的 Tenant 删除子流程（`DD-99`）：它是 `tenant.delete` 新增的平台事实类别，与其处理器同一构建登记；每个 binding 的 native 删除是独立子流程，声明 `retain_on_tenant_delete` 的实现只撤 binding、撤凭据、保留审计并登记待人工处置；同时注册 `tenant_delete.retain_by_decision`。

#### 验收映射

`V-SCN-07`、`08`、`18`、`31`、`33`、`38`、`39`、`47`–`57`、`65`、`66`、`75`、`76`、`78`、`79`、`80`、`81`、`82`。其中 `V-SCN-07` 验证 adapter 侧旧 ActionToken 的 fresh 拒绝；`V-SCN-08` 以 Adapter Protocol 一致性套件与示例组件的真实异步 native task 验证按声明的 cancel capability 取消并 observe 到终态，参考实现在 EXT-FILE/EXT-KNOW；`V-SCN-31` 验证组件 binding 删除子流程（示例组件的 `NATIVE_DELETE`、声明 `retain_on_tenant_delete` 的 binding 的 `RETAINED_DECLARED`）；`V-SCN-38` 以示例组件验证 native dispatch 的 ExternalExecution 部分；`V-SCN-39` 验证 ActionToken 部分；`V-SCN-65` 验证 remote module 入口，在线编辑入口在 EXT-FILE；`V-SCN-78` 只验证 Core 侧（`request_read_grant` 准入含 Quota、令牌签发、撤销 `reader` 后 Core 拒绝新批次），来源端对已签发令牌的 fresh 拒绝在 §9 的联合验收中验证；`V-SCN-79` 验证 release 隔离与 `secret_schema` 声明的准入；`V-SCN-81` 验证 Core 的 descriptor 校验与许可集合派生及下发，surface 端到端由 EXT-FILE 覆盖；`V-SCN-82` 以示例组件验证 `resource.create` 的创建、`LOOKUP` 对账与 `refuse_create_type_keys[]` 注入的确定拒绝。

#### 退出门禁

- 部署引导只在端口没有 active binding 时写入并留审计，对已有 active binding 的端口拒绝；之后的 provider 建立与升级没有另一位 Catalog admin 批准不能生效；
- 未批准、digest 不符、API 不兼容、越界 import、缺 i18n key 的 artifact 均拒绝登记或加载；
- 新 generation 校验失败不切流，旧 invocation 固定旧 generation；
- binding 停用先 fail closed，再撤 route/tool/schedule/projection 并保留历史；
- manifest 不能创建未知 platform port 或加载未编译 driver；ApplicationBinding 不能选择 `EMBEDDED_DRIVER` 或 `INTERNAL`；
- 运行时登记的能力契约只能使用固定 permission 与封闭声明，引用未编译 ProtocolSession kind 或新 Workflow kind 的契约被拒绝；契约批准不能由登记者本人完成；
- 兼容 release 能在不重发 Core 与两个承载端的条件下注册（引入部署级许可集合尚未包含的 editor origin 时，Web 只重启静态服务，Desktop 由 BFF 运行时下发，不发新包，`DD-95`、`DD-104`），超出既有 slot/API/port/protocol/能力契约版本的 release 被拒绝；
- 缺 `implements[]`、缺必选键或缺已声明能力对应的条件键、缺隔离与数据位置声明或缺 `secret_schema` 的 release 拒绝登记；`VENDOR_MANAGED` 缺数据位置或未经平台管理员批准不得 `APPROVED`；外部实现不因 `source_commit` 为空被拒；同 scope 同类别第二个 active binding 被拒绝；
- Core 拒绝 `editor_origin` 不在 release 登记集合、与该 binding 实例 origin 不等或 `action_url` origin 不符的 DocumentLaunchDescriptor；Tenant 与 binding 配置不能扩大许可集合；Desktop 对 `REMOTE_MODULE` 入口显示确定状态；
- 服务读取边的 Core 侧成立：`request_read_grant` 按 SERVICE scope guard、fresh `read` 与 Quota 准入，签发的 ActionToken 固定来源契约端点 audience、来源 Resource target 与该批 operation；撤销 `reader` 关系后 Core 拒绝新批次申请；未声明 `read_edge` 的实现不参与授予与申请；
- 示例组件的异步 native task、`resource.create` 与 `NATIVE_DELETE` 以真实副作用通过：响应不明进入 `UNKNOWN` 且只按登记的幂等键对账，`resource.create` 只以 `LOOKUP` 对账、不以 `CREATE` 重放；`UNKNOWN`/`PROVISIONING` 的 Resource 不接受其他动作；
- 示例组件的 Tool 调用经 AgentGateway ExtMcp PEP，缺有效会话级 bearer、fresh SpiceDB Check 或 binding scope 不符时被拒绝（`DD-101`）；
- 声明 `retain_on_tenant_delete` 的 binding 不阻断 Tenant 状态机；
- 撤销与停用动作不经审批即 fail closed，release 批准不能由登记者本人完成；
- 一名未参与平台开发的工程师仅凭接入面完成组件接入（`V-SCN-66`）。

### 10.2 能力扩展 EXT-FILE：文件存储（含在线编辑条件能力）

#### 目标链

```text
承载端按能力类别渲染的文件页面
→ Core Resource/owner/permission 与 ContentReference
→ FILE_STORAGE 实现（Adapter Protocol）
→ 实现声明 online_editing=SUPPORTED 时：open_view/open_edit admission → ProtocolSession → 实现 adapter 生成 DocumentLaunchDescriptor → Core 校验 origin
→ Web：通用 SOURCE_BOUND_PROTOCOL surface（ProtocolDocumentSurface）iframe；Desktop：独立 editor 窗口
→ FILE_STORAGE 写入 evidence 与新 head revision
→ ProtocolSession saved/conflict/unknown
```

#### 能力契约与一致性套件

- 以 `file_storage.v1` 的契约键、permission 映射与一致性套件为准（`.design/07` §2.4）；在线编辑是其条件能力：只有声明 `online_editing=SUPPORTED`（同时声明 `revision_query=SUPPORTED`）的实现实现并暴露 `file_storage.open_view@v1`、`file_storage.open_edit@v1`（`DD-103`）；
- 实现 `ProtocolSession`（`kind=file_storage.edit_session`）与通用 `ComponentTaskWorkflow(kind=PROTOCOL_SESSION_RECONCILE)`：保存结果证据被接受且确认新 revision 才在原 Action 内终结，写入或 revision 结果不明才进入对账（`DD-90`）；
- 实现 Buzz Web 内置的通用 `SOURCE_BOUND_PROTOCOL` surface `ProtocolDocumentSurface`（属 Kailo TypeScript 平台包，经 `SS-WEB-COMPONENT-HOST` 挂载）：只消费经 Core 校验的 DocumentLaunchDescriptor，以其 `editor_origin` 打开，不含产品分支、不拼接实现私有 config，iframe 显式声明 `sandbox` 与 `allow` 白名单；Web CSP 的 `frame-src`/`form-action` 只为 `EXT-BASE` 固定的部署级 editor origin 许可集合放宽，`script-src 'self'` 不变（`DD-30`、`DD-60`、`DD-95`）；
- 闭合 `SS-DSK-EDITOR-WINDOW`，实现 Desktop 的独立 editor 窗口（`DD-104`）：BFF 为已准入的 ProtocolSession 签发一次性 launch 地址，Desktop 以 `kailo-editor-*` 窗口经 `WebviewUrl::External` 打开，`on_navigation` 只放行该 launch 地址与本次 `editor_origin`（仍属于运行时许可集合），窗口不属于任何 Tauri capability；主窗口 CSP 不变；撤权、会话终结或许可集合移除该 origin 时关闭窗口；
- 某端有效集合尚未包含该 origin 时编辑入口显示确定状态（Web：许可集合 ∩ Web 已生效集合；Desktop：运行时下发的许可集合）；
- 每次 launch 请求携带 Buzz resolved theme 与 `en/zh-CN` locale，由实现的 adapter 映射为其私有参数写入 descriptor，surface 不理解这些参数，活跃会话保持 launch 快照（`DD-36`、`DD-95`）；
- 文件所属实现未声明 `online_editing=SUPPORTED` 时文件只显示元数据与受权下载；业务文档消息只保存 ContentReference。

#### 内置参考实现：Cells + ONLYOFFICE

Cells 与 ONLYOFFICE DocumentServer 部署为一个声明 `online_editing=SUPPORTED` 的 `FILE_STORAGE` 能力组件，二者之间的 WOPI 是组件内部集成，对平台是一个 ApplicationBinding（`DD-90`、`DD-103`）；实现细节以 `.design/18` 为准。

- 实现 Cells 的 `file_storage.<kind>` Resource、owner、preview/download/upload 与版本视图；
- 闭合 `SS-CEL-WOPI`、`SS-OFF-WOPI`（在线编辑）与 `SS-CEL-MATERIALIZATION`（为接收方提供完整列举读取，release 声明 `read_edge=SOURCE`）；
- 实现平台 Human/session/permission 到 Cells PAT/WOPI 的安全投影；
- 实现 PutFile 前置 PEP、timestamp、partial write 与 NodeVersions 对账，结果不明进入 `PROTOCOL_SESSION_RECONCILE`；
- 每个 Tenant 使用 dedicated DocumentServer 实例；固定 DocumentServer ipfilter、JWT direct request 与 private IP 相关部署不变式（`DD-33`）；
- 该参考实现的 release 关闭 ONLYOFFICE chat、AI plugin、宏与插件（`DD-35`）；
- 删除能力受 `GAP-LCM-01` 阻断，release 声明 `retain_on_tenant_delete`。

#### 可替换外部实现

- 任一通过 `file_storage.v1` 一致性套件的实现按外部实现路径准入，声明 `online_editing=SUPPORTED` 时叠加在线编辑的条件键语义；未声明在线编辑的文件存储只提供元数据与受权下载；
- 可替换的单位是文件存储实现本身：平台不在编辑器与文件存储之间建立数据通道，不以一个实现的编辑器编辑另一实现的文件（`DD-103`）；
- 替换后既有 ContentReference 仍指向原 binding，不静默改写，也不以旧实现的 native ref 访问新实现。

#### 验收映射

`V-SCN-05`、`08`、`24`–`26`、`49`、`65`、`74`、`76`、`81`，以及 `.design/18` 的 WOPI 交互矩阵。其中 `V-SCN-65` 验证在线编辑入口，`V-SCN-81` 验证 Web iframe 与 Desktop 独立 editor 窗口的端到端。

#### 退出门禁

- `file_storage.v1` 一致性套件对每个待激活实现全部通过，声明在线编辑的实现同时通过其条件键语义；
- 每个 active binding 满足其 binding 激活门禁；
- 撤权后新 launch 与既有会话的保存都 fail closed，Desktop editor 窗口随之关闭；
- 只有契约登记的保存证据与新 head revision 同时成立才显示 SAVED，结果不明进入确定冲突或 `UNKNOWN` 对账；
- Desktop editor 窗口拒绝许可集合外的导航且没有 IPC 权限；新增 editor origin 不需要发布 Desktop 包；
- 承载端不按产品分支渲染；Mobile 不渲染在线编辑入口。

#### 参考实现验收

- read-only session 无法因 Cells 原生默认行为获得写权限；
- 只有 PutFile evidence 与新 NodeVersions head 同时成立才显示 SAVED；
- 409、partial write、500 with bytes 和响应不明进入确定冲突或 UNKNOWN 对账；
- DocumentServer 只能请求绑定 Tenant 的 Cells origin。

### 10.3 能力扩展 EXT-KNOW：知识

#### 目标链

```text
接收方在自己的管理面配置数据源连接器
→ Governed Action（含审批）授予接收方 ServicePrincipal 来源 reader
→ 接收方经来源能力契约自拉，内部完成增量、去重与删除收敛
→ 知识 Tool（consume）经 AgentGateway ExtMcp PEP
→ 回答/citation/受控 derived Asset + usage/audit
```

#### 能力契约与一致性套件

- 以 `knowledge.v1` 的契约键、permission 映射与一致性套件为准；全部知识 Tool 都映射到契约键，按工具名不获得额外权限；
- `consume` 只返回回答、citation、aggregate 与受控 derived Asset；
- ResourceType 登记 `NATIVE_INTERNAL` 并经 Adapter Protocol 暴露稳定 native ref、revision 与 ready/failed/unknown；
- 接收方自拉的对端以 `file_storage.v1` 契约验证，不以某个文件存储实现为前提；平台只治理授权与动作，不持有逐项状态；
- 平台不把服务自带的 memory、会话抽取与 prompt 注入纳入 Agent 上下文或用户入口，Agent 只经契约 Tool 取得结果，不规定服务内部是否启用（`DD-92`）；
- 作为服务读取边接收方的实现在 release 中声明 `read_edge=RECEIVER` 或 `BOTH`；未声明时它仍是完整的知识实现，只是不自拉其他服务的数据（`DD-89`）。

#### 内置参考实现：WeKnora

- 实现 WeKnora KB/knowledge/file/task 的 `knowledge.<kind>` Resource、owner、permission 与 native scope；
- 闭合 `SS-WEK-MATERIALIZATION`（release 声明 `read_edge=RECEIVER`）；`SS-WEK-ASYNC-TRACE`、`SS-WEK-LLM-CTX` 是逐调用 trace 增强项，不列入 binding `ACTIVE` 门禁；binding 声明 `PLATFORM_LLM_ROUTE`（`DD-20`、`DD-92`）；
- 实现两把最小权限 API key 或移除无法安全提供的 export Action；
- CocoIndex 只在该知识能力组件内部运行：绝对 `db_path`、稳定 app name、state 备份与恢复，状态目录不在 Core/Worker（`DD-89`、`DD-93`）；
- 实现完整列举门禁、hash 引用集合、create-new→ready→delete-old 与部分列举禁删；
- 图谱作为同一 KB 的可选索引，不引入 EdgeQuake 第二图谱（`DD-18`）；
- 该参考实现的 release 关闭 WeKnora 原生 memory 路由、抽取与 prompt 注入；`SYSTEM_AES_KEY` 按 `secret_schema` 校验；
- 删除能力受 `GAP-LCM-01` 阻断，release 声明 `retain_on_tenant_delete`。

#### 可替换外部实现

- 同类别内切换到新实现按 `.design/07` §2.4 的切换规则对账后接管契约键；AgentVersion 不重发，ToolBinding 按契约键重绑；NIP-AE 记忆、Codex Thread 与 Relay 历史不受影响；已开始的执行固定旧 generation 到终态。

#### 验收映射

`V-SCN-05`、`08`、`19`–`22`、`49`、`72`、`76`、`77`，以及 `.design/13` 的增量失败语义。

#### 退出门禁

- `knowledge.v1` 一致性套件对每个待激活实现全部通过；
- 每个 active binding 满足其 binding 激活门禁；
- Agent consume 只得到回答、citation 与受控 derived Asset，得不到 raw file、chunk 或私有记忆；
- 撤销来源 `reader` 后接收方的后续读取被拒（来源端 fresh 拒绝只在 §9 的联合验收中验证）；平台没有跨服务同步状态、Schedule 或 Workflow；
- 替换实现不重发 AgentVersion、不迁移或清空 Agent 记忆。

#### 参考实现验收

- 同 node 内容变更、同内容多 node、删除、runner 迁移、部分列举、WeKnora 失败均可恢复；
- state 不可达时不会换空目录继续；
- 新知识 ready 前旧知识保持可用；
- export 不会通过一个拥有隐含写权限的通用 credential 暴露；
- 图谱启用条件、检索范围和 Tool 权限与源码合同一致；
- WeKnora 自拉 Cells 的组合只在 EXT-FILE 也启用时验收。

### 10.4 能力扩展 EXT-DATA：数据查询

#### 目标链

```text
DATA_QUERY 实现登记的模型版本 Resource/Asset
→ CAPABILITY_VERSION_PUBLISH（仅 versioned_model=SUPPORTED）：该版本的运行时与工具端点收敛
→ Client Surface/Agent 语义查询
→ AgentGateway → ExtMcp PEP → 实现 runtime
→ bounded result/Asset + usage/audit
```

#### 能力契约与一致性套件

- 以 `data_query.v1` 的契约键、permission 映射与一致性套件为准：query/dry_run 映射 `execute`，describe 映射 `read`，条件键 publish_version 映射 `update`，仅对声明 `versioned_model=SUPPORTED` 的实现适用；
- 可查询模型由实现按能力契约注册为 Resource，声明 `versioned_model=SUPPORTED` 的实现另把发布版本注册为不可变 Asset；Core 不含数据查询模型实体（`DD-88`、`DD-90`）；
- 实现通用 `ComponentTaskWorkflow(kind=CAPABILITY_VERSION_PUBLISH)`，只对 `versioned_model=SUPPORTED` 的实现、只依能力契约与 binding 固定的版本 Resource/Asset 工作，不含产品专属步骤；未声明该能力的实现（如 text2sql 服务）不进入该 Workflow；
- 人发起的查询与 Agent 走同一条 Tool 链，ExtMcp 做逐方法 RBAC；
- 实现 query timeout、平台停止等待、迟到结果丢弃与结果行数/字段暴露限制；取消按实现声明的取消能力执行。

#### 内置参考实现：Wren

- 每个已发布模型版本固定 runtime、profile SecretRef（按 `secret_schema` 投递）与数据库原生只读 role（`DD-12`）；
- 固定 `no_connect=false`、`allow_write=false`、`strict_mode=true`，`store_query` 保持 `EXCLUDED`；
- runtime 位于只有 AgentGateway 可达的网络边界内；
- native cancel 声明 `UNSUPPORTED`（`GAP-WRN-01`），不阻断其 binding `ACTIVE`；
- 删除能力受 `GAP-LCM-01` 阻断，release 声明 `retain_on_tenant_delete`。

#### 可替换外部实现

- 新实现注册自己的模型 Resource；声明 `versioned_model=SUPPORTED` 时另注册版本 Asset 并经同一 `CAPABILITY_VERSION_PUBLISH` 收敛；契约键、permission 映射与 Tool 不变，旧实现版本不被改写，新实现不复用旧实现的 native runtime 或凭据。

#### 验收映射

`V-SCN-05`、`09`、`10`、`49`、`73`、`76`，以及 `.design/08` 的 Wren 权限映射。

#### 退出门禁

- `data_query.v1` 一致性套件对每个待激活实现全部通过；
- 每个 active binding 满足其 binding 激活门禁；
- 不为任何实现新增 Workflow kind 或 Core 实体；
- 取消能力为 `UNSUPPORTED` 时只显示平台停止等待并丢弃迟到结果，不宣称数据库查询已取消；
- 不同版本的 runtime、credential、工具端点和 usage 不串用。

#### 参考实现验收

- 数据库原生只读 role 是最终写保护；Wren SQL policy 不被当成安全边界；
- Wren runtime 的 MCP 端点只对 AgentGateway 可达。

## 11. 不进入路线的能力

- 平台编排的跨服务数据同步：`MATERIALIZATION` 端口、MaterializationBinding 与对应 Workflow kind 已按 `DD-89` 撤销；
- 业务能力服务以 `EMBEDDED_DRIVER` 接入、共用数据库或共享凭据（`DD-87`、`DD-93`）；
- 内置 `DATA_QUERY` 参考实现 Wren 的 native query cancel：该实现声明 `UNSUPPORTED`（`GAP-WRN-01`）；
- 内置参考实现的 native Tenant 删除：`GAP-LCM-01` 未闭合，三者均声明 `retain_on_tenant_delete`；平台 Tenant 销毁本身在 Stage 3 交付；
- Tenant CONTROL 身份的轮换与撤销：`BLOCKED: GAP-BUZ-01`。泄漏只以 KV `delete` 遏制，该 Tenant 的投影随之 fail closed；
- 长存 MCP bearer 的原地轮换：`GAP-AGW-01`。撤权只以结束旧 turn 与重建 client 收敛，不承诺已建连接换 token；
- 跨 Tenant 资源转移（`V-SCN-30`）：首批全部 ResourceType 的 `transfer_formats=[]`，`RESOURCE_EXPORT`/`RESOURCE_IMPORT` Action 在一期不注册。领域合同已在 `.design` 冻结，但没有可交付的用户入口；
- Cells 自有 editor provider 接缝（`SS-CEL-EDITOR`）：设计已判定它只能返回 `PreSignedURL`，不足以表达承载端所需的结构化 editor config，不作为一期主接缝；
- 跨 Tenant 直接共享；
- 本地 computer use（Desktop 与 Mobile 属一期三端交付，见 §1.1）；
- 第二套聊天、图谱、Workflow、Agent Registry、Memory 或计费权威；
- 成为平台核心第二运行链或重复管理面的任何集成形态（`.design/01` §5）；Mattermost 与 temporal-ui 的运行时集成；
- Buzz Relay 自带 workflow：在 Kailo 部署中关闭（`DD-106`），用户可见的自动化由 Stage 5 的 Temporal 自动化承接（`DD-107`）；
- Tenant 上传后端 executable、动态库或未知 embedded driver。
