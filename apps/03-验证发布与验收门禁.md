# 验证、发布与验收门禁

## 1. 核心原则

验证目标不是证明服务“能调用”，而是证明设计合同在成功、拒绝、超时、重试、撤权、重启和结果不明时仍成立。所有完成声明必须附实际命令、版本、环境、结果和 artifact digest。

## 2. 追溯单元

每个可交付能力建立一条机器可读追溯记录，字段与校验规则以 `06-工程基线规范.md` §1 为准，完备性以 `05-设计覆盖矩阵.md` 的归属为判据。记录至少覆盖能力标识、exposure 级别、设计引用（要求/决策/事实/接缝/阻断/实体）、验证场景与测试、实现路径与 schema/迁移、发布产物与 digest。

检查器必须拒绝：

- active 能力引用不存在的设计 ID；
- `ADAPTER_REQUIRED` 能力缺少对应 `SS-*` 实现，或缺少该接缝在固定 commit 上仍成立的证据；
- `BLOCKED` 或 `EXCLUDED` 能力出现在 route、menu、Action、Tool、Workflow、manifest 或部署清单；
- release artifact 无来源 commit、依赖锁或 digest；
- 能力在 `05-设计覆盖矩阵.md` 中没有 Stage 归属；
- 追溯记录的 `stage` 与覆盖矩阵的归属不一致；
- schema/Workflow 变更没有 compatibility 结论。

## 3. 必须被证明的维度

下表是"什么必须被证明成立"，不是测试分层，也不规定证明手段或先后顺序。自动化测试、脚本化演练、可复现的手工核验记录都算证据，只要下一个人能照着复核。

| 维度 | 必须成立 | 常见的出错方式 |
|---|---|---|
| 领域规则 | 状态机、权限组合、hash、idempotency、redaction | 非法跃迁、scope 丢失、重复扣减 |
| 模块与事务 | Core 模块与事务/outbox/锁的组合行为 | intent 与 outbox 分裂、generation 非原子切换 |
| 合同一致 | Rust/Go/TS/Dart/adapter schema 与错误码一致 | 枚举漂移、旧客户端无法读取新字段 |
| 上游接缝 | 每个 `SS-*` 在固定 commit 上仍然成立 | 上游签名变化、hook 顺序变化、配置默认值变化 |
| Workflow 重放 | 录制 history 在当前与升级 Worker 重放 | nondeterminism、changeID 缺失、Activity 类型漂移 |
| 组件集成 | 固定上游版本的真实 API/协议行为 | 终态误判、取消语义错误、credential 过宽 |
| 端到端场景 | `.design/16` 的用户场景 | 治理链缺环、UI 与权威状态不一致 |
| 故障与恢复 | crash、timeout、network split、duplicate、late result | 重复副作用、UNKNOWN 被当成功、slot 提前复用 |
| 安全边界 | authn/authz、header、token、secret、Tenant isolation | header spoof、跨 Tenant、token 重放、secret 泄漏 |
| 呈现 | theme、i18n、a11y、权限裁剪、恢复 | 原生英文泄漏、失权菜单残留、脏界面强刷 |

## 4. 必须成立的不变式

### 4.1 身份与 scope

- issuer+subject 只来自 Gateway 已验证投影；外来 `x-kailo-*` header 全部清理；
- 缺身份 header 的任意请求，包括 OPTIONS，不进入 Admission；
- Tenant/Workspace 不从 payload、component response、Buzz roster 或 native role 推断；
- PlatformSession 撤销立即关闭新请求与 stream；
- Browser、Agent 和 Remote module 无法取得 service credential。

### 4.2 授权、审批与撤权

- scope guard 先于 Resource permission；
- Agent permission 是 permission、Delegation、ToolBinding、Exposure 与 binding scope 的交集；
- Approval 冻结 action/version/target/parameter hash/owner/policy version；
- approval 不增加 permission，dispatch 前重新 fresh Check；
- 撤权使新动作 fail closed，并触发既有 stream/turn/client 的设计规定收敛。

### 4.3 Workflow 与外部副作用

- 相同业务实体/version 只产生一个固定 workflow ID；
- Start、dispatch、callback、usage publish 的重试保持稳定 idempotency key；
- native ref 缺失且响应不明时不自动重放副作用；
- cancel accepted 不等于 cancelled；
- TaskProjection 落后不改变 Temporal history；
- heartbeat timeout 不等于 holder terminal；
- Workflow 版本升级通过真实 history replay。

### 4.4 Quota、Usage 与账单

- strict reservation 仅覆盖封闭 producer 与可证上界；
- reserved、unsettled、committed 参与同一 admission 判定；
- usage event 使用稳定 namespace/source/id/body；
- OpenMeter accepted、committed、charge、invoice final 分开显示；
- usage 或 correlation 缺失显示明确不可计费状态，不填零值。

### 4.5 组件与前端

- release immutable，binding pin exact release 与 generation；
- snapshot 是完整受权状态，event 只触发 refetch；
- artifact digest、import 根、API range、slot、i18n catalog 全部校验；
- module dispose、异常归因和 generation 切换不改变 native/binding 权威；
- 失权后 menu、route、module、Tool 和 stream 一并消失；
- BFF 永远重做 authorization，前端隐藏不参与安全判定。

## 5. 合并门禁

每个变更合并前必须通过：

1. 格式与静态检查；
2. 受影响范围的验证及其可复核记录；
3. contract compatibility 检查；
4. 数据迁移前进与回退/停止演练；
5. 受影响 Workflow replay；
6. 设计 ID 与验证场景追溯检查；
7. secret、依赖、许可证与供应链扫描；
8. 上游 seam diff 检查；
9. 受影响安全不变式的验证；
10. 文档、runbook 与 release note 同步检查。

只修改文档时，至少运行 `tools/check-docs.sh`：它覆盖禁用词、相对链接、设计 ID 闭合、`05-设计覆盖矩阵.md` 的三项计数、`V-SCN-*` 覆盖与 markdownlint，检查范围含本目录顶层实施合同与 `docs/` 下的 ADR 与 runbook，失败时以非零码退出，可直接作为 CI 步骤。它是 ADR-07 所定统一入口 `tools/check.sh` 的文档快路径，两者行为保持一致。

## 6. 环境晋级门禁

### 集成环境

- 固定上游版本与测试数据；
- 每个 platform port、adapter 和 protocol peer health/identity/config hash 可核验；
- `07-运行与运维基线.md` §1 的部署前置不变式全部校验通过；
- schema migration、Temporal namespace/Search Attribute、OpenMeter meter 与 SpiceDB schema 对账完成；
- `BLOCKED` 能力不存在 exposure。

### 预发布环境

- 使用与生产相同的 artifact digest；
- 完成关键 `V-SCN-*` 端到端、故障注入和恢复演练；
- 完成撤权、secret rotation、runtime restart、Worker upgrade/replay、binding rollback；
- 完成 Tenant/Workspace 隔离与越权核验；
- 完成容量上限、backpressure 与慢依赖验证；
- 完成审计、usage 和 evidence 对账。

### 生产发布

- `.design/15` 的一期生产总门禁全部闭合；
- 每个 `ADAPTER_REQUIRED` 能力有对应 artifact、接缝证据与 read-back evidence；
- 数据迁移与 Workflow 兼容顺序已演练；
- 回滚不会使新 schema/history 被旧版本误读；
- dashboards、alerts 与 runbooks 使用 `06-工程基线规范.md` §4 的稳定业务 reason code，且 `07-运行与运维基线.md` §6 的必备 runbook 全部经过演练；
- 发布清单包含所有 runtime、adapter、patch、schema 与 baseline digest。

## 7. 分批发布顺序

一次发布按兼容顺序执行：

1. 向后兼容 schema 与 contracts；
2. 能读取新旧格式的 Core/Worker/adapter；
3. 上游 patch 与 platform provider；
4. projection reconcile；
5. Web/Component release；
6. capability exposure；
7. 观察 audit/usage/error/latency 与 reconcile gap；
8. 移除旧读路径，作为后续独立发布。

Workflow 行为变化先部署兼容 Worker，再以 `GetVersion` 控制新 execution。Binding 升级建立新 generation；旧 invocation 不强切。不可逆数据迁移或 native 副作用不与 capability exposure 同一步执行。

## 8. 回滚与停止条件

出现以下任一情况立即停止 exposure 或回滚新 generation：

- identity、scope、authorization 或 secret audience 无法验证；
- Core 与 SpiceDB/Buzz/Gateway/native projection hash 不一致；
- Workflow replay 失败；
- durable usage、audit intent 或 operation correlation 出现缺口；
- native terminal 无法观察且设计没有 reconcile seam；
- artifact digest、schema range 或 adapter handshake 不一致；
- 跨 Tenant 数据、credential 或 stream 泄漏；
- 旧版本无法安全读取已写入的新 schema/history。

回滚不得删除历史 Action、Workflow、Audit、Usage 或 ExternalExecution，也不得把 `UNKNOWN` 改写为失败或成功。

## 9. Stage 验收报告

每个 Stage 关闭时提交一份报告，至少包括：

- 范围与未进入范围；
- 已闭合的 `SS-*` 与仍存在的 `GAP-*`；
- 设计/代码/验证/artifact 追溯表；
- 实际执行的验证命令和结果；
- migration 与 Workflow replay 结果；
- 安全、故障和恢复演练；
- 性能与容量边界；
- 已知限制及其 UI 表达；
- 发布、回滚和数据保留结论。
