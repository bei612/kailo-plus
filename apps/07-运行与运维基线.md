# 运行与运维基线

本文件把分散在 `.design` 各篇的运行前提汇总为可执行清单，并固定实施工程在可观测性、数据保留、容量与运维手册上的最低要求。

它不重定义任何设计语义。每条不变式都标注设计来源；与来源冲突时以 `.design` 为准。它也不选择具体产品——数据库、编排、日志后端等仍由 `00-实施总纲.md` §6 的 ADR 决定。

## 1. 部署前置不变式

以下条件在 `.design` 中分散登记，任一不满足都会静默削弱安全或可用性边界。它们必须成为部署校验的一部分：Core 启动时或 binding 进入 `ACTIVE` 前主动核验，核验失败即拒绝启动或拒绝激活，而不是写在文档里靠人记住。

本节分两张表（`DD-91`）：第一张是平台核心不变式，「零业务能力 binding」部署同样全部校验，失败即拒绝启动或拒绝平台 binding 激活；第二张是业务能力参考实现不变式，只在对应 ApplicationBinding 启用时校验，失败只拒绝该 binding 进入 `ACTIVE`，不阻止平台启动。

### 1.1 平台核心不变式

## 2. 本地开发环境

目标是让任一工程师在一台机器上跑通一条纵向切片，而不是复刻生产拓扑。

本地初始化统一使用 `deploy/local/init-local.sh`，不再临时手工拼接密钥生成、数据库迁移、OpenBao 解封、Core 启动和首位测试管理员。先将 `deploy/local/.env.example` 复制为不入库的 `.env`，填写所有必需配置，尤其是 `BOOTSTRAP_USER`、`VERIFY_USER`、`VERIFY_TENANT_SLUG`、`VERIFY_TENANT_NAME` 与 `VERIFY_BOOTSTRAP_WAIT_SECONDS`。Keycloak realm 分别导入首位管理员 `BOOTSTRAP_USER` 和走查用户 `VERIFY_USER`，两者必须不同，口令分别只保存在 `deploy/local/secrets/bootstrap_user_password` 与 `deploy/local/secrets/verify_user_password`。`bootstrap-tenant` 只用首位管理员真实 OIDC subject，经过既有 Tenant、成员及管理员生命周期创建业务 Tenant，不直接插入一套测试关系。走查用户不预先加入该 Tenant：一期无登录时选择 Tenant 的入口，Web/Native 走查开通临时 Tenant 后才能唯一确定 scope。

本地部署的非密输入只有这份 `.env`；Compose 从 `OIDC_ISSUER` 派生该 Keycloak realm 的 JWKS 与 token URL，从 `PUBLIC_ORIGIN` 派生浏览器回调与邀请页地址，从 `TEMPORAL_ADDRESS` 派生 Core 的 Temporal target。`OIDC_REALM` 必须与 issuer 的 `/realms/<realm>` 路径一致，两个 URL 主值都不得以 `/` 结尾；初始化在任何 `--fresh` 删除前拒绝不一致输入。这个路径规则只适用于本地 Keycloak 拓扑，不是可替换 OIDC 提供方的通用 URL 规则。Core 数据库连接串由 `CORE_DB_USER`、`CORE_DB_NAME` 和 `secrets/core_db_password` 生成到受控 `secrets/core-db-url.env`；宿主迁移临时连接串从同一组值构造，不再从 `.env` 读取含密码的 `CORE_DATABASE_URL`。进程环境和上游组件模板是上述输入的投影，不是各组件独立维护的配置副本；不同角色的 OIDC client ID、Temporal 公开 frontend 与 internal-frontend、内外网地址仍保持不同事实。

已有本地 `.env` 需按新样例补必填的 `PLATFORM_DISPLAY_NAME`、`PUBLIC_HOST`、`OIDC_HOST`、`BUZZ_RELAY_HOST`，将 `PUBLIC_ORIGIN` 与 `OIDC_ISSUER` 改为使用这些主机名与对应发布端口的变量表达式，并移除 `OIDC_JWKS_URI`、`OIDC_TOKEN_URL`、`OIDC_REDIRECT_URI`、`TENANT_INVITATION_LINK_BASE`、`TEMPORAL_TARGET_URL`、`CORE_SERVICE_URL`、`CORE_DATABASE_URL`、`BUZZ_RELAY_TRANSPORT`、`BUZZ_RELAY_WS_URL`、`RELAY_OPERATOR_API_ORIGIN` 的手填值；旧值不再参与 Compose 投影。配置错误只拒绝启动，不自动重建数据库或重发身份。

2026-09-28 的本地静态核验：`tools/check.sh security` 覆盖的 23 个服务均通过；分别恢复独立 `OIDC_TOKEN_URL` 输入、把 Web 显示名投影改为字面量、增加重复的 Compose `environment` 键、把 `PUBLIC_ORIGIN` 派生表达式改为固定 URL，四次破坏检查均以退出码 1 报错，逐次还原后检查退出码 0。用不含真实凭据的内存夹具改动域名、端口、库名与 Unicode 品牌，通过 Compose 解析核对 19 项环境投影和 7 个网络 alias 一致。此记录只证明配置单源门禁与 Compose 派生关系，不替代实际容器启动与三端验收。

同日 Web HTTP 构建镜像的页面实测通过：显示名包含 Unicode、script 字样、单双引号与 `&` 时，HTML 的 title/meta 与 manifest JSON 值准确且未注入标记；manifest 的 MIME、no-store 与 CSP 均按发布合同返回。显示名为空或仅含空白时服务启动拒绝。这项证据只覆盖 Web 公开页面的品牌投影，不代表业务链端到端验收。

同日 `tools/check.sh --full` 在 CPU/内存受限的 cgroup 内退出 0；未提供 `DATABASE_URL`，实际迁移前进/回退演练明确跳过，内置秘密扫描通过但本机未安装 gitleaks。Web 镜像与受共享文案影响的 Desktop Linux 安装包均已重建，摘要由构建工具写回；Mobile 只同步生成文案与源码摘要，产物仍为 `none`。现有环境的 `.env` 与凭据未被本次核验修改，也未以这批配置重启现有服务。

库名、OIDC realm 与 Community domain 是持久身份或存储绑定，不是展示名：集中配置不赋予原地重命名这些既有事实的能力。新部署从统一输入初始化；已有部署变更上述值须执行对应迁移，不能把配置替换当作无损升级。

`PLATFORM_DISPLAY_NAME` 当前只贯穿该本地 Compose 的 Web 公开页面；Desktop/Mobile 原生包的显示名、设备侧发布配置尚未从同一字段派生。该范围不得被记录为三端品牌配置已完成。

本地拓扑的 `PUBLIC_HOST`、`OIDC_HOST`、`BUZZ_RELAY_HOST` 分别是公开入口、IdP 与 Relay 网内 DNS alias 的主机名输入，不能与每个 Tenant 的 `BUZZ_COMMUNITY_DOMAIN` 混用。`PUBLIC_ORIGIN` 与 `OIDC_ISSUER` 分别从前两者、各自的发布端口和本地 HTTP 协议派生；初始化同时核对 host、端口、scheme 与 realm，不接受手填 URL 漂移。Relay 的网内 HTTP、WebSocket 与 operator origin 从 `BUZZ_RELAY_HOST` 和 `BUZZ_RELAY_PORT` 派生，保证 operator 签名目标与 Relay 配置逐字符一致。固定的回环发布绑定仍是本地安全边界。

已有环境的连接串统一由 [`deploy/local/database-url.sh`](deploy/local/database-url.sh) 编码，`bootstrap.sh`、`init-local.sh` 与 `core/verify/integration-env.sh` 共用；容器入口与宿主入口各用自身 authority，用户、库名、密码仍取同一份配置与受控文件。密码中的 URL 保留字符按百分号编码，不要求更换已有密码，也不重新引入手填连接串。`bootstrap.sh --validate-config` 在生成凭据和 `--fresh` 删除前拒绝空白展示名及无效数据库端口；校验模式不写文件、不访问上游服务。

Keycloak 持久 realm 不会因本地导入文件改变而重新导入。`init-local.sh` 在 IdP 就绪后调用 `bootstrap.sh --sync-browser-client`：只更新已存在且唯一的 `OIDC_BROWSER_CLIENT_ID` 的 `redirectUris` 和 `webOrigins`，回调由 `PUBLIC_ORIGIN` 派生；随后回读确认。用户、subject、client secret、角色、protocol mapper 均不写入。不存在对应 client 时拒绝，不创建替代身份；请求超时或回读不一致时初始化失败，重跑先读现状再收敛。单独迁移已有本地公开入口时，先运行 `bootstrap.sh` 生成同源投递，再运行该同步模式，按受限构建与一次性凭据规则重建受影响服务；不使用 `--fresh`，不重导入 realm。该模式不承担 realm、client ID 或原生包回调 scheme 的更名迁移。

2026-09-28 后续实测已将本地 `.env` 迁移为单源字段：保留原数据库和凭据，生成的宿主连接串成功查询原 Core 数据库；浏览器客户端回调首次同步后回读一致，第二次调用报告无需更新。Web、AgentGateway 与 Core 已按新配置重建，Core 的编译层命中缓存、BuildKit 保持 16 GiB 内存及 4 CPU cgroup 上限。配置门禁真实运行临时目录中的 `bootstrap.sh --validate-config`，验证 Unicode 展示名、空白拒绝、无效数据库端口及无文件副作用；数据库编码覆盖两种 authority 和保留字符口令。分别破坏密码编码、删除初始化前置校验调用时门禁退出 1，恢复后退出 0。完整 Web 走查本轮在夹具准备阶段返回 `TENANT_SELECTION_NOT_AVAILABLE`，并报告夹具拆除失败；该结果不是浏览器业务链通过，也不解除 Stage 1/2 门禁。

同轮诊断中把连接串放入 `PGDATABASE` 环境被 `psql` 当成数据库名并在错误中回显；后续核验固定使用分离的 `PGHOST/PGPORT/PGUSER/PGDATABASE/PGPASSWORD`，不把含密连接串放进命令行或该环境变量。该本地 Core 数据库密码已轮换，实际验证新凭据可连接、旧凭据被拒绝；其他组件凭据与数据库内容未重建。这次口令轮换是诊断泄露风险处置，不是共享配置迁移要求用户更换密码。

```bash
cd deploy/local
export BUILDX_BUILDER='填入已有受限 builder 名'
./init-local.sh
```

无参数执行只补齐现有 `kailo-local` 环境：保留数据库卷和凭据，运行 Core 迁移，重验上游初始化并重建需要一次性 OpenBao 引导凭据的 Core。重跑时复用同一首位管理员和 Tenant；已有其他有效管理员的 Tenant 由 `bootstrap-tenant` 拒绝追加管理员，命令以失败结束。Keycloak H2 位于本 Compose 专属持久卷，避免容器重建后 IdP subject 改变而 Core 身份映射仍指向旧 subject。旧版无 Keycloak 持久卷的本地容器、realm 只有 `VERIFY_USER`、或该用户已作为首位管理员加入 Tenant 时，入口不悄悄改写身份归属；须在确认该环境测试数据可丢弃后显式执行下文的 `--fresh`。脚本在构建前核对现有编译进程、CPU/内存压力与 BuildKit 容器的 cgroup 限额；缺少受限 builder、`sqlx`、固定版本镜像或必要配置时直接失败，不退回不受限构建器。固定版本 Buzz、buzz-web、AgentGateway 镜像须按 `04-上游适配与升级.md` 先放入本地 registry；初始化脚本不从 `.references` 构建。

只有确实要销毁这套本地测试数据时才运行 `./init-local.sh --fresh --confirm-delete=kailo-local`。该操作仅对 Compose 中名称为 `kailo-local` 的项目执行 `down --volumes`，删除其五个数据库卷（含 Keycloak）及本目录的 `secrets/`、`data/openbao/`、`data/buzz-objects/`；保留 `.env` 和 `data/registry/` 的固定版本镜像缓存。此前的测试用户、OIDC subject、Tenant、审计和对象字节均不可恢复，不能用于保留数据的升级，更不作用于旧 Kailo 的 K8S。脚本未执行 `--fresh` 时不会删除这些数据。

当前 Compose 只包含已经接入的本地服务，不代表全部目标上游组件已经部署。脚本成功只证明本地协作与治理主链可启动并建立测试 Tenant，不能代替 `tools/check.sh --full`、真实端到端验收或生产发布门禁。若初始化中途失败，修正报错后原样重跑；Core 的一次性 wrapped secret 不允许用 `docker compose restart core-bff` 重试，入口会重新调用 `start-core.sh` 投递。

- 上游服务使用 `04-上游适配与升级.md` 的 baseline manifest 所固定的版本，以 artifact 或镜像引入，不从 `.references` 工作树构建。
- 本地拓扑必须保留 `01-工程结构与模块边界.md` §8 的网络边界形状：Browser 只到达公开入口，BFF 只接受身份投影，管理面不可直达。本地可以简化副本数与持久化，不可以简化边界。
- §1 的部署前置不变式在本地同样生效。降低其中任何一条都会让本地验证失去意义——尤其是 Relay 成员校验、MCP audiences 与 RBAC 规则集。
- 提供一条统一命令完成格式、静态检查、contract 检查、迁移演练与追溯检查，与 CI 使用同一入口；其余验证按需接入同一入口。
- 开发用 secret 也经受控投递面取得，不在仓库、环境文件或脚本中出现明文。
- 名字按生产的形状解析，不为本地另开别名：IdP 以 issuer 里的主机名与端口在本机发布（`KEYCLOAK_PORT` 与 issuer 端口一致），令牌的 `iss` 才与 BFF、Temporal 配置的 issuer 相等；IdP 与 Relay 的主机名、核验时临时开通的 Community host 经 `/etc/hosts` 指向本机，Community host 由核验脚本在开通后加入、结束时删除。

## 3. 可观测性实现要求

`.design/14` 定义的是受权只读的业务视图。本节规定实现侧必须产生什么信号，以及什么绝对不能进入信号。

必须发出：

- 每个 Governed Action 的开始与终结，带 `operation_id`、Tenant、Workspace、actor、ActionDefinition 版本与终态 reason code；
- 每次外部副作用的 dispatch 与观察结果，带 ExternalExecution 引用与 native 状态原值；
- 每个 Workflow 的状态跃迁投影写入结果，以及投影落后的显式度量；
- 每次 usage 发布与其 committed 确认，以及缺口计数；
- 每个 binding、generation、projection 的对账结果与不一致计数；
- 每类 §1 不变式的校验结果，作为启动与激活的门禁信号。

禁止进入任何日志、指标标签或链路属性：

- 消息正文、文件内容、chunk、SQL 行、prompt 与 response、文档内容；
- secret 值、token、cookie、私钥、PAT；
- 高基数的自由文本。标签只用封闭枚举与稳定 ID。

链路关联以 `operation_id` 为主键贯穿 Core、Worker、adapter 与组件。对目前无法透传关联上下文的跳，按 `.design` 的对应接缝结论记为不可归因，并在业务视图中显示确定状态，不以推测补齐。

## 4. 数据保留、备份与恢复

权威分散在多个系统，因此不存在"一次备份全部"。恢复演练必须按权威逐个进行。

| 权威 | 保存内容 | 保留与备份要求 |
|---|---|---|
| Core 数据库 | scope、owner、binding、Action/Operation、Approval 投影、ExternalExecution、Audit、Outbox、SecretRef locator | 平台恢复的主对象；需要按时间点恢复能力；Audit 与 Usage 记录不可删改 |
| OpenBao | secret 版本与 lease | 独立备份与恢复流程；恢复顺序先于依赖它的一切 binding |
| Temporal | Workflow history | 受 namespace retention 约束，不是长期档案；终态必须已投影进 Core |
| Buzz Relay | Community、Channel、消息、NIP-AE 记忆 | 协作与记忆权威，按其自身机制备份 |
| SpiceDB | schema 与关系 | 授权关系权威。只经其批量导出与导入 API 做逻辑备份与恢复：revision 是 Postgres 事务 id，SQL 级转储恢复到另一集群后关系全部不可见（`SF-SPZ-06`） |
| IdP | 用户及其稳定 subject | Core 的 ExternalIdentity 以 (issuer, subject) 对应到人；subject 变化即所有人无法登录。与 Core 数据库同一时间点备份 |
| OpenMeter | committed usage 与账单 | 计费权威，不可由平台重算覆盖 |
| 可选能力实现：`FILE_STORAGE`（参考实现 Cells） | 文件字节与版本链 | 仅在该 binding 启用时适用。文件权威，由该实现按自身机制备份，数据库与对象存储独立于平台核心 |
| 可选能力实现：其他业务能力（参考实现 WeKnora 及其内部 CocoIndex 状态、Wren） | 该实现自有的数据、索引、内部增量状态与已发布版本 | 仅在对应 binding 启用时适用，由该实现按自身机制备份。派生数据丢失时由该实现从来源能力重新自拉，平台不承担重建、不持有其状态（`DD-89`） |

恢复顺序固定为：OpenBao → Core 数据库 → 平台核心各组件权威 → 投影对账 → 平台能力重新开放。对账完成前不恢复用户可达入口。已启用的业务能力实现各自恢复并完成 binding 对账后才重新开放该 binding，不阻塞平台恢复。

恢复不得把 `UNKNOWN` 改写为成功或失败，也不得删除历史 Action、Workflow、Audit、Usage 或 ExternalExecution。

## 5. 容量与性能框架

本节不给数字，只固定必须被测量、被设界并在超限时有确定行为的维度。每个维度在预发布环境取得基线值后写入发布清单。

- BFF 并发连接与订阅：受 Relay 的订阅数、filter 数、帧大小与每身份限流约束，必须在 BFF 侧先行设界并给出明确拒绝，而不是把压力透传给 Relay;
- Core 写事务与严格 reservation 的串行化热点：按 Tenant 加 subject 加 meter 的键测量排队时间；
- Workflow 与 Activity 的并发、心跳间隔与重试放大；
- 单个 Workflow 的 history 事件数与 pending Activity 数，触及门限前必须 continue-as-new；
- 业务能力实现内部增量的批次与失败隔离边界：由该实现测量并声明，平台只观测其 readiness 与失败；
- 模型调用的并发与配额交互；
- 启用 `DOCUMENT_EDITING` 时 ProtocolSession 的并发数与保存冲突率。

任一维度超限时的行为必须是确定的拒绝或排队，并映射到 `06-工程基线规范.md` §4 的 `LIMIT` 类 reason code，不允许静默降级或无限等待。

## 6. 必备 Runbook

以下场景在生产发布前必须各有一份经过演练的 runbook，存放于 `docs/runbooks/`：

1. 部署前置不变式校验失败（按 §1 逐组件的排查与修复）；
2. Secret 轮换与紧急撤销，含旧版本销毁顺序与在途执行的处理；
3. 撤权收敛未完成（membership、binding、delegation 三类）；
4. Workflow replay 失败与 Worker 回滚；
5. 投影落后与对账缺口修复；
6. usage 或 audit 缺口的定位与补录边界；
7. 外部副作用结果不明的对账（按组件分别说明可用的查询接缝）；
8. binding generation 切换失败与回滚；
9. 上游升级中止与基线还原；
10. 灾难恢复全流程演练。

每份 runbook 必须写明触发信号、判定依据、可执行步骤、不可执行的动作，以及完成判据。禁止出现"视情况处理"这类无判据的步骤。
