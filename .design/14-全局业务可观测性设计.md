# 全局业务可观测性设计

业务可观测性是第八项全局贯穿能力。它观察用户、Agent 与业务资源在平台中的动作和结果，不观察主机、容器、进程、网络等基础设施状态，也不要求 OpenObserve、SigNoz、OTLP Collector 或另一套日志平台。

## 1. 边界与事实权威

| 业务问题 | 事实权威 |
|---|---|
| 谁发起、谁实际执行、在哪个 Tenant/Workspace、目标是什么 | Platform ActionExecution/AuditEvent |
| 为什么允许或拒绝 | SpiceDB decision/ZedToken、Delegation、Approval evidence |
| 审批和长任务当前在哪一步 | Temporal Workflow/History/Schedule、TaskProjection |
| 应用组件是否完成、进度和结果是什么 | 组件同步结果或 native status/task/job |
| Agent 以哪个 Version/Installation/effective generation 调了什么工具/模型、结果是什么 | Core AgentInvocation/RuntimeProjection、Codex turn/tool refs、AgentGateway request log |
| 模型调用完整可计费用量是什么 | SS-AGW-USAGE 闭合后的 durable Gateway usage |
| 使用量、费用和结算状态是什么 | OpenMeter committed usage/cost/billing |
| 谁因何执行了什么且最终结果如何 | Platform Core AuditEvent |

Core 不复制这些系统的完整 history、账本、正文或原始响应。它以 `operation_id` 和 native evidence ref 形成受权业务读模型。Business Observability 不能推进 Workflow、重新计费或替代审计事实。

## 2. 一个业务动作的关联主键

每个 Governed Action 由 Core 生成并固定：

```text
tenant_id
workspace_id | NONE
operation_id
correlation_id
action_key + action_version
resource_id | NONE
initiator_principal_id
actor_principal_id
agent_invocation_id | NONE
delegation_id | NONE
approval_workflow_id | NONE
business_workflow_id/run_id | NONE
component_binding_id | NONE
component_release_id | NONE
component_projection_generation | NONE
native_execution_ref | NONE
gateway_request_log_id | NONE
openmeter_event_id | NONE
```

- `operation_id` 是一次业务意图从准入到终态、撤销或对账的唯一关联键。
- `initiator` 是提出意图的人或服务，`actor` 是实际执行者。用户委托 Agent 时两者必须同时保留。
- retry、callback 和 reconcile 继续引用原 operation；每次 native attempt 使用自己的稳定 native ref。
- Temporal Start 结果不明时以已持久 WorkflowRef 的固定 workflow ID Describe/History；native dispatch 结果不明时以 ExternalExecution 的 idempotency key/request digest 和已登记 query seam 对账。两者都不得用新 ID制造重复 operation（DD-48）。
- Browser、prompt、工具参数和 callback 不能覆盖 Tenant、Workspace、initiator、actor 或 Resource。
- AgentGateway 原生 trace/span ID 只作为其 request-log evidence；业务视图不依赖全局 tracing 后端。Codex 模型链在 SS-COD-TRACE 闭合前没有 operation 派生 trace，不能以 Gateway trace 反推业务归属，usage attribution 固定为 `NONE`。

## 3. BusinessObservabilityContract

每个 ComponentRelease 登记 BusinessObservabilityContract，每个 ActionDefinition 登记 BusinessObservabilityPolicy；ActionExecution 固定实际使用的 release 与 ComponentRuntimeProjection generation：

| 合同项 | 固定规则 |
|---|---|
| correlation | 必须能从 `operation_id` 到一个同步结果或稳定 native ref；不能按时间窗口猜归属 |
| terminal truth | `SYNC_RESULT`、`TEMPORAL` 或 `NATIVE` 三选一 |
| progress | `TEMPORAL`、`NATIVE` 或显式 `NONE`；源码没有百分比就不生成百分比 |
| usage/cost | `DRIVER`、`GATEWAY_DURABLE_USAGE`、`OPENMETER` 或显式 `NONE`；同一 meter 只有一个 actual source。原始 AgentGateway log 不是完整 usage source |
| dimensions | 只允许 Tenant、Workspace、Resource、Asset、Agent、action、component、status 等受控业务维度 |
| redaction | 不进入正文、Secret、完整 prompt/response、原始 SQL、结果行、文件内容或工具 raw body |

注册时与 Tenant、Workspace、Authorization、Approval、Workflow、Capacity/Quota/Billing 和 Operation Audit 一起校验。缺任一合同项，用户/Agent 可达 action 不得 active。

Release 注册、批准、撤销与 Binding provision/upgrade/rollback/disable 也各自是业务 operation。组件视图必须区分：Catalog Tenant 中的 release 合同状态、业务 Tenant 中的 binding/generation 状态、旧 generation 尚未终结的 execution，以及新 generation 当前承接的流量。不得用“组件版本”一个字段合并这四类事实，也不得把 Web module 已加载当作 adapter/native ready。

## 4. 用户行为审计

审计发生在服务端权威入口，不依赖浏览器自行上报。一个 action 按事实产生下列追加事件：

```text
INTENT
→ DECISION(ALLOW|DENY)
→ APPROVAL(wait/approved/rejected/expired) when required
→ DISPATCH(native/workflow ref)
→ OUTCOME(success/failure/unknown/cancelled)
→ REVOCATION or RECONCILIATION when it occurs
```

外部副作用前，Core 必须在同一持久边界写入 audit intent 与 dispatch outbox；写入失败就不执行副作用。结果、撤销和对账以相同 operation 追加。`event_key` 对同一阶段和 native attempt 稳定，重试不得复制同一事实。

所有 Governed Action 审计显式带 Tenant，Workspace action 还带 Workspace；`tenant_id=NONE` 只用于 OIDC callback 后、Core Tenant 解析前的 `AUTHENTICATION|SESSION` 事件。该类事件没有业务 target，使用 HumanIdentity 或不可逆外部 subject hash 归因。EvidenceRef 只保存 authority/type/stable ID/version-or-digest/sensitivity；详情每次 fresh授权，不保存或下发临时 native URL/token（DD-52）。

必须审计的业务行为：

- Buzz 消息发送、编辑、删除及由消息触发的 Agent 动作；只保存 event ID/hash，不复制消息正文。
- 文件/知识/数据模型的创建、修改、删除、分享，以及敏感读取、搜索、下载和导出。
- Tenant/Workspace 成员、角色、owner、关系授权、委托、Agent/Tool/LLM Route binding 变化。
- Agent invocation、工具调用、模型调用、人工确认、审批决定和结果暴露。
- Workflow 创建、暂停、恢复、取消、重试、超时和 reconcile。
- 组件注册/绑定/停用、物化配置与 purge、quota/billing adjustment/export。

页面打开、菜单点击、滚动、hover 等前端交互不属于安全审计；它们不改变业务事实。平台可审计 AgentGateway 已完成的 OIDC callback、Core PlatformSession 建立/撤销和本地 logout；发生在外部 IdP 内部且未到达 AgentGateway 的登录失败不在平台事实边界内，当前明确不可见（SF-AGW-10）。

## 5. Audit 与 Business Observability 的关系

两者共享 operation 关联，但回答不同问题：

| 能力 | 回答 | 数据形态 |
|---|---|---|
| Operation Audit | 谁依据什么权限/审批执行了什么，结果是什么 | 追加式最小事实与 evidence refs |
| Business Observability | 该业务动作现在到哪一步，涉及谁/什么资源，耗时、用量和成本是多少 | 对各权威的受权联合读模型与聚合 |

AuditEvent 不存组件 payload；业务视图按 evidence ref 查询当前权威。Audit 历史不能因组件任务或 Resource 被删除而删除。业务视图不得把缺失状态显示成成功、失败、零用量或零成本，只能显示 `UNKNOWN`、`SETTLEMENT_PENDING` 或 `RECONCILING`。

## 6. 一期组件的业务埋点位置

这里的“埋点”是业务状态落点或 evidence 引用，不是函数级日志埋点。

| 组件/边界 | 必记业务事件 | 源码事实 |
|---|---|---|
| Client Surface/BFF | session scope、action intent、initiator/actor、target、参数 hash、允许/拒绝、结果暴露 | Web route 可二开；业务 command 统一经过 BFF（SS-WEB-01） |
| Buzz Relay | Community/Channel、event ID/hash、persist/fan-out、roster/admin mutation、Agent reply ref | Relay 先持久再 fan-out并有稳定查询游标（SF-BUZ-04/05/07/09） |
| SpiceDB | permission、object/subject ref、allow/deny、consistency、ZedToken | Check/Lookup/Write/Watch/ZedToken 与一致性原语（SF-SPZ-01/02） |
| Temporal Worker | workflow/run/schedule、等待审批、signal/update/cancel、Activity attempt、heartbeat、terminal | Server 提供完整 lifecycle，Application Worker 执行业务逻辑（SF-TMP-01/02/05） |
| Codex | Agent Definition/Version/Installation、projection generation/reason、thread/turn/item、工具请求/批准/结果、reply event ref；模型 usage 在 SS-COD-TRACE 闭合前显示 `BILLING_UNAVAILABLE` | Core Agent model + app-server turn/item/tool notification 与 MCP approval seam；模型 request header 尚无 operation trace（SF-COD-01/02/06/07/08、SS-COD-APP、SS-COD-TRACE，DD-21/25/27） |
| AgentGateway | route/tool/model、PEP allow/deny、已持久 request-log ID、provider/model、status/error/duration/token/page/cost；durable usage settlement ref | logging database 后的 request log 可查但 writer 失败会丢批次；计费需 SS-AGW-USAGE（SF-AGW-06/09） |
| Cells | DriveSpace/node/version/action/job ref、BackgroundAction status/progress/control result | Node/Version/Action/BackgroundAction 接口（SF-CEL-01/02） |
| ONLYOFFICE | DocumentSession、Platform Human、WOPI session/correlation、requested/admitted mode、dirty/close、Check/Get/Put bytes/result、Cells base/result revision | SS-CEL-WOPI 补齐 dirty/close FileInfo 字段并在流式写入前执行 PEP；部分写入 500 进入 UNKNOWN、NodeVersions 对账（SF-OFF-07、SF-CEL-05/06/07/11/13/15） |
| WeKnora | KB/knowledge/task/graph/query ref、parse/reparse/cancel status、Gateway log ref | native task/cancel、图谱、模型调用接缝（SF-WEK-03/05/06） |
| Wren | SemanticModel version、query action、query hash/ref、row-limit/truncated、success/error | fixed context、query tools、read-only policy、同步 query/no cancel（SF-WRN-01/02/03/04） |
| CocoIndex | binding/pipeline version、snapshot revision/completeness、run、create/update/delete/pending/reconcile count | SDK update、keyed diff 与 target state（SF-CIX-01/02/03/04） |
| OpenMeter | entitlement/credit check、UsageEvent/OpenMeter event、Customer/subject、quantity/cost、event stored 与 invoice 状态 | 单 default namespace、Tenant Customer/subject、entitlement/usage/billing、stable event identity 与stored/validation字段；查询只经 SS-OMT-AUTH（SF-OMT-01/02/04/05/06/07） |

组件内部没有源码接缝的状态不补造。Cells/WeKnora 的 queued/cancel accepted、OpenMeter 的 202、Wren wrapper 停止等待都不能直接变成业务终态。

ONLYOFFICE WOPI page 的 loading/dirty/close postMessage 只属于 Web 会话进度与 UI evidence，不能单独成为 permission、usage 或保存终态。Cells WOPI PEP 接受 GetFile证明一次受权读取；保存终态必须同时满足 PutFile evidence 被接受且 Cells NodeVersions 返回新 revision。冲突或写入结果不明分别显示 `CONFLICT/UNKNOWN/RECONCILING`，不能以编辑器关闭推断保存成功（SF-OFF-07、SF-CEL-05/06/07）。

## 7. Web 业务视图

三端通过同一 BFF 提供四个视图（Buzz Mobile 为只读），不直接暴露 Temporal、AgentGateway、OpenMeter 或组件管理 UI：

| 视图 | 内容 | 权限 |
|---|---|---|
| My Operations | 我发起或被委托执行的 action 时间线、状态、结果摘要、自身 usage | initiator/actor + ResultExposurePolicy |
| Resource Activity | 某 Resource/Asset 的变更、Agent 消费、Workflow、物化与 usage 时间线 | Resource `read`；敏感 evidence 还需 `audit` |
| Workspace Business Observability | 按 action/component/Agent/Resource/status 聚合的运行中、等待审批、成功、失败、UNKNOWN、耗时、usage/cost | Workspace `audit` |
| Tenant Business Observability | 跨 Workspace 的业务吞吐、失败、审批积压、任务积压、quota/usage/cost、settlement/reconcile | Tenant `audit` |

成功率与耗时只从 ActionExecution/Audit 的开始和确定终态计算。等待审批、运行中、UNKNOWN、已撤销和 reconcile 必须单列，不能从成功率分母中静默丢弃。用量事件查询 OpenMeter event `stored_at`，202 只显示 `SETTLEMENT_PENDING`；`validation_errors` 是读时重算值，视图把它显示为配置告警而非事件状态；结算侧状态读 charge/invoice 落库的 `validation_issues`；账单状态单独查询 invoice，不能由 UsageEvent 推断 finalized（SF-OMT-07/08、DD-51）。

四个视图都是 `BUZZ_NATIVE` surface：图表、状态色、表格和详情只使用 Buzz CSS variables；状态、聚合维度、错误分类和空态只使用 Buzz `MessageKey/t`，日期/数字使用 `getLocale()`。Resource 名称与 native error 原文属于业务内容/受权 evidence，保持原文，不得代替本地化状态文案，也不得因 locale 不同改变筛选、聚合或审计事实（REQ-08、SF-WEB-03、DD-36/53）。

## 8. 故障与一致性

- TaskProjection 落后时显示 `PROJECTION_DELAYED`；控制命令仍查询 Temporal 和 fresh permission。
- native callback 缺失或外部结果不明时显示 `UNKNOWN` 并进入 reconcile，不从最后一条日志推断 terminal。
- AgentGateway log 已持久但没有 durable usage 时显示 `BILLING_UNAVAILABLE`；durable usage 已产生而 OpenMeter 未可查时显示 `SETTLEMENT_PENDING`；同稳定 request-log ID 只能生成一个 UsageEvent。
- Business Observability 读模型不可用不回滚已发生副作用；Action/Audit outbox、Temporal/native ref 和 OpenMeter 账链继续作为恢复依据。
- Tenant 停用后拒绝新动作和新业务视图查询；历史审计、已发生副作用和已结算 usage 仍按原 scope 保留。

## 9. 上游差异闭环

Buzz event、Temporal lifecycle、AgentGateway request-log schema、Cells node/version/WOPI、DocumentServer WOPI、WeKnora native task、Wren query、CocoIndex target state 或 OpenMeter usage schema发生源码差异时，先重验 `02` 对应 SF/SS，再更新 BusinessObservabilityContract、Action Policy、`08` 组件矩阵和 `16` 验证场景。

基础设施监控不属于本文或一期业务要求。以后增加此能力时应另立需求和源码基线，不得反向改变这里的业务事实权威、审计链或计费幂等性。
