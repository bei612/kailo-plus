# 授权、审批与撤权一致性

## 1. 写入与检查一致性

SpiceDB 提供 relationship write、Check/Lookup、Watch 和 ZedToken（SF-SPZ-01），也能表达 `FullyConsistent` 与 `AtLeastAsFresh`（SF-SPZ-02）。平台固定使用规则：

| 场景 | consistency |
|---|---|
| 列表/发现 | 允许低延迟 Lookup，但点击动作仍 fresh Check |
| 刚写 relationship 后的同一因果链 | `AtLeastAsFresh(write_zed_token)` |
| 审批后、撤权后、无因果 token 且即将发生不可逆外部副作用 | `FullyConsistent` |

Core Resource/Asset owner 事实与 SpiceDB owner relationship 通过 outbox 投影。两者未闭合时，owner approval、owner-only delete/share/transfer 全部拒绝，不从任一一侧推断成功。

## 2. 审批是一次性决策证据

Approval 仅对下列五元组有效：

```text
action_execution_id
action_definition_version
parameter_hash
approval_policy_version
target_owner_version
```

`target_owner_version` 指目标 Resource/Asset 版本中冻结的 owner 事实；多 Resource、Materialization 两端和 TenantLifecycleSnapshot 中是完整 `affected_owner_refs[]`，每项包含 target ID/version 与 owner Principal ID。ApprovalPolicy 的 `ALL_AFFECTED_OWNERS` 要求所有不同 active HUMAN owner 分别批准；静态 `role_requirements[]`（例如 Tenant admin）另行逐项满足，不能用总人数替代某一组要求。

selector 的检查对象固定：`RESOURCE_APPROVER` 对目标 Resource/Asset 做 `approve`；`WORKSPACE_ADMIN` 对冻结 Workspace 做 `manage`；`TENANT_ADMIN` 对冻结 Tenant 做 `manage`；owner requirement 同时比对 Core owner 事实和 SpiceDB owner relationship。selector 没有对应目标或两份 owner 事实不一致时 fail closed，不换用更宽角色。

审批决定以 Temporal Update 提交。Validator 只做确定性状态判断（Approval 已终结、该 approver 已有决定、已过 `expires_at`、approver 不在冻结名单内），因为它运行在只读 dispatcher 且重放时跳过；approver 是 active HUMAN、当前 `approve` permission、policy selector、owner requirement 和 self-approval rule 由 handler 体内的 `FreshApprovalAdmission` Activity 检查，失败作为一条被拒决定进入 history（SF-TSDK-03/09、DD-69）。每人只有一个不可变决定；任一有效 DENY 终结本次请求。消费批准前再做完整 Admission。任一元组、permission、Delegation、binding、capacity 或 quota 变化，就记 `INVALIDATED`，不修补旧批准（DD-47）。

MaterializationBinding 的批准额外冻结 source/target Resource ID、两端 owner version、source/target contract key 与 pipeline version。任一端 owner 转移会暂停 Schedule；新 owner 完成其端 owner approval 且权限 fresh check 通过后才可恢复。普通周期 run 不重复审批，但不能复用已失效 owner 决策。

文件相关审批把 `FileReference(resource_id, asset_id|NONE, node_uuid, revision)` 纳入 parameter hash。审批页默认打开该 revision；`openLatest` 是另一读取动作，不改变审批对象。revision、File Asset owner 或父 DriveSpace owner version 变化会使旧批准失效，不能把“同一 node”解释为“同一审批内容”。

Temporal Server 支持 Signal/Update/Cancel/Poll/Respond（SF-TMP-01），但应用 Workflow 必须由 Worker 执行（SF-TMP-02）。审批运行链由 DD-69 的 Application Worker 承接（`DESIGN_DEFINED`），Approval 决定经 Update 与 `Validator` 进入 history（SF-TSDK-03）；不能以 Core DB status 代替。

## 3. Agent 委托的三次检查

| 时点 | 必查 |
|---|---|
| 工具发现 | AgentPrincipal、exact AgentVersion、active projection、ChannelAgentBinding、DelegationScope、ToolBinding、Resource discover/consume |
| 发起动作/请求审批 | 上述全部 + grantor 当前可委托 permission + parameter exposure |
| 外部副作用前 | 上述全部 fresh Check + approval/expiry/max_uses + binding/capacity/quota |

`max_uses` 按唯一 operation 在首次真实 dispatch 时消费，同 operation 重试不重复消费。Agent 不继承用户所有权限，也不从频道成员关系推导业务 Resource permission。

DelegationScope 没有“字段为空即全部”的语义：既有目标固定 action+target，创建固定 action+Workspace，Tool 调用再固定 Tool Resource。Grant/Scope/Installation/AgentPrincipal 必须同 Tenant/Workspace。消费用 `(delegation_id, operation_id)` 唯一 DelegationUse 原子写入；写入失败不 dispatch（DD-49）。

SkillVersion 的依赖声明、AgentVersion 的 declared tools 与 Codex `enabled_tools` 均不是授权。三者只能收窄发现集合，真正动作仍在请求审批与外部副作用前完成上表检查。

## 4. 撤权收敛

1. Core 将 membership/Delegation/binding 标记为不可用，新 Admission 立即拒绝。
2. 写 SpiceDB relationship revoke，保留 ZedToken。
3. 关闭已知 BFF stream、Relay bridge；对已知 Codex 在途 turn 发送 `turn/interrupt`，随后以 `config/mcpServer/reload` 重建 MCP client（SF-COD-14）。
4. 隐藏 navigation/tool discovery；撤回 waiting Approval 用 `withdraw` Update，终止运行中 Workflow 用 `RequestCancelWorkflowExecution`（Workflow 在 disconnected context 上完成 native cancel 与对账后才终结），不用 Signal 取消。
5. 后续每个副作用以 `AtLeastAsFresh(revoke_zed_token)` 或 `FullyConsistent` 拒绝。
6. 已发生副作用、usage 和 audit 保留，不伪造回滚。

对跨组件能力还要执行定向收敛：

| 撤销对象 | 收敛动作 |
|---|---|
| MaterializationBinding/source export/target manage | 立即暂停对应 Temporal Schedule；运行中 Workflow 在下一副作用前拒绝，已启动 native task按真实 cancel/observe 收敛；不自动 purge target |
| `llm_route:execute` | 停 route discovery，撤 Codex/WeKnora ComponentProjection，终止已知 Codex turn/client；Gateway rate-limit/authorization 继续拒绝，已完成 log 仍结算 |
| PlatformProviderBinding/ApplicationBinding machine identity | 停新调用，撤 secret/version 与 route projection，保留 UNKNOWN native refs 进入对账 |
| Workspace membership | 关闭 stream/tool/menu，并对该 Workspace 下运行中 action 发 signal/cancel；不影响同 Tenant 其他 Workspace 的独立权限 |
| Cells FileReference 的 `read/update/export` | 停止新 ONLYOFFICE launch；按 DocumentSession revocation key 撤销 PAT；Cells WOPI Check/Get/Put fresh reject；已渲染像素不可追回，已发生的 Cells revision/usage/audit 不删除 |

已签发 ActionToken 只能通过短过期、精确 audience、PEP fresh scope/permission/delegation Check 和已知连接关闭收敛。Token 内的 allow 不能覆盖当前 deny。Codex 长存 MCP client 的 bearer 不支持即时原地轮换（GAP-AGW-01），因此撤权时先 `turn/interrupt` 再 reload/restart 旧 client；`turn/interrupt` 与 `config/mcpServer/reload` 都不能收回已经写入 rollout 或已发生的外部副作用，不能声称 token 本体已从所有载体撤销（SF-COD-14）。

## 5. 特殊生命周期

- Tenant 成员撤权/离职：Core TenantMembership 先进 `REVOKING`，撤 PlatformSession 并立即拒绝其全部 Tenant/Workspace 新动作。收敛 Workflow 再由 Tenant admin 将其所有 active Resource/Asset owner 转给另一 active HUMAN，撤 SpiceDB tenant/workspace relationships 与 Buzz relay/Channel roster，最后进入 `REVOKED`；Tenant 销毁 Workflow 按 TenantLifecycleSnapshot 处理而不转 owner。历史 AuditEvent 保留原 Principal ID（DD-45）。
- MaterializationBinding owner 离职：先暂停 Schedule并转移 binding owner；source/target Resource owner 规则分别执行，不能把 pipeline owner 转移当成端点 owner 批准。
- Workspace member revoke：Core WorkspaceMembership 先进 `REVOKING` 并立即拒绝新动作，`ComponentTaskWorkflow(kind=MEMBERSHIP_REVOCATION)` 再撤 SpiceDB relationship/Buzz roster、关闭 stream/tool/menu 并 signal/cancel 该 Workspace 中运行 action。对账后才 `REVOKED`；重新授权创建新 membership version，不复活旧投影。收敛链为 `DESIGN_DEFINED`（DD-41/69）。
- Workspace scope：先检查 Workspace `ACTIVE`；HUMAN 要求 active WorkspaceMembership，Tenant admin 只有 fresh workspace `manage` 为真时例外；AGENT 要求 active Installation/Principal、workspace `discover`、Buzz roster 与 ChannelAgentBinding。随后才检查 Resource/Asset permission。直接 owner/Resource permission 不能使已撤成员或失效 Agent 继续进入 Workspace；暂停/恢复从 Tenant scope 发起（DD-46/50）。
- Tenant suspend：`SUSPENDING` 先拒绝全部新动作/stream/trigger/Schedule 并禁止新 Resource/Asset，再撤投影/连接。`SUSPENDED` 不删 native 数据，经全量对账可进 `RESTORING→ACTIVE`。
- Tenant delete：合同使用不可变 TenantLifecycleSnapshot；Tenant admin 与 snapshot 中每个不同 Resource/Asset HUMAN owner 分别批准其受影响 ID+version digest。第一个不可逆 native delete 前可取消回 `SUSPENDED`；之后只允许恢复 Workflow 执行/对账，不声称数据可还原。任一 native ref 未 terminal 保持 `ERROR/UNKNOWN` 与 fail closed，审计、usage 和 tombstone 保留（DD-43）。当前因 GAP-LCM-01 不注册该 delete Action；此条是后续闭合源码证据时必须整体满足的设计门禁。
- 组件 disabled：Core 先把 binding 置为 `DISABLING` 并停新动作，`ComponentTaskWorkflow(kind=COMPONENT_DISABLE)` 再撤投影并对账 retained native refs。不删 Resource/Audit/Usage 事实；Workflow 对账完成前不标记 disabled 收敛完成（DD-44/69）。
- ComponentRelease revoked：Catalog Tenant 立即禁止新 Binding/upgrade；所有 pin 该 release 的业务 Binding 先 fail closed，分别按其 Tenant/Workspace 建立 `COMPONENT_DISABLE` Workflow。不得由 Catalog action 跨 Tenant 直接删除业务 Resource，也不得静默切换到另一 release。每个业务 Tenant 保留自己的 operation、owner、usage、audit 与旧 generation execution（DD-56/59）。

## 6. 跨 Tenant 导出/导入授权边界

- `share` 只在 Resource/Asset 所属 Tenant 内写 relationship；Core 在写前验证 object、subject、owner 与 Workspace 同 Tenant。目标 Principal 来自其他 Tenant 时直接拒绝，Approval 不能改写该不变式。
- `RESOURCE_EXPORT` 检查源 Resource/Asset `export`、源 owner approval、格式 adapter、Capacity/Quota 和结果暴露；结果是源 Tenant 的 ExportPackage Asset，不是跨 Tenant capability。
- `RESOURCE_IMPORT` 只在目标 Tenant session 中检查 Tenant/Workspace `create`，重算 package digest 并选择 active HUMAN owner。当 owner 不是 importer 时需其批准。源 package 内的 owner/ACL/Tenant/native ID/URL/token 全部忽略。
- 两个 Workflow 无共享 ActionToken、ExecutionContext、SpiceDB relationship 或 native ref；只用 package format/version+digest 校验字节一致性。该转移链为 `DESIGN_DEFINED`（DD-42/69）。
