# 业务能力实现的增量更新与跨服务数据获取

本文定义两件事：业务能力实现如何对自身数据负责增量、对账与就绪；一个业务能力服务需要另一服务的数据时，如何按 DD-89 经授权由接收方自行获取。平台不编排跨服务数据同步，不接管组件内部索引，不持有逐项增量状态，也不把“定时全量重建”命名为增量。本文是内置参考实现文档（README 权威规则），不给平台新增实体、权限、Workflow kind、端口或门禁；§4.3 起的产品细节只约束一期内置参考实现。

## 1. 权威与边界

| 事实 | 权威 |
|---|---|
| Resource、owner、scope、relationship 与授权动作 | Platform Core + SpiceDB |
| 能力契约、ResourceType 的 IncrementalContract | Platform Core Catalog / ComponentRelease（`07` §2.4、§8.1） |
| 业务正文、native 对象与版本、派生索引（chunk/vector/graph 等）、native task | 对应业务能力实现 |
| 接收方从来源方拉取的逐项状态、去重、删除跟踪与调度 | 接收方业务能力实现 |
| 版本发布的生命周期 | Temporal（`ComponentTaskWorkflow(kind=CAPABILITY_VERSION_PUBLISH)`） |
| entitlement、committed usage、billing | OpenMeter |
| 模型 request/token/cost observability evidence | AgentGateway request log |
| 模型 billable usage source | `PLATFORM_LLM_ROUTE`：SS-AGW-USAGE 闭合后的 durable Gateway usage；`SELF_MANAGED_MODEL`：服务经 Adapter Protocol 上报的 usage（DD-92） |
| 平台操作审计 | Platform Core AuditEvent |

平台不持有的内容固定为：

- 任何业务能力实现内部的增量状态、索引、队列或游标；
- 两个业务能力服务之间的逐项映射、去重表或同步游标；
- 任何业务能力服务的数据库凭据（DD-93）。

平台自有的持久流仍各归原权威：Buzz event 消费游标与 AgentGateway log tail 游标是已有持久流的 `IngressCheckpoint`，不属于业务能力实现。

## 2. IncrementalContract

每个 ResourceType 至少登记一份合同：

```text
NATIVE_INTERNAL / NATIVE
VERSIONED_PUBLICATION / VERSIONED_REPUBLISH
```

`NATIVE_INTERNAL` 表示新增、修改、删除与处理逻辑变更的增量、对账和就绪全部在该实现内部完成。实现必须经 Adapter Protocol 暴露：

- 跨调用稳定、同一 Resource 内唯一的 native object ref；
- 内容 revision，而非仅修改时间；
- 删除是否可观察，以及删除后的 native ref 状态；
- ready/failed/cancelled/unknown 的判定与 query/reconcile 接缝；
- 处理逻辑变更（如重新解析、重新索引）的触发方式与进度。

`VERSIONED_PUBLICATION` 表示以完整不可变版本发布替换，不对版本内部项做差异；业务能力实现的版本发布与下线由通用 `CAPABILITY_VERSION_PUBLISH` 收敛，Workflow 只依能力契约与 binding 固定的版本 Resource/Asset 工作，不含产品专属步骤（DD-90）。

只提供 mtime、只 create 无 delete/readiness、或要求平台直写组件数据库、vector store、图数据库的类型不得登记为 active。平台与其他服务禁止直写任何业务能力实现的数据库；实现内部的派生索引继续由该实现自己维护。

## 3. 一期 ResourceType 合同

平台核心：

| ResourceType | 合同 | 结论 |
|---|---|---|
| Buzz Community/Channel | `NATIVE_INTERNAL` | Relay event 是 native 权威；Core 以稳定 event ID+cursor 消费 |
| AgentGateway LLM Route | `VERSIONED_PUBLICATION` | ConfigResource version/reload 是 native 配置投影（SF-AGW-01） |
| AgentGateway request log | 观测流 checkpoint | logging database 中已成功持久化的稳定 log ID+tail cursor 供业务观测；不承担完整计费（SF-AGW-06/09） |

内置参考实现（可缺席、可替换）：

| 能力类别 / 实现 | 合同 | 结论 |
|---|---|---|
| `FILE_STORAGE` / Cells 空间 | `NATIVE_INTERNAL` | node/version/job 留在 Cells；完整目录列举与按 revision 读取经 `FILE_STORAGE` 契约供接收方自拉（SF-CEL-01/03、SS-CEL-MATERIALIZATION） |
| `KNOWLEDGE` / WeKnora KnowledgeBase | `NATIVE_INTERNAL` | parse/chunk/vector/graph 与导入状态全在 WeKnora 能力组件内（SF-WEK-03/05/07） |
| `DATA_QUERY` / Wren 语义模型 | `VERSIONED_PUBLICATION` | 完整模型版本发布为固定 Python Streamable HTTP ServeContext，不对 model 内部项做差异（SF-WRN-01） |

`DOCUMENT_EDITING` 不出现在 ResourceType 表：它作用于 `FILE_STORAGE` 的 ContentReference，不拥有增量合同、文件目录或第二内容副本。内置参考实现中，编辑保存只有在 WOPI PutFile 已写回 Cells 且 NodeVersions 确认新 head revision 后，才成为 Cells 空间的普通 revision 变化（SF-CEL-05/06/07、DD-32）。

## 4. 跨服务数据获取

### 4.1 两条路径

一个业务能力服务需要另一服务的数据时只有两条路径（DD-89）：

1. **接收方自拉。** 接收方在自己的管理面（经 Component Host 露出）配置数据源连接器，指向来源方的一个 Resource。平台以既有机制授权：一个 Governed Action 为接收方 binding 的 ServicePrincipal 写入来源 Resource 的 `reader` 关系，并投递按 `secret_schema` 声明的受限凭据 SecretRef。接收方经来源方公开的能力契约自行拉取；来源方契约端点的 PEP 对每次读取以接收方 ServicePrincipal fresh Check 来源 Resource 权限。增量、状态、去重与删除收敛全在接收方内部。
2. **人或 Agent 显式读写。** 人或 Agent 经两边各自暴露的 Tool 显式读取一侧、写入另一侧；每一步都是独立 Governed Action，各自授权、审批、计量与审计。

平台只治理授权与动作：不经手数据、不持有同步状态、不为同步建立 Schedule 或 Workflow、不在两个服务之间配置数据面直连（`07` §5.1）。

### 4.2 授权动作的治理

写入与撤销 `reader` 关系都是 Governed Action，按八项贯穿执行：

| 能力 | 规则 |
|---|---|
| Tenant | 来源 Resource、接收方 binding 与其 ServicePrincipal 必须同 Tenant；跨 Tenant 数据只走 REQ-09 两段导出/导入 |
| Workspace | 来源 Resource 按自己的 home Workspace 做 scope/permission；授权不产生隐式跨 Workspace 共享 |
| Authorization | 发起者须对来源 Resource 持有 `share`、对接收方 Resource 持有 `update`（DD-89）；来源方契约端点的 PEP 对接收方 ServicePrincipal 做 fresh `read` Check；Agent 另与 Delegation/ToolBinding 求交 |
| Approval | ApprovalPolicy 绑定来源 Resource、接收方 binding 与 parameter hash；发起者不是来源 Resource owner 时，来源 owner 必须批准；Approval 不能补 permission |
| Workflow | 授予与撤销是一次关系写入与投递，结果不明按既有 ActionExecution/UNKNOWN 规则对账；接收方的拉取运行不是平台 Workflow |
| Capacity/Quota/Billing | 来源方按其 meter 对接收方 ServicePrincipal 的读取计量；接收方按其 meter 对导入处理计量；模型 usage 按 §6 |
| Operation Audit | 记录授予/撤销的 actor、来源 Resource、接收方 binding、ServicePrincipal、SecretRef version、Approval；来源方的每次读取作为来源方 native execution evidence 归因到该 ServicePrincipal |
| Business Observability | 平台视图展示授权关系状态与双方各自暴露的 native 进度/错误；不展示逐项同步状态 |

### 4.3 撤权收敛

撤销 `reader` 关系即收回读取权：来源方 PEP 对后续读取 fresh 拒绝，受限 SecretRef 同步撤销。接收方已经导入的内容由接收方按其能力契约声明的删除语义处置；平台不代为删除接收方数据，也不宣称撤权使已导入内容消失。接收方 binding 停用时，平台撤其 ServicePrincipal 的全部 `reader` 关系与凭据；来源方 binding 停用时，接收方后续拉取失败，接收方按自身规则保留或标记失效，不得把拉取失败解释为来源内容已删除。

### 4.4 内置 `KNOWLEDGE` 实现从 `FILE_STORAGE` 自拉

本节只约束一期内置参考实现：WeKnora 能力组件内部的导入器从 `FILE_STORAGE`（内置实现为 Cells）拉取文件。导入器属于知识能力组件，运行于其自身运行体；如使用 CocoIndex，它只作为导入器内部的增量引擎，状态目录属于该组件自身存储，Core 不感知（`08` §8、DD-89/93）。

**来源身份。**

```text
item_key = ContentReference.native_object_ref（Cells node UUID）
revision = ContentReference.native_revision（Cells VersionId）+ streamed content hash
```

Node UUID 提供稳定身份；版本用于快速候选比较，受权读取流计算的内容 hash 决定正文是否改变。仅路径、文件名、大小或 mtime 不构成 revision。移动/重命名保持 item key，不重复创建正文。只有一次完整、成功的列举才允许把“上次存在、本次缺失”解释为删除；分页、授权或读取失败使本次导入失败，不提交不完整 desired set。导入器经 `FILE_STORAGE` 契约读取，不能通过 presigned URL 绕过下一次 scope/expiry 校验（SS-CEL-MATERIALIZATION）。

**写入 WeKnora 的内部规则。**

| 来源状态 | 导入器动作 |
|---|---|
| 新内容 | 上传 Knowledge，记录 native ref，观察 parse 到 ready |
| 相同 key/revision | 无正文动作；只处理允许的 metadata 差异 |
| 相同 key、新 revision | 创建新 Knowledge，等待 ready；成功后在旧 hash 无引用时删除旧 ref |
| key 从完整列举消失 | 删除本导入配置拥有且已无引用的 target ref |
| target ref 丢失或状态不一致 | 进入导入器内部 reconcile，按来源 desired state 重建或确认已删除 |
| 写/删/reparse 返回 409 且响应体顶层无 `code`（跨 KB 移动中；`ErrConflict` 的数值 code 嵌在 `error` 对象下） | 该项保留 pending 并在下次导入重试，本次导入计为失败；不得吞掉该 409 并记为已应用。使用 CocoIndex 时，sink 返回错误使引擎保留 pending 多态并以 `prev_may_be_missing` 重试（SF-CIX-03/06） |
| 创建返回 409、响应体 `code` 以 `duplicate_` 开头且 `data` 携带既有 Knowledge（`*DuplicateKnowledgeError`，SF-WEK-07） | 视为幂等成功，把 `data` 中的 Knowledge ID 绑定为该 item 的 target ref 并继续观察 parse；两类 409 只能按响应体区分 |
| 创建超时 | 先依 WeKnora dedupe/query 接缝确认 native ref；结果未知时标 `UNKNOWN`，不盲目重复副作用 |
| 新 target ready、旧 delete 失败 | 新版本可服务，旧 ref 留 pending delete；后续 reconcile 回收 |

WeKnora 创建按 `(tenant, knowledge_base, type=file, file_hash, file_type)` 去重并返回已存在 Knowledge——文件名与大小不参与；公开写入面没有 idempotency key、external-ID、按外部 ID 删除或文件替换 route（SF-WEK-07/11）。因此导入器的 desired item key 固定为去重元组中随内容变化的部分 `(file_hash, file_type)`：同 hash 的多个 node 先归并为一个 item，item 值携带引用它的全部 node UUID 集合，只有集合变空时才删除。禁止以 node UUID 作 target key 后把同一 Knowledge ID 绑给多个 item——WeKnora 按 Knowledge ID 删除且没有引用计数（SF-WEK-07/11、SF-CIX-02）。服务层 `ReplaceKnowledgeFile` 不用于被多个 node 共享的 Knowledge，replace 固定为 create-new → ready → delete-old（SS-WEK-MATERIALIZATION）。本实现不承诺跨 Cells/WeKnora 原子事务或 exactly-once。

WeKnora 的 chunk、embedding、实体/关系图谱继续由 native parse 生成。导入器只调用上传、任务观察/取消和删除 API，禁止直写 WeKnora DB、vector store 或 Neo4j。使用 CocoIndex 时另受 `08` §8 的状态目录约束：`db_path` 显式绝对路径、每个导入配置独立 LMDB environment、run 成功判据含各组件 `num_errors == 0`、清除前先跑空 desired set 再 `drop_state`（SF-CIX-04/06/07）。

## 5. ContentReference 回链与编辑保存

检索与问答结果的 citation 以 ContentReference 回链来源内容，不保存临时 URL、token 或编辑器 config。内置参考实现中，导入器在 WeKnora 上传请求的 `metadata` 写入 `source_resource_id/source_asset_id/source_native_object_ref/source_native_revision/import_config_ref`；固定源码证明 multipart route 将 JSON 解析为 `map[string]string`，创建服务持久化到内部 `Knowledge.Metadata`，且该字段与用户描述性 `CustomMetadata` 分离（SF-WEK-08）。检索引用给出 `knowledge_id`，BFF 经受 KB read guard 的知识详情接口读取 Metadata 并重建 ContentReference（SF-WEK-09）。用户打开 citation 时按 `FILE_STORAGE` 目标 Resource 当前权限重新授权；来源 binding 已停用或无权时只显示不可用状态。

编辑保存不直接触发知识实现。内置参考实现中，WOPI PutFile 成功写回 Cells 并确认新 revision 后，只成为 Cells 的普通 revision 变化；导入器下一次自拉时以既有 node UUID 和新 revision 识别差异。DocumentServer、Cells、WeKnora 各自只有一个权威职责。

## 6. 模型调用与计量关联

业务能力实现内部的模型调用按其 binding 声明的 `model_call_mode` 治理（`07` §8.3、DD-92）：

- `PLATFORM_LLM_ROUTE`：服务经配置指向 AgentGateway `llm_route`；actual token/cost 只取 SS-AGW-USAGE 闭合后的 durable Gateway usage，以稳定 request-log ID 去重生成一次 OpenMeter event。
- `SELF_MANAGED_MODEL`：服务自管模型，经 Adapter Protocol 上报 usage；平台照常执行 Quota 与审计。

逐调用关联以标准 W3C `traceparent` 与 operation 头为可选增强：存在时把模型 usage 归因到平台 operation；缺失只降低成本归因精度，durable usage 仍按 gateway identity 归属到 Tenant/Workspace binding，不按时间窗口猜 operation，也不接收组件自报 token 替代。

内置参考实现 WeKnora 采用 `PLATFORM_LLM_ROUTE`。其精确归因链为：

```text
知识导入或检索 operation
→ WeKnora upload/query request
→ DocumentProcessPayload trace carrier
→ Asynq worker context
→ Chat/Embedding/Rerank HTTP traceparent
→ AgentGateway StoredRequestLog.trace_id（业务观测）
→ durable Gateway usage（计费；仅 SS-AGW-USAGE 闭合后）
→ Platform operation / OpenMeter UsageEvent
```

WeKnora 已有 Asynq `TracingContext` 注入/恢复接缝，但当前受 Langfuse enabled 门控（SS-WEK-ASYNC-TRACE）；出站模型请求已携带 context，但当前只应用静态 ModelParameters headers（SS-WEK-LLM-CTX）。本实现的二开固定为：trace carrier 不依赖可选观测产品开关，并由模型 HTTP transport 从当前 context 注入 W3C `traceparent`。该二开不改变 WeKnora 业务 task、模型接口或 provider 协议；未闭合时本实现 binding 仍可 `ACTIVE`，模型 usage 只归属到 binding 而不归属到单次 operation。

Gateway identity 的 user/group 来自 apiKey/JWT 认证属性（SF-AGW-08），用于验证 Tenant/Workspace binding。Core 以 `IngressCheckpoint` 读取 durable usage tail，以稳定 request-log ID 去重；原始 log tail 只供业务观测，其 writer 丢批次边界由 SF-AGW-09 证明。缺 tenant/workspace identity 或 token/cost 不完整的 durable usage 进入 reconcile。

## 7. 停用、撤权、删除与恢复

| 命令/故障 | 确定语义 |
|---|---|
| 撤销接收方 `reader` 关系 | 来源方 PEP 对后续读取 fresh 拒绝，受限 SecretRef 撤销；接收方已导入内容按其删除语义处置，平台不代删 |
| 停用接收方 binding | `COMPONENT_DISABLE` 撤其 ServicePrincipal 的 `reader` 关系、凭据、route 与 Tool；不删除来源数据 |
| 停用来源方 binding | 接收方后续拉取失败；拉取失败不得解释为来源内容删除 |
| 来源不可用或列举不完整 | 接收方本次导入失败；不提交删除 desired state |
| 业务能力实现内部 reindex/reparse | 该实现内部的处理逻辑变更，经 Adapter Protocol 暴露进度与终态；平台不重建 |
| 删除来源条目 | 仅在接收方完整列举中缺失才删除接收方自己拥有的派生内容 |
| Tenant 删除 | 每个 ApplicationBinding 的 native 删除是独立子流程；声明 `retain_on_tenant_delete` 的实现撤 binding、撤凭据、保留审计并登记待人工处置，不阻断平台 Tenant 状态机（DD-91） |
| Durable usage cursor 重放 | 稳定 log ID/CloudEvent key 去重；cursor 只优化恢复，不提供 exactly-once；原始 log writer 未闭合时不产生计费事件 |

暂停导入、撤销读取授权、停用 binding 与删除派生内容是四个不同动作，UI 与 Agent tool 不得合并按钮或复用 action key。暂停导入属于接收方管理面上的本组件动作，不是平台 Workflow 状态。

## 8. 上游升级闭环

`.references/UPDATE_TASKS.json` 只告知 source/manual 差异，只作用于内置参考实现与平台核心。涉及 Cells node/version/data/WOPI API、DocumentServer WOPI client、WeKnora upload/metadata/delete/task/model transport、CocoIndex update/target state、AgentGateway log schema 的差异，必须先重验本文引用的 SF/SS，再更新对应 IncrementalContract 与该参考实现的 release。

新上游能力不会自动扩大来源读取范围、导入动作、文件类型、图谱链或 meter。只有能力契约、owner/permission、Workflow、quota 和审计验证全部闭合的新 ComponentRelease 才能获批；旧 binding 继续固定旧 release/generation，直到受治理升级完成。外部实现的演进按 `07` §2.5 与 §10 重跑一致性测试套件。
