# 资源增量更新与物化

本文定义跨 Resource 派生副本的唯一设计。它不接管组件内部索引，也不把“定时全量重建”命名为增量。

## 1. 权威与边界

| 事实 | 权威 |
|---|---|
| Resource、owner、scope、MaterializationBinding | Platform Core |
| source/target endpoint contract | ComponentRelease / ResourceTypeDefinition |
| Workflow、Schedule、run lifecycle | Temporal |
| 逐项 previous/desired/pending、target owner/generation | CocoIndex state store |
| 文件正文、KB 文档、chunk/vector/graph | Cells / WeKnora |
| relationship allow/deny | SpiceDB |
| entitlement、committed usage、billing | OpenMeter |
| 模型 request/token/cost observability evidence | AgentGateway request log |
| 模型 billable usage source | SS-AGW-USAGE 闭合后的 durable Gateway usage |
| 平台操作审计 | Platform Core AuditEvent |

CocoIndex 是 Rust SDK，不是独立 API server 或 scheduler。源码提供 LMDB `db_path`、App namespace、`App::update_with_options`、keyed `mount_each` 与 target reconcile（SF-CIX-01/02/03/04）；`db_path` 是可选参数，未设置时 SDK 静默回落到按进程工作目录解析的相对路径 `./coco_state`，因此“状态目录固定”不是上游保证，而是 Core runner 必须始终显式传入绝对路径并在 run 前校验的平台义务。周期触发由 Temporal Schedule 承接（`ScheduleClient`，SF-TSDK-07）；Worker→Rust runner 的执行绑定为 `DESIGN_DEFINED`——Application Worker 的 Activity 调用 Rust runner（SF-TSDK-04、DD-69），实现前不声明已嵌入 Worker。

以下内容明确不属于 CocoIndex：

- Cells 自身 node version/job；
- WeKnora 自身 parse、chunk、embedding、Neo4j entity/relation；
- Wren 已发布 SemanticModel 的 runtime；
- Buzz event 消费游标；
- AgentGateway log tail 游标。

前三类由 native/versioned contract 维护；后两类是已有持久流的 `IngressCheckpoint`。这避免建立第二份内部索引或消息队列权威（DD-19/22）。

## 2. IncrementalContract

ResourceType 可同时登记多份合同：

```text
NATIVE_INTERNAL / NATIVE
MATERIALIZATION_SOURCE / COCOINDEX
MATERIALIZATION_TARGET / COCOINDEX
VERSIONED_PUBLICATION / VERSIONED_REPUBLISH
```

MaterializationBinding 是 `type_key=materialization_binding` 的 Resource 扩展。Resource 固定 Tenant、home Workspace、HUMAN owner 与权限关系；扩展固定 active source/target contract、两端 Resource、pipeline key/version 以及 `coco_environment_ref/coco_app_name`。后两者把每次 run 固定回同一 LMDB db_path/App namespace；Core 在每次 run 前显式传入 `coco_environment_ref` 解析出的绝对路径并校验该目录已存在且已初始化，不可达时失败，禁止换空 state 后继续——SDK 自身在 `db_path` 缺省时会静默新建 `./coco_state`，该失败语义只能由 Core 强制。合同不可在 active binding 内原地换 key/revision/delete/readiness 语义；变更产生新的 binding version和新 App namespace（SF-CIX-04）。每个 binding 使用独立的 LMDB environment（独立绝对 db_path），因为 `drop_state` 不释放 named-DB 目录项，App 名随 pipeline version 增长会耗尽同一 environment 的 max_dbs（SF-CIX-07）。

### Source contract

必须定义：

- 受权 snapshot 边界；
- 跨 run 稳定且同一 source Resource 内唯一的 item key；
- 内容 revision，而非仅修改时间；
- snapshot 缺失是否代表删除；
- 正文读取方式和最大受理边界；
- snapshot/revision 失败时整次 run 的处理。

### Target contract

必须定义：

- create、replace、delete 的公开 API；
- source key/revision 与 native target ref 的映射；
- ready/failed/cancelled/unknown 判定；
- retry/query 接缝与幂等约束；
- 哪些 target 只允许由本 binding 删除；
- purge 后保留哪些审计/计量 refs。

缺 source revision、target delete/readiness 或必须直写组件数据库的 endpoint 不得注册。CocoIndex 的 target owner/generation 只允许回收本 pipeline 创建的 target，不扫描或删除用户在目标 Resource 中原生创建的内容（SF-CIX-03）。

## 3. 一期 ResourceType 合同

| ResourceType | 合同 | 结论 |
|---|---|---|
| Buzz Community/Channel | `NATIVE_INTERNAL` | Relay event 是 native 权威；Core 以稳定 event ID+cursor 消费，不进入 CocoIndex |
| Cells DriveSpace | `NATIVE_INTERNAL` + `MATERIALIZATION_SOURCE` | node/job 留在 Cells；受控 snapshot 可作为跨资源 source（SF-CEL-01/03） |
| WeKnora KnowledgeBase | `NATIVE_INTERNAL` + `MATERIALIZATION_TARGET` | parse/chunk/vector/graph 留在 WeKnora；上传/删除/reparse 作为 target API（SF-WEK-03/05/07） |
| Wren SemanticModel | `VERSIONED_PUBLICATION` | 完整模型 version 发布为固定 Python Streamable HTTP ServeContext，不对 model 内部项做 CocoIndex 差异（SF-WRN-01） |
| AgentGateway LLM Route | `VERSIONED_PUBLICATION` | ConfigResource version/reload 是 native 配置投影（SF-AGW-01） |
| AgentGateway request log | 观测流 checkpoint | logging database 中已成功持久化的稳定 log ID+tail cursor 供业务观测，不进入 CocoIndex；不承担完整计费（SF-AGW-06/09） |

一期只激活 `Cells DriveSpace → WeKnora KnowledgeBase` 跨 Resource pipeline。WeKnora 已提供实体/关系图谱并在同一 parse/retrieval 链维护（SF-WEK-05），因此不再向 EdgeQuake 物化第二套 GraphRAG（DD-18）。

ONLYOFFICE 不出现在 ResourceType 表：它是以 `cells_drive_space` 为目标、再由 FileReference 定位 native child/可选 File Asset 的 Capability Component，不拥有增量合同、文件目录或第二内容副本。编辑保存只有在 WOPI PutFile 已写回 Cells 且 NodeVersions 确认新 head revision 后，才成为 Cells source 的普通 revision 变化（SF-CEL-05/06/07、DD-32）。

## 4. Cells → WeKnora pipeline

### 4.1 Source identity

```text
item_key = Cells node UUID
revision = Cells node version + streamed content hash
```

Node UUID 提供稳定身份；版本用于快速候选比较，受权下载流计算的内容 hash 决定正文是否改变。仅路径、文件名、大小或 mtime 不构成 revision。移动/重命名保持 item key，不重复创建正文；路径/名称作为 metadata 变化进入同 item 的 target action。

Snapshot 固定 DriveSpace Resource 与已登记 root。Driver 用同一 ExecutionContext 查询 node/version 并读取文件流（SF-CEL-01/03）；不能通过 presigned URL 绕过下一次 scope/expiry 校验。只有一次完整、成功的 snapshot 才允许把“上次存在、本次缺失”解释为删除；分页、授权或读取失败使 run 失败，不提交不完整 desired set。

### 4.2 Target mapping

每个 item 的 CocoIndex target state 保存当前 WeKnora knowledge native ref 与 source revision。平台不把该逐项映射复制到 Core。

| source 状态 | target action |
|---|---|
| 新 key | 上传 Knowledge，记录 native ref，观察 parse 到 ready |
| 相同 key/revision | 无正文动作；只处理合同允许的 metadata 差异 |
| 相同 key、新 revision | 创建新 Knowledge，等待 ready；成功后删除旧 ref |
| key 从完整 snapshot 消失 | 删除该 binding 拥有的当前 target ref |
| target ref 丢失或状态不一致 | 进入 reconcile，按 source desired state 重建或确认已删除 |
| target Knowledge 处于跨 KB 移动状态（写/删/reparse 返回 409 且响应体顶层无 `code`——`ErrConflict` 的数值 code 嵌在 `error` 对象下） | target sink 对该项返回错误，使引擎保留该项的 pending 多态、下次 run 以 `prev_may_be_missing` 重试且不重复创建；本次 run 因此计为失败（`num_errors > 0`，`update` 返回 Err）。不允许 sink 吞掉该 409 返回成功——那样 tracking 会被写成已应用，该项再不会被重试（SF-CIX-03/06） |
| 合并 sink batch 中一个 component 失败 | CocoIndex 先整批 apply，再只沿 component 边界二分隔离；不拆单个 component action。成功 sibling 按已提交处理，失败 component 保留错误；取消与 deadline 不二分并作用于失败 sub-batch 全部 component（SF-CIX-08） |

WeKnora 创建按 `(tenant, knowledge_base, type=file, file_hash, file_type)` 去重并返回已存在 Knowledge——文件名与大小不参与，hash 分支命中与未命中都直接返回；公开写入面没有 idempotency key、external-ID、按外部 ID 删除或文件替换 route（SF-WEK-07/11）。服务层虽已有 `ReplaceKnowledgeFile`，一期不把它暴露给 target adapter：本 pipeline 以 hash 元组归并多个同内容 Cells node，一个 Knowledge ID 会被整个引用集合共享，单 node 正文变化不能原位改写该共享对象（SS-WEK-MATERIALIZATION）。因此 replace 仍固定为 create-new → ready → delete-old：创建/parse 失败时旧版本继续服务，不先删旧内容；delete 失败保留 pending state 与 native ref。CocoIndex 不承诺外部系统原子事务，Platform 也不宣称跨 Cells/WeKnora exactly-once（SF-CIX-03）。

WeKnora 的 chunk、embedding、实体/关系图谱继续由 native parse 生成。Materialization target 只调用上传、任务观察/取消和删除 API，禁止直写 WeKnora DB、vector store 或 Neo4j。

### 4.3 来源引用与 ONLYOFFICE 保存

WeKnora 上传请求的 `metadata` 可携带 `source_resource_id/source_asset_id/source_node_uuid/source_revision/materialization_binding_id`；固定源码证明 multipart route 将 JSON 解析为 `map[string]string`，创建服务持久化到内部 `Knowledge.Metadata`，且该字段与用户描述性 `CustomMetadata` 分离（SF-WEK-08）。检索引用给出 `knowledge_id`，BFF 再走受 KB read guard 的知识详情接口读取 Metadata 并重建 FileReference（SF-WEK-09）；citation 本身不保存 Cells presigned URL 或 DocumentServer config。

ONLYOFFICE 保存链不直接触发 WeKnora API，也不写 CocoIndex state。WOPI PutFile 成功写回 Cells 并确认新 revision 后；下一次同 binding 的 snapshot/update 以既有 node UUID 和新 revision 识别差异，再按新的 hash 归并结果执行 create-new → ready → delete-old。这样 DocumentServer、Cells、CocoIndex、WeKnora 各自只有一个权威职责。

## 5. Temporal 生命周期

一个 active binding 对应一个 Temporal Schedule，overlap policy 固定 `SKIP`；每次 scheduled、manual catch-up 或 reconcile 都创建新的 `ComponentTaskWorkflow(kind=MATERIALIZATION)`。

```text
resolve binding/version
→ fresh eight-dimension admission
→ resolve stable coco_environment_ref/coco_app_name
→ acquire CocoIndex runner CapacityLease
→ complete source snapshot
→ App::update_with_options(UpdateOptions{full_reprocess:false, live:false,...})
→ observe required WeKnora ExternalExecution
→ reconcile target state
→ settle actual usage + append audit
→ terminal
```

Schedule 只是触发权威，不携带长期授权。每次 run 和每个尚未发生的副作用前重新检查 binding、source/target permission、Delegation、component health、capacity 与 quota。审批绑定的是创建/变更该长期 binding 的意图；普通周期 run 不重复向 owner 弹审批，但 fresh check 失败会停止副作用。

`full_reprocess=true` 只属于单独 Governed Action：用于 pipeline version 迁移或经 owner 批准的重建，不能由普通 retry 自动升级。`live=true` 不在一期使用，因为一期 source 是周期 snapshot，CocoIndex 又没有独立外部事件 service（SF-CIX-01、DD-22）。

## 6. 八项贯穿治理

| 能力 | 物化规则 |
|---|---|
| Tenant | MaterializationBinding、source/target Resource、owners 与两端 ApplicationBinding 必须同 Tenant；runner 不接收调用方自报 Tenant |
| Workspace | binding 固定 home Workspace；两端 Resource 各按自己的 home Workspace 做 scope/permission，跨 Workspace 不产生隐式共享 |
| Authorization | create/run 前检查 source `read/export`、target `create/manage`、Binding Resource `execute`；pause/change/purge 检查 Binding Resource `manage`；Agent 叠加 Delegation/ToolBinding。WeKnora 侧另以目标 ApplicationBinding 的 API key 出示 `ingest` capability 与 Editor grant，切换执行 tenant 不授予权限（SF-WEK-10） |
| Approval | 创建、改 source/target/pipeline、full reprocess、purge 绑定 parameter hash；initiator 不是某端 owner 时该端 owner 必须批准；Approval 不能补 permission |
| Workflow | Schedule、每次 run、ExternalExecution、cancel、UNKNOWN/reconcile 全由 Temporal；CocoIndex/WeKnora native state 不被改写成另一套 Workflow |
| Capacity/Quota/Billing | CocoIndex runner=`PLATFORM_SLOT`，WeKnora parse=`NATIVE`；run 前 entitlement/credit `CHECK`，无可证明上界不做 strict reservation；文件写入量从 native evidence 入账，模型 token/page/cost 只从 SS-AGW-USAGE 闭合后的 durable usage 写 OpenMeter |
| Operation Audit | 记录 binding/pipeline version、snapshot revision、run、create/delete/reconcile counts、Cells/WeKnora refs、Approval/ZedToken/lease/quota/Gateway/OpenMeter evidence；不记录正文/chunk/vector/graph/prompt |
| Business Observability | 以 operation/binding/run/native refs 展示 Schedule/run state、snapshot completeness、diff/create/delete/reconcile counts、WeKnora task progress/error、Gateway token/cost 与 OpenMeter settlement；按 binding/source/target `read/audit` 和 exposure 过滤 |

owner 关系有三层且不互相覆盖：source Resource owner 决定持续 export，target Resource owner 决定持续 managed write/purge，MaterializationBinding owner 对 pipeline 配置、失败处理和暂停负责。三者都必须是 active HUMAN；Agent/service 只能作为 producer/actor。

## 7. 模型网关与计量关联

WeKnora parse 内的 Chat/Embedding/Rerank 统一指向 AgentGateway（SF-WEK-06、SF-AGW-05）。平台 trace 按以下链闭合：

```text
Materialization Workflow trace
→ WeKnora upload request
→ DocumentProcessPayload trace carrier
→ Asynq worker context
→ Chat/Embedding/Rerank HTTP traceparent
→ AgentGateway StoredRequestLog.trace_id（业务观测）
→ durable Gateway usage（计费；仅 SS-AGW-USAGE 闭合后）
→ Platform operation / OpenMeter UsageEvent
```

WeKnora 已有 Asynq `TracingContext` 注入/恢复接缝，但当前受 Langfuse enabled 门控（SS-WEK-ASYNC-TRACE）；出站模型请求已携带 context，但当前只应用静态 ModelParameters headers（SS-WEK-LLM-CTX）。平台二开固定为：trace carrier 不依赖可选观测产品开关，并由模型 HTTP transport 从当前 context 注入 W3C `traceparent`。该二开不改变 WeKnora 业务 task、模型接口或 provider 协议。

Gateway identity 的 user/group 来自 apiKey/JWT 认证属性（SF-AGW-08），用于验证 Tenant/Workspace binding；trace ID 用于关联单次 operation。Core 以 `IngressCheckpoint` 读取 durable usage tail，以稳定 request-log ID 去重并生成一次 OpenMeter event。原始 log tail 只供业务观测；其 writer 丢批次边界由 SF-AGW-09 证明。缺 tenant/workspace identity、trace 无法映射 operation 或 token/cost 不完整的 durable usage 进入 reconcile，不按时间窗口猜归属，也不接收组件自报 token 替代。

## 8. 暂停、取消、删除与恢复

| 命令/故障 | 确定语义 |
|---|---|
| Pause binding | 暂停 Temporal Schedule；当前已开始的副作用按 Workflow cancel policy 收敛；保留 target 内容 |
| Cancel run | 停止新 CocoIndex action；对已创建 WeKnora task发 best-effort cancel并继续观察，不等于 purge |
| Delete source item | 仅在完整 snapshot 中缺失才删除本 binding 拥有的 target |
| Purge binding targets | 独立 owner-approved Governed Action，状态 `DELETING`；逐项 reconcile 后 `DELETED` |
| Source unavailable/partial snapshot | run 失败；不提交 deletion desired state |
| Create timeout | 先依 WeKnora dedupe/query 接缝确认 native ref；结果未知时标 `UNKNOWN`，不盲目重复副作用 |
| Create 返回 409、响应体 `code` 以 `duplicate_` 开头且 `data` 携带既有 Knowledge（`*DuplicateKnowledgeError`，SF-WEK-07） | 视为幂等成功，把 `data` 中的 Knowledge ID 绑定为**该 item**（key 为去重元组，见下条）的 target ref 并继续观察其 parse 状态；不报错、不再次上传。其余 409 按上文跨 KB 移动行处理，两者只能按响应体区分 |
| 两个 Cells 节点正文字节相同 | pipeline 的 desired item key 固定为 WeKnora 去重元组中随内容变化的部分 `(file_hash, file_type)`，不是节点 UUID；同 hash 的多个节点在进入 `mount_each` 前先按该 key 归并为一个 item，item 值携带引用它的全部节点 UUID 集合。只有该集合变空时 reconcile 才发出 Delete。禁止用节点 UUID 作 target key 后把同一 Knowledge ID 绑给多个 item——那样任一节点消失都会删掉仍被其他节点引用的 Knowledge，且 WeKnora 的删除是按 Knowledge ID、没有引用计数（SF-WEK-07/11、SF-CIX-02） |
| New target ready、old delete failed | 新版本可服务，旧 ref 留 pending delete；后续 reconcile 回收 |
| Durable usage cursor 重放 | 稳定 log ID/CloudEvent key 去重；cursor 只优化恢复，不提供 exactly-once；原始 log writer 未闭合时不产生计费事件 |

MaterializationBinding 删除后仍保留最小 tombstone、pipeline version、target evidence、usage 和 audit refs；正文及逐项运行缓存按各权威的保留策略清除。暂停、Workflow cancel、Resource revoke 与 purge 是四个不同动作，UI 与 Agent tool 不得合并按钮或复用 action key。

## 9. 上游升级闭环

`.references/UPDATE_TASKS.json` 只告知 source/manual 差异。涉及 Cells node/version/data/WOPI API、DocumentServer WOPI client、WeKnora upload/metadata/delete/task/model transport、CocoIndex update/target state、Temporal Schedule、AgentGateway log schema 的差异，必须先重验本文引用的 SF/SS，再更新对应 IncrementalContract 与 pipeline version。

新上游能力不会自动扩大 source root、target action、文件类型、图谱链或 meter。只有合同、owner/permission、Workflow、quota 和审计验证全部闭合的新 ComponentRelease 才能获批；旧 binding 继续固定旧 release/generation，直到受治理升级完成。
