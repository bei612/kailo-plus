## 3. Web 与 Buzz 协议链

Buzz Relay 不认 OIDC，且 ingest 要求 event signer 与 NIP-42 认证 pubkey 一致（SF-BUZ-02/03）。因此一期 Web 链固定为：

```text
AgentGateway OIDC authorization-code+PKCE→加密 HttpOnly cookie→validated jwt.sub
→ route transformation 移除外来身份 header并写入已验证 subject
→ BFF 以 issuer+subject 解析 HumanIdentity、TenantMembership 与 PlatformSession
→ Browser 只通过 BFF transport 发类型化 query/stream/semantic command/media request
→ BFF 完成 Action Admission
→ 读取该 Principal 的 BuzzIdentityBinding secret
→ 以同一 pubkey 完成 NIP-42 并签名正常 Nostr event
→ Relay 执行成员/per-kind 校验、持久化与 fan-out
```

- AgentGateway 的 OIDC 登录、cookie session 与本地 cookie logout route 是 `UPSTREAM_SUPPORTED`；claims→BFF header、logout 后同步撤销 Core PlatformSession 与关闭 BFF stream 是 `ADAPTER_REQUIRED`，精确接缝为 SS-AGW-OIDC。BFF 只允许从 Gateway 内网路径到达，不接受 Browser 自报身份 header（SF-AGW-10）。
- buzz-web 现有的 concrete `BuzzRelayClient`、query/subscribe/publish、NIP-42/NIP-98、media 和 NIP-44 user-state 是一个完整 `ADAPTER_REQUIRED` 替换面（SF-WEB-01/04/05、SS-WEB-RELAY）。仅替换 signer 仍会留下浏览器直连，不符合一期边界。
- BFF transport 不接受 raw signed event 或任意 Relay filter。它按当前 PlatformSession 构造 scope，把查询/订阅结果以现有 `NostrEvent` 读模型传给 UI，把写入意图映射成固定 event kind/tags 后再代签（DD-39）。
- Relay inline media 的 upload/get 亦经 BFF 以 acting Principal 的 Buzz identity 执行 NIP-98 签名；Browser 只传文件字节/返回的 descriptor。企业文件、Office 文档、审批附件和任务产物仍使用 Cells FileReference，不将 Relay media URL 冒充文件权威。
- 收藏、静音和已读位置不再走 kind:30078/NIP-44；BFF 读写 Core CollaborationUserState，Browser localStorage 不是跨端权威（SF-WEB-05、DD-40）。
- Human 和 Agent 各有独立 Nostr key；服务端不用共享 Relay key 伪装业务 actor（DD-02）。
- CONTROL SERVICE identity 只执行 Community/roster 协议投影与 Tenant NIP-AE Memory Counterparty/受权解密，不作业务 actor 或 Resource/Asset owner（SF-BUZ-04/06/16/19，DD-03/66）。
- `RelayActionSink` 只保留为 Buzz 自身 `buzz:workflow=true` 的 Relay 工作流回复能力；不用于人类消息、Agent 身份回复或通用 Core command（SF-BUZ-09）。
- Buzz SDK `/v1/action` 只有客户端合同，Relay 没有 host route，因此不进入拓扑（SF-BUZ-10）。

OIDC client/cookie secret 与服务端 Nostr 私钥托管于 OpenBao（DD-70/72）；claims→BFF 投影（SS-AGW-OIDC）闭合前整条链为 `ADAPTER_REQUIRED`。

## 4. 成员与 scope 投影

```text
Platform Tenant membership active
→ SpiceDB tenant/workspace relationships written
→ CONTROL identity 发布 Buzz relay-admin/channel-admin event
→ Relay 查询证明投影成功
→ 开放该 scope 的 Buzz stream/navigation
```

建立与撤权都是持久多投影事务：Tenant/Workspace 建立分别使用 `ComponentTaskWorkflow(kind=TENANT_LIFECYCLE|WORKSPACE_LIFECYCLE)`；TenantMembership/WorkspaceMembership 建立与撤权共用 `ComponentTaskWorkflow(kind=MEMBERSHIP_PROJECTION|MEMBERSHIP_REVOCATION)`，input 以 `TENANT|WORKSPACE` target type 区分 relay roster 与 Channel roster。Core 先持久相应实体 version、ActionExecution 与 fail-closed 状态，再以稳定 Temporal workflow ID 启动对应 kind。撤权在 Core `REVOKING` 时已拒绝新动作并关闭 BFF session/stream，Workflow 再撤 SpiceDB relationship、用 CONTROL identity 移除 Relay/Channel 成员并查证。Buzz 投影失败不恢复平台权限。这些运行链由 DD-69 的 Application Worker 承接，为 `DESIGN_DEFINED`。Community 创建通过 RelayOperatorIdentity 与 SS-BUZ-OPERATOR 调用源码已有的 NIP-98 operator 入口，为 `ADAPTER_REQUIRED`；不绕过 Relay DB（SF-BUZ-06）。

## 5. 动作路径

### 同步动作

```text
session → TenantMembership active
→ Tenant scope，或 Workspace ACTIVE + active WorkspaceMembership/workspace manage
→ ActionDefinition → Resource/Asset SpiceDB Check + Delegation
→ Approval=not-required → Capacity/Quota → durable audit intent
→ in-process Driver(ExecutionContext) → native result
→ exposure → usage/audit result
```

同请求完成且无等待/恢复需求的读写不创建 Workflow。

### 持久动作

```text
admission → ApprovalWorkflow when required → fresh recheck
→ Start Workflow → Worker schedules Activity
→ Driver/native operation → ExternalExecution observe/signal
→ exposure/usage/audit → Temporal terminal state
```

Temporal Server 不执行应用 Workflow；Application Worker 是必需角色（SF-TMP-02）。Worker 按 DD-69 以 `temporal-sdk-go` 自建，链路为 `DESIGN_DEFINED`；实现并通过重放回归前不是可运行能力。

## 6. Agent 与工具链

```text
Relay persisted event + Core checkpoint
→ resolve active AgentInstallation + exact AgentVersion/projection generation
→ idempotent AgentInvocation/AgentTaskWorkflow
→ isolated Codex app-server turn
→ optional Temporal Approval
→ fresh admission + short ActionToken
→ AgentGateway Streamable HTTP MCP + ExtMcp PEP
→ backend/result exposure/usage/audit
→ Agent identity 签名 Buzz reply
```

- ACP EventQueue 只是内存结构；触发恢复依据 Relay 持久 event 与 Core checkpoint（SF-BUZ-07/08，DD-04）。
- Definition 在 Tenant，Installation 在 Workspace，ChannelAgentBinding 只控制触发；每个 Invocation 固定不可变 AgentVersion 与 active projection generation（DD-25/27）。
- 每个 Installation 的 CODEX_HOME 根本不配置 local environment，这是跨 `thread/resume` 的承重封堵。`thread/start.environments=[]`、Core 从不发 `turn/start.environments`、`shell_tool=false` 与 `shell_type=disabled` 都是纵深防御；turn override 可影响当前及后续 turn，不能作为权威封堵。Core 不调用 `command/exec`、`process/spawn`、`thread/shellCommand`（SF-COD-03/04/11/12，DD-15）。
- Codex 自定义 Responses provider 的 `base_url` 指向 AgentGateway，使模型路由与 usage observation 也经 Gateway（SF-COD-05、SF-AGW-04，DD-17）。
- WeKnora 远程 Chat、Embedding 与通用 Rerank 的 `base_url` 同样指向 AgentGateway；AgentGateway ConfigResource 是 provider/model/认证路由权威，WeKnora model row 只是 ComponentProjection（SF-AGW-01/05、SF-WEK-06，DD-20）。
- 配置 logging database 后，AgentGateway request log 可记录模型、token 与 cost并供业务观测；原始 writer 在数据库失败时丢批次，不能作计费完整性来源（SF-AGW-06/09）。只有 SS-AGW-USAGE 闭合为持久确认的 usage outbox 后，Core 才能以 IngressCheckpoint/稳定 log ID 生成 OpenMeter UsageEvent（DD-21）。
- ActionToken 只跨进程/网络边界使用：Core→AgentGateway 或 Core→独立 runtime。Core 内 Driver 直接接受不可伪造的 ExecutionContext。
- AgentGateway 通过 ConfigResource store/API 接收 Catalog 投影；xDS 不用于该路径（SF-AGW-01/03，DD-13）。ConfigResource API、整份配置文件读写 `GET|POST /api/config`（POST 直接覆写网关配置文件）、`llm.settings`/`mcp.settings` 监听端口与 TLS、日志/成本/预算查询、debug 与 `quitquitquit` shutdown route 位于同一个无认证 admin router；必须在 SS-AGW-ADMIN 加入 Core-only service authentication，内网地址和 CORS 都不构成认证（SF-AGW-02、SS-AGW-ADMIN）。

SpiceDB、Temporal、OpenMeter 与 AgentGateway admin 都不接受 Browser/Agent 直连。Core/Worker 分别使用源码证明的 bearer PSK、显式启用 default mapper/authorizer 的 Temporal JWT role，以及 SS-OMT-AUTH/SS-AGW-ADMIN 的 service authentication；Temporal 空 auth 配置的 no-op 路径禁止进入 active binding。所有最终用户/Agent 业务 permission 仍在 Core 以 SpiceDB Check 判定（SF-SPZ-03、SF-TMP-06、DD-37）。OpenMeter 固定单一 default namespace，并以 Tenant→Customer、子 scope→subject 映射隔离计量归属（SF-OMT-05/06、DD-38）。

## 7. 客户端产品面

Buzz Client Surface 是仅有的壳，由 Buzz Web、Buzz Desktop、Buzz Mobile 三端构成（REQ-01、DD-74）。下列导航在 Web 与 Desktop 上完整可达；Buzz Mobile 按 REQ-21 对「业务」「AI」「治理」三组提供受权只读视图与可降级入口，不承载 Component Host 与 editor surface：

```text
协作：Channels / My Tasks / Approvals
业务：Drive / Knowledge / Data & Models / Assets
AI：Agents / Skills / Tools
治理：Members & Roles / Usage & Billing / Business Operations / Audit / Components
```

Buzz Web 与 Buzz Desktop 共用同一 TypeScript 主体，仍以静态 routeTree 构建；一次性 Component Host 增加固定 `/apps/$componentKey/$` catch-all route，不在运行时修改 TanStack routeTree。当前 `BuzzWebApp.Workspace`、`WorkspaceTool` union 与内容条件链是封闭壳；Component Host 固定一个由 index/chat 与 app route 共用的 WorkspaceShell，Host 根据 BFF 返回的 scope-authorized `ComponentRuntimeProjectionSnapshot` 生成导航和 surface mount。Session stream 只通知 monotonic generation 变化，Browser 重取完整快照并 reconcile；加载时由 Host 内部 pending load 绑定 type/release/generation/digest/注入元素，module 的同步 register 先暂存描述符，只有 script load 后全字段与 API 匹配才提交。Mattermost 证明 active manifest→script registration→scoped registry→版本 reconcile/unload 的运行模式，Buzz 当前没有该能力，因此完整边界是 `ADAPTER_REQUIRED: SS-WEB-COMPONENT-HOST`（SF-MAT-03/04、SF-WEB-02、DD-61）。Mattermost 的事件路径把 WebSocket payload 当作完整状态直接 load/remove，全量 reconcile 只在重连时发生（SF-MAT-06）——这正是 Kailo 拒绝的模式，DD-61 以“事件只通知 generation、Browser 重取完整快照”与之相反。

同窗口 remote module 是宿主信任代码，不是安全沙箱。平台管理员批准的 release 固定 source baseline、source entry URL、digest 和 Host API range；Catalog 只把验证后的 bytes 暴露为同源内容寻址路径，Browser 不加载外域 script，保留 buzz-web 的 `script-src 'self'`（SF-WEB-06、DD-60）。Tenant 管理员只能启用。模块只获得 Component Host API 与 mount root，不获得 Redux/store、Relay signer、组件管理 credential 或平台权威服务 credential。即使模块自行发起同源 BFF 请求，BFF 仍只接受语义 API并重做 session、scope、SpiceDB、Approval、Quota 与 Audit；前端代码从不成为授权边界（DD-55/56）。

宿主扩展槽一期固定为管理导航页、Resource view 和聊天附件 action；新的槽位意味着宿主 API 变化并需要两个承载端（Buzz Web 与 Buzz Desktop）各自发布。`HOST_NATIVE` 组件无需 remote module，复用同一通用管理页面；`SOURCE_BOUND_PROTOCOL` 仅由固定 descriptor 打开协议 surface。ONLYOFFICE 是固定 source commit/origin/WOPI descriptor 的协议 surface，官方 WOPI page 在受限 iframe 内创建 editor，不开放为通用 iframe 插件（SF-OFF-03，DD-30/58）。

所有 Host-native 与 remote module 都只消费 Buzz `FrontendPresentationContext`：主题沿用 ThemeProvider/CSS variables，平台文案沿用 `AppLocale + MessageKey/t`，release 同时登记 namespaced `en/zh-CN` catalog。Cells、WeKnora、Wren、Temporal 等上游原生 UI 不嵌入；非分离 monolith 保留在后端，由 adapter 与 Host-native 页面接入。ONLYOFFICE 是 source-bound surface，launch 时把 Buzz resolved theme/locale 映射为 WOPI `thm/ui/lang`（SF-WEB-03、SF-OFF-07、DD-36/58）。

BFF 对 Web 只暴露 context/navigation、resource query、action preview/command、task/approval query/command 四类语义。直接 URL 与菜单都不是授权边界，最终动作仍走 Admission。

## 7.1 组件 release 与两类 binding 生命周期

```text
Platform Catalog Tenant / platform admin
→ register immutable ComponentRelease
→ source baseline + manifest/API range + governance contracts + artifact digest validation
→ Approval/Temporal ComponentTaskWorkflow
→ APPROVED release

PLATFORM release
→ Platform Catalog admin creates/upgrades PlatformProviderBinding for exact known port
→ validate provider contract and switch new calls to ACTIVE generation

APPLICATION release
→ Business Tenant/Workspace admin creates/upgrades ApplicationBinding
→ resolve native scope + Adapter Protocol/protocol/driver contract
→ reconcile Resource/Action/Tool/route/observability/presentation projections
→ switch ComponentRuntimeProjection generation ACTIVE
→ authorized Buzz Web snapshot contains its runtime descriptors
```

Release 登记、provider binding 和 application binding 是三种不同 scope 的动作。全局 release 与 PlatformProviderBinding 属于 Platform Catalog scope；ApplicationBinding、Resource、native scope、usage 与 audit 属于业务 Tenant/Workspace。Binding upgrade/rollback 不修改 release；旧 generation 保留给已开始的 Workflow/ExternalExecution，只有新调用使用新 generation。任何兼容范围、digest、native scope或治理投影不一致都 fail closed，不退回默认实例或 latest（DD-56/59/62）。

## 8. ONLYOFFICE 文档协作链

→ BFF Admission / DocumentSession

## 9. 跨组件增量物化链

```text
MaterializationBinding action/Approval
→ ComponentTaskWorkflow(kind=MATERIALIZATION)
→ Worker 读取受权 Cells DriveSpace 快照
→ CocoIndex 以 node UUID + revision 计算逐项差异
→ WeKnora knowledge create/delete
→ WeKnora native parse/index/graph ExternalExecution
→ usage/audit/task projection
```

- MaterializationBinding 是通用 Resource 的一对一扩展：Resource 固定 Tenant、home Workspace、HUMAN owner，扩展固定源/目标 Resource、source/target contract key 与 pipeline version；不存在默认 Tenant、默认 Workspace 或跨 Tenant binding。
- 启动、定时触发和恢复由 Temporal 承接；CocoIndex 不成为第二 scheduler 或 Workflow 权威。固定源码只证明 Rust SDK 能在 LMDB `db_path`/App namespace 执行 update（`db_path` 未设时 SDK 静默回落相对路径 `./coco_state`，Core 必须始终显式传入绝对路径）；Worker→Rust runner 的运行绑定为 `DESIGN_DEFINED`（Activity 内调用，DD-69）；实现前不能宣称“已嵌入 Worker”（SF-CIX-01/04、SF-TMP-04、SF-TSDK-04）。
- Cells node UUID 是稳定 item key；node version 用于筛选候选变化，受权文件流的 content hash 决定正文 revision。path/name 是同 item metadata，稳定身份不随改名改变。
- CocoIndex target 只调用 WeKnora 受控 API，不写其数据库、向量库或 Neo4j。WeKnora 自己完成 parse、chunk、embedding、keyword 和可选 graph（SF-WEK-03/05/07）。
- Materialization 暂停只阻止后续读取/写入；物化内容清除是独立 owner 审批动作。具体状态和八维治理以 `03`、`05`、`06`、`13`、`14` 为准。

## 10. 跨 Tenant 转移与封闭收敛链

一期不存在跨 Tenant 共享数据面。已注册 `TransferFormat` 时，转移是两条分离的链：

```text
源 Tenant session / RESOURCE_EXPORT / source owner Approval
→ ComponentTaskWorkflow(kind=RESOURCE_EXPORT)
→ 源 Tenant ExportPackage Asset + digest
→ HUMAN 下载文件

目标 Tenant session / HUMAN 重新上传 / RESOURCE_IMPORT
→ 重算 digest + 固定 format/version 验证
→ ComponentTaskWorkflow(kind=RESOURCE_IMPORT)
→ 新 native object + 新 Resource/Asset + 新 HUMAN owner
```

两段使用不同 PlatformSession、ExecutionContext、operation 和 Workflow；目标端不接收源 Tenant 的 relationship、binding、native ID、owner、ACL、临时 URL 或 token。当前没有任一 ResourceType 在 `02` 登记了完整的成对 `TransferFormat` SOURCE_SEAM，因此当前全部 `transfer_formats=[]`，Web/Agent 不暴露导出/导入 Action。该结论只表示当前证据登记不支持 active 路径，不把代码搜索结果扩张成上游项目的全局否定。

封闭收敛链只有一个业务权威：

```text
Core 先改 Tenant/WorkspaceMembership/ApplicationBinding 状态并 fail closed
→ 冻结 TenantLifecycleSnapshot
→ Temporal ComponentTaskWorkflow(kind=TENANT_LIFECYCLE)
→ SpiceDB/Buzz/Component projection 撤销
→ 每个 native delete 记为 ExternalExecution
→ Audit/Usage/tombstone 保留
```

Workspace 成员撤权不等待投影完成才拒绝新动作；Core 进入 `REVOKING` 即 fail closed，然后对账 SpiceDB relationship 和 Buzz roster。Workspace 暂停同样先关闭 scope/stream/Schedule/新动作，再把 Channel archive；恢复完成全部投影对账后才重新开放。Buzz 的 Channel soft-delete 没有处理平台 Resource/Asset/binding/owner，因此当前不注册 Workspace delete Action，也不在 Workspace 状态机中保留不可达的删除状态（SF-BUZ-15、DD-46）。Tenant 同样先进入 `SUSPENDING/SUSPENDED`。`TENANT_LIFECYCLE` 运行链为 `DESIGN_DEFINED`（DD-69）；全部 native 删除契约受 GAP-LCM-01 阻断，因此当前不注册 Tenant delete Action，不宣称 `DELETING/DELETED` 可达。

组件停用也不是一次状态更改：Core 先持久 `DISABLING` 与 ActionExecution 并 fail closed，再由 `ComponentTaskWorkflow(kind=COMPONENT_DISABLE)` 按固定 binding version 与受影响 refs 撤 Schedule、relationship、route/tool、连接并对账 native refs、usage 和 audit。该运行链同样为 `DESIGN_DEFINED`（DD-69）。

## 11. 数据与故障语义

- Buzz event、Codex stream、MCP、Cells 文件流、DocumentServer editor/WOPI stream、WeKnora 检索和 Wren query 保留原生数据面；Core 不复制正文。
- ONLYOFFICE 保存只有在 Cells PutFile evidence 被接受并取得 Cells result revision 后才完成；iframe loading/dirty/close 与 DocumentServer cache 都不是文件终态（SF-CEL-06/07、SF-OFF-07）。
- 外部超时且副作用未知时记 `UNKNOWN`，先用 native ref 对账，不盲目重放。
- SpiceDB、required audit intent 或 strict reservation 不可用时，相关动作 fail closed。
- OpenMeter 不可用时拒绝新的 `CHECK/STRICT_RESERVATION` 动作；已发生 usage 保留 outbox 重试。
- TaskProjection 落后只影响展示；控制命令重查 Temporal 与当前 permission。
- 撤权阻止未执行步骤，不改写已发生副作用、usage 或 audit。
- AgentGateway log tail 的游标只解决已持久记录的重复读取，稳定 source ID只防重复计费；它不能恢复 SF-AGW-09 在数据库写失败时已经丢失的记录。SS-AGW-USAGE 未闭合前，LLM 账单显示 `BILLING_UNAVAILABLE`，不得显示零用量或已结算。
- CocoIndex 与 WeKnora 之间没有分布式事务；变化文件按“创建新 Knowledge→等待 native ready→删除旧 Knowledge”收敛。新建失败时保留旧版本，旧版本删除失败时保留 pending ref 供 reconcile；不声明原子替换或 exactly-once。
