# 紧凑总体架构与端到端交互

本文只组合 `02` 已冻结的源码接缝与 `03` 的领域对象，不增加新权威服务。拓扑、权威边界与端到端链只以平台核心为前提；业务能力服务按能力类别接入，可缺席、可替换，其产品细节属于内置参考实现文档 `08`、`13`、`18`（DD-87/88）。

## 3. Web 与 Buzz 协议链

Buzz Relay 不认 OIDC，且 ingest 要求 event signer 与 NIP-42 认证 pubkey 一致（SF-BUZ-02/03）。因此一期 Web 链固定为：

```text
AgentGateway OIDC authorization-code+PKCE→加密 HttpOnly cookie→validated jwt.sub
→ route transformation 移除外来身份 header并写入已验证 subject
→ BFF 以 issuer+subject 解析 HumanIdentity、TenantMembership 与 PlatformSession
→ Browser 只通过 BFF transport 发类型化 query/stream/semantic command/media request
→ BFF 完成 Action Admission
→ 读取该 Principal 的 BuzzIdentityBinding secret
→ 以同一 pubkey 完成 NIP-42 并签名正常 Nostr event
→ Relay 执行成员/per-kind 校验、持久化与 fan-out
```

- AgentGateway 的 OIDC 登录、cookie session 与本地 cookie logout route 是 `UPSTREAM_SUPPORTED`；claims→BFF header、logout 后同步撤销 Core PlatformSession 与关闭 BFF stream 是 `ADAPTER_REQUIRED`，精确接缝为 SS-AGW-OIDC。BFF 只允许从 Gateway 内网路径到达，不接受 Browser 自报身份 header（SF-AGW-10）。
- buzz-web 现有的 concrete `BuzzRelayClient`、query/subscribe/publish、NIP-42/NIP-98、media 和 NIP-44 user-state 是一个完整 `ADAPTER_REQUIRED` 替换面（SF-WEB-01/04/05、SS-WEB-RELAY）。仅替换 signer 仍会留下浏览器直连，不符合一期边界。
- BFF transport 不接受 raw signed event 或任意 Relay filter。它按当前 PlatformSession 构造 scope，把查询/订阅结果以现有 `NostrEvent` 读模型传给 UI，把写入意图映射成固定 event kind/tags 后再代签（DD-39）。
- Relay inline media 的 upload/get 亦经 BFF 以 acting Principal 的 Buzz identity 执行 NIP-98 签名；Browser 只传文件字节/返回的 descriptor。审批附件、任务产物与聊天引用使用 ContentReference 或 Relay media：Workspace 有 active `FILE_STORAGE` 实现时引用其 ContentReference，没有文件能力 binding 时退回 Relay media；ContentReference 不写成 Relay media URL，Relay media 也不冒充业务能力实现的内容权威（DD-90）。
- 收藏、静音和已读位置不再走 kind:30078/NIP-44；BFF 读写 Core CollaborationUserState，Browser localStorage 不是跨端权威（SF-WEB-05、DD-40）。
- Human 和 Agent 各有独立 Nostr key；服务端不用共享 Relay key 伪装业务 actor（DD-02）。
- CONTROL SERVICE identity 只执行 Community/roster 协议投影与 Tenant NIP-AE Memory Counterparty/受权解密，不作业务 actor 或 Resource/Asset owner（SF-BUZ-04/06/16/19，DD-03/66）。
- `RelayActionSink` 不在 Kailo 拓扑中：Kailo 部署经 SS-BUZ-GOVERNANCE 关闭 Buzz 自带 workflow（SF-BUZ-45、DD-106），`RelayActionSink` 不再产生 `buzz:workflow=true` 消息，ACP 的 workflow 唤醒（SF-BUZ-25）也没有输入源；它不用于人类消息、Agent 身份回复或通用 Core command（SF-BUZ-09）。用户可见的自动化由 Core 定义、Temporal 执行（DD-107）。
- Buzz SDK `/v1/action` 只有客户端合同，Relay 没有 host route，因此不进入拓扑（SF-BUZ-10）。

OIDC client/cookie secret 与服务端 Nostr 私钥托管于 OpenBao（DD-70/72）；claims→BFF 投影（SS-AGW-OIDC）闭合前整条链为 `ADAPTER_REQUIRED`。

## 4. 成员与 scope 投影

```text
Platform Tenant membership active
→ SpiceDB tenant/workspace relationships written
→ CONTROL identity 发布 Buzz relay-admin/channel-admin event
→ Relay 查询证明投影成功
→ 开放该 scope 的 Buzz stream/navigation
```

建立与撤权都是持久多投影事务：Tenant/Workspace 建立分别使用 `ComponentTaskWorkflow(kind=TENANT_LIFECYCLE|WORKSPACE_LIFECYCLE)`；TenantMembership/WorkspaceMembership 建立与撤权共用 `ComponentTaskWorkflow(kind=MEMBERSHIP_PROJECTION|MEMBERSHIP_REVOCATION)`，input 以 `TENANT|WORKSPACE` target type 区分 relay roster 与 Channel roster。Core 先持久相应实体 version、ActionExecution 与 fail-closed 状态，再以稳定 Temporal workflow ID 启动对应 kind。撤权在 Core `REVOKING` 时已拒绝新动作并关闭 BFF session/stream，Workflow 再撤 SpiceDB relationship、用 CONTROL identity 移除 Relay/Channel 成员并查证。Buzz 投影失败不恢复平台权限。这些运行链由 DD-69 的 Application Worker 承接，为 `DESIGN_DEFINED`。Community 创建通过 RelayOperatorIdentity 与 SS-BUZ-OPERATOR 调用源码已有的 NIP-98 operator 入口，为 `ADAPTER_REQUIRED`；不绕过 Relay DB（SF-BUZ-06）。

## 5. 动作路径

### 同步动作

```text
session → TenantMembership active
→ Tenant scope，或 Workspace ACTIVE + active WorkspaceMembership/workspace manage
→ ActionDefinition → Resource/Asset SpiceDB Check + Delegation
→ Approval=not-required → Capacity/Quota → durable audit intent
→ Application Adapter Dispatcher（ActionToken）/ 平台端口 client（ExecutionContext） → native result
→ exposure → usage/audit result
```

同请求完成且无等待/恢复需求的读写不创建 Workflow。

### 持久动作

```text
admission → ApprovalWorkflow when required → fresh recheck
→ Start Workflow → Worker schedules Activity
→ adapter/native operation → ExternalExecution observe/signal
→ exposure/usage/audit → Temporal terminal state
```

Temporal Server 不执行应用 Workflow；Application Worker 是必需角色（SF-TMP-02）。Worker 按 DD-69 以 `temporal-sdk-go` 自建，链路为 `DESIGN_DEFINED`；实现并通过重放回归前不是可运行能力。

## 6. Agent 与工具链

```text
Relay persisted event + Core checkpoint
→ resolve active AgentInstallation + exact AgentVersion/projection generation
→ idempotent AgentInvocation/AgentTaskWorkflow
→ isolated Codex app-server turn
→ optional Temporal Approval
→ fresh admission + 会话级 bearer（PEP 逐次裁决，DD-105）
→ AgentGateway Streamable HTTP MCP + ExtMcp PEP
→ backend/result exposure/usage/audit
→ Agent identity 签名 Buzz reply
```

- ACP EventQueue 只是内存结构；触发恢复依据 Relay 持久 event 与 Core checkpoint（SF-BUZ-07/08，DD-04）。
- Definition 在 Tenant，Installation 在 Workspace，ChannelAgentBinding 只控制触发；每个 Invocation 固定不可变 AgentVersion 与 active projection generation（DD-25/27）。
- 每个 Installation 的 CODEX_HOME 根本不配置 local environment，这是跨 `thread/resume` 的承重封堵。`thread/start.environments=[]`、Core 从不发 `turn/start.environments`、`shell_tool=false` 与 `shell_type=disabled` 都是纵深防御；turn override 可影响当前及后续 turn，不能作为权威封堵。Core 不调用 `command/exec`、`process/spawn`、`thread/shellCommand`（SF-COD-03/04/11/12，DD-15）。
- Codex 自定义 Responses provider 的 `base_url` 指向 AgentGateway，使模型路由与 usage observation 也经 Gateway（SF-COD-05、SF-AGW-04，DD-17）。
- 业务能力实现的模型调用模式由 release 声明允许的集合、ApplicationBinding 在其中选定一种，切换模式是需要审批的 Governed Action；调用模型的 binding 其 meter 能力必须为 `SUPPORTED`。`PLATFORM_LLM_ROUTE` 经配置把服务的模型出口指向 AgentGateway `llm_route`，由平台计量；`SELF_MANAGED_MODEL` 由服务自管模型，经 Adapter Protocol 上报 usage 作为 actual usage source，平台照常执行 Quota 与审计。平台不向服务数据写入模型配置；trace 以标准 `traceparent`/operation 头关联，缺失时按 gateway identity 或上报身份解析出的 binding scope 入账，只降低到 operation 的归因精度，不阻断 binding，也不免于计量（DD-20/92、`07` §8.3）。
- 配置 logging database 后，AgentGateway request log 可记录模型、token 与 cost并供业务观测；原始 writer 在数据库失败时丢批次，不能作计费完整性来源（SF-AGW-06/09）。只有 SS-AGW-USAGE 闭合为持久确认的 usage outbox 后，Core 才能以 IngressCheckpoint/稳定 log ID 生成 OpenMeter UsageEvent（DD-21）。
- ActionToken 只跨进程/网络边界使用：Core→AgentGateway、Core→remote adapter 或 Core→独立 runtime。Core 内平台端口调用直接接受不可伪造的 ExecutionContext；业务能力实现全部在进程外，因此不存在以 ExecutionContext 直调业务能力的路径。
- AgentGateway 通过 ConfigResource store/API 接收 Catalog 投影；xDS 不用于该路径（SF-AGW-01/03，DD-13）。ConfigResource API、整份配置文件读写 `GET|POST /api/config`（POST 直接覆写网关配置文件）、`llm.settings`/`mcp.settings` 监听端口与 TLS、日志/成本/预算查询、debug 与 `quitquitquit` shutdown route 位于同一个无认证 admin router；必须在 SS-AGW-ADMIN 加入 Core-only service authentication，内网地址和 CORS 都不构成认证（SF-AGW-02、SS-AGW-ADMIN）。

SpiceDB、Temporal、OpenMeter 与 AgentGateway admin 都不接受 Browser/Agent 直连。Core/Worker 分别使用源码证明的 bearer PSK、显式启用 default mapper/authorizer 的 Temporal JWT role，以及 SS-OMT-AUTH/SS-AGW-ADMIN 的 service authentication；Temporal 空 auth 配置的 no-op 路径禁止进入 active binding。所有最终用户/Agent 业务 permission 仍在 Core 以 SpiceDB Check 判定（SF-SPZ-03、SF-TMP-06、DD-37）。OpenMeter 固定单一 default namespace，并以 Tenant→Customer、子 scope→subject 映射隔离计量归属（SF-OMT-05/06、DD-38）。

## 7. 客户端产品面

Buzz Client Surface 是仅有的壳，由 Buzz Web、Buzz Desktop、Buzz Mobile 三端构成（REQ-01、DD-74）。下列导航在 Web 与 Desktop 上完整可达；Buzz Mobile 按 REQ-21 对「业务」「AI」「治理」三组提供受权只读视图与可降级入口，不承载 Component Host 与 editor surface：

```text
协作：Channels / My Tasks / Approvals
AI：Agents / Workflows / Skills / Tools
治理：Members & Roles / Usage & Billing / Business Operations / Audit / Components
业务：由授权后的 ComponentRuntimeProjection 快照生成，无 active 业务能力 binding 时为空
```

固定入口只有协作、AI、治理三组，由平台核心提供；平台资产（Agent Version、Skill 等当前可达的 Asset）属于治理组。「业务」分组没有固定条目：每个条目来自当前 scope 授权后的 `ComponentRuntimeProjectionSnapshot` 中 active ApplicationBinding 的导航描述，按能力类别归组；binding 停用、切换实现或撤权后，条目随快照 generation 消失或替换，不留空壳页面。

Buzz Web 与 Buzz Desktop 是两个上游代码库（buzz-web 的 `web/` 与 Buzz 的 `desktop/`），共享由 Buzz 原版提取的 TypeScript 页面、组件与交互主体，以及 Kailo 平台包与契约生成物；两端只在认证、签名、传输和宿主能力适配处区分，各自以 SS-WEB-COMPONENT-HOST、SS-DSK-COMPONENT-HOST 接入 Component Host，两端都仍以静态 routeTree 构建（2026-09-28 按 DD-74 修订）。Web 的一次性 Component Host 增加固定 `/apps/$componentKey/$` catch-all route，不在运行时修改 TanStack routeTree；Desktop 在 `src/app/routes.ts` 显式登记固定 `route("/apps/$componentKey/$", …)` 并随构建进入生成的 routeTree，在 `AppShell` 内容区以运行时 surface registry 挂载 `HOST_NATIVE` 与 `SOURCE_BOUND_PROTOCOL` surface，`AppSidebar` 的业务条目由快照生成（SS-DSK-COMPONENT-HOST）。Desktop 的 CSP 编译在签名包内，不执行 `REMOTE_MODULE` 的运行时 script，对应入口显示确定状态并指向 Web（SF-DSK-03）。以下 remote module 的加载与 reconcile 描述只适用于 Web。当前 `BuzzWebApp.Workspace`、`WorkspaceTool` union 与内容条件链是封闭壳；Component Host 固定一个由 index/chat 与 app route 共用的 WorkspaceShell，Host 根据 BFF 返回的 scope-authorized `ComponentRuntimeProjectionSnapshot` 生成导航和 surface mount。Session stream 只通知 monotonic generation 变化，Browser 重取完整快照并 reconcile；加载时由 Host 内部 pending load 绑定 type/release/generation/digest/注入元素，module 的同步 register 先暂存描述符，只有 script load 后全字段与 API 匹配才提交。Mattermost 证明 active manifest→script registration→scoped registry→版本 reconcile/unload 的运行模式，Buzz 当前没有该能力，因此完整边界是 `ADAPTER_REQUIRED: SS-WEB-COMPONENT-HOST`（SF-MAT-03/04、SF-WEB-02、DD-61）。Mattermost 的事件路径把 WebSocket payload 当作完整状态直接 load/remove，全量 reconcile 只在重连时发生（SF-MAT-06）——这正是 Kailo 拒绝的模式，DD-61 以“事件只通知 generation、Browser 重取完整快照”与之相反。

同窗口 remote module 是宿主信任代码，不是安全沙箱。平台管理员批准的 release 固定来源标识（按 `admission_path` 取证，DD-94(1)）、source entry URL、digest 和 Host API range；Catalog 只把验证后的 bytes 暴露为同源内容寻址路径，Browser 不加载外域 script，保留 buzz-web 的 `script-src 'self'`（SF-WEB-06、DD-60）。Tenant 管理员只能启用。模块只获得 Component Host API 与 mount root，不获得 Redux/store、Relay signer、组件管理 credential 或平台权威服务 credential。即使模块自行发起同源 BFF 请求，BFF 仍只接受语义 API并重做 session、scope、SpiceDB、Approval、Quota 与 Audit；前端代码从不成为授权边界（DD-55/56）。

宿主扩展槽一期固定为管理导航页、Resource view 和聊天附件 action；新的槽位意味着宿主 API 变化并需要两个承载端（Buzz Web 与 Buzz Desktop）各自发布。`HOST_NATIVE` 组件无需 remote module，复用同一通用管理页面；`SOURCE_BOUND_PROTOCOL` 仅由 release 固定的 editor origin 与 DocumentLaunchDescriptor 打开协议 surface：descriptor 由实现的 adapter 生成、经 Core 校验 origin 后下发，该能力实现自己的协议页面在受限 iframe 内创建 editor，不开放为通用 iframe 插件；editor origin 须已进入该端的部署级许可集合（DD-30/58/95）。内置参考实现的协议形态见 `18`。

所有 Host-native 与 remote module 都只消费 Buzz `FrontendPresentationContext`：主题沿用 ThemeProvider/CSS variables，平台文案沿用 `AppLocale + MessageKey/t`，release 同时登记 namespaced `en/zh-CN` catalog。业务能力实现与 Temporal 的上游原生 UI 不嵌入；业务能力服务的管理面只经 Component Host 露出，非分离 monolith 保留在后端，由 adapter 与 Host-native 页面接入（DD-87 第 3 条）。`SOURCE_BOUND_PROTOCOL` surface 固定 `LAUNCH_MAPPED`：launch 请求携带 Buzz resolved theme/locale，由该实现的 adapter 映射为其私有参数写入 descriptor（SF-WEB-03、DD-36/58/95）。

BFF 对 Web 只暴露 context/navigation、resource query、action preview/command、task/approval query/command 四类语义。直接 URL 与菜单都不是授权边界，最终动作仍走 Admission。

## 7.1 组件 release 与两类 binding 生命周期

```text
Platform Catalog Tenant / platform admin
→ register immutable ComponentRelease
→ 来源标识（按 admission_path，DD-94(1)）+ manifest/API range + governance contracts + artifact digest validation
→ Approval/Temporal ComponentTaskWorkflow
→ APPROVED release

PLATFORM release
→ Platform Catalog admin creates/upgrades PlatformProviderBinding for exact known port
→ validate provider contract and switch new calls to ACTIVE generation

APPLICATION release
→ Business Tenant/Workspace admin creates/upgrades ApplicationBinding
→ resolve native scope + implements[category@version] 能力契约 + Adapter Protocol/标准协议
→ reconcile Resource/Action/Tool/route/observability/presentation projections
→ switch ComponentRuntimeProjection generation ACTIVE
→ authorized Buzz Web snapshot contains its runtime descriptors
```

Release 登记、provider binding 和 application binding 是三种不同 scope 的动作。全局 release 与 PlatformProviderBinding 属于 Platform Catalog scope；ApplicationBinding、Resource、native scope、usage 与 audit 属于业务 Tenant/Workspace。Binding upgrade/rollback 不修改 release；旧 generation 保留给已开始的 Workflow/ExternalExecution，只有新调用使用新 generation。任何兼容范围、digest、native scope或治理投影不一致都 fail closed，不退回默认实例或 latest（DD-56/59/62）。同一类别在某 Workspace 的实现按 Workspace 级 binding 优先、其次 Tenant 级 binding 解析；类别内换成另一实现不走 generation 切换，而是新建 binding 对账到 `ACTIVE` 后旧 binding 转 `DISABLED` 只读保留，旧 Resource 只可 discover 元数据，相关 WorkspaceCapabilityDefault、DelegationScope 与 ToolBinding 按 `07` §2.4 失效或重绑（DD-88）。

## 8. 业务能力 surface 通用链

```text
ContentReference + requested mode
→ BFF Admission（scope、SpiceDB、Delegation、Approval、Capacity/Quota、audit intent）/ ProtocolSession
→ launch 请求携带 Buzz 已解析的 theme/locale，路由到目标 ContentReference 所属 ApplicationBinding 的 adapter
→ 该 adapter 映射实现私有参数并生成 DocumentLaunchDescriptor
→ Core 校验 editor_origin ∈ release editor_origins[] 且等于该 binding 的实例 origin、action_url origin = editor_origin、字段均为字符串、未过期，原样下发
→ Buzz Web 的 ProtocolDocumentSurface 以 Web 有效集合内的 editor origin 在 iframe 中打开；Buzz Desktop 在独立 editor 窗口中打开，导航钩子按运行时许可集合校验（DD-104）
→ 组件按自身协议执行；每个协议入口经 Core PEP 入站 service 边 fresh Check
→ 证据回传：能力契约登记的 result revision/evidence
→ exposure / usage / audit / ProtocolSession 终态
```

- ProtocolSession 只记录 kind、binding、target ContentReference、requested/admitted mode、native_session_ref 与 state；协议细节、token 形态与保存机制属于实现该能力的组件，平台只认能力契约登记的证据（DD-90）。
- `admitted_mode` 不超过 requested mode 与当前 permission；组件自身 ACL 只继续收窄。iframe loading/dirty/close 与组件缓存都不是终态；只有能力契约登记的结果证据被接受，ProtocolSession 才终结。结果不明时进入 `ComponentTaskWorkflow(kind=PROTOCOL_SESSION_RECONCILE)`，按该 binding 登记的查证手段对账，不重新触发组件保存。
- Buzz Web 与 Buzz Desktop 承载该 surface，Buzz Mobile 不承载（REQ-07/21）。BFF 在运行时持有部署级许可集合并据此决定各端编辑入口：Web 有效集合是许可集合与 Web 已生效集合的交集（由同一份部署配置投影出 CSP 与 BFF 读取值）；Desktop 不把 origin 编入安装包，主窗口 CSP 不变，编辑器在独立 `platform-editor-*` WebviewWindow 中打开，其 `on_navigation` 钩子只放行一次性 launch 地址与本次 editor origin，Desktop 有效集合就是 BFF 运行时下发的许可集合，新增 origin 不需要发布 Desktop 包（DD-104、SS-DSK-EDITOR-WINDOW）；有效集合未包含该 editor origin 时，该端编辑入口显示确定状态，不隐藏也不报错（DD-95）。编辑入口按目标 ContentReference 所属实现判定：该实现未声明 `online_editing=SUPPORTED` 时不出现编辑入口，ContentReference 只显示元数据并按 `FILE_STORAGE` 能力契约登记的 Action 受权下载；没有 `FILE_STORAGE` 实现时附件与产物退回 Relay media。
- 云盘、Channel/Thread 引用卡片、审批附件、任务产物与知识 citation 都只传 ContentReference 并复用同一条链。内置“文件存储与在线编辑”参考实现的 token、权限、保存、主题/i18n、容量与撤权细节以 `18` 为准。

## 9. 跨服务数据获取

平台不编排跨服务数据同步，没有物化端口、物化 binding 或物化 Workflow kind（DD-89）。一个业务能力服务需要另一服务的数据时只有两条路：

```text
(a) 接收方自行拉取
接收方管理面（经 Component Host）配置数据源连接器
→ Governed Action（含审批；发起者须对来源 Resource 持有 share、对接收方 Resource 持有 update）：
  为接收方 binding ServicePrincipal 写入来源 Resource `reader` 关系
→ 每批拉取经服务读取边：接收方 binding 经 Adapter Protocol request_read_grant 申请
  → Core 以 SERVICE actor 准入（scope guard、fresh read Check、Quota），为该批建立 operation
  → 签发短期 ActionToken（audience=来源实现契约端点，target=来源 Resource）
  → 接收方凭令牌经来源方能力契约读取；来源 PEP 校验令牌并再 fresh read Check
  → 该批的审计、Usage 与观测归属该 operation
→ 增量、状态、去重与删除收敛全部在接收方内部
→ 撤销该关系即收回读取权：Core 拒绝后续申请，来源 PEP fresh 拒绝后续读取

(b) 显式读写
人或 Agent 经两边各自暴露的 Tool 读取与写入，每一步都是 Governed Action
```

接收方不持有来源实现的 native 凭据；经平台签发令牌访问来源的契约端点不是服务间数据面直连。平台只治理授权与动作，不经手数据、不持有同步状态、不为同步建立 Temporal Schedule。服务读取边的八项治理以 `07` §8.2 为准；接收方内部如何增量与对账属于该实现，内置参考实现的说明见 `13`。

## 10. 跨 Tenant 转移与封闭收敛链

一期不存在跨 Tenant 共享数据面。已注册 `TransferFormat` 时，转移是两条分离的链：

```text
源 Tenant session / RESOURCE_EXPORT / source owner Approval
→ ComponentTaskWorkflow(kind=RESOURCE_EXPORT)
→ 源 Tenant ExportPackage Asset + digest
→ HUMAN 下载文件

目标 Tenant session / HUMAN 重新上传 / RESOURCE_IMPORT
→ 重算 digest + 固定 format/version 验证
→ ComponentTaskWorkflow(kind=RESOURCE_IMPORT)
→ 新 native object + 新 Resource/Asset + 新 HUMAN owner
```

两段使用不同 PlatformSession、ExecutionContext、operation 和 Workflow；目标端不接收源 Tenant 的 relationship、binding、native ID、owner、ACL、临时 URL 或 token。当前没有任一 ResourceType 在 `02` 登记了完整的成对 `TransferFormat` SOURCE_SEAM，因此当前全部 `transfer_formats=[]`，Web/Agent 不暴露导出/导入 Action。该结论只表示当前证据登记不支持 active 路径，不把代码搜索结果扩张成上游项目的全局否定。

封闭收敛链只有一个业务权威：

```text
Core 先改 Tenant/WorkspaceMembership/ApplicationBinding 状态并 fail closed
→ 冻结 TenantLifecycleSnapshot
→ Temporal ComponentTaskWorkflow(kind=TENANT_LIFECYCLE)
→ SpiceDB/Buzz/Component projection 撤销
→ 每个 native delete 记为 ExternalExecution
→ Audit/Usage/tombstone 保留
```

Tenant 销毁以平台自有事实为前提：平台核心自有 ResourceType 的删除由 `TENANT_LIFECYCLE` 按平台核心销毁链执行，不适用保留；每个 ApplicationBinding 的 native 删除是独立子流程（`03` TenantDeleteSubprocess），删除能力由其能力契约声明。准入时声明 `retain_on_tenant_delete` 的实现，在 Tenant 删除时只撤 binding、撤凭据、保留审计并登记待人工处置（`RETAINED_DECLARED`），不阻断平台 Tenant 状态机；已声明删除能力的子流程失败或结果不明时 fail closed 持续对账，只有该业务 Tenant 的 admin 经 owner 审批的 Governed Action 可把它处置为 `RETAINED_BY_DECISION`（DD-91）。

Workspace 成员撤权不等待投影完成才拒绝新动作；Core 进入 `REVOKING` 即 fail closed，然后对账 SpiceDB relationship 和 Buzz roster。Workspace 暂停同样先关闭 scope/stream/Schedule/新动作，再把 Channel archive；恢复完成全部投影对账后才重新开放。Buzz 的 Channel soft-delete 没有处理平台 Resource/Asset/binding/owner，因此当前不注册 Workspace delete Action，也不在 Workspace 状态机中保留不可达的删除状态（SF-BUZ-15、DD-46）。Tenant 同样先进入 `SUSPENDING/SUSPENDED`。`TENANT_LIFECYCLE` 运行链为 `DESIGN_DEFINED`（DD-69）；Tenant delete Action 按 `06` §7.2 在注册时已存在的每个平台事实类别都有经验证的销毁处理器后注册，之后新增的类别与其处理器同一构建登记，注册前不宣称 `DELETING/DELETED` 可达（DD-99）。业务能力实现的删除缺口（GAP-LCM-01）只作用于该实现的删除能力声明，不阻断该 Action 的注册（DD-91）。

组件停用也不是一次状态更改：Core 先持久 `DISABLING` 与 ActionExecution 并 fail closed，再由 `ComponentTaskWorkflow(kind=COMPONENT_DISABLE)` 按固定 binding version 与受影响 refs 撤 Schedule、relationship、route/tool、连接并对账 native refs、usage 和 audit。该运行链同样为 `DESIGN_DEFINED`（DD-69）。

## 11. 数据与故障语义

- Buzz event、Codex stream、MCP 与各业务能力实现的协议流、检索和查询保留原生数据面；Core 不复制正文。
- ProtocolSession 只有在能力契约登记的结果证据被接受后才终结；surface 状态与组件缓存都不是终态。各内置参考实现的保存与故障语义以 `18`、`13` 为准。
- 外部超时且副作用未知时记 `UNKNOWN`，先用 native ref 对账，不盲目重放。
- SpiceDB、required audit intent 或 strict reservation 不可用时，相关动作 fail closed。
- OpenMeter 不可用时拒绝新的 `CHECK/STRICT_RESERVATION` 动作；已发生 usage 保留 outbox 重试。
- TaskProjection 落后只影响展示；控制命令重查 Temporal 与当前 permission。
- 撤权阻止未执行步骤，不改写已发生副作用、usage 或 audit。
- AgentGateway log tail 的游标只解决已持久记录的重复读取，稳定 source ID只防重复计费；它不能恢复 SF-AGW-09 在数据库写失败时已经丢失的记录。SS-AGW-USAGE 未闭合前，LLM 账单显示 `BILLING_UNAVAILABLE`，不得显示零用量或已结算。
- 业务能力实现不可用只影响该能力类别的 Resource/Action/Tool：对应动作与工具调用 fail closed；binding 停用或撤销后该类别不再有 active 实现，Agent 工具 effective 为 `NO_PROVIDER`；协作、Agent、任务、审批与治理不受影响。

## 12. 零业务能力 binding 的平台

没有任何 active ApplicationBinding 时，平台就是完整产品（DD-87 第 1 条、DD-91）：

- 协作：Community/Channel/Thread/DM、成员与 roster 投影、Relay media 附件完整可用。
- Agent：Definition/Version/Installation、Channel 触发、Codex 回合、模型调用经 AgentGateway、Relay/Codex/NIP-AE 四层记忆与平台原生工具（`PLATFORM_NATIVE`）完整可用；声明了业务能力需求的工具 effective 为 `NO_PROVIDER`，Installation 仍可 `ACTIVE`（DD-92）。
- 任务与审批：Temporal Workflow、审批箱与任务工作台完整可用；附件与产物使用 Relay media。
- 治理：成员与角色、平台资产（Agent Version、Skill 等当前可达的平台 Asset）、额度与计费、业务操作时间线、审计与组件管理页可用；导航「业务」分组为空。
- 门禁：该部署必须能通过全部平台 Stage 退出门禁与一期生产门禁；业务能力实现的接缝缺口只阻断其 ComponentRelease `APPROVED` 或 ApplicationBinding `ACTIVE`（DD-91）。
