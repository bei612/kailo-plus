# 统一治理设计

统一治理同时约束平台主体、每个 Platform Component 和每个 Application Component。一个用户/Agent 业务意图只建立一条 Governed Action；该链内部的 SpiceDB Check、Temporal poll、OpenMeter query 和 Connector 转发不递归建立新动作。

## 1. 唯一准入顺序

```text
1 authenticate Human/Service
2 resolve Tenant/Workspace/target/binding
3 load exact ActionDefinition version and normalize parameters
4 SpiceDB permission with required consistency
5 validate Agent Delegation/ToolBinding/result exposure when actor is Agent
6 resolve Approval policy and wait in Temporal when required
7 acquire operational Capacity when policy=PLATFORM_SLOT, or record NATIVE mode
8 check OpenMeter entitlement/credit and create strict QuotaReservation when required
9 durably persist audit intent + dispatch outbox
10 dispatch SYNC / PROTOCOL / TEMPORAL
11 expose result, settle/release reservation, emit usage and append audit outcome
```

审批完成后、每个尚未发生的外部副作用前，重做 2、4、5、7、8。审批只解决人的决策，不补足 scope、permission、Delegation、binding、capacity 或 quota。

## 2. 八维贯穿合同

| 维度 | 权威 | 准入 | 执行/完成 |
|---|---|---|---|
| Tenant | Platform Core | active membership、target 与 binding 同 Tenant | 运行中不允许换 Tenant；停用阻止后续步骤 |
| Workspace | Platform Core | route、Resource home、Tool/Component binding 对齐 | Workflow/native ref 固定 scope；撤权关闭发现和订阅 |
| Authorization | SpiceDB | Check 规范 permission | 因果链 `AtLeastAsFresh`；不可逆外部副作用且无 token 时 `FullyConsistent` |
| Approval | Temporal | ActionDefinition/ApprovalPolicy 决定是否等待 | 决定经 Update+Validator 推进、超时经 Timer；批准绑定 action/parameter/policy version（DD-69） |
| Workflow | Temporal | 只有持久生命周期动作启动 | history 是状态权威；TaskProjection 只读 |
| Capacity/Quota/Billing | Core CapacityLease + OpenMeter + Core QuotaReservation | 先占平台可控 slot，再查 entitlement/credit/严格保留 | 释放 slot；使用实际 usage 结算；OpenMeter 保存 committed usage/billing |
| Operation Audit | Platform Core | dispatch 前持久 intent | 追加 decision、native evidence、usage、terminal/revoke/reconcile |
| Business Observability | Core Action/Audit + 各业务执行权威 + OpenMeter usage/cost，BFF 联合只读 | ActionDefinition 固定 operation correlation、terminal/progress/usage/cost/redaction source | operation/native refs 关联发起者、actor、Resource、审批、状态、错误、usage/cost；按 Resource `read/audit` 与 exposure 过滤 |

这八维对组件每个用户可达 action 都必须有确定策略；`NONE` 是明确策略，不是缺省逃逸。Business Observability 与 Operation Audit 分离：前者回答“该业务动作现在到哪一步、涉及谁和什么资源、耗费多少”，后者回答“谁因何被允许并做了什么”。

### 2.1 统一模型调用的八维闭环

平台自有 Agent 的模型调用始终经 AgentGateway；业务能力实现的模型调用模式由其 release 声明允许的集合 `allowed_model_call_modes[]`，ApplicationBinding 在其中选定 `PLATFORM_LLM_ROUTE` 或 `SELF_MANAGED_MODEL` 之一；切换模式是需要审批的 Governed Action；调用模型的 binding 其 release 对所启用类别的 meter 能力必须为 `SUPPORTED`（DD-92，字段以 `03` §3 为准）。

| 维度 | `PLATFORM_LLM_ROUTE` / AgentGateway | `SELF_MANAGED_MODEL` |
|---|---|---|
| Tenant | `llm_route`、调用方 binding 与 gateway identity 必须同 Tenant；Gateway 的 apiKey/JWT user/group 映射回已登记 ServicePrincipal，不接受请求体自报 Tenant | usage 上报以该 binding 的 ServicePrincipal 认证，Tenant 取自 binding，不接受上报 payload 自报 Tenant |
| Workspace | Workspace 来自父 ActionExecution；Workspace 级 route 只能被该 Workspace 发现；Tenant 级 route 管理使用 TENANT_ONLY，但 Workspace 内调用按 INHERIT_PARENT 保留父 Workspace，不能由模型名或 Resource home 反推 scope（DD-54） | Workspace 来自父 ActionExecution；上报携带的 operation 必须解析到该 binding scope 内的 ActionExecution，否则只按 binding scope 入账并标记归因缺口 |
| Authorization | 调用前检查 `llm_route:execute` 和父 action；Agent 还要经过 Delegation/ToolBinding；Gateway route authorization 与 rate-limit 是第二 PEP，不替代 SpiceDB | 父 Action/Tool 已 fresh Check；服务内部模型调用不再逐次 Check；平台不持有、不写入其模型配置与模型凭据 |
| Approval | 普通模型调用继承父 Governed Action 的审批结果，不为每个 token call 新建审批；route/provider/credential 变更与父高风险动作各按自己的 ActionDefinition 审批 | 继承父 Governed Action 的审批结果；`model_call_mode` 切换是需要审批的 Governed Action，且只能在 release `allowed_model_call_modes[]` 内选择 |
| Workflow | 同步模型调用属于父 action 的一步；Agent turn、组件 native task 等长任务仍由其父 Temporal Workflow 承接，不另建“模型调用 Workflow” | 同左；服务内部模型调用是其 native execution 的一部分 |
| Capacity/Quota/Billing | Gateway rate-limit 管运行保护；父 action 负责 entitlement/credit/严格保留。原始 request log 不入账；durable Gateway usage 按稳定 ID 去重写入 OpenMeter，OpenMeter 才是 committed usage/billing 权威 | 父 action 负责 entitlement/credit；经 Adapter Protocol 上报的 usage 作为已登记 meter 的 actual source，按稳定 ID 去重写入 OpenMeter；无可证明上界时不得标成 `STRICT_RESERVATION` |
| Operation Audit | 记录 route、gateway identity、trace ID、request-log ID、provider/model、status、tokens/cost、OpenMeter event ID；不复制 prompt/response body | 记录 binding/generation、`model_call_mode`、operation、上报 usage 的 evidence ID 与 OpenMeter event ID；不复制 prompt/response body |
| Business Observability | AgentGateway log 提供请求状态/model/token/cost，父 Workflow/Action 提供业务状态，OpenMeter 提供 committed usage/cost；按 operation/request-log ref 关联且受 `read/audit` 过滤；业务能力 binding 的调用缺 `traceparent` 时按 gateway identity 解析出的 binding scope 入账 | 按标准 `traceparent`/operation 头与上报 usage 关联父 operation；关联头缺失时按上报身份解析出的 binding scope 入账，只降低到 operation 的归因精度，不阻断 binding，也不免于计量 |

这里的“继承父动作”只表示复用同一个 `operation_id/correlation_id`；授权、quota 和运行状态仍在每个尚未发生的外部副作用前刷新。AgentGateway 原始请求日志只证明已成功持久化的模型调用观测，不证明调用全集；SS-AGW-USAGE 闭合后的 durable usage 才证明可结算消耗。Platform AuditEvent 证明谁在什么 Tenant/Workspace 下为何获准调用。

### 2.2 SOURCE_BOUND_PROTOCOL surface 与 ProtocolSession 的八维闭环

| 维度 | `SOURCE_BOUND_PROTOCOL` surface / ProtocolSession |
|---|---|
| Tenant | target ContentReference、ProtocolSession、实现该能力的 ApplicationBinding 同 Tenant；在线编辑是 `FILE_STORAGE` 的条件能力，target 只能是声明 `online_editing=SUPPORTED` 的同一实现自己的 ContentReference，平台不在编辑器与文件存储之间建立数据通道（DD-90/103）；协议 body/query 不接受自报 scope |
| Workspace | `WorkspaceCapabilityDefault` 只解析该类别的默认 Resource 且可空，按 Workspace 级 binding 优先、其次 Tenant 级 binding 解析；目标 Resource/Asset 仍按当前 Workspace `discover/read/update/export` 校验；Channel 中出现引用不授予内容权限 |
| Authorization | launch 先 admission；组件协议的每个读写入口经 Core PEP 入站 service 边（Adapter Protocol `pep_check`）分别 fresh Check；组件自身 ACL 只继续收窄 |
| Approval | share/export、冲突覆盖、owner 变更按对应 ActionDefinition；批准固定 `native_revision`、参数 hash、owner/policy version，不批准后续任意版本 |
| Workflow | 正常 open/save 是同一 PROTOCOL action；审批、跨请求转换和结果不明才进入 Temporal（`ComponentTaskWorkflow(kind=PROTOCOL_SESSION_RECONCILE)`，经 Adapter Protocol `query_revision` 对账），不把 UI message 包成 Workflow；`expires_at` 前未到终态时，无写入迹象转 `EXPIRED`，有写入迹象转 `UNKNOWN` 并对账（`03` §3） |
| Capacity/Quota/Billing | surface 固定 `NATIVE`；OpenMeter 记录能力契约登记 meter 的受权读写字节；组件自身的容量降级以其协议证据呈现，BFF 不伪造 launch 前 capacity check |
| Operation Audit | 记录 ProtocolSession、actor、ContentReference、requested/admitted mode、native correlation、permission、result revision 和 usage；不记录 token、正文/光标流 |
| Business Observability | 以 operation→ProtocolSession→协议 evidence→result revision 关联 opening/read-only/dirty/saved/conflict/revoked/expired/unknown/failed；surface 关闭不冒充保存终态 |

提供在线编辑的 `FILE_STORAGE` 实现不因此获得内容 owner 或独立 Resource。ProtocolSession 只继承 target ContentReference 所指 Resource/Asset 的 HUMAN owner；组件协议入口是受控入口，仍走 scope、permission、quota、audit 和 terminal reconciliation（DD-30..34、DD-90/103）。内置参考实现如何满足本表见 `18`。

### 2.3 跨 Tenant 转移与 Tenant 生命周期的八维闭环

| 维度 | RESOURCE_EXPORT / RESOURCE_IMPORT | TENANT_LIFECYCLE |
|---|---|---|
| Tenant | 源/目标分属两个 session、ExecutionContext、operation 和 Workflow；package 是源 Tenant Asset，import 只创建目标 Tenant 新对象 | Tenant ID 与 TenantLifecycleSnapshot 全程不变；`SUSPENDING` 后禁止新对象 |
| Workspace | export 按源 Resource home Workspace，import 按目标 create Workspace；package 不携带可信 Workspace | 冻结全部 Workspace；恢复时逐 binding/membership 重新对账 |
| Authorization | export 检查 `export`；import 检查目标 `create`；禁止跨 Tenant relationship | 暂停与恢复由 Platform Catalog Tenant 的 platform-admin 发起（Check Catalog Tenant `manage`，DD-96）；删除由 Tenant admin 经受限会话从 `SUSPENDED` 发起；每个 native delete 前 fresh Check snapshot/version 与当前销毁权限 |
| Approval | 源 owner 批准导出；指定目标 owner 不是 importer 时由其批准 | Tenant admin + snapshot 中所有不同 HUMAN owner 按 ID/version digest 批准；任一 owner/version 变化使批准失效；已声明删除能力的子流程停在 `UNKNOWN` 时，只有该业务 Tenant 的 admin 经 owner 审批的 Governed Action 可处置为 `RETAINED_BY_DECISION`，不改写 binding 声明字段（DD-91） |
| Workflow | 两个 `ComponentTaskWorkflow` kind，不共享 history/context | `ComponentTaskWorkflow(kind=TENANT_LIFECYCLE)` + ExternalExecution；Temporal 是恢复/重试权威 |
| Capacity/Quota/Billing | 分别按 export/import adapter 字节、native task 与持久结果计量；不把一端 usage 记到另一 Tenant | 无新业务消费准入；已发生 usage 先结算，delete native operation 按已登记 meter 记录 |
| Operation Audit | 两 Tenant 各自记录 actor、owner decision、format/version/digest 和自身 native refs；不复制对方 ACL/ID | 记录 snapshot digest、owner 决策、首个不可逆 dispatch、每个 TenantDeleteSubprocess 的终态（含 `RETAINED_DECLARED`/`RETAINED_BY_DECISION` 处置与理由）、retained ref 与最终 tombstone |
| Business Observability | 每端只显示自身 Workflow/Asset/native/usage；digest 是唯一字节对应证据，不授权跨 Tenant drill-down | 工作台显示 suspended/restoring/deleting/error、owner waiting 和各组件对账缺口；未闭合不显示 deleted |

表中是不可绕过的合同，不表示当前 Catalog 已注册该 Action。当前 `RESOURCE_EXPORT/RESOURCE_IMPORT` 因全部 `transfer_formats=[]` 不暴露；Tenant 可进入 fail-closed 封闭态；delete Action 在注册时已存在的每个平台事实类别都有经验证的销毁处理器后注册，之后新增的平台核心 ResourceType 或平台存储面必须与其处理器同一构建登记；业务能力实现的删除能力不阻断它（DD-91/99）。

### 2.4 成员投影与组件停用的八维闭环

| 维度 | MEMBERSHIP_PROJECTION / MEMBERSHIP_REVOCATION | COMPONENT_DISABLE |
|---|---|---|
| Tenant | TenantMembership 的 Principal 与 Tenant 固定；WorkspaceMembership、Principal、Workspace 必须同 Tenant；不修改其他 Tenant 投影 | Binding、受影响 Resource/route/tool/native refs 均限定同 Tenant |
| Workspace | TenantMembership 固定 `workspace_id=NONE`；WorkspaceMembership 固定 Workspace ID/version；新建在对账前不 active，撤权在 `REVOKING` 即 fail closed | Workspace-scoped binding 固定该 Workspace；Tenant-scoped binding 固定受影响 Workspace 清单 |
| Authorization | Tenant/Workspace admin 按 target type 执行建立/撤权 permission；每个 SpiceDB/Buzz 副作用前 fresh Check membership version | Tenant/Workspace admin 的 component manage permission；每个撤投影/控制副作用前 fresh Check binding version |
| Approval | 固定 `confirmation_mode=EXPLICIT`、`approval_policy=NONE`；Approval 不能绕过 admin permission | 停用可逆且不删 native data，固定 `confirmation_mode=EXPLICIT`、`approval_policy=NONE`；native delete 属于另一 owner-approved Action |
| Workflow | `ComponentTaskWorkflow(kind=MEMBERSHIP_PROJECTION\|MEMBERSHIP_REVOCATION)`，input 固定 `TENANT\|WORKSPACE` target type、membership version 与投影 refs | `ComponentTaskWorkflow(kind=COMPONENT_DISABLE)`，input 固定 binding version 与 Schedule/relationship/route/tool/connection/native refs |
| Capacity/Quota/Billing | 管理投影固定 `capacity_policy=NONE`、`quota_policy=NONE`、`meters=[]`；不伪造业务消费 | 不准入新消费；已发生 usage 继续结算，只有已登记的 native control meter 才生成新 UsageEvent |
| Operation Audit | 记录 actor、membership/version、旧/新状态、SpiceDB ZedToken、Buzz event/query evidence 与失败投影 | 记录 actor、binding/version、受影响 refs digest、每次撤销/控制结果、retained ref 和 usage 对账 |
| Business Observability | operation→Workflow→SpiceDB/Buzz evidence；分开显示 fail-closed 与 projection-converged | operation→Workflow→各 projection/native evidence；分开显示 `DISABLING`、retained/unknown 与 `DISABLED`；`DISABLED` binding 下的 Resource 显示为保留只读 |

两类动作的领域合同与运行链均为 `DESIGN_DEFINED`（DD-69）。不允许用 Core 单次 state update、后台随机重试或组件本地任务替代 Temporal history。

### 2.5 前端一致性贯穿

主题与 i18n 不改变八维后端 admission，也不建立新的权威服务。它们通过 `03` 的 FrontendPresentationContext 与每个 release 的 FrontendPresentationContract 贯穿全部前端：Host-native 页面固定 `BUZZ_NATIVE`；获批准 remote module 固定 `HOST_API_REMOTE`，由 Host API 传入 resolved theme/locale并登记 namespaced `en/zh-CN` messages；`SOURCE_BOUND_PROTOCOL` surface 固定 `LAUNCH_MAPPED + theme/locale NEXT_LAUNCH`；无 Web surface 的组件固定 `NONE`；`NATIVE_PAGE` 也可声明 presentation `NONE`，保留原生页面主题与语言，支持时传递宿主偏好。未登记来源的 iframe、remote module 自带全局 CSS reset、Kailo 自有页面缺语言 catalog 和平台后端返回最终界面文案均禁止；不以原生后台有自己的偏好为由拒绝接入。主题偏好设备本地，locale 固定浏览器解析；一期不宣称跨设备主题同步或语言设置（REQ-08/11、SF-WEB-03、SF-MAT-04、DD-36/53/55）。

### 2.6 ComponentRelease 与两类 Binding 的八维闭环

| 维度 | Release 登记/批准 | PlatformProviderBinding | ApplicationBinding 与运行 |
|---|---|---|---|
| Tenant | 只在 Platform Catalog Tenant 中由 platform-admin Principal 操作 | 只属 Platform Catalog scope，不建业务 Resource | Binding、Resource、native scope、usage/audit 固定业务 Tenant |
| Workspace | release 不进入业务 Workspace | `workspace_id=NONE` | 明确 `NONE` 或一个同 Tenant Workspace，不接受 manifest 自报 |
| Authorization | Platform Catalog Tenant 上的 `manage`（登记、批准与撤销）；tenant schema 没有 `approve`，批准由另一位 Catalog Tenant admin 经 ApprovalWorkflow 决定（DD-100）；ComponentRelease 不是 SpiceDB object type，Check 对象固定为该 Catalog Tenant | platform admin 只能为 exact known port 绑 provider，不因此取得业务 Resource permission | Tenant/Workspace admin 只管自己 binding；Resource/Action/Tool 仍 fresh Check |
| Approval | 按 §2.8：release 批准由另一位 Catalog Tenant admin 经 ApprovalWorkflow 决定，批准时冻结来源标识（按 `admission_path`：source commit 或 vendor/artifact version/digest，DD-94(1)）、package/artifact、Host/Adapter Protocol 和治理合同；`VENDOR_MANAGED` 的数据位置声明由平台管理员批准 | 按 §2.8：首个 binding 由部署引导 0→1 写入（DD-108），之后的建立与升级由另一位 Catalog Tenant admin 批准；`COMPONENT_DISABLE` 按 §2.4 固定 NONE | 按 §2.8：建立与升级 `EXPLICIT`、模型调用模式切换需审批；`COMPONENT_DISABLE` 按 §2.4 固定 NONE；native delete/owner 变更是另一受审批 Action |
| Workflow | `ComponentTaskWorkflow(kind=COMPONENT_RELEASE)` | `COMPONENT_BINDING/DISABLE` + `binding_kind=PLATFORM_PROVIDER` | `COMPONENT_BINDING/DISABLE` + `binding_kind=APPLICATION`；native task 记 ExternalExecution |
| Capacity/Quota/Billing | catalog 管理显式 NONE；artifact 只按已登记 meter 计量 | provider 变更显式 NONE/CHECK；provider 调用继承父 operation 的治理 | 激活显式 NONE/CHECK；每个业务 Action 使用自己的 policy/meter |
| Operation Audit | 来源标识（source commit 或 vendor/artifact version）、manifest/package digest、批准、兼容裁决、revoke reason | port/binding/release/generation、切流/回滚和 retained calls | binding/release/generation、scope、native refs、投影切换和 retained execution |
| Business Observability | release 校验、批准与兼容状态 | operation→provider generation→service evidence→usage/cost | operation→application generation→adapter/native evidence→usage/cost |

ComponentRelease 只放声明与上界（`admission_path`、`implements[]`、`vendor/artifact_version` 或 `source_project/source_commit`、`data_store_isolation`、`data_location`、`allowed_model_call_modes[]`、`secret_schema`、`capability_declarations`），ApplicationBinding 只放上界内的选择（启用的 `capability_categories[]`、`model_call_mode`、`retain_on_tenant_delete`），字段以 `03` §3 为准。Platform Component 与 Application Component 都遵守此表。Platform release 只绑 Core 已知 `platform_port_key`；Application release 只在既有 canonical permission、Workflow kind 与扩展槽内登记 ResourceType/Action/Tool。任何一列未闭合时 release 不得 `APPROVED` 或 binding 不得 `ACTIVE`（DD-56/57/59/62）。

### 2.7 业务能力服务的八维治理

业务能力服务（预置种子类别 `FILE_STORAGE`、`KNOWLEDGE`、`DATA_QUERY` 以及平台管理员在 Catalog 运行时登记的类别，DD-102/103）不获得治理豁免。能力契约键（`<category>.<verb>@vN`）声明的 Action/Tool 与 Core 自有动作走同一条准入顺序；独立服务保留原生管理面并可嵌入客户端。下表管理列仅指 Kailo 接入管理及公共服务操作，不涵盖服务全部内部业务；服务自身的身份会话、数据库、工作流和计费不自动成为 Kailo 权威。调用平台公共服务时仍按本表准入，不能以原生页面绕过（DD-87 第 3 条、DD-88）。

| 维度 | 能力契约键的 Action/Tool | Kailo 接入与公共服务管理面 |
|---|---|---|
| Tenant | Resource、ApplicationBinding、usage 与 audit 固定业务 Tenant；实现只经 binding 的 native scope 映射，契约参数不携带 Tenant | 管理页只来自本 scope 授权后的 ComponentRuntimeProjection 快照；模块不获得跨 Tenant 数据或组件管理 credential |
| Workspace | 同一 Tenant 或 Workspace 的同一类别同时只有一个 active ApplicationBinding；Workspace 级 binding 在该 Workspace 内覆盖 Tenant 级 binding，ToolBinding 与 `WorkspaceCapabilityDefault` 都按 Workspace 级优先、其次 Tenant 级解析；`WorkspaceCapabilityDefault` 可空，不是 Workspace `ACTIVE` 的前提 | Workspace-scoped binding 只在该 Workspace 管理；Tenant-scoped binding 按 Tenant admin scope 管理 |
| Authorization | 契约键映射到固定 SpiceDB permission，dispatch 前 fresh Check；Agent 还要经 Delegation/ToolBinding；实现自身 ACL 只继续收窄 | 管理操作是 Governed Action，经 BFF 语义 API 重做 session、scope 与 SpiceDB；前端代码不是授权边界 |
| Approval | ActionDefinition、ApprovalPolicy、DelegationScope 只引用契约键，不引用产品名；切换实现不改变已冻结的审批参数语义，但以旧 binding Resource/Tool 为 target 的 DelegationScope 随旧 binding `DISABLED` 失效，需重新授予 | binding 启用/升级、类别内切换实现（新建 binding、旧 binding 转 `DISABLED` 只读保留）、`model_call_mode` 切换、数据源连接器授权（DD-89 的 `reader` 关系，发起者须对来源持有 `share`、对接收方 Resource 持有 `update`）按对应 ActionDefinition 审批；服务读取边的每批读取不再审批 |
| Workflow | 同请求完成的动作为 SYNC；native task 进入 `ComponentTaskWorkflow` + ExternalExecution；cancel/observe/heartbeat 只使用能力契约与 manifest 声明、经一致性套件验证的能力 | `COMPONENT_BINDING`/`COMPONENT_DISABLE`；平台不为跨服务同步建立 Workflow 或 Schedule |
| Capacity/Quota/Billing | 实现 runtime 固定 `capacity=NATIVE`；meter 来自能力契约声明；模型调用按 §2.1 的 binding 模式计量 | 管理动作显式 `NONE/CHECK`；不伪造业务消费 |
| Operation Audit | 记录契约键与版本、实现 binding/release/generation、native refs 与 usage；不记录正文 | 记录 actor、binding/generation、配置 digest、授权与凭据变化 |
| Business Observability | operation→application generation→adapter/native evidence→usage/cost | 管理动作进入同一业务操作时间线，按 `read/audit` 过滤 |

实现缺少某项声明能力时按声明收敛，例如不支持 cancel 的实现其 ExternalExecution 取消结果固定 `UNSUPPORTED`，不支持 native 删除的实现在准入时声明 `retain_on_tenant_delete`（DD-91）。实现的接缝缺口只阻断其 ComponentRelease `APPROVED` 或 ApplicationBinding `ACTIVE`，不阻断平台门禁。

## 3. Tenant、Workspace 与认证

- AgentGateway Browser OIDC 是固定认证接入面，支持任意满足 discovery/issuer/JWKS 的 OIDC Provider；登录、cookie session 与本地 cookie logout 均为上游能力（SF-AGW-10）。Keycloak 仅是默认 issuer 选择，不声明其内部行为。claims→BFF 投影与 logout 后的 Core PlatformSession/BFF stream 协同撤销为 SS-AGW-OIDC 的 `ADAPTER_REQUIRED`；生产 credential 按 DD-70/71 托管于 OpenBao 并投递。
- IdP claim 只完成 HumanIdentity 认证；TenantMembership 与 SpiceDB relationship 决定业务权限。
- 用户与 Agent 不持有 SpiceDB、Temporal、OpenMeter 或 AgentGateway admin 凭据。Core/Worker 分别使用 SF-SPZ-03、SF-TMP-06、SS-OMT-AUTH、SS-AGW-ADMIN 的 service authentication；native service role 不能替代用户/Agent 的 SpiceDB Check（DD-37）。OpenMeter 和 AgentGateway 的接缝未闭合前，其管理 API 不得进入 active 运行拓扑。
- scope 只由 Core 从 session、route、Resource 和 ApplicationBinding 构造；PlatformProviderBinding 只由 Platform Port Router 按 exact port/generation 解析。浏览器、prompt、Agent 参数与 callback 不是 scope 权威。
- Workspace scope 在任何 Resource/Asset permission 之前先检查 Workspace `ACTIVE`。HUMAN 要求 active WorkspaceMembership 或 fresh workspace `manage`；AGENT 要求 active Installation/Principal、workspace `discover`、Buzz roster 与 ChannelAgentBinding。owner/Resource permission 不替代此检查。Workspace 暂停/恢复 Action 从 Tenant scope 执行（DD-46/50）。
- 组件不必原生支持 Tenant/Workspace；每个 binding 必须选择 `03` 的一种已证明隔离模式，无绑定不调用。
- UI 切换 scope 只切换 session context、stream、navigation 和缓存；已创建 Workflow、Resource、AgentInvocation 不随 UI 迁移。

## 4. Authorization、owner 与 Delegation

SpiceDB 固定 schema 和 consistency 规则以 `03` 为权威。Resource/Asset 业务 owner 事实在 Core，关系投影在 SpiceDB；两者不一致时 owner-only 高风险动作 fail closed。

Agent 最终允许集合为：

```text
AgentPrincipal permission
∩ grantor 当前可委托 permission
∩ DelegationScope/有效期/使用次数
∩ active AgentInstallation/AgentVersion/ChannelAgentBinding
∩ SkillVersion/ToolBinding/LLM Route binding
∩ ResultExposurePolicy
```

- Agent/service 只能是 producer，不能成为 Resource/Asset accountable owner。
- `consume` 仅允许收窄的 answer/citation/aggregate/derived Asset；原文、download、原始查询结果行、数据模型定义需要 `read/export`。
- DelegationScope 不允许省略 action 后形成通配：既有对象固定 target ID；创建固定 Grant Workspace。`max_uses` 在首次 dispatch 以 operation 唯一消费。ResultExposurePolicy 只收窄 Tool output，不能把 `consume` 提升为 `read/export`（DD-49）。
- RoleTemplate 只把角色名展开为 SpiceDB relationships，不建立第二授权引擎。
- owner transfer 经 ActionExecution/ApprovalWorkflow；Core owner 事实与 SpiceDB owner 关系闭合前，新旧 owner 都不可执行 owner-only 高风险动作。
- AgentVersion 的工具、Skill 和模型引用只是 requested 声明；只有 `17` 的 EffectiveAgentConfig 求交结果才能进入 runtime。版本发布、Workspace 安装、Channel 触发和实际动作是四个不同准入点，前一步成功不授权后一步。

## 5. Approval 与 Workflow

| 类型 | 边界 | 结果 |
|---|---|---|
| Admission Approval | 主业务 Workflow 之前 | 批准后 fresh recheck，再启动主 Workflow |
| Step Approval | 已运行 Workflow 的某个副作用之前 | child ActionExecution + child ApprovalWorkflow，父 Workflow 等结果 |

一次批准只绑定 `action_execution_id + parameter_hash + policy_version`。参数、owner、approver 资格、permission 或 Delegation 改变使旧批准失效。Temporal 不替换组件 native task，只以 ExternalExecution 记录和控制能力契约与 manifest 声明、并经一致性套件验证的能力（DD-11/88）。

ApprovalPolicy 只保存静态 `role_requirements + owner_requirement + self_approval + expiry`。每次请求把 ActionDefinition version、target、parameter hash、全部受影响 owner ID/version 与角色要求冻结进 ApprovalWorkflow input；ApprovalProjection 仅由 history 生成。所有 owner 与角色要求分别满足、没有有效 DENY、且消费前 fresh Admission 通过，才允许本次 ActionExecution 一次性进入主动作（DD-47）。

Approval 与持久 Workflow 只由 DD-69 的 Application Worker 承接；实现前不降级成 Core 自建状态机、组件 task 或 Buzz workflow 表。Buzz 自带 workflow 在 Kailo 部署中关闭（DD-106），用户可见的自动化由 Temporal 承接（DD-107，§2.9）。

## 6. Capacity、Quota、Usage 与 Billing

ActionDefinition 只能选：

| 策略 | 含义 |
|---|---|
| `capacity=NONE` | 无平台可控 slot |
| `capacity=PLATFORM_SLOT` | 只用于平台自有 Agent runtime（Codex）取 CapacityLease；业务能力实现的 runtime 不占平台 slot |
| `capacity=NATIVE` | 保留组件真实 health/rate-limit/job 结果，不伪造 lease |
| `quota=NONE` | 不查商业额度，不创建空 meter |
| `quota=CHECK` | 执行前查 entitlement/credit，执行后发实际 usage |
| `quota=STRICT_RESERVATION` | 以可证明最坏上界创建短期 QuotaReservation，防止 202 异步计量窗口并发超卖 |

OpenMeter 保存 plan、entitlement、credit、committed usage 和 billing（SF-OMT-01）；Core 的 QuotaReservation 只保存未结算上界，不复制这些总账（DD-07）。无法给出最坏上界的动作不得使用严格准入。

OpenMeter event ingest 是异步 202，且 ingest/sink dedupe 默认均关闭（SF-OMT-02/03）。因此绑定必须启用两层 durable dedupe，outbox 重试保持同一 `namespace + source + event.id + body`（SF-OMT-04，DD-08）。组件 native 结果可作为其已登记 meter 的 actual source。平台自有 Agent 与 `PLATFORM_LLM_ROUTE` 模式的模型调用只有 SS-AGW-USAGE 闭合后的 durable Gateway usage 才可作为 actual source；原始 request log 仅作观测；经网关路由的调用，调用方自报 token 不形成计费事件（SF-AGW-09、DD-21）。`SELF_MANAGED_MODEL` 模式不经网关，以服务经 Adapter Protocol 上报的 usage 作为已登记 meter 的 actual source，平台照常执行 Quota 与审计（DD-92）。服务读取边的每批读取在准入时做 Quota，来源方与接收方的 usage 都归属该批 operation（DD-89）。

OpenMeter 固定使用开源 server 的单一 default namespace；Tenant 以唯一 Customer 隔离，Workspace/Resource/Agent/operation 以归属该 Customer 的 subject keys/dimensions 表达（SF-OMT-05/06、DD-38）。Core 同时固定 namespace、customer 与 subject，不允许 Web、Agent 或组件自报其中任一值。

STRICT_RESERVATION 不是 OpenMeter 原生能力，也不宣称跨系统事务。它只在全部该 Tenant+subject+meter usage 都由 Core 产生且有最坏上界时启用；Core 按该键串行合并 OpenMeter committed credit、未结算 UsageEvent 和 active reservation。其他路径固定使用 CHECK 或拒绝 hard-limit action（DD-51）。

## 7. Operation Audit

AuditEvent 按 operation 追加，至少记录 initiator、实际 actor、scope、action/version、target、parameter hash、allow/deny、ZedToken/Delegation/Approval/Quota evidence、dispatch/native ref、result exposure、usage 与 terminal/revoke/reconcile。

- 外部副作用前必须持久 audit intent 与必要 outbox；拒绝也记录。
- 消息发送/编辑/删除、敏感读取/搜索、下载/导出、分享、成员与角色变更、owner/授权/委托变更、Agent/工具/模型调用、审批、Workflow 控制、组件配置和 quota/billing 调整都使用其 Governed Action 的审计策略。页面打开、菜单点击、滚动和 hover 不属于安全审计。
- Agent 代用户执行时 `initiator` 保留用户，`actor` 记录 AgentPrincipal；Delegation、ToolBinding、Approval、Gateway request-log 与最终 Buzz reply/native result 都作为 evidence refs，不能把行为归因给“系统”。
- Audit 不自建 hash-chain；Buzz event ID、Temporal workflow/run、SpiceDB ZedToken、OpenMeter event ID 和 native job ID 作为 evidence refs。
- Secret/private key、正文、完整 prompt/response、原始 SQL/结果行、AgentGateway raw body 不进 AuditEvent、Buzz event 或 Temporal history。
- Governed Action 的审计永远带 Tenant；`tenant_id=NONE` 只用于 OIDC callback 后、Tenant 解析前的认证/Session事件。EvidenceRef 是带 authority/type/version-or-digest/sensitivity 的稳定引用，查看时 fresh授权，不是可直接访问的 native URL（DD-52）。

## 8. 撤权与短期 token

```text
membership/relationship/delegation/binding revoke
→ Core/SpiceDB 对新动作立即拒绝
→ 关闭已知 BFF stream 和已知长连接
→ 停止 Web/Tool discovery
→ cancel waiting Approval; signal/cancel running Workflow
→ 保留已发生 side effect/usage/audit
```

ActionToken 不是可通用即时撤销的 capability：它只承载 DD-49 的固定 claims，已签发 token 依赖短过期、精确 audience、目标 PEP fresh check 和已知连接关闭收敛。不声称平台能从所有未知载体中“删除 token”。GAP-AGW-01 对长存 Codex MCP client 的限制保持显式。
