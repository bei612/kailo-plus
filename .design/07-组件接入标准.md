# 组件接入标准

本文件是平台级组件、应用级组件、Component Package、Component Host 和 Component Adapter Protocol 的设计权威。Component Host 由 Buzz Web 与 Buzz Desktop 两端承载同一份契约：两端是两个上游代码库，只共享 Kailo 自有的 TypeScript 平台包与契约生成物，各自以 SS-WEB-COMPONENT-HOST、SS-DSK-COMPONENT-HOST 接入；Desktop 不执行 `REMOTE_MODULE`（SF-DSK-03）。Buzz Mobile 不是组件宿主（REQ-11/21、DD-74）。外部组件独立运行、独立管理，保留原生后台与直接访问入口；可复用平台公共服务并嵌入管理页面，但不取得 Kailo 的 Tenant、Workspace、owner、授权、审批、Workflow、Quota/Billing 或 Audit 权威。

本文同时是能力类别与版本化能力契约的接入权威（DD-88）。平台核心（Core/BFF、Application Worker、Buzz Relay 与三端 Client Surface、Codex、AgentGateway、SpiceDB、Temporal、OpenBao、OpenMeter）以 Platform Component 与平台自有模块强集成；业务能力服务（文件存储、在线文档编辑、知识库、数据查询及以后同类）只以 Application Component 按能力契约接入，数据平面解耦、可缺席、可替换，只经 Catalog/ApplicationBinding 配置与 Adapter Protocol、MCP 等协议集成（DD-87）。零业务能力 binding 时，本文全部平台机制仍成立。本文的 binding、治理与收敛合同只覆盖 Kailo 接入及公共服务调用，不要求平台接管外部服务的全部内部业务、任务或部署。工具实际通过 AgentGateway 注册、发现与调用；Core Catalog 与 ToolBinding 仅为治理元数据和投影引用，不是第二工具注册中心。

## 1. Buzz 的确定起点

承载端当前没有运行时组件系统：routeTree、router、导航、`WorkspaceTool` 和内容分支均是构建期静态源码，i18n catalog 也是静态的（Web：SF-WEB-02、SS-WEB-COMPONENT-HOST；Desktop：`routes.ts` 显式列举生成的静态 routeTree 与 `AppSidebar` 的固定 props，SS-DSK-COMPONENT-HOST）。因此运行时注册不是 Buzz 上游现成能力，而是一次性 Buzz 二开后形成的固定产品边界。

Mattermost 只证明四个可复用机制：manifest、active manifest 快照、同源 script registration、版本 reconcile/unload（SF-MAT-01/03）；其事件路径把 payload 当完整状态，是 §4.2 明确不采用的反例（SF-MAT-06）。不复用其全局 enable、完整 Redux store、宽 PluginAPI 或本机 executable plugin：这些边界分别不满足 Tenant/Workspace 绑定、最小权限和独立服务交付（SF-MAT-02/04/05）。

一次性二开后的稳定结构为：

```text
Component Host（Buzz Web + Buzz Desktop）
        ↕ authorized runtime projection
Platform Core Catalog
        ├─ Platform Port Router → PlatformProviderBinding → platform service
        └─ Application Adapter Dispatcher → ApplicationBinding → adapter → native app
```

兼容发布在后端为独立远程服务、无后端或只引用当前主体已编译 key 时，可在运行时注册、升级、回滚和停用，无需重发 Core 或任一承载端；唯一例外是 release 引入部署级许可集合中尚未包含的 editor origin（DD-95）：Web 重启静态服务；Desktop 由 BFF 运行时下发新的许可集合，不需要发布新包（DD-104、§9）。这不等于组件零交付：组件后端服务仍独立部署，Web artifact 仍需交付、校验和批准；新 embedded/internal 代码仍须重发对应主体（DD-59/64）。

## 2. 两类组件与两种绑定

| 分类 | 作用 | 绑定 | 当前对应 |
|---|---|---|---|
| Platform Component | 实现 Core 已知的治理与协作平台端口；属于平台核心，不可缺席 | `PlatformProviderBinding` | AgentGateway（`IDENTITY_EDGE` 与 `AI_GATEWAY` 两个 Definition）、SpiceDB（`AUTHORIZATION`）、Temporal（`APPROVAL_WORKFLOW`）、OpenMeter（`METERING_BILLING`）、OpenBao（`SECRET_STORE`）、Buzz Relay（`COLLABORATION_RELAY`） |
| Application Component | 实现某能力类别契约、为人与 Agent 提供数据或工具的业务能力服务；可缺席、可替换 | `ApplicationBinding` | 一期内置参考实现：`FILE_STORAGE`（Cells 与 ONLYOFFICE 作为一个能力组件，声明 `online_editing=SUPPORTED`，DD-103）、`KNOWLEDGE`（WeKnora）、`DATA_QUERY`（Wren），见 `08` |

平台端口只有治理与协作类：`IDENTITY_EDGE`、`AI_GATEWAY`、`AUTHORIZATION`、`APPROVAL_WORKFLOW`、`METERING_BILLING`、`SECRET_STORE`、`COLLABORATION_RELAY`，外加 Core 自身的 `CORE_INTERNAL`。业务能力不以平台端口表达；跨服务数据同步不是平台端口（DD-89）。

### 2.1 Platform Component

Platform release 只能实现 Core 已编译的 `platform_port_key`。`PlatformProviderBinding` 属于 Platform Catalog scope，固定 port、release、provider target、config/secret reference 和 active generation。Provider target 只能是独立远程服务、当前主体已编译 driver key 或 Core internal key。它不属于业务 Tenant/Workspace，不挂到 Resource/Asset，不拥有业务数据。

每个 port 同时只选一个 active provider generation。新调用解析 active generation；已开始的 ActionExecution、Workflow 和 ExternalExecution 固定旧 generation 到终态。同一 port 下的兼容远程 provider 可运行时切换；切换指同一端口已登记产品的实例、版本或配置，平台核心组件产品本身不可替换（DD-64/87）。Embedded/internal binding 只能选当前 Core/Worker registry 已有代码；新 driver 或 driver 代码升级必须重发 Core/Worker（DD-64）。`EMBEDDED_DRIVER` 只属于平台自身，业务能力服务不得以嵌入式 driver 接入（DD-87）。新 platform port、新 canonical permission 或新 Workflow 语义也必须改变 Core 契约。

### 2.2 Application Component

Application release 以 `implements[category@version]` 声明实现的能力类别契约，并在该契约的标准 ResourceType 族、Action/Tool 契约键和宿主扩展槽内登记业务能力。`ApplicationBinding` 属于业务 Tenant，可进一步限定 Workspace，固定 release、在 release `implements[]` 内实际启用的能力类别（`capability_categories[]`）、adapter service 或协议端点、native instance/scope、isolation mode、`model_call_mode`、`retain_on_tenant_delete`、config/secret reference 和 active generation。release 放声明与上界，binding 只放上界内的选择：数据存储隔离与数据位置只由 release 声明，binding 的 `model_call_mode` 必须属于 release 的 `allowed_model_call_modes[]`，`retain_on_tenant_delete` 必须与 release 的 Tenant 删除声明一致（`03` §3）。应用 Resource 是 Core 对外部对象的授权引用，只经 `resource.create` 首次登记：同 Tenant active ApplicationBinding、HUMAN accountable owner、Core 事实与 SpiceDB relationship 沿原准入。已有对象以冻结 binding/native scope 的原生协议证据或可信运行投递事实核实；裸 native ID 不自动 `ACTIVE`，不能证明归属则登记能力未闭合。同一绑定/引用复用原 Resource，不重复建立 owner/ACL；未知只核原引用，不发 CREATE。只有明确支持的 `REMOTE_ADAPTER` 原生创建才执行原 `resolve_native_scope(CREATE/LOOKUP)` 流程（DD-98）；平台 owner 不改变服务自己的 owner/ACL 或授予上游 admin。binding 转 `DISABLED` 后其 Resource 保留只读（§2.4）。

上游应用不必原生具有 Kailo Tenant/Workspace。Adapter 必须根据固定 binding 把平台 scope 解析为该实现已证明的 native tenant、namespace、resource filter、dedicated instance 或 resource instance：内置参考实现以 `02` 的 SOURCE_FACT/SOURCE_SEAM 证明，外部实现以准入时声明、经一致性测试套件验证并由平台管理员批准的隔离模式证明（§2.5）。解析失败必须拒绝，不得回退到默认实例。

### 2.3 共享对象与不可混合的对象

```text
ComponentDefinition       稳定组件类型（PLATFORM | APPLICATION）
  └─ ComponentRelease    不可变契约和 artifact 快照
       └─ ComponentPackage  manifest 与 Web artifact 交付包

PlatformProviderBinding  只引用 PLATFORM release
ApplicationBinding       只引用 APPLICATION release
ComponentRuntimeProjection(binding kind + id + release + generation)
```

`ComponentBinding` 只是文档中对两种 binding 的总称，不是一张混合两种 scope 的业务表。

### 2.4 能力类别与能力契约

业务能力以能力类别加版本化能力契约接入（DD-88）。能力类别与契约是 Platform Catalog 的运行时数据（DD-102）：下表三类是随平台构建交付的预置种子，Catalog 启用时由部署引导一次性登记为 `ACTIVE`（DD-108）；只使用固定 permission 与通用 Resource/Action/Tool 语义的新类别或新契约版本由平台管理员经受审批的 Governed Action 登记，不需要发版；需要新 ProtocolSession kind、Workflow kind、能力声明、前端交付模式或 permission 的类别只能随 Core 发版加入。预置种子为：

| 能力类别 | 为人与 Agent 提供 | `type_key` 命名空间 |
|---|---|---|
| `FILE_STORAGE` | 文件目录、字节、版本与分享；实现可另声明条件能力 `online_editing=SUPPORTED`，对本实现自己的 ContentReference 提供查看与协同编辑，以 DocumentLaunchDescriptor 启动（DD-90/95/103） | `file_storage.<kind>` |
| `KNOWLEDGE` | 企业知识的检索、问答与受控导入 | `knowledge.<kind>` |
| `DATA_QUERY` | 受控数据查询（text2sql 等） | `data_query.<kind>` |

每份能力契约由平台定义，内容固定为：

- 标准 ResourceType 族与 `type_key` 命名空间 `<category>.<kind>`，`type_key` 不含产品名；
- Action/Tool 契约键 `<category>.<verb>@vN`（如 `knowledge.search@v1`）及其参数/结果 schema；
- 每个契约键到固定 SpiceDB permission（`discover/read/consume/export/update/execute/manage/audit` 等 `03` 已有 canonical permission）的映射；
- ContentReference 语义：`native_object_ref`、`native_revision` 与授权目标的判定规则（DD-90）；返回 ContentReference 的结果（如 `KNOWLEDGE` 检索的 citation）由实现的 adapter 按契约直接给出，BFF 只做授权与解析，不调用实现的原生接口重建；
- 协议会话类能力的启动描述：`file_storage.v1` 为声明 `online_editing=SUPPORTED` 的实现定义与产品无关的 `DocumentLaunchDescriptor(method[GET|POST], action_url, form_fields{string→string}, editor_origin, expires_at)`。launch 请求携带 Buzz 已解析的 theme 与 locale（主题语义值与 `en/zh-CN`），descriptor 由目标 ContentReference 所属 ApplicationBinding 的 adapter 生成，实现私有的参数映射、协议发现与 action 选择（如 WOPI discovery）全在 adapter 内；Core 只校验 `editor_origin` 属于该 release 登记的 `editor_origins[]` 且等于该 binding 固定的实例 origin（release 以 host 通配登记时也逐 binding 精确比对）、`action_url` 的 origin 等于 `editor_origin`、字段均为字符串且未过期，再原样下发（DD-95/103）；
- 观测、计量、取消、revision 查询、版本化模型（`versioned_model`）、在线编辑（`online_editing`）、服务读取边（`read_edge`，§8.2）与 Tenant 删除能力声明，缺失字段不等于 `NONE` 或 `UNSUPPORTED`；revision 查询指按 `native_object_ref` 查询当前 revision（Adapter Protocol `query_revision`），`FILE_STORAGE` 实现未声明 `revision_query=SUPPORTED` 时不得声明 `online_editing=SUPPORTED`（DD-90/103）；
- 一致性测试套件：在 Adapter Protocol 或所声明的标准协议线上验证契约语义、终态、幂等、取消、错误映射、redaction 与 ContentReference 往返。

预置种子各类别的 v1 契约键与 permission 映射固定如下；种子的参数与结果 schema、错误映射和一致性套件以 `contracts/adapter/<category>.v1` 为唯一权威。运行时登记的契约，其 schema 与一致性套件测试向量以 digest 固定在 Catalog 中，由平台发布的通用一致性套件运行器执行（DD-102）。内置参考实现对这些键的逐项映射在 `08`：

| 能力类别 | v1 契约键 → permission |
|---|---|
| `FILE_STORAGE` | `file_storage.list@v1`→`discover`；`file_storage.read@v1`、`file_storage.list_revisions@v1`→`read`；`file_storage.export@v1`→`export`；`file_storage.write@v1`→`update`；`file_storage.delete@v1`→`delete`；`file_storage.share@v1`→`share`；条件键 `file_storage.open_view@v1`→目标 ContentReference 的 `read`、`file_storage.open_edit@v1`→`update`（会话内下载、复制、打印→`export`），仅 `online_editing=SUPPORTED` 的实现实现并暴露，ProtocolSession kind 为 `file_storage.edit_session`（DD-103） |
| `KNOWLEDGE` | `knowledge.search@v1`→`consume`；`knowledge.read@v1`→`read`；`knowledge.export@v1`→`export`；`knowledge.ingest@v1`→`update`；`knowledge.delete@v1`→`delete` |
| `DATA_QUERY` | `data_query.query@v1`、`data_query.dry_run@v1`→`execute`；`data_query.describe@v1`→`read`；条件键 `data_query.publish_version@v1`→`update`，仅 `versioned_model=SUPPORTED` 的实现实现并暴露，经 `CAPABILITY_VERSION_PUBLISH` 收敛该版本的运行时与工具端点（DD-90） |

契约键的新增、删除或语义变化只能以新契约版本（`@v2`）发布，旧版本在兼容窗口内继续有效；契约键分必选键与条件键：条件键只随实现在 release 中声明 `SUPPORTED` 的对应能力（如 `versioned_model`）一起实现，未声明即不实现、不暴露；实现声明 `implements[category@version]` 时必须实现该版本的全部必选键，以及其已声明能力所对应的条件键，不能只实现子集（DD-88）。上表未标“条件键”的均为必选键。

ComponentRelease 以 `implements[category@version]` 声明实现。`action_key`、ToolDefinition、DelegationScope、ApprovalPolicy 与 AgentVersion 能力需求只引用契约键；`component_type_key` 只记实现来源，不进入任何授权、审批或 Agent 能力判定。产品专属扩展只能位于该组件自身命名空间 `<category>.<kind>` 之下的扩展键内，不得改变契约键的语义、permission 映射或结果形状，也不得被 AgentVersion 作为能力需求引用。

同一 Tenant 或同一 Workspace 的同一能力类别同时只有一个 active ApplicationBinding。Workspace 级 binding 在该 Workspace 内覆盖 Tenant 级 binding，Workspace 未绑定该类别时解析到 Tenant 级 binding；ToolBinding 与 WorkspaceCapabilityDefault 都按这一顺序解析（DD-88）。

ComponentRelease 只声明门禁已闭合的能力类别，未闭合的类别在后续 release 中加入，不存在按类别部分激活的 binding（DD-88）。类别内切换实现是「新建 binding、旧 binding 转 `DISABLED` 只读保留」，不是在旧 binding 上换 generation：新 binding 经 `COMPONENT_BINDING` 对账到 `ACTIVE` 接管契约键，旧 binding 经 `COMPONENT_DISABLE` 转 `DISABLED`，已开始的执行固定旧 binding/generation 到终态。旧 binding 下的 Resource 转为保留只读，只可 discover 元数据、不可发起新动作；指向旧 binding Resource 的 WorkspaceCapabilityDefault 清空待重新选择；以旧 Resource 或旧 Tool 为 target 的 DelegationScope 与 ToolBinding 失效，ToolBinding 按契约键重绑到新 binding，DelegationScope 由 grantor 重新授予，AgentVersion 不重发；历史 ContentReference（含 `mem/*` citation）保留原值，解析为不可用而不报成功或失败（DD-88/92）。Workspace 在某类别下的默认 Resource 由可空的 `WorkspaceCapabilityDefault(workspace_id, category, resource_id)` 记录，它不是 Workspace `ACTIVE` 的前提（DD-90）。

平台自有能力（记忆、Buzz 消息、任务、审批等）的工具来源为 `PLATFORM_NATIVE`，不依赖任何 ApplicationBinding：它们由 Core 自托管的 Streamable HTTP MCP 端点提供，Core 经 SS-AGW-ADMIN 把该端点登记为 AgentGateway 的 MCP target，调用同样经会话级 bearer 与 ExtMcp PEP，不需要 adapter、Adapter Protocol 或 ActionToken（DD-105）；业务能力工具来源为 `APPLICATION`，经 MCP 与 AgentGateway ExtMcp PEP 调用。Workspace 内某契约键没有 active 实现时，该工具 effective 状态为 `NO_PROVIDER`，AgentInstallation 仍可 `ACTIVE`（DD-92）。

### 2.5 准入路径

ComponentRelease 登记 `APPROVED` 只有两条路径（DD-88）：

| 路径 | 适用 | 准入条件 |
|---|---|---|
| 内置参考实现 | 一期随平台交付的业务能力实现（`08`） | `02` 的 SOURCE_FACT/SOURCE_SEAM 证明 native scope、API、状态与治理映射，加该能力契约的一致性测试套件全过 |
| 外部实现 | 第三方或自研实现，含闭源与 SaaS | 能力契约、一致性测试套件全过、平台管理员批准，并在 release 中以 `vendor`、`artifact_version` 与 artifact digest 标识来源、声明隔离模式与数据位置；`source_commit` 可空，不要求 `.references` 中存在其源码（DD-94(1)） |

两条路径都经 `ComponentTaskWorkflow(kind=COMPONENT_RELEASE)` 与 ApprovalWorkflow，按实际接入范围校验治理、业务可观测性与隔离合同；主题/i18n 的宿主强制合同适用于 Kailo 自有页面与同窗口 module，不要求独立原生后台重写。外部实现声明的隔离模式与数据位置写入 release 的 governance 段并固定 digest；声明与一致性套件结果不符即拒绝。平台核心的 Platform Component 不走外部实现路径，仍以源码证据与 Core 已编译端口准入。本文与 `03`–`06` 中凡要求“固定 source commit/source baseline”的准入、Workflow input 与运行时注册条件，都按 `admission_path` 的来源标识解读，外部实现不因无源码被拒（DD-94(1)）。

业务能力实现的 `REMOTE_ADAPTER` 运行体一律部署在平台运维域内（`adapter_build_ref` 固定 digest、独立凭据、独立私有数据网络），外部与 SaaS 实现也不例外，其服务端点只是 adapter 的上游。ActionToken 验签公钥与 `secret_schema` 声明的凭据（含供应商签发给该 Tenant 的 API 凭据）统一经 OpenBao Agent 投递到 adapter 运行体，与 AgentGateway 的做法相同，不新增公钥或凭据分发通道。以 `PROTOCOL_PEER` 接入的实现不接收 ActionToken，不能作为服务读取边（§8.2）的来源方（DD-94）。

### 2.6 数据存储与凭据隔离

平台核心每个服务与每个自托管的业务能力实现各自使用独立数据库实例，至少独立 database，并使用独立凭据与独立私有数据网络；禁止共用 schema 与跨库访问。外部托管（SaaS）实现的数据位于供应商环境、与平台及其他实现不共享存储，其 adapter 运行体仍使用独立凭据与独立私有数据网络（DD-93/94）。约束固定为：

- Core 不持有任何业务能力服务的数据库凭据；平台对业务数据的一切访问只经能力契约暴露的 Resource/Action/Tool。
- 组件状态目录不放在 Core/Worker 运行体内；业务能力实现的增量状态、索引与缓存属于该实现自己的运行体与存储。
- 两个业务能力服务之间不直连数据面、不共用数据库；跨服务数据获取只按 §8.2。
- 接入凭据及明确选择由平台托管的密钥由 release manifest 声明 `secret_schema`：`secret_key`、类型、长度或格式、轮换类别 `SERVICE_CREDENTIAL|DATA_KEY`、投递方式、是否需重启。Core 按通用 schema 校验并经 OpenBao 托管与投递，不内置任何产品的密钥语义；未交由平台托管的服务内部密钥由服务独立管理；`DATA_KEY` 轮换后已存密文的重加密是该服务自己的数据平面职责，平台只按声明的轮换类别投递新版本；服务经 Adapter Protocol `report_rekey` 回报重加密完成后，平台才记录结果并允许销毁旧版本；未回报或结果不明时旧版本保留、该 binding 进入对账并计入度量，直到回报或平台管理员经审计处置（DD-93）。
- release 声明 `data_store_isolation[DEDICATED_INSTANCE|DEDICATED_DATABASE|VENDOR_MANAGED]` 与 `data_location`，随 release digest 固定，供平台管理员批准时核对；`VENDOR_MANAGED` 只用于外部托管（SaaS）实现，必须同时声明数据位置并经平台管理员批准（2026-09-28 按 DD-93 修订）；缺失任一声明的 release 不得 `APPROVED`。binding 不另存这两项，一律以其 pin 的 release 为准。

## 3. Component Package 与不可变 Release

Component Package 包含：

```text
manifest
manifest digest
package digest
WebArtifactSet[path, media_type, digest][]
backend_delivery = EXTERNAL_SERVICE | BUILD_BOUND | NONE
```

Package 不包含 Core 要启动的本机 executable，也不携带 credential、native access token 或临时 URL。`EXTERNAL_SERVICE` 只表示该 release 要求独立服务，服务地址属于 binding；`BUILD_BOUND` 表示可执行代码已与主体构建绑定，package 只能引用当前 registry 已有 key，且只允许 PLATFORM release 使用；APPLICATION release 只能是 `EXTERNAL_SERVICE` 或 `NONE`（SF-MAT-05、DD-58/64/87）。

`WebArtifactSet` 的 canonical 清单整体计算 `web_artifact_set_digest`。Catalog 把每个文件固定服务于 `/component-artifacts/<release_id>/<sha256>/<path>`；entry 的静态相对 import 必须解析在同一 release 根内，绝对外域、父目录越界或未列入 artifact set 的 import 一律拒绝登记。该路径位于 Buzz Web Service Worker 的 `/app/` scope 外；snapshot endpoint 固定 `Cache-Control: no-store`。Buzz Web Caddy 只提供静态 `/app/*`，单一公开 origin 由 AgentGateway 路径前缀路由组合：`/app/*` 到 Buzz Web 静态站、`/api/*` 到 BFF、`/component-artifacts/*` 到 Core artifact handler（SF-WEB-07/08、DD-60）。

Release manifest 必须完整声明：

```text
identity
  component_type_key / release_id / semantic version / manifest_schema_version
  admission_path[BUILTIN_REFERENCE|EXTERNAL]
  BUILTIN_REFERENCE: source_project / exact source_commit（必填）
  EXTERNAL: vendor / artifact_version（必填）；source_commit 可空

compatibility
  platform_port_key | NONE
  implements[category@version] | NONE
  host_api_range | NONE
  adapter_protocol_range | NONE

delivery
  FrontendDelivery（SOURCE_BOUND_PROTOCOL 含 editor_origins[] / launch_descriptor_schema_version；NATIVE_PAGE 含 native_page_origins[]）
  ExecutionConnector
  ComponentPackage digest + WebArtifactSet

domain
  ResourceTypeDefinition[] / ActionDefinition[] / ToolDefinition[]
  target_resource_type_keys[] for capability components

governance
  isolation / call identity
  data_store_isolation / data_location / secret_schema
  capability_declarations[cancel / observe / meter / revision_query / versioned_model / tenant_delete | retain_on_tenant_delete]
  Approval / Workflow / Capacity / Quota / Meter / Audit contracts
  BusinessObservabilityContract
  IncrementalContract / LLMGatewayContract(allowed_model_call_modes[])
  native status / error / cancel / idempotency / reconcile mapping
  FrontendPresentationContract
```

manifest 只写声明与上界；binding 在其中的选择（启用的 `capability_categories[]`、`model_call_mode`、`retain_on_tenant_delete`）属于 ApplicationBinding，字段以 `03` §3 为准。

Release 一经 `APPROVED` 不原地修改。source commit 或外部 artifact version、schema、artifact bytes/digest、`implements[]`、Resource/Action/Tool、meter、redaction、隔离声明或兼容范围改变都生成新 release。能力进入 release 的证明按 §2.5 的准入路径：内置参考实现以 `02` 的 SOURCE_FACT/SOURCE_SEAM 和 adapter 契约证明，外部实现以能力契约一致性测试套件与平台管理员批准证明；两者都无法证明的能力不进入 release。

## 4. Component Host

### 4.1 固定宿主边界

Buzz Web 与 Buzz Desktop 是两个上游代码库，只共享 Kailo 自有的 TypeScript 平台包（Host API、surface registry、BFF 客户端与契约生成物），Component Host 的一次性变更边界按端分别由两条接缝定位（2026-09-28 按 DD-74 修订）：

| 承载端 | 接缝 | 一次性变更边界 | 可承载的 FrontendDelivery |
|---|---|---|---|
| Buzz Web（buzz-web `web/`） | SS-WEB-COMPONENT-HOST | 在静态 routeTree 中只增加一个 `/apps/$componentKey/$` catch-all route；从 `BuzzWebApp.Workspace` 提炼 index 与 app route 共用的 `WorkspaceShell`；用 surface registry 取代封闭 `WorkspaceTool` union 和硬编码内容分支；增加同源 loader、动态 i18n source 与同源内容寻址 artifact route | `HOST_NATIVE`、`REMOTE_MODULE`、`NATIVE_PAGE`、`SOURCE_BOUND_PROTOCOL` |
| Buzz Desktop（Buzz `desktop/`） | SS-DSK-COMPONENT-HOST | 在 `src/app/routes.ts` 显式登记固定 `route("/apps/$componentKey/$", …)`，随构建进入生成的 routeTree；`AppShell` 内容区以运行时 surface registry 按 BFF 快照挂载 surface；`AppSidebar` 的业务条目由快照生成，取代其固定 props 中的逐项入口（`useAppNavigation` 只是跳转函数集合） | `HOST_NATIVE`、隔离的 `NATIVE_PAGE`、`SOURCE_BOUND_PROTOCOL`；CSP 编译在签名包内，不执行 `REMOTE_MODULE` 运行时 script，对应入口显示确定状态并指向 Web（SF-DSK-03） |

两端共同的宿主规则：

- 导航、路由子路径、图标标识、文案 key 和排序由宿主根据 projection descriptor 渲染，不由 module 注入任意 router 或 DOM。
- 宿主保留登录、协作、审批、任务、治理、主题和 i18n 控制权。

一期扩展槽只有：

| Extension slot | 作用 | 宿主准入 |
|---|---|---|
| `MANAGEMENT_PAGE` | Platform/Tenant/Workspace 管理页及受控子路径 | descriptor scope + `discover/manage/audit` |
| `RESOURCE_VIEW` | Resource/Asset 详情、查询和动作 | Resource/Asset permission + ResultExposure |
| `CHAT_ATTACHMENT_ACTION` | 频道内的 Resource/ContentReference 打开与动作 | Workspace scope + target permission |

新 slot 是 Host API 变更，不能通过 manifest 动态创建，且两个承载端必须同时实现。Desktop 对 `REMOTE_MODULE` 交付的 slot 内容显示确定状态并指向 Web，§4.2–§4.4 的 remote module 加载与 Host API 只在 Web 执行（SF-DSK-03）。

扩展槽承载 Kailo 接入管理、受权资源视图及可选的独立原生管理页面。Kailo 自有页面发起的业务数据操作（上传、导入、查询、发布、分享、删除等）与 Agent 走相同 Governed Action/Tool 链：Browser→BFF 语义命令→Admission→Adapter Protocol 或 AgentGateway MCP→实现。独立原生管理页面通过自己的会话访问自己的后端；调用 Kailo 公共服务时按对应认证与准入合同执行，不把全部内部 API 改造成 BFF 命令。`HOST_NATIVE` 只实现通用接入管理及平台资源视图，不为 Cells、WeKnora、Wren 重写后台；产品原生后台可按 `NATIVE_PAGE` 嵌入，也可独立访问，`REMOTE_MODULE` 不是其唯一交付方式。没有 active binding 时不显示该服务的 Kailo 嵌入入口，不影响其独立入口和业务运行。

### 4.2 运行时快照、通知与 reconcile

BFF 只返回当前 PlatformSession、Tenant、Workspace 和 Principal 可发现的完整 `ComponentRuntimeProjectionSnapshot`：

```text
snapshot_generation
scope_digest
projections[
  binding_kind / binding_id / release_id / generation
  component_type_key / authorized surface descriptors
  served_entry_path / artifact digest / host_api_range
]
```

BFF session stream 只通知 `snapshot_generation` 变化，Browser 立即重取完整快照并做 set reconciliation。新增 projection 直接 load；版本变更时，新导航解析新 generation，已挂载旧 surface 保留到卸载或用户确认刷新，不能在存在未保存输入时强制 dispose；projection 消失则停止新导航并请求已打开 surface 安全关闭。断线重连、页面恢复可见或 generation 不连续时也重取完整快照。事件只是失效通知，不是授权或组件状态权威（DD-61）。Mattermost 在事件路径上把 payload 当完整状态直接 load/remove、只在重连时全量 reconcile（SF-MAT-06），是本设计明确不采用的反例。

### 4.3 前端 module 加载协议

```text
Host 按(type, release_id, generation, entry_digest)登记 pending load
→ 校验 served_entry_path 为当前 release digest 的同源内容寻址路径
→ 在现有 script-src 'self' 下注入 module script
→ module 求值期同步调用 register(descriptor)
→ Host 暂存 descriptor；script load 事件后按 pending load 全字段匹配并接受
→ module mount(host-owned root, narrow Host API)
→ snapshot 移除/变更时 dispose + unregister
```

pending load 只在 Host 内部存在，绑定 Browser session、projection、注入元素与过期时间；静态 module artifact 不携带会话 ticket。无 pending、重复 register、load 失败、字段不一致或 Host API 不兼容均拒绝。`register` 在 module 求值期只暂存 descriptor，必须等对应注入元素的 load 事件发生后才 commit，避免把无关脚本的全局调用接受为该 projection。

Host 以 try/catch 包住 `mount()` 与 `dispose()`，并监听 `window.error`/`unhandledrejection`；当 `ErrorEvent.filename` 或可解析 stack URL 命中该 generation 的 artifact 根前缀时，尽力 dispose，将 Host 侧 generation 置 `ERROR`，并在槽位显示本地化 fallback。React error boundary 不作为 remote module 隔离承诺；事件 handler、timer 与 promise 错误也走上述全局归因。该错误只改变浏览器 Host generation，不改 ApplicationBinding、native task 或后端 projection 状态。

`dispose()` 的强制合同是：清空 Host 分配的 DOM root，移除 module 自有 style、全局 listener 与 timer，注销其 i18n namespace；CSS selector 必须以 Host 注入的 `data-platform-component=<type>` 与 `data-platform-generation=<generation>` 双属性作用域化。ES module 代码本身不会从同一 window 卸载，因此旧 generation 不得再次 mount；无法履行 dispose 的 release 在 Catalog 登记时拒绝。

`source_entry_url` 只供 Catalog 登记流程取件。批准前按密码学 digest 固定 bytes，Browser 只请求同源 immutable `served_entry_path`，不请求外域 script，不放宽承载端当前 `script-src 'self'`（SF-WEB-06、SF-MAT-01/03、DD-60）。

Remote module 是平台管理员批准的同窗口信任代码，不是安全沙箱。Tenant 管理员只能启用已批准 release，不能上传或替换 JavaScript。

### 4.4 窄 Host API

Host API 只提供：

- 当前受限 scope 和 FrontendPresentationContext 读取；
- BFF Resource query；
- action preview 与 semantic command；
- Task/Approval/operation 状态订阅；
- 受权导航、`subscribePresentation(cb)` 与 namespaced `hostI18n.t(namespace,key)` 注册。

Module 不获得完整宿主 store、Relay signer、ActionToken signing key、native credential 或 SpiceDB/Temporal/OpenMeter/AgentGateway 管理凭据。即使 module 自行发起同源 BFF 请求，BFF 仍对每个 query/action 重做 session、scope、SpiceDB、Approval、Quota 和 Audit 准入；前端代码不是授权边界。

### 4.5 主题与 i18n

- `HOST_NATIVE` 直接使用 Buzz CSS variables、`MessageKey/t/getLocale`。
- `REMOTE_MODULE` 通过 `subscribePresentation(cb)` 持续接收 resolved `LIGHT/DARK` 与 `EN/ZH_CN`，使用 Buzz tokens；不得只在 mount 时读取一次。Catalog 登记时校验 namespaced `en` 与 `zh-CN` catalog 的 key 集完全一致且覆盖 manifest 声明的全部 key，不一致即拒绝 release；remote key 不进入 Buzz 封闭的 `MessageKey` 类型或本地 `check-i18n` 扫描面（SF-WEB-03/08、SS-WEB-COMPONENT-HOST）。
- `SOURCE_BOUND_PROTOCOL` 的 launch 请求携带 Buzz 已解析的 theme 与 locale，由实现的 adapter 映射为其私有参数并写入 DocumentLaunchDescriptor，每次 launch 固定；surface 与 Core 不理解这些参数；内置参考实现的映射见 `18`（SF-WEB-03、DD-95）。
- `NATIVE_PAGE` 保留服务自身呈现，支持原生参数时传递 theme/locale，不要求 Host API、双语 catalog 或重写原生后台。平台自身状态使用宿主稳定 code 和 i18n key，组件页面自身错误由组件呈现。

独立管理页面的隔离嵌入按 §4.6；在线编辑仍使用独立的 `SOURCE_BOUND_PROTOCOL` 合同，不以管理页面嵌入替代文档编辑准入。release 固定 editor origin 与 DocumentLaunchDescriptor schema 版本、并按 §2.5 准入路径取得 `APPROVED` 后，承载端只有一个通用 `SOURCE_BOUND_PROTOCOL` surface `ProtocolDocumentSurface`，按 `FILE_STORAGE` 契约的在线编辑条件能力消费 adapter 生成、经 Core 校验后下发的 DocumentLaunchDescriptor，不含产品专名分支，WOPI 只是内置参考实现的一种取值（DD-95）。在线编辑所需的 Web CSP `frame-src`/`form-action` 来源取自部署级 editor origin 许可集合，独立管理页面的许可来源另按 §4.6 合并：该集合等于平台管理员批准的 release 所登记 `editor_origins[]` 的并集，Tenant 与 binding 不能扩大，不随会话变化。BFF 在运行时持有该集合并据此决定各端编辑入口：Web 端由同一份部署配置同时投影出 Web 静态服务 CSP 与 BFF 读取的 Web 已生效集合，变更时重启 Web 静态服务、不重建镜像，Web 有效集合是许可集合与 Web 已生效集合的交集；Desktop 主窗口 CSP 编译在签名包内且不放宽，编辑器不嵌入主窗口，而在独立 `platform-editor-*` WebviewWindow 中打开，其 `on_navigation` 钩子按 BFF 运行时下发的许可集合逐次校验，Desktop 有效集合就是该运行时许可集合，新增 origin 不需要发布 Desktop 包（DD-104、SS-DSK-EDITOR-WINDOW）。Desktop 在线编辑当前为 `BLOCKED: GAP-DSK-EDITOR-01`，上述窗口与动态许可集合是阻断解除后的合同，当前不注册该端编辑 Route 或 Action；不阻断 Web 编辑与普通 Desktop 功能。某端有效集合未包含该 origin 时，该端编辑入口按 REQ-21 显示确定状态，不回落为隐藏或报错。`script-src 'self'` 不因任何 release 放宽（DD-60/95/104、SF-WEB-06、SF-DSK-03）。文件所属的 `FILE_STORAGE` 实现未声明 `online_editing=SUPPORTED` 时，该文件只显示元数据与受权下载（REQ-07、DD-90/103）。

### 4.6 独立原生管理页面

`NATIVE_PAGE` 复用外部服务已有前端，不复制其源码或业务页面到 Kailo。release 以 `native_page_origins[]` 声明允许来源，binding 配置实际页面入口；BFF 只向有权发现该 binding 的用户返回入口，核对 URL origin 同时属于 release 和部署许可集合。URL 不携带平台 service credential、管理令牌或长期密钥，不接受用户提供的任意跳转地址。

Web 使用跨来源隔离 frame，来源必须由服务自己的嵌入策略允许；宿主不关闭对方的 CSP/frame-ancestors 或绕过登录。Desktop 保持主窗口脚本和 IPC 边界，外部页面在隔离的原生页面承载区运行，不取得 Tauri 命令；Web/Desktop 共用入口解析与平台管理呈现。Mobile 不渲染该入口，不用 WebView 绕过。

页面用服务自己的用户会话访问自己的后端，可对接公共身份服务实现统一登录；统一登录不等于共享平台管理员或机器凭据。Kailo 管理 API 仍经 BFF，工具仍经 AgentGateway，公共工作流/审批/额度等调用仍由各自权威准入。页面嵌入不要求每次组件内部操作都建立 Kailo ActionExecution，也不把组件内部任务、数据库、模型配置或账单复制到 Core。

没有嵌入能力、被对方来源策略拒绝或端能力不支持时，只说明该端无法嵌入；不因此关闭独立服务、禁止它提供工具，或重写其后台。binding 停用或用户被撤销平台接入权时撤去 Kailo 入口与公共服务调用权；组件自身的会话和内部权限由其身份/权限集成处理，不宣称关闭 frame 已注销外部服务。

## 5. Component Adapter Protocol

### 5.1 与上游项目形态解耦

| Connector | 适用条件 | 边界 |
|---|---|---|
| `PLATFORM_PORT_CLIENT` | Platform Component 实现已知 port | Core typed client 通过 Port Router 调 provider；不再套 application adapter |
| `REMOTE_ADAPTER` | Application Component 默认形态 | Core/Worker 调独立 adapter，adapter 调 native API |
| `EMBEDDED_DRIVER` | 仅平台自身，上游明确提供 library runtime | 代码与 Core/Worker 构建绑定；业务能力服务不得使用（DD-64/87） |
| `PROTOCOL_PEER` | Application Component 只经 AgentGateway 的 MCP Tool 传输接入（DD-12/58） | 端点属于 binding 配置，不写死产品配对；Gateway 双相 PEP/Core 执行完整统一准入、fresh 授权、审批、Quota 与审计，不要求原生 peer 接受 ActionToken 或实现 Adapter API；不用于两个业务服务之间的数据面直连。需要上游 Adapter Protocol、ActionToken、ProtocolSession 或该协议 revision 查询的能力（含在线编辑与服务读取边来源）必须经 `REMOTE_ADAPTER`（DD-94/103） |
| `INTERNAL` | Core 自身领域，仅 `class=PLATFORM` 且 `platform_port_key=CORE_INTERNAL` | 不生成网络 adapter 或自签 token 循环；`class=APPLICATION` 不得使用 |

不变式：`class=APPLICATION` release 的 `execution_connector.mode` 只取 `REMOTE_ADAPTER` 或 `PROTOCOL_PEER`，`PLATFORM_PORT_CLIENT`、`EMBEDDED_DRIVER` 与 `INTERNAL` 只属 `class=PLATFORM`（DD-58/64）；ApplicationBinding 的 `call_identity_mode` 不含 `INTERNAL`。业务能力服务只使用 `REMOTE_ADAPTER`，或仅为 MCP Tool 传输使用经 binding 配置的 `PROTOCOL_PEER`；`PROTOCOL_PEER` 的平台 Resource 引用登记依 DD-98 核实原生协议或可信运行投递证据，不为此强加 Adapter 创建接口；证据未闭合时该入口保持关闭。`SOURCE_BOUND_PROTOCOL` 前端交付的 launch 由该实现的 `REMOTE_ADAPTER` 生成 descriptor，不属于 `PROTOCOL_PEER`（DD-58/95）。一个能力组件内部为实现其契约而使用的协议（如内置参考实现中 Cells 与 ONLYOFFICE 之间的 WOPI）属于该组件内部集成，对平台仍是一个 ApplicationBinding，不构成两个服务之间的平台级连接（DD-90）。

业务能力实现可保持原 monolith/service，不需要为 Buzz 强拆前后端。Remote adapter 只在稳定 native API 上实现能力契约；原生后台继续独立存在，Buzz 可用 `NATIVE_PAGE` 直接嵌入，不要求重写或强拆；`HOST_NATIVE` 仅处理平台接入与通用资源视图，`REMOTE_MODULE` 是可选呈现方式。内置参考实现的 native API 证据见 `08`（SF-CEL-01/03、SF-WEK-01/03、SF-WRN-01、DD-58）。

### 5.2 版本化深接口

Adapter Protocol 只包含以下逻辑操作，传输编码由 release 的协议版本固定。出站操作由 Core/Worker 发起、adapter 应答：

```text
handshake(protocol range, component/release identity, capabilities)
validate_binding(binding ref/version, normalized config digest, secret ref versions)
resolve_native_scope(binding ref, platform resource ref, mode[CREATE|LOOKUP], ActionToken)  // 仅明确 REMOTE_ADAPTER 原生创建分支
execute(action key/version, normalized args, ActionToken)
observe(external execution ref, ActionToken)
cancel(external execution ref, ActionToken)
reconcile(binding or execution ref, ActionToken)
query_revision(native_object_ref, ActionToken)
extract_usage(native evidence ref)
map_native_status_error(native status/error)
```

入站操作由业务能力实现以其 binding 的 ServicePrincipal 发起、Core 应答，与 `09` ServicePrincipal 表的「业务能力实现 → Core PEP（入站 service 边）」和「服务读取边」两行一致：

```text
pep_check(binding ref, protocol session ref | action token ref, target ContentReference, requested operation)
report_rekey(binding ref, secret_key, new secret version, result[COMPLETED|FAILED])
request_read_grant(receiver binding ref, source resource ref, batch parameters)
```

- `resolve_native_scope` 的 `mode=CREATE` 在 binding 固定的 native scope 内按 platform resource ref 幂等创建或取回 native 对象，返回 native type/ref 或确定的 `REFUSED`；`mode=LOOKUP` 只查不建，返回 `FOUND`（native type/ref）或 `ABSENT_FENCED`——确认该 ref 没有 native 对象，并在同一原子步骤为该 ref 写入拒绝标记，此后该 ref 的 `CREATE` 一律返回 `REFUSED`。`ComponentTaskWorkflow(kind=RESOURCE_PROVISION)` 结果不明时只以同一 Resource ref 调 `LOOKUP` 对账，不以 `CREATE` 重放；一致性套件验证幂等、`REFUSED` 与 `ABSENT_FENCED` 之后的拒绝（DD-98）。
- 登记服务既有对象不是 `resolve_native_scope(CREATE)` 的别名，不要求原生 peer 实现 Adapter Protocol。Core 复用 `resource.create`/`RESOURCE_PROVISION` 核实冻结 binding/native scope、native type/ref 与来源证据，再完成原 SpiceDB 投影；证据只来自固定原生协议或可信运行投递事实，不新增假定存在的查询 API。记录及对账不保存正文、临时 URL 或凭据；未知只重核同一引用，不发 CREATE。必要归属证据不能闭合时，对应引用登记能力未闭合，不生成入口。原 CREATE/LOOKUP/ABSENT_FENCED 一致性向量只适用于明确原生创建；既有引用向量验证已有对象、重复绑定、证据不足、scope 不一致、撤权与 UNKNOWN 收敛（DD-98）。
- `query_revision` 按 `native_object_ref` 返回当前 revision，是声明 revision 查询能力的实现必须提供的操作；ProtocolSession `UNKNOWN` 对账与 EDIT admission 的 head 查证都只经它进行（DD-90）。
- `pep_check` 是协议会话内每个读写入口的 fresh Check，继承父 operation，不新建 Action/Workflow/Quota；Core 不可达或超时一律拒绝。
- `report_rekey` 回报 `DATA_KEY` 轮换后的重加密结果；只有 `COMPLETED` 回报使平台记录结果并允许销毁旧版本，其他情形旧版本保留、binding 进入对账（DD-93）。
- `request_read_grant` 是服务读取边的申请入口：Core 以接收方 ServicePrincipal 为 SERVICE actor 做 Governed Action 准入，通过后为该批建立 operation 并返回短期 ActionToken（audience 为来源实现的契约端点，target 为来源 Resource），规则见 §8.2（DD-89）。来源方 PEP 即来源实现在平台运维域内的 adapter，其验签公钥经 OpenBao Agent 投递；`PROTOCOL_PEER` 实现不接收 ActionToken，不能作为来源方（DD-94）。

Handshake 成功只证明协议兼容，不表示 binding active。Binding 只在 service identity、config digest、SecretRef audience/version、native scope、隔离方式、capability 和全部 projection 对账后 active。

Core 在 dispatch 前完成准入。Core→adapter 的 ActionToken 由 adapter 运行体校验，验签公钥（JWKS）与 `secret_schema` 声明的凭据经 OpenBao Agent 投递到 adapter，不另设分发通道（DD-94）。ActionToken 固定 issuer/audience、Tenant/Workspace、actor、delegation、action/version、target、operation、parameter hash、ResultExposure 和短 expiry。Adapter 校验 token 后仍按 `03` 的 PEP 合同将请求收窄到 binding 已固定 native scope。Adapter 不接受 payload 自报 Tenant/Workspace、不自行扩大权限、不回退默认实例（DD-63）。

ResultExposure 由确切 ActionDefinition 决定：固定 `NONE` 且只返回平台 ID 与状态的管理动作，其 ActionToken 内容策略 ID 与版本按 `03` §6 成对为 `NONE`；协议操作名或管理父动作不构成该例外。实际业务内容访问与返回内容的子动作仍需其有效内容策略及 fresh 授权，不以 `NONE` token 执行业务读取，也不以自造 `CONSUME_ONLY` 策略填充管理调用。

真实副作用在 dispatch 前建立 ExternalExecution 和稳定 operation/idempotency key。超时且无 native query/dedupe 接缝时进入 `UNKNOWN`，不自动重发。Adapter 只映射源码存在的 progress/cancel/terminal；HTTP 200/202、queued 或 cancel accepted 都不等于业务完成。

## 6. 两类 Binding 的生命周期

### 6.1 PlatformProviderBinding

```text
approved PLATFORM release
→ create/upgrade provider binding for exact known port
→ PENDING projection generation
→ validate connector/target registry/service identity/config/secret/readiness/governance
→ Port Router atomically selects ACTIVE generation for new calls
```

变更由 Platform Catalog Tenant 的 `ComponentTaskWorkflow(kind=COMPONENT_BINDING, binding_kind=PLATFORM_PROVIDER)` 承接。旧 generation 保留给已开始调用；新 generation 校验失败不切流。安全撤销导致 provider fail closed，不静默切换未批准实现。

### 6.2 ApplicationBinding

```text
approved APPLICATION release
→ Tenant/Workspace creates or upgrades exact binding
→ PENDING projection generation
→ validate adapter handshake/config/secret/native scope/isolation/governance/Web artifact
→ reconcile Resource/Action/Tool/Gateway/route/observability projections
→ atomically select ACTIVE generation
```

变更由业务 Tenant/Workspace 的 `ComponentTaskWorkflow(kind=COMPONENT_BINDING, binding_kind=APPLICATION)` 承接。同一 binding 升级到同一实现的新 release 时生成新 generation：已开始的 ActionExecution/Workflow/ExternalExecution 继续使用旧 generation；新 Action 只解析 active generation。Rollback 也创建新 generation，不改写旧 release 或历史执行。换成另一实现不走 generation 切换，而是 §2.4 的「新建 binding、旧 binding 转 `DISABLED` 只读保留」。切换 `model_call_mode` 是需要审批的 Governed Action，同样经本 Workflow 生成新 generation（DD-92）。

### 6.3 Disable

两类 binding 的停用都使用 `ComponentTaskWorkflow(kind=COMPONENT_DISABLE, binding_kind=...)`。Core 先置 `DISABLING` 并停止新 discovery/action/call，再暂停该 binding 的 Kailo Schedule、撤平台授权/AgentGateway route/tool/Web projection、观察 Kailo 发起的在途 execution 并对账 usage/audit。不停止外部服务进程、不暂停组件自有工作流，不因平台 binding 停用而删除原生后台入口。Disable 不删除 Resource/Asset/native data；`DISABLED` binding 下的 Resource 保留只读，只可 discover 元数据，其 ContentReference 解析为不可用；该 binding ServicePrincipal 的全部 `reader` 关系随之撤销；保留或不明 ref 存在时不伪造已收敛。业务能力 binding 停用只影响它提供的契约键：对应 `APPLICATION` 工具 effective 变为 `NO_PROVIDER`（该类别无其他 active 实现）或 `DISABLED`，AgentInstallation、协作、记忆与 `PLATFORM_NATIVE` 工具不受影响（DD-92）。

## 7. 全局治理契约

每个经 Kailo 或调用其公共服务的用户、Agent、Schedule、callback 或 Workflow action 必须声明；外部服务独立入口的内部动作不自动纳入本表：

| 贯穿项 | Release 声明 | 运行时强制点 |
|---|---|---|
| Tenant | scope rule、binding isolation、native scope derivation | Core 从 session/parent action 构造；adapter 不接受自报 |
| Workspace | WorkspaceRule 与 binding scope | scope guard 先于 Resource permission；execution 固定 scope |
| Authorization | canonical permission、target、ResultExposure | SpiceDB fresh Check；Agent 另与 Delegation/ToolBinding 求交 |
| Approval | confirmation mode、ApprovalPolicy、owner rule | Temporal Approval 固定 exact action/parameter/owner/policy version，消费前重检 |
| Workflow | `SYNC/PROTOCOL/TEMPORAL`、kind、idempotency/UNKNOWN/cancel | Temporal 持有持久生命周期；native task 是 ExternalExecution |
| Capacity/Quota/Billing | capacity/quota mode、meter、strict upper bound | CapacityLease/QuotaReservation/OpenMeter；actual usage 只有一个 source |
| Operation Audit | intent/decision/dispatch/outcome/revoke/reconcile 与 redaction | 外部副作用前先持久 intent；结果沿同一 operation 追加 |
| Business Observability | correlation、terminal/progress/usage/cost source 和 redaction | operation→release/binding generation→native evidence→usage/cost 的受权联合视图 |

`NONE` 只能是明确策略值，缺失字段不等于 `NONE`。平台 provider 的内部 RPC 继承父 operation，不递归创建 Governed Action；任何用户可达的 provider 管理动作仍完整经过上表。

## 8. Resource 附加合同

### 8.1 IncrementalContract

每个 ResourceType 至少登记一份合同：

```text
NATIVE_INTERNAL / NATIVE
VERSIONED_PUBLICATION / VERSIONED_REPUBLISH
```

`NATIVE_INTERNAL` 表示新增、修改、删除与处理逻辑变更的增量、对账和就绪全部在该实现内部完成。实现必须经 Adapter Protocol 暴露：

- 跨调用稳定、同一 Resource 内唯一的 native object ref；
- 内容 revision，而非仅修改时间；
- 删除是否可观察，以及删除后的 native ref 状态；
- ready/failed/cancelled/unknown 的判定与 query/reconcile 接缝；
- 处理逻辑变更（如重新解析、重新索引）的触发方式与进度。

`VERSIONED_PUBLICATION` 表示以完整不可变版本发布替换，不对版本内部项做差异；业务能力实现的版本发布与下线收敛由通用 `ComponentTaskWorkflow(kind=CAPABILITY_VERSION_PUBLISH)` 承接，Workflow 只依能力契约与 binding 固定的版本 Resource/Asset 工作，不含产品专属步骤（DD-90）。

只提供 mtime、只 create 无 delete/readiness、或要求平台直写组件数据库、vector store、图数据库的类型不得登记为 active。平台与其他服务禁止直写任何业务能力实现的数据库；实现内部的派生索引由该实现自己维护。

平台不接管组件内部索引，不持有逐项增量状态，不为业务数据建立跨 Resource 的派生副本；平台不存在物化端口、物化 binding 或物化 Workflow kind（DD-89）。平台不持有的内容固定为：任何业务能力实现内部的增量状态、索引、队列或游标；两个业务能力服务之间的逐项映射、去重表或同步游标；任何业务能力服务的数据库凭据（DD-93）。平台自有的持久流仍各归原权威：Buzz event 消费游标与 AgentGateway log tail 游标是已有持久流的 `IngressCheckpoint`。

平台核心 ResourceType 的合同固定为：

| ResourceType | 合同 | 结论 |
|---|---|---|
| Buzz Community/Channel | `NATIVE_INTERNAL` | Relay event 是 native 权威；Core 以稳定 event ID+cursor 消费 |
| AgentGateway LLM Route | `VERSIONED_PUBLICATION` | ConfigResource version/reload 是 native 配置投影（SF-AGW-01） |
| AgentGateway request log | 观测流 checkpoint | logging database 中已成功持久化的稳定 log ID+tail cursor 供业务观测；不承担完整计费（SF-AGW-06/09） |

内置业务能力参考实现的合同见 `13` §3。

### 8.2 跨服务数据获取

服务读取边是 release 可声明的可选能力：release 以能力声明 `read_edge[SOURCE|RECEIVER|BOTH|NONE]` 声明本实现可作来源方、接收方、两者或都不作，未声明 `SOURCE` 的实现不接受读取令牌，未声明 `RECEIVER` 的实现不得调用 `request_read_grant`。没有这条边时，两个服务各自仍完整可用，只是彼此不取数；平台不因缺少读取边降级任一服务（DD-87/89）。一个业务能力服务需要另一服务的数据时只有两条路径（DD-89）：

1. **接收方自拉**：接收方在自己的管理面（独立访问或经 Component Host 嵌入）配置数据源连接器，指向来源方的一个 Resource。平台以既有机制授权：一个 Governed Action（按 ApprovalPolicy 可含来源 Resource owner 审批）为接收方 binding 的 ServicePrincipal 写入来源 Resource 的 `reader` 关系；授予要求发起者对来源 Resource 持有 `share`、对接收方 Resource 持有 `update`。接收方每批拉取经**服务读取边**完成，经来源方公开的能力契约读取。增量、状态、去重与删除收敛全在接收方内部，Core 不感知其状态。
2. **人或 Agent 显式读写**：人或 Agent 经两边各自暴露的 Tool 显式读取一侧、写入另一侧，每一步都是独立 Governed Action，各自授权、审批、计量与审计。

**服务读取边。** 接收方 binding 经 Adapter Protocol `request_read_grant` 向 Core 申请读取来源 Resource；Core 以接收方 ServicePrincipal 为 SERVICE actor 做 Governed Action 准入：scope guard 要求接收方 binding 与来源 Resource 同 Tenant，Workspace 级接收方还须与来源 home Workspace 一致或来源为 Tenant 级 Resource；对来源 Resource fresh `read` Check；Quota。通过后 Core 为该批建立 operation，签发短期 ActionToken（audience 为来源实现的契约端点，target 为来源 Resource，携带该批 operation）；来源实现的 PEP 按 `03` §6 的通用 ActionToken 规则校验并再做 fresh `read` Check。来源方 PEP 即来源实现在平台运维域内的 adapter 运行体，外部与 SaaS 实现也不例外；验签公钥与其凭据经 OpenBao Agent 投递到该 adapter；以 `PROTOCOL_PEER` 接入的实现不接收 ActionToken，不能作为服务读取边的来源方（§2.5、DD-94）。接收方不持有来源实现的 native 凭据；平台为接收方 binding 投递的 SecretRef 只是其自身服务凭据，用于认证 Adapter Protocol，不能直接访问来源。经平台签发令牌访问来源的契约端点不是服务间数据面直连（§5.1、DD-89）。

授予、撤销与每批读取都按八项贯穿执行：

| 能力 | 规则 |
|---|---|
| Tenant | 来源 Resource、接收方 binding 与其 ServicePrincipal 必须同 Tenant；跨 Tenant 数据只走 REQ-09 两段导出/导入 |
| Workspace | 授予按来源 Resource 的 home Workspace 做 scope/permission；每批读取按 `03` §2 的 SERVICE scope guard，执行 Workspace 取接收方 binding 的 Workspace（Tenant 级为 NONE）；授权不产生隐式跨 Workspace 共享 |
| Authorization | 授予要求发起者对来源 Resource 持有 `share`、对接收方 Resource 持有 `update`；每批读取在 Core 准入与来源 PEP 各做一次对接收方 ServicePrincipal 的 fresh `read` Check；Agent 发起授予时另与 Delegation/ToolBinding 求交 |
| Approval | 授予的 ApprovalPolicy 绑定来源 Resource、接收方 binding 与 parameter hash；发起者不是来源 Resource owner 时，来源 owner 必须批准；Approval 不能补 permission。每批读取不再审批 |
| Workflow | 授予与撤销是一次关系写入，结果不明按既有 ActionExecution/UNKNOWN 规则对账；每批读取是 `SYNC` 准入与令牌签发；接收方的拉取运行不是平台 Workflow |
| Capacity/Quota/Billing | 每批读取在准入时做 Quota；来源方按其 meter 对该批读取计量、接收方按其 meter 对导入处理计量，UsageEvent 都归属该批 operation；模型 usage 按 §8.3 |
| Operation Audit | 授予/撤销记录 actor、来源 Resource、接收方 binding、ServicePrincipal 与 Approval；每批读取记录 SERVICE actor、来源 Resource、ActionToken `jti` 与该批 operation，来源方的 native execution evidence 归属同一 operation |
| Business Observability | 平台视图展示授权关系状态、每批读取 operation 与双方各自暴露的 native 进度/错误；不展示逐项同步状态 |

**撤权收敛。** 撤销 `reader` 关系即收回读取权：Core 对后续 `request_read_grant` 拒绝，来源方 PEP 对已签发未过期令牌的后续读取 fresh 拒绝。接收方已取得数据的处置由接收方按其能力契约声明的删除语义负责；平台不代为删除接收方数据，也不宣称撤权使已导入内容消失。接收方 binding 停用时，平台撤其 ServicePrincipal 的全部 `reader` 关系；来源方 binding 停用时，接收方后续申请失败，接收方按自身规则保留或标记失效，不得把拉取失败解释为来源内容已删除。

暂停导入、撤销读取授权、停用 binding 与删除派生内容是四个不同动作，UI 与 Agent tool 不得合并按钮或复用 action key。暂停导入属于接收方管理面上的本组件动作，不是平台 Workflow 状态。

平台只治理授权与动作，不经手数据、不持有同步状态、不以 Schedule 或 Workflow 编排跨服务同步。

### 8.3 LLMGatewayContract

Kailo 接入范围内的模型调用模式由 release 声明允许的集合 `allowed_model_call_modes[]`，binding 在其中选定一种 `model_call_mode`；切换模式是需要审批的 Governed Action。`model_call_mode≠NONE` 的 binding，其 release 对所启用类别的 meter 能力必须为 `SUPPORTED`（DD-92）：

| `model_call_mode` | 合同 | 计量 |
|---|---|---|
| `PLATFORM_LLM_ROUTE` | 服务的模型 base URL 经 binding 配置指向 AgentGateway `llm_route`；协议必须属于 AgentGateway 已实现的 Chat/Responses/Embeddings/Messages/Gemini/Rerank，provider credential 只存在 Gateway SecretRef（SF-AGW-04/05） | Actual token/cost 只取 SS-AGW-USAGE 闭合后的 durable usage 并写 OpenMeter；经网关路由的调用，组件自报 token 不形成计费事件，也不形成第二份账 |
| `SELF_MANAGED_MODEL` | 服务自管模型与凭据，平台不向服务数据写入模型配置 | 服务经 Adapter Protocol `extract_usage` 上报的 usage 是 actual usage source，Core 按稳定 source identity 去重写入 OpenMeter 并标注来源模式；平台照常执行 Quota 与审计 |
| `NONE` | 当前接入能力不调用模型，不代表独立服务内部没有模型 | 无本接入模型 usage |

逐调用关联以标准 W3C `traceparent` 与 operation 头为可选增强：存在时把模型调用归因到平台 operation；缺失时按 gateway identity（`PLATFORM_LLM_ROUTE`）或 Adapter Protocol 上报身份（`SELF_MANAGED_MODEL`）解析出的 binding scope 入账，只降低到 operation 的归因精度，不阻断 binding `ACTIVE`，也不免于计量（DD-20/92）。平台自有 Agent 的模型调用始终经 AgentGateway，不受本节模式选择影响。

### 8.4 Transfer 与 Tenant delete

`transfer_formats[]` 必须同时证明 export、import/create、format/version、digest、terminal 和错误语义；缺任一端则不注册跨 Tenant Action。组件停用不等于删除 native data。

Tenant 销毁以平台自有事实为前提（DD-91）。平台核心自有 ResourceType（Agent、Skill、Tool、`llm_route` 等）的删除由 `ComponentTaskWorkflow(kind=TENANT_LIFECYCLE)` 按平台核心销毁链执行，不适用保留；Tenant delete Action 在注册时已存在的每个平台事实类别都有经验证的销毁处理器后注册，之后新增的平台核心 ResourceType 或平台存储面必须与其处理器同一构建登记，snapshot 中出现没有处理器的类别时准入拒绝（DD-99）；业务能力实现的删除缺口不阻断注册。每个 ApplicationBinding 的 native 删除是 Tenant 删除中独立的子流程（`03` TenantDeleteSubprocess），由能力契约的 Tenant 删除能力声明决定：

- 声明支持删除的实现必须提供稳定 native ref、幂等 delete、terminal query 和 retained-error 语义，登记 `tenant_delete_action_key`；该子流程失败或结果不明时按 fail closed 持续对账，其他子流程照常推进；
- 不具备的实现在准入时声明 `retain_on_tenant_delete`：Tenant 删除时撤该 binding、撤凭据、保留审计，并把该 binding 的 native 数据登记为待人工处置项，子流程进入 `RETAINED_DECLARED`，不阻断平台 Tenant 状态机；
- 已声明删除能力的子流程停在 `UNKNOWN` 时，只有该业务 Tenant 的 admin 经 owner 审批的 Governed Action 可把它处置为 `RETAINED_BY_DECISION`；处置不改写 binding 或 release 的声明字段，处置与理由进入审计。

Tenant 只在全部子流程到达终态后进入 `DELETED`。任何业务能力实现的删除缺口只影响该实现自身的删除子流程，不阻断平台 Tenant 生命周期。

`REQ-11` 保证组件可在运行时注册，`REQ-22` 保证第三方能在开发期独立做出组件。后者的交付物固定为六件，与 Component Host 同 Stage 交付（`DD-76`）：

| 接入面 | 内容 | 来源 |
|---|---|---|
| Component SDK | TypeScript 包：Host API 类型与调用封装、Adapter Protocol 客户端/服务端骨架、错误六分类与 reason code 常量、slot descriptor 构造 | 由 `contracts/` 生成或派生，不手写 |
| manifest schema 与校验器 | 可本地运行的 manifest 校验，错误信息指向具体字段与允许取值 | 本文 §3 的 manifest 定义 |
| 脚手架 | 生成含前端 module、后端 adapter、manifest 与一致性测试配置的最小可运行组件 | — |
| 本地开发环境 | 不接真实平台即可加载 module、应答 Adapter Protocol、模拟 binding 与 presentation context | — |
| 一致性测试套件 | 在 Adapter Protocol 线协议层验证 handshake、终态语义、幂等、取消、错误映射与 redaction；按 `implements[]` 叠加对应能力契约的契约键语义、permission 映射与 ContentReference 往返 | 本文 §2.4、§5 与 `03-领域模型与权限模型.md` 的状态约束 |
| 示例组件 | 一个端到端参考实现，覆盖三个扩展槽中至少一个与一条 Tool 路径；自带独立 database 与一个可取消的异步 native task，按 DD-98 幂等创建 Resource 并声明支持 Tenant 删除，是组件与能力契约底座中带真实 native 副作用的产出方；ResourceType 为 `component.<component_type_key>.<kind>`，动作与工具为 `component.<component_type_key>.<verb>`，binding 配置 `refuse_create_type_keys[]` 注入确定拒绝（DD-101） | — |

约束：

- SDK 是 `contracts/` 的消费者，不是第二权威；两者冲突以 `contracts/` 为准，`contracts/` 与本文冲突以本文为准。
- 前端 remote module 只能是 TypeScript，由承载端运行时决定；后端 adapter 的契约是线协议，因此首方不承诺多语言 SDK，任意语言实现以一致性套件自证。
- 接入面随 Host API 与 Adapter Protocol 的 range 一起版本化。新增扩展槽或 Host API 不兼容变更时，接入面必须同步发布，否则第三方拿到的类型与真实宿主不一致。
- 一致性套件通过是登记 release 的必要条件，不是充分条件；平台管理员批准、digest 固定、隔离与数据位置声明核对和全局治理校验仍然独立执行。外部实现（含闭源与 SaaS）以该套件作为源码证据的替代，按 §2.5 准入。
- 接入面不暴露平台内部实体、SpiceDB schema、Core 数据库结构或任何 service credential。
- 示例组件以 `implements=[]` 登记，是唯一允许的该形态 Application release：它不是业务能力服务，不获得契约键；其 ResourceType `type_key` 固定为 `component.<component_type_key>.<kind>`，ActionDefinition 与 ToolDefinition 的 `action_key` 固定为 `component.<component_type_key>.<verb>`、`capability_contract_key=NONE`，归类为组件自有动作（既非平台核心动作也非能力契约动作，`capacity_policy=NATIVE`，其余策略逐项声明），`component.` 前缀保留、能力类别登记不得使用（DD-102）；其 binding 配置 `refuse_create_type_keys[]`（只用于验证部署，进入 `config_digest`）列入的 `type_key` 在 `resolve_native_scope(mode=CREATE)` 时确定返回 `REFUSED`，作为 DD-98 确定拒绝分支的注入点；其 Tool 不能被 AgentVersion 作为能力需求引用，不作服务读取边任一方（`read_edge=NONE`）；零业务能力 binding 部署与生产 Catalog 不登记其 release（DD-101）。

## 9. 无需重发 Core/承载端的精确边界

| 变化 | Core/承载端重发 | 原因 |
|---|---|---|
| 新增/升级兼容 Application release | 不需要 | 使用已有 manifest、Adapter Protocol、Resource/Action/Tool 和 slot |
| release 引入部署级许可集合尚未包含的 editor origin | Web 重启静态服务（不重建镜像）；Desktop 的不重发合同仅在 GAP-DSK-EDITOR-01 闭合后成立 | Web CSP 的 `frame-src`/`form-action` 只为部署级许可集合放宽（DD-95、SF-WEB-06）；Desktop 主窗口 CSP 不变，编辑器在独立 editor 窗口中按 BFF 运行时下发的许可集合校验导航（DD-104、SS-DSK-EDITOR-WINDOW）。Desktop 在线编辑当前不注册（`BLOCKED: GAP-DSK-EDITOR-01`）；某端有效集合未包含该 origin 时，编辑入口显示确定状态 |
| 启用/停用/回滚 ApplicationBinding | 不需要 | 只切换运行时 projection generation |
| 为已有 platform port 更换兼容远程 provider | 不需要 | Port Router 只切换 PlatformProviderBinding generation；指同一端口已登记产品的实例、版本或配置，平台核心组件产品不可替换（DD-64/87） |
| 新增或升级 embedded/internal provider 代码（仅平台自身） | 需要 Core/Worker | 可执行代码与主体构建绑定，manifest 只能引用已有 registry key |
| 同一能力类别内切换实现 | 不需要 | 契约键不变；新建 ApplicationBinding、旧 binding 转 `DISABLED` 只读保留，ToolBinding 按契约键重绑（§2.4） |
| 只使用固定 permission 与通用 Resource/Action/Tool 语义的新能力类别或新契约版本 | 不需要 | 平台管理员经受审批的 Governed Action 在 Catalog 登记，schema 与测试向量以 digest 固定（DD-102） |
| 需要新 ProtocolSession kind、Workflow kind、能力声明、前端交付模式或 permission 的能力类别 | 需要 Core | 改变平台能力语义（DD-102） |
| 新 canonical permission、SpiceDB object type、Workflow 语义或 platform port | 需要 Core | 改变 Core 权威契约 |
| 新 extension slot；两端共用部分的 Host API 不兼容变更 | 需要 Buzz Web 与 Buzz Desktop | 宿主需理解新界面语义，两端契约必须同版本；两端是两个代码库，各自按 SS-WEB-COMPONENT-HOST、SS-DSK-COMPONENT-HOST 发布 |
| 只属于 remote module 的 Host API 变更（module 加载、`subscribePresentation`、namespaced i18n 注册等） | 只需要 Buzz Web | Desktop 不执行 `REMOTE_MODULE`（SF-DSK-03），不消费这部分 Host API |
| Adapter Protocol 不兼容变更 | 需要 Core/adapter | Dispatcher 与 adapter 协议契约改变 |

运行时注册必须同时满足：manifest schema 可解析；只使用已有 port/permission/Workflow kind/slot 与已有能力契约版本；Host API 或 Adapter Protocol range 相交；按 `admission_path` 取证的来源标识（DD-94(1)）、artifact digest、全局治理、业务可观测性、主题+i18n 和隔离合同全部通过；binding 完成 projection reconcile。任一项不成立都 fail closed，manifest 不得绕过边界。

## 10. `.references` 差异与 Release 演进

`.references/UPDATE_TASKS.json` 只告知 upstream diff，只作用于内置参考实现与平台核心。差异命中 release 引用的 SOURCE_FACT/SOURCE_SEAM 时，重验 native scope、API、状态、增量、LLM、治理和前端合同，通过后形成新 immutable release。旧 binding 继续 pin 旧 release；源码新增 endpoint、UI、Resource、Tool 或 meter 不自动进入 manifest，不自动扩大 relationship、Delegation、route 或 quota。新 release 只在 Catalog 批准、binding 变更和新 generation 对账后对新调用可见。外部实现的新 artifact version 同样形成新 immutable release，按 §2.5 重跑一致性测试套件并经平台管理员批准。
