# 组件接入标准

本文件是平台级组件、应用级组件、Component Package、Component Host 和 Component Adapter Protocol 的设计权威。Component Host 由 Buzz Web 与 Buzz Desktop 两端承载同一份契约，Buzz Mobile 不是组件宿主（REQ-11/21、DD-74）。组件保留自身数据面，但不取得 Kailo 的 Tenant、Workspace、owner、授权、审批、Workflow、Quota/Billing 或 Audit 权威。

本文同时是能力类别与版本化能力契约的接入权威（DD-88）。平台核心（Core/BFF、Application Worker、Buzz Relay 与三端 Client Surface、Codex、AgentGateway、SpiceDB、Temporal、OpenBao、OpenMeter）以 Platform Component 与平台自有模块强集成；业务能力服务（文件存储、在线文档编辑、知识库、数据查询及以后同类）只以 Application Component 按能力契约接入，数据平面解耦、可缺席、可替换，只经 Catalog/ApplicationBinding 配置与 Adapter Protocol、MCP 等协议集成（DD-87）。零业务能力 binding 时，本文全部平台机制仍成立。

## 1. Buzz 的确定起点

承载端当前没有运行时组件系统：routeTree、router、导航、`WorkspaceTool` 和内容分支均是构建期静态源码，i18n catalog 也是静态的（SF-WEB-02、SS-WEB-COMPONENT-HOST）。因此运行时注册不是 Buzz 上游现成能力，而是一次性 Buzz 二开后形成的固定产品边界。

Mattermost 只证明四个可复用机制：manifest、active manifest 快照、同源 script registration、版本 reconcile/unload（SF-MAT-01/03）；其事件路径把 payload 当完整状态，是 §4.2 明确不采用的反例（SF-MAT-06）。不复用其全局 enable、完整 Redux store、宽 PluginAPI 或本机 executable plugin：这些边界分别不满足 Tenant/Workspace 绑定、最小权限和独立服务交付（SF-MAT-02/04/05）。

一次性二开后的稳定结构为：

```text
Component Host（Buzz Web + Buzz Desktop）
        ↕ authorized runtime projection
Platform Core Catalog
        ├─ Platform Port Router → PlatformProviderBinding → platform service
        └─ Application Adapter Dispatcher → ApplicationBinding → adapter → native app
```

兼容发布在后端为独立远程服务、无后端或只引用当前主体已编译 key 时，可在运行时注册、升级、回滚和停用，无需重发 Core 或任一承载端。这不等于组件零交付：组件后端服务仍独立部署，Web artifact 仍需交付、校验和批准；新 embedded/internal 代码仍须重发对应主体（DD-59/64）。

## 2. 两类组件与两种绑定

| 分类 | 作用 | 绑定 | 当前对应 |
|---|---|---|---|
| Platform Component | 实现 Core 已知的治理与协作平台端口；属于平台核心，不可缺席 | `PlatformProviderBinding` | AgentGateway（`IDENTITY_EDGE` 与 `AI_GATEWAY` 两个 Definition）、SpiceDB（`AUTHORIZATION`）、Temporal（`APPROVAL_WORKFLOW`）、OpenMeter（`METERING_BILLING`）、OpenBao（`SECRET_STORE`）、Buzz Relay（`COLLABORATION_RELAY`） |
| Application Component | 实现某能力类别契约、为人与 Agent 提供数据或工具的业务能力服务；可缺席、可替换 | `ApplicationBinding` | 一期内置参考实现：`FILE_STORAGE`+`DOCUMENT_EDITING`（Cells 与 ONLYOFFICE 作为一个能力组件）、`KNOWLEDGE`（WeKnora）、`DATA_QUERY`（Wren），见 `08` |

平台端口只有治理与协作类：`IDENTITY_EDGE`、`AI_GATEWAY`、`AUTHORIZATION`、`APPROVAL_WORKFLOW`、`METERING_BILLING`、`SECRET_STORE`、`COLLABORATION_RELAY`，外加 Core 自身的 `CORE_INTERNAL`。业务能力不以平台端口表达；跨服务数据同步不是平台端口（DD-89）。

### 2.1 Platform Component

Platform release 只能实现 Core 已编译的 `platform_port_key`。`PlatformProviderBinding` 属于 Platform Catalog scope，固定 port、release、provider target、config/secret reference 和 active generation。Provider target 只能是独立远程服务、当前主体已编译 driver key 或 Core internal key。它不属于业务 Tenant/Workspace，不挂到 Resource/Asset，不拥有业务数据。

每个 port 同时只选一个 active provider generation。新调用解析 active generation；已开始的 ActionExecution、Workflow 和 ExternalExecution 固定旧 generation 到终态。同一 port 下的兼容远程 provider 可运行时切换。Embedded/internal binding 只能选当前 Core/Worker registry 已有代码；新 driver 或 driver 代码升级必须重发 Core/Worker（DD-64）。`EMBEDDED_DRIVER` 只属于平台自身，业务能力服务不得以嵌入式 driver 接入（DD-87）。新 platform port、新 canonical permission 或新 Workflow 语义也必须改变 Core 契约。

### 2.2 Application Component

Application release 以 `implements[category@version]` 声明实现的能力类别契约，并在该契约的标准 ResourceType 族、Action/Tool 契约键和宿主扩展槽内登记业务能力。`ApplicationBinding` 属于业务 Tenant，可进一步限定 Workspace，固定 release、所实现的能力类别、adapter service 或协议端点、native instance/scope、isolation mode、数据位置、config/secret reference 和 active generation。应用 Resource 只能指向同 Tenant 的 active ApplicationBinding。

上游应用不必原生具有 Kailo Tenant/Workspace。Adapter 必须根据固定 binding 把平台 scope 解析为该实现已证明的 native tenant、namespace、resource filter、dedicated instance 或 resource instance：内置参考实现以 `02` 的 SOURCE_FACT/SOURCE_SEAM 证明，外部实现以准入时声明、经一致性测试套件验证并由平台管理员批准的隔离模式证明（§2.5）。解析失败必须拒绝，不得回退到默认实例。

### 2.3 共享对象与不可混合的对象

```text
ComponentDefinition       稳定组件类型（PLATFORM | APPLICATION）
  └─ ComponentRelease    不可变契约和 artifact 快照
       └─ ComponentPackage  manifest 与 Web artifact 交付包

PlatformProviderBinding  只引用 PLATFORM release
ApplicationBinding       只引用 APPLICATION release
ComponentRuntimeProjection(binding kind + id + release + generation)
```

`ComponentBinding` 只是文档中对两种 binding 的总称，不是一张混合两种 scope 的业务表。

### 2.4 能力类别与能力契约

业务能力以能力类别加版本化能力契约接入（DD-88）。一期能力类别固定为四类，新增类别须改变平台契约并重发 Core：

| 能力类别 | 为人与 Agent 提供 | `type_key` 命名空间 |
|---|---|---|
| `FILE_STORAGE` | 文件目录、字节、版本与分享 | `file_storage.<kind>` |
| `DOCUMENT_EDITING` | 对 `FILE_STORAGE` ContentReference 的查看与协同编辑 | `document_editing.<kind>` |
| `KNOWLEDGE` | 企业知识的检索、问答与受控导入 | `knowledge.<kind>` |
| `DATA_QUERY` | 语义模型上的受控数据查询 | `data_query.<kind>` |

每份能力契约由平台定义，内容固定为：

- 标准 ResourceType 族与 `type_key` 命名空间 `<category>.<kind>`，`type_key` 不含产品名；
- Action/Tool 契约键 `<category>.<verb>@vN`（如 `knowledge.search@v1`）及其参数/结果 schema；
- 每个契约键到固定 SpiceDB permission（`discover/read/consume/export/update/execute/manage/audit` 等 `03` 已有 canonical permission）的映射；
- ContentReference 语义：`native_object_ref`、`native_revision` 与授权目标的判定规则（DD-90）；
- 观测、计量、取消与 Tenant 删除能力声明，缺失字段不等于 `NONE` 或 `UNSUPPORTED`；
- 一致性测试套件：在 Adapter Protocol 或所声明的标准协议线上验证契约语义、终态、幂等、取消、错误映射、redaction 与 ContentReference 往返。

一期各类别的 v1 契约键与 permission 映射固定如下；参数与结果 schema、错误映射和一致性套件以 `contracts/adapter/<category>.v1` 为唯一权威。内置参考实现对这些键的逐项映射在 `08`：

| 能力类别 | v1 契约键 → permission |
|---|---|
| `FILE_STORAGE` | `file_storage.list@v1`→`discover`；`file_storage.read@v1`、`file_storage.list_revisions@v1`→`read`；`file_storage.export@v1`→`export`；`file_storage.write@v1`→`update`；`file_storage.delete@v1`→`delete`；`file_storage.share@v1`→`share` |
| `DOCUMENT_EDITING` | `document_editing.open_view@v1`→目标 ContentReference 的 `read`；`document_editing.open_edit@v1`→`update`；会话内下载、复制、打印→`export` |
| `KNOWLEDGE` | `knowledge.search@v1`→`consume`；`knowledge.read@v1`→`read`；`knowledge.export@v1`→`export`；`knowledge.ingest@v1`→`update`；`knowledge.delete@v1`→`delete` |
| `DATA_QUERY` | `data_query.query@v1`、`data_query.dry_run@v1`→`execute`；`data_query.describe@v1`→`read`；`data_query.publish_version@v1`→`update`（经 `CAPABILITY_VERSION_PUBLISH` 收敛运行时与 MCP target） |

契约键的新增、删除或语义变化只能以新契约版本（`@v2`）发布，旧版本在兼容窗口内继续有效；实现声明 `implements[category@version]` 时必须实现该版本的全部契约键，不能只实现子集。

ComponentRelease 以 `implements[category@version]` 声明实现。`action_key`、ToolDefinition、DelegationScope、ApprovalPolicy 与 AgentVersion 能力需求只引用契约键；`component_type_key` 只记实现来源，不进入任何授权、审批或 Agent 能力判定。产品专属扩展只能位于该组件自身命名空间 `<category>.<kind>` 之下的扩展键内，不得改变契约键的语义、permission 映射或结果形状，也不得被 AgentVersion 作为能力需求引用。

同一 Tenant 或同一 Workspace 的同一能力类别同时只有一个 active ApplicationBinding。类别内切换实现是一次 `COMPONENT_BINDING` 变更：新实现以新 binding generation 对账后接管契约键，已开始的执行固定旧 generation 到终态；ToolBinding 按契约键重绑，AgentVersion 不重发（DD-92）。Workspace 在某类别下的默认 Resource 由可空的 `WorkspaceCapabilityDefault(workspace_id, category, resource_id)` 记录，它不是 Workspace `ACTIVE` 的前提（DD-90）。

平台自有能力（记忆、Buzz 消息、任务、审批等）的工具来源为 `PLATFORM_NATIVE`，不依赖任何 ApplicationBinding；业务能力工具来源为 `APPLICATION`，经 MCP 与 AgentGateway ExtMcp PEP 调用。Workspace 内某契约键没有 active 实现时，该工具 effective 状态为 `NO_PROVIDER`，AgentInstallation 仍可 `ACTIVE`（DD-92）。

### 2.5 准入路径

ComponentRelease 登记 `APPROVED` 只有两条路径（DD-88）：

| 路径 | 适用 | 准入条件 |
|---|---|---|
| 内置参考实现 | 一期随平台交付的业务能力实现（`08`） | `02` 的 SOURCE_FACT/SOURCE_SEAM 证明 native scope、API、状态与治理映射，加该能力契约的一致性测试套件全过 |
| 外部实现 | 第三方或自研实现，含闭源与 SaaS | 能力契约、一致性测试套件全过、平台管理员批准，并在 release 中声明隔离模式与数据位置；不要求 `.references` 中存在其源码 |

两条路径都经 `ComponentTaskWorkflow(kind=COMPONENT_RELEASE)` 与 ApprovalWorkflow，都受全局治理、业务可观测性、主题+i18n 与隔离合同的同一套校验。外部实现声明的隔离模式与数据位置写入 release 的 governance 段并固定 digest；声明与一致性套件结果不符即拒绝。平台核心的 Platform Component 不走外部实现路径，仍以源码证据与 Core 已编译端口准入。

### 2.6 数据存储与凭据隔离

平台核心每个服务与每个业务能力实现各自使用独立数据库实例，至少独立 database，并使用独立凭据与独立私有数据网络；禁止共用 schema 与跨库访问（DD-93）。约束固定为：

- Core 不持有任何业务能力服务的数据库凭据；平台对业务数据的一切访问只经能力契约暴露的 Resource/Action/Tool。
- 组件状态目录不放在 Core/Worker 运行体内；业务能力实现的增量状态、索引与缓存属于该实现自己的运行体与存储。
- 两个业务能力服务之间不直连数据面、不共用数据库；跨服务数据获取只按 §8.2。
- 业务能力服务的密钥由 release manifest 声明 `secret_schema`：`secret_key`、类型、长度或格式、轮换类别 `SERVICE_CREDENTIAL|DATA_KEY`、投递方式、是否需重启。Core 按通用 schema 校验并经 OpenBao 托管与投递，不内置任何产品的密钥语义；`DATA_KEY` 轮换后已存密文的重加密是该服务自己的数据平面职责，平台只按声明的轮换类别投递新版本并记录结果。
- release 声明 `data_store_isolation[DEDICATED_INSTANCE|DEDICATED_DATABASE]` 与 `data_location_ref`，随 release digest 固定，供平台管理员批准时核对；缺失任一声明的 release 不得 `APPROVED`。

## 3. Component Package 与不可变 Release

Component Package 包含：

```text
manifest
manifest digest
package digest
WebArtifactSet[path, media_type, digest][]
backend_delivery = EXTERNAL_SERVICE | BUILD_BOUND | NONE
```

Package 不包含 Core 要启动的本机 executable，也不携带 credential、native access token 或临时 URL。`EXTERNAL_SERVICE` 只表示该 release 要求独立服务，服务地址属于 binding；`BUILD_BOUND` 表示可执行代码已与主体构建绑定，package 只能引用当前 registry 已有 key，且只允许 PLATFORM release 使用；APPLICATION release 只能是 `EXTERNAL_SERVICE` 或 `NONE`（SF-MAT-05、DD-58/64/87）。

`WebArtifactSet` 的 canonical 清单整体计算 `web_artifact_set_digest`。Catalog 把每个文件固定服务于 `/component-artifacts/<release_id>/<sha256>/<path>`；entry 的静态相对 import 必须解析在同一 release 根内，绝对外域、父目录越界或未列入 artifact set 的 import 一律拒绝登记。该路径位于 Buzz Web Service Worker 的 `/app/` scope 外；snapshot endpoint 固定 `Cache-Control: no-store`。Buzz Web Caddy 只提供静态 `/app/*`，单一公开 origin 由 AgentGateway 路径前缀路由组合：`/app/*` 到 Buzz Web 静态站、`/api/*` 到 BFF、`/component-artifacts/*` 到 Core artifact handler（SF-WEB-07/08、DD-60）。

Release manifest 必须完整声明：

```text
identity
  component_type_key / release_id / semantic version / manifest_schema_version
  admission_path[BUILTIN_REFERENCE|EXTERNAL]
  BUILTIN_REFERENCE: source_project / exact source_commit
  EXTERNAL: vendor / artifact version / isolation and data location declaration

compatibility
  platform_port_key | NONE
  implements[category@version] | NONE
  host_api_range | NONE
  adapter_protocol_range | NONE

delivery
  FrontendDelivery
  ExecutionConnector
  ComponentPackage digest + WebArtifactSet

domain
  ResourceTypeDefinition[] / ActionDefinition[] / ToolDefinition[]
  target_resource_type_keys[] for capability components

governance
  isolation / call identity
  data_store_isolation / data_location_ref / secret_schema
  capability_declarations[cancel / observe / meter / tenant_delete | retain_on_tenant_delete]
  Approval / Workflow / Capacity / Quota / Meter / Audit contracts
  BusinessObservabilityContract
  IncrementalContract / LLMGatewayContract(model_call_mode)
  native status / error / cancel / idempotency / reconcile mapping
  FrontendPresentationContract
```

Release 一经 `APPROVED` 不原地修改。source commit 或外部 artifact version、schema、artifact bytes/digest、`implements[]`、Resource/Action/Tool、meter、redaction、隔离声明或兼容范围改变都生成新 release。能力进入 release 的证明按 §2.5 的准入路径：内置参考实现以 `02` 的 SOURCE_FACT/SOURCE_SEAM 和 adapter 契约证明，外部实现以能力契约一致性测试套件与平台管理员批准证明；两者都无法证明的能力不进入 release。

## 4. Component Host

### 4.1 固定宿主边界

Component Host 对承载端的一次性变更边界已由 SS-WEB-COMPONENT-HOST 定位（该接缝在 buzz-web 上取证，Buzz Desktop 因与 Web 共用同一 TypeScript 主体而适用同一改造面，SF-MOB-02）：

- 在静态 routeTree 中只增加一个 `/apps/$componentKey/$` catch-all route。
- 从 `BuzzWebApp.Workspace` 提炼 index 与 app route 共用的 `WorkspaceShell`。
- 用 surface registry 取代封闭 `WorkspaceTool` union 和硬编码内容分支。
- 导航、路由子路径、图标标识、文案 key 和排序由宿主根据 projection descriptor 渲染，不由 module 注入任意 router 或 DOM。
- 宿主保留登录、协作、审批、任务、治理、主题和 i18n 控制权。

一期扩展槽只有：

| Extension slot | 作用 | 宿主准入 |
|---|---|---|
| `MANAGEMENT_PAGE` | Platform/Tenant/Workspace 管理页及受控子路径 | descriptor scope + `discover/manage/audit` |
| `RESOURCE_VIEW` | Resource/Asset 详情、查询和动作 | Resource/Asset permission + ResultExposure |
| `CHAT_ATTACHMENT_ACTION` | 频道内的 Resource/ContentReference 打开与动作 | Workspace scope + target permission |

新 slot 是 Host API 变更，不能通过 manifest 动态创建，且两个承载端必须同时实现。

扩展槽的定位是业务能力服务的管理面与受权检视：binding 配置、Resource 详情、状态与受权查询结果的呈现。人发起的业务数据操作（上传、导入、查询、发布、分享、删除等）复用与 Agent 相同的 Governed Action/Tool 链：Browser→BFF 语义命令→Admission→Adapter Protocol 或 AgentGateway MCP→实现，不为人另开一条绕过 Tool 契约的数据通道。`HOST_NATIVE` 页面只按能力类别或通用 descriptor 渲染（如 `FILE_STORAGE` 的目录与版本视图、`KNOWLEDGE` 的检索视图、`DATA_QUERY` 的查询视图），承载端主体中禁止出现以某个产品命名或只服务某个产品的页面代码；产品专属界面只能以获批准的 `REMOTE_MODULE` 交付。没有 active 业务能力 binding 时，对应导航与槽位不渲染，平台导航不残留业务入口。

### 4.2 运行时快照、通知与 reconcile

BFF 只返回当前 PlatformSession、Tenant、Workspace 和 Principal 可发现的完整 `ComponentRuntimeProjectionSnapshot`：

```text
snapshot_generation
scope_digest
projections[
  binding_kind / binding_id / release_id / generation
  component_type_key / authorized surface descriptors
  served_entry_path / artifact digest / host_api_range
]
```

BFF session stream 只通知 `snapshot_generation` 变化，Browser 立即重取完整快照并做 set reconciliation。新增 projection 直接 load；版本变更时，新导航解析新 generation，已挂载旧 surface 保留到卸载或用户确认刷新，不能在存在未保存输入时强制 dispose；projection 消失则停止新导航并请求已打开 surface 安全关闭。断线重连、页面恢复可见或 generation 不连续时也重取完整快照。事件只是失效通知，不是授权或组件状态权威（DD-61）。Mattermost 在事件路径上把 payload 当完整状态直接 load/remove、只在重连时全量 reconcile（SF-MAT-06），是本设计明确不采用的反例。

### 4.3 前端 module 加载协议

```text
Host 按(type, release_id, generation, entry_digest)登记 pending load
→ 校验 served_entry_path 为当前 release digest 的同源内容寻址路径
→ 在现有 script-src 'self' 下注入 module script
→ module 求值期同步调用 register(descriptor)
→ Host 暂存 descriptor；script load 事件后按 pending load 全字段匹配并接受
→ module mount(host-owned root, narrow Host API)
→ snapshot 移除/变更时 dispose + unregister
```

pending load 只在 Host 内部存在，绑定 Browser session、projection、注入元素与过期时间；静态 module artifact 不携带会话 ticket。无 pending、重复 register、load 失败、字段不一致或 Host API 不兼容均拒绝。`register` 在 module 求值期只暂存 descriptor，必须等对应注入元素的 load 事件发生后才 commit，避免把无关脚本的全局调用接受为该 projection。

Host 以 try/catch 包住 `mount()` 与 `dispose()`，并监听 `window.error`/`unhandledrejection`；当 `ErrorEvent.filename` 或可解析 stack URL 命中该 generation 的 artifact 根前缀时，尽力 dispose，将 Host 侧 generation 置 `ERROR`，并在槽位显示本地化 fallback。React error boundary 不作为 remote module 隔离承诺；事件 handler、timer 与 promise 错误也走上述全局归因。该错误只改变浏览器 Host generation，不改 ApplicationBinding、native task 或后端 projection 状态。

`dispose()` 的强制合同是：清空 Host 分配的 DOM root，移除 module 自有 style、全局 listener 与 timer，注销其 i18n namespace；CSS selector 必须以 Host 注入的 `data-kailo-component=<type>` 与 `data-kailo-generation=<generation>` 双属性作用域化。ES module 代码本身不会从同一 window 卸载，因此旧 generation 不得再次 mount；无法履行 dispose 的 release 在 Catalog 登记时拒绝。

`source_entry_url` 只供 Catalog 登记流程取件。批准前按密码学 digest 固定 bytes，Browser 只请求同源 immutable `served_entry_path`，不请求外域 script，不放宽承载端当前 `script-src 'self'`（SF-WEB-06、SF-MAT-01/03、DD-60）。

Remote module 是平台管理员批准的同窗口信任代码，不是安全沙箱。Tenant 管理员只能启用已批准 release，不能上传或替换 JavaScript。

### 4.4 窄 Host API

Host API 只提供：

- 当前受限 scope 和 FrontendPresentationContext 读取；
- BFF Resource query；
- action preview 与 semantic command；
- Task/Approval/operation 状态订阅；
- 受权导航、`subscribePresentation(cb)` 与 namespaced `hostI18n.t(namespace,key)` 注册。

Module 不获得完整宿主 store、Relay signer、ActionToken signing key、native credential 或 SpiceDB/Temporal/OpenMeter/AgentGateway 管理凭据。即使 module 自行发起同源 BFF 请求，BFF 仍对每个 query/action 重做 session、scope、SpiceDB、Approval、Quota 和 Audit 准入；前端代码不是授权边界。

### 4.5 主题与 i18n

- `HOST_NATIVE` 直接使用 Buzz CSS variables、`MessageKey/t/getLocale`。
- `REMOTE_MODULE` 通过 `subscribePresentation(cb)` 持续接收 resolved `LIGHT/DARK` 与 `EN/ZH_CN`，使用 Buzz tokens；不得只在 mount 时读取一次。Catalog 登记时校验 namespaced `en` 与 `zh-CN` catalog 的 key 集完全一致且覆盖 manifest 声明的全部 key，不一致即拒绝 release；remote key 不进入 Buzz 封闭的 `MessageKey` 类型或本地 `check-i18n` 扫描面（SF-WEB-03/08、SS-WEB-COMPONENT-HOST）。
- `SOURCE_BOUND_PROTOCOL` 只使用该实现已证明的 launch 映射，每次 launch 固定 theme/locale；内置参考实现的映射证据见 `18`（SF-WEB-03、SF-OFF-07）。
- 不能接受 presentation contract 的原生 UI 不嵌入任一承载端。native error 原文只作受权 evidence，用户界面使用宿主稳定 code 和 i18n key。

Iframe 不是常规组件形态，因为它无法保证 Host API、主题、i18n 和逐动作治理。只有 WOPI 类协议型编辑器这样、宿主与编辑器之间固定协议已按 §2.5 准入路径证明的 `SOURCE_BOUND_PROTOCOL` 才能使用隔离页面；承载端只有一个通用 `SOURCE_BOUND_PROTOCOL` surface，按 `DOCUMENT_EDITING` 契约消费 BFF 下发的 launch descriptor，不含产品专名分支。Workspace 没有 active `DOCUMENT_EDITING` binding 时，`FILE_STORAGE` 文件只显示元数据与受权下载（REQ-07）。

## 5. Component Adapter Protocol

### 5.1 与上游项目形态解耦

| Connector | 适用条件 | 边界 |
|---|---|---|
| `PLATFORM_PORT_CLIENT` | Platform Component 实现已知 port | Core typed client 通过 Port Router 调 provider；不再套 application adapter |
| `REMOTE_ADAPTER` | Application Component 默认形态 | Core/Worker 调独立 adapter，adapter 调 native API |
| `EMBEDDED_DRIVER` | 仅平台自身，上游明确提供 library runtime | 代码与 Core/Worker 构建绑定；业务能力服务不得使用（DD-64/87） |
| `PROTOCOL_PEER` | Application Component 经 binding 配置的标准协议（MCP、WOPI 等） | 协议由能力契约或标准定义，端点属于 binding 配置，不写死产品配对；平台宿主或 AgentGateway 是协议一端，不用于两个业务能力服务之间的数据面直连 |
| `INTERNAL` | Core 自身领域 | 不生成网络 adapter 或自签 token 循环 |

业务能力服务只使用 `REMOTE_ADAPTER` 或经 binding 配置的标准协议（`PROTOCOL_PEER`）。一个能力组件内部为实现其契约而使用的协议（如内置参考实现中 Cells 与 ONLYOFFICE 之间的 WOPI）属于该组件内部集成，对平台仍是一个 ApplicationBinding，不构成两个服务之间的平台级连接（DD-90）。

业务能力实现可保持原 monolith/service，不需要为 Buzz 强拆前后端。Remote adapter 只在稳定 native API 上实现能力契约；Buzz 端使用 `HOST_NATIVE`（按能力类别渲染）或获批准 `REMOTE_MODULE`，不嵌入原生管理后台。内置参考实现的 native API 证据见 `08`（SF-CEL-01/03、SF-WEK-01/03、SF-WRN-01、DD-58）。

### 5.2 版本化深接口

Adapter Protocol 只包含以下逻辑操作，传输编码由 release 的协议版本固定：

```text
handshake(protocol range, component/release identity, capabilities)
validate_binding(binding ref/version, normalized config digest, secret ref versions)
resolve_native_scope(binding ref, platform resource ref)
execute(action key/version, normalized args, ActionToken)
observe(external execution ref, ActionToken)
cancel(external execution ref, ActionToken)
reconcile(binding or execution ref, ActionToken)
extract_usage(native evidence ref)
map_native_status_error(native status/error)
```

Handshake 成功只证明协议兼容，不表示 binding active。Binding 只在 service identity、config digest、SecretRef audience/version、native scope、隔离方式、capability 和全部 projection 对账后 active。

Core 在 dispatch 前完成准入。ActionToken 固定 issuer/audience、Tenant/Workspace、actor、delegation、action/version、target、operation、parameter hash、ResultExposure 和短 expiry。Adapter 校验 token 后仍按 `03` 的 PEP 合同将请求收窄到 binding 已固定 native scope。Adapter 不接受 payload 自报 Tenant/Workspace、不自行扩大权限、不回退默认实例（DD-63）。

真实副作用在 dispatch 前建立 ExternalExecution 和稳定 operation/idempotency key。超时且无 native query/dedupe 接缝时进入 `UNKNOWN`，不自动重发。Adapter 只映射源码存在的 progress/cancel/terminal；HTTP 200/202、queued 或 cancel accepted 都不等于业务完成。

## 6. 两类 Binding 的生命周期

### 6.1 PlatformProviderBinding

```text
approved PLATFORM release
→ create/upgrade provider binding for exact known port
→ PENDING projection generation
→ validate connector/target registry/service identity/config/secret/readiness/governance
→ Port Router atomically selects ACTIVE generation for new calls
```

变更由 Platform Catalog Tenant 的 `ComponentTaskWorkflow(kind=COMPONENT_BINDING, binding_kind=PLATFORM_PROVIDER)` 承接。旧 generation 保留给已开始调用；新 generation 校验失败不切流。安全撤销导致 provider fail closed，不静默切换未批准实现。

### 6.2 ApplicationBinding

```text
approved APPLICATION release
→ Tenant/Workspace creates or upgrades exact binding
→ PENDING projection generation
→ validate adapter handshake/config/secret/native scope/isolation/governance/Web artifact
→ reconcile Resource/Action/Tool/Gateway/route/observability projections
→ atomically select ACTIVE generation
```

变更由业务 Tenant/Workspace 的 `ComponentTaskWorkflow(kind=COMPONENT_BINDING, binding_kind=APPLICATION)` 承接。已开始的 ActionExecution/Workflow/ExternalExecution 继续使用旧 generation；新 Action 只解析 active generation。Rollback 也创建新 generation，不改写旧 release 或历史执行。

### 6.3 Disable

两类 binding 的停用都使用 `ComponentTaskWorkflow(kind=COMPONENT_DISABLE, binding_kind=...)`。Core 先置 `DISABLING` 并停止新 discovery/action/call，再暂停 Schedule、撤授权/route/tool/Web projection、观察已运行 execution 并对账 usage/audit。Disable 不删除 Resource/Asset/native data；保留或不明 ref 存在时不伪造已收敛。业务能力 binding 停用只影响它提供的契约键：对应 `APPLICATION` 工具 effective 变为 `NO_PROVIDER`（该类别无其他 active 实现）或 `DISABLED`，AgentInstallation、协作、记忆与 `PLATFORM_NATIVE` 工具不受影响（DD-92）。

## 7. 全局治理契约

每个用户、Agent、Schedule、callback 或 Workflow 可达 action 必须声明：

| 贯穿项 | Release 声明 | 运行时强制点 |
|---|---|---|
| Tenant | scope rule、binding isolation、native scope derivation | Core 从 session/parent action 构造；adapter 不接受自报 |
| Workspace | WorkspaceRule 与 binding scope | scope guard 先于 Resource permission；execution 固定 scope |
| Authorization | canonical permission、target、ResultExposure | SpiceDB fresh Check；Agent 另与 Delegation/ToolBinding 求交 |
| Approval | confirmation mode、ApprovalPolicy、owner rule | Temporal Approval 固定 exact action/parameter/owner/policy version，消费前重检 |
| Workflow | `SYNC/PROTOCOL/TEMPORAL`、kind、idempotency/UNKNOWN/cancel | Temporal 持有持久生命周期；native task 是 ExternalExecution |
| Capacity/Quota/Billing | capacity/quota mode、meter、strict upper bound | CapacityLease/QuotaReservation/OpenMeter；actual usage 只有一个 source |
| Operation Audit | intent/decision/dispatch/outcome/revoke/reconcile 与 redaction | 外部副作用前先持久 intent；结果沿同一 operation 追加 |
| Business Observability | correlation、terminal/progress/usage/cost source 和 redaction | operation→release/binding generation→native evidence→usage/cost 的受权联合视图 |

`NONE` 只能是明确策略值，缺失字段不等于 `NONE`。平台 provider 的内部 RPC 继承父 operation，不递归创建 Governed Action；任何用户可达的 provider 管理动作仍完整经过上表。

## 8. Resource 附加合同

### 8.1 IncrementalContract

每个 ResourceType 至少登记 `NATIVE_INTERNAL` 或 `VERSIONED_PUBLICATION`：前者表示新增、修改、删除与处理逻辑变更的增量、对账和就绪全在该实现内部完成，并经 Adapter Protocol 暴露稳定 native ref、revision 与 ready/failed/unknown 状态；后者表示以完整版本发布替换；业务能力实现的版本发布与下线收敛由通用 `ComponentTaskWorkflow(kind=CAPABILITY_VERSION_PUBLISH)` 承接，Workflow 只依能力契约与 binding 固定的版本 Resource/Asset 工作，不含产品专属步骤（DD-90）。只提供 mtime、只 create 无 delete/readiness 或要求平台直写组件数据库的类型不得登记为 active。

平台不接管组件内部索引，不持有逐项增量状态，不为业务数据建立跨 Resource 的派生副本；平台不存在物化端口、物化 binding 或物化 Workflow kind（DD-89）。完整规则以 `13` 为准。

### 8.2 跨服务数据获取

一个业务能力服务需要另一服务的数据时只有两条路径（DD-89）：

1. **接收方自拉**：接收方在自己的管理面（经 Component Host 露出）配置数据源连接器。平台以既有机制授权：一个 Governed Action（按 ApprovalPolicy 可含来源 Resource owner 审批）为接收方 binding 的 ServicePrincipal 写入来源 Resource 的 `reader` 关系，并投递受限凭据 SecretRef；接收方经来源方公开的能力契约自行拉取。增量、状态、去重与删除收敛全在接收方内部，Core 不感知其状态。撤销该 `reader` 关系即收回读取权，来源方 PEP 对后续读取 fresh 拒绝；接收方已取得数据的处置由接收方按其能力契约声明的删除语义负责。
2. **人或 Agent 显式读写**：人或 Agent 经两边各自暴露的 Tool 显式读取一侧、写入另一侧，每一步都是独立 Governed Action，各自授权、审批、计量与审计。

平台只治理授权与动作，不经手数据、不持有同步状态、不以 Schedule 或 Workflow 编排跨服务同步。两个业务能力服务之间不建立平台配置的数据面直连（§5.1）。

### 8.3 LLMGatewayContract

业务能力服务的模型调用由 ApplicationBinding 声明两种模式之一（DD-92）：

| `model_call_mode` | 合同 | 计量 |
|---|---|---|
| `PLATFORM_LLM_ROUTE` | 服务的模型 base URL 经 binding 配置指向 AgentGateway `llm_route`；协议必须属于 AgentGateway 已实现的 Chat/Responses/Embeddings/Messages/Gemini/Rerank，provider credential 只存在 Gateway SecretRef（SF-AGW-04/05） | Actual token/cost 只取 SS-AGW-USAGE 闭合后的 durable usage 并写 OpenMeter，组件自报 token 不形成第二份账 |
| `SELF_MANAGED_MODEL` | 服务自管模型与凭据，平台不向服务数据写入模型配置 | 服务经 Adapter Protocol `extract_usage` 上报 usage；平台照常执行 Quota 与审计 |
| `NONE` | 实现不调用模型 | 无模型 usage |

逐调用关联以标准 W3C `traceparent` 与 operation 头为可选增强：存在时把模型调用归因到平台 operation，缺失只降低成本归因精度，不阻断 binding `ACTIVE`。平台自有 Agent 的模型调用始终经 AgentGateway，不受本节模式选择影响。

### 8.4 Transfer 与 Tenant delete

`transfer_formats[]` 必须同时证明 export、import/create、format/version、digest、terminal 和错误语义；缺任一端则不注册跨 Tenant Action。组件停用不等于删除 native data。

Tenant 销毁以平台自有事实为前提（DD-91）。每个 ApplicationBinding 的 native 删除是 Tenant 删除中独立的子流程，由能力契约的 Tenant 删除能力声明决定：

- 声明支持删除的实现必须提供稳定 native ref、幂等 delete、terminal query 和 retained-error 语义，登记 `tenant_delete_action_key`；
- 不具备的实现在准入时声明 `retain_on_tenant_delete`：Tenant 删除时撤该 binding、撤凭据、保留审计，并把该 binding 的 native 数据登记为待人工处置项，不阻断平台 Tenant 状态机。

任何业务能力实现的删除缺口只影响该实现自身的删除子流程，不阻断平台 Tenant 生命周期。

## 8.1 第三方接入面

`REQ-11` 保证组件可在运行时注册，`REQ-22` 保证第三方能在开发期独立做出组件。后者的交付物固定为六件，与 Component Host 同 Stage 交付（`DD-76`）：

| 接入面 | 内容 | 来源 |
|---|---|---|
| Component SDK | TypeScript 包：Host API 类型与调用封装、Adapter Protocol 客户端/服务端骨架、错误六分类与 reason code 常量、slot descriptor 构造 | 由 `contracts/` 生成或派生，不手写 |
| manifest schema 与校验器 | 可本地运行的 manifest 校验，错误信息指向具体字段与允许取值 | 本文 §3 的 manifest 定义 |
| 脚手架 | 生成含前端 module、后端 adapter、manifest 与一致性测试配置的最小可运行组件 | — |
| 本地开发环境 | 不接真实平台即可加载 module、应答 Adapter Protocol、模拟 binding 与 presentation context | — |
| 一致性测试套件 | 在 Adapter Protocol 线协议层验证 handshake、终态语义、幂等、取消、错误映射与 redaction；按 `implements[]` 叠加对应能力契约的契约键语义、permission 映射与 ContentReference 往返 | 本文 §2.4、§5 与 `03-领域模型与权限模型.md` 的状态约束 |
| 示例组件 | 一个端到端参考实现，覆盖三个扩展槽中至少一个与一条 Tool 路径 | — |

约束：

- SDK 是 `contracts/` 的消费者，不是第二权威；两者冲突以 `contracts/` 为准，`contracts/` 与本文冲突以本文为准。
- 前端 remote module 只能是 TypeScript，由承载端运行时决定；后端 adapter 的契约是线协议，因此首方不承诺多语言 SDK，任意语言实现以一致性套件自证。
- 接入面随 Host API 与 Adapter Protocol 的 range 一起版本化。新增扩展槽或 Host API 不兼容变更时，接入面必须同步发布，否则第三方拿到的类型与真实宿主不一致。
- 一致性套件通过是登记 release 的必要条件，不是充分条件；平台管理员批准、digest 固定、隔离与数据位置声明核对和全局治理校验仍然独立执行。外部实现（含闭源与 SaaS）以该套件作为源码证据的替代，按 §2.5 准入。
- 接入面不暴露平台内部实体、SpiceDB schema、Core 数据库结构或任何 service credential。

## 9. 无需重发 Core/承载端的精确边界

| 变化 | Core/承载端重发 | 原因 |
|---|---|---|
| 新增/升级兼容 Application release | 不需要 | 使用已有 manifest、Adapter Protocol、Resource/Action/Tool 和 slot |
| 启用/停用/回滚 ApplicationBinding | 不需要 | 只切换运行时 projection generation |
| 为已有 platform port 更换兼容远程 provider | 不需要 | Port Router 只切换 PlatformProviderBinding generation |
| 新增或升级 embedded/internal provider 代码（仅平台自身） | 需要 Core/Worker | 可执行代码与主体构建绑定，manifest 只能引用已有 registry key |
| 同一能力类别内切换实现 | 不需要 | 契约键不变，只切换 ApplicationBinding generation；ToolBinding 按契约键重绑 |
| 新能力类别或能力契约不兼容版本 | 需要 Core | 改变平台能力契约 |
| 新 canonical permission、SpiceDB object type、Workflow 语义或 platform port | 需要 Core | 改变 Core 权威契约 |
| 新 extension slot、Host API 不兼容变更 | 需要 Buzz Web 与 Buzz Desktop | 宿主需理解新界面语义，两端契约必须同版本 |
| Adapter Protocol 不兼容变更 | 需要 Core/adapter | Dispatcher 与 adapter 协议契约改变 |

运行时注册必须同时满足：manifest schema 可解析；只使用已有 port/permission/Workflow kind/slot 与已有能力契约版本；Host API 或 Adapter Protocol range 相交；source baseline、artifact digest、全局治理、业务可观测性、主题+i18n 和隔离合同全部通过；binding 完成 projection reconcile。任一项不成立都 fail closed，manifest 不得绕过边界。

## 10. `.references` 差异与 Release 演进

`.references/UPDATE_TASKS.json` 只告知 upstream diff，只作用于内置参考实现与平台核心。差异命中 release 引用的 SOURCE_FACT/SOURCE_SEAM 时，重验 native scope、API、状态、增量、LLM、治理和前端合同，通过后形成新 immutable release。旧 binding 继续 pin 旧 release；源码新增 endpoint、UI、Resource、Tool 或 meter 不自动进入 manifest，不自动扩大 relationship、Delegation、route 或 quota。新 release 只在 Catalog 批准、binding 变更和新 generation 对账后对新调用可见。外部实现的新 artifact version 同样形成新 immutable release，按 §2.5 重跑一致性测试套件并经平台管理员批准。
