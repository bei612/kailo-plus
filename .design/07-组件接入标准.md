# 组件接入标准

本文件是平台级组件、应用级组件、Component Package、Component Host 和 Component Adapter Protocol 的设计权威。Component Host 由 Buzz Web 与 Buzz Desktop 两端承载同一份契约：两端是两个上游代码库，共享由 Buzz 原版提取的 TypeScript 页面、组件与交互主体，以及 Kailo 平台包与契约生成物；两端只在认证、签名、传输和宿主能力适配处区分，各自以 SS-WEB-COMPONENT-HOST、SS-DSK-COMPONENT-HOST 接入；Desktop 不执行 `REMOTE_MODULE`（SF-DSK-03）。Buzz Mobile 不是组件宿主（REQ-11/21、DD-74）。外部组件独立运行、独立管理，保留原生后台与直接访问入口；可复用平台公共服务并通过宿主打开完整原生页面，但不取得 Kailo 的 Tenant、Workspace、owner、授权、审批、Workflow、Quota/Billing 或 Audit 权威。

本文同时是能力类别与版本化能力契约的接入权威（DD-88）。平台核心（Core/BFF、Application Worker、Buzz Relay 与三端 Client Surface、Codex、AgentGateway、SpiceDB、Temporal、OpenBao、OpenMeter）以 Platform Component 与平台自有模块强集成；业务能力服务（文件存储、在线文档编辑、知识库、数据查询及以后同类）只以 Application Component 按能力契约接入，数据平面解耦、可缺席、可替换，只经 Catalog/ApplicationBinding 配置与 Adapter Protocol、MCP 等协议集成（DD-87）。零业务能力 binding 时，本文全部平台机制仍成立。本文的 binding、治理与收敛合同只覆盖 Kailo 接入及公共服务调用，不要求平台接管外部服务的全部内部业务、任务或部署。工具实际通过 AgentGateway 注册、发现与调用；Core Catalog 与 ToolBinding 仅为治理元数据和投影引用，不是第二工具注册中心。

## 1. Buzz 的确定起点

承载端当前没有运行时组件系统：routeTree、router、导航、`WorkspaceTool` 和内容分支均是构建期静态源码，i18n catalog 也是静态的（Web：SF-WEB-02、SS-WEB-COMPONENT-HOST；Desktop：`routes.ts` 显式列举生成的静态 routeTree 与 `AppSidebar` 的固定 props，SS-DSK-COMPONENT-HOST）。因此运行时注册不是 Buzz 上游现成能力，而是一次性 Buzz 二开后形成的固定产品边界。

Mattermost 只证明四个可复用机制：manifest、active manifest 快照、同源 script registration、版本 reconcile/unload（SF-MAT-01/03）；其事件路径把 payload 当完整状态，是 §4.2 明确不采用的反例（SF-MAT-06）。不复用其全局 enable、完整 Redux store、宽 PluginAPI 或本机 executable plugin：这些边界分别不满足 Tenant/Workspace 绑定、最小权限和独立服务交付（SF-MAT-02/04/05）。

一次性二开后的稳定结构为：

```text
Component Host（Buzz Web + Buzz Desktop）
        ↕ authorized runtime projection
Platform Core Catalog
        ├─ Platform Port Router → PlatformProviderBinding → platform service
        └─ Application Adapter Dispatcher → ApplicationBinding → adapter → native app
```

兼容发布在后端为独立远程服务、无后端或只引用当前主体已编译 key 时，可在运行时注册、升级、回滚和停用，无需重发 Core 或任一承载端；唯一例外是 release 引入部署级许可集合中尚未包含的 editor origin（DD-95）：Web 重启静态服务；Desktop 由 BFF 运行时下发新的许可集合，不需要发布新包（DD-104、§9）。这不等于组件零交付：组件后端服务仍独立部署，Web artifact 仍需交付、校验和批准；新 embedded/internal 代码仍须重发对应主体（DD-59/64）。

## 2. 两类组件与两种绑定

| 分类 | 作用 | 绑定 | 当前对应 |
|---|---|---|---|
| Platform Component | 实现 Core 已知的治理与协作平台端口；属于平台核心，不可缺席 | `PlatformProviderBinding` | AgentGateway（`IDENTITY_EDGE` 与 `AI_GATEWAY` 两个 Definition）、SpiceDB（`AUTHORIZATION`）、Temporal（`APPROVAL_WORKFLOW`）、OpenMeter（`METERING_BILLING`）、OpenBao（`SECRET_STORE`）、Buzz Relay（`COLLABORATION_RELAY`） |
| Application Component | 实现某能力类别契约、为人与 Agent 提供数据或工具的业务能力服务；可缺席、可替换 | `ApplicationBinding` | 一期内置参考实现：`FILE_STORAGE`（Cells 与 ONLYOFFICE 作为一个能力组件，声明 `online_editing=SUPPORTED`，DD-103）、`KNOWLEDGE`（WeKnora）、`DATA_QUERY`（Wren），见 `08` |

平台端口只有治理与协作类：`IDENTITY_EDGE`、`AI_GATEWAY`、`AUTHORIZATION`、`APPROVAL_WORKFLOW`、`METERING_BILLING`、`SECRET_STORE`、`COLLABORATION_RELAY`，外加 Core 自身的 `CORE_INTERNAL`。业务能力不以平台端口表达；跨服务数据同步不是平台端口（DD-89）。

### 2.1 Platform Component

Platform release 只能实现 Core 已编译的 `platform_port_key`。`PlatformProviderBinding` 属于 Platform Catalog scope，固定 port、release、provider target、config/secret reference 和 active generation。Provider target 只能是独立远程服务、当前主体已编译 driver key 或 Core internal key。它不属于业务 Tenant/Workspace，不挂到 Resource/Asset，不拥有业务数据。

每个 port 同时只选一个 active provider generation。新调用解析 active generation；已开始的 ActionExecution、Workflow 和 ExternalExecution 固定旧 generation 到终态。同一 port 下的兼容远程 provider 可运行时切换；切换指同一端口已登记产品的实例、版本或配置，平台核心组件产品本身不可替换（DD-64/87）。Embedded/internal binding 只能选当前 Core/Worker registry 已有代码；新 driver 或 driver 代码升级必须重发 Core/Worker（DD-64）。`EMBEDDED_DRIVER` 只属于平台自身，业务能力服务不得以嵌入式 driver 接入（DD-87）。新 platform port、新 canonical permission 或新 Workflow 语义也必须改变 Core 契约。

### 2.2 Application Component

Application release 以 `implements[category@version]` 声明实现的能力类别契约，并在该契约的标准 ResourceType 族、Action/Tool 契约键和宿主扩展槽内登记业务能力。`ApplicationBinding` 属于业务 Tenant，可进一步限定 Workspace，固定 release、在 release `implements[]` 内实际启用的能力类别（`capability_categories[]`）、adapter service 或协议端点、native instance/scope、isolation mode、`model_call_mode`、`retain_on_tenant_delete`、config/secret reference 和 active generation。release 放声明与上界，binding 只放上界内的选择：数据存储隔离与数据位置只由 release 声明，binding 的 `model_call_mode` 必须属于 release 的 `allowed_model_call_modes[]`，`retain_on_tenant_delete` 必须与 release 的 Tenant 删除声明一致（`03` §3）。应用 Resource 是 Core 对外部对象的授权引用，只经 `resource.create` 首次登记：同 Tenant active ApplicationBinding、HUMAN accountable owner、Core 事实与 SpiceDB relationship 沿原准入。已有对象以冻结 binding/native scope 的原生协议证据或可信运行投递事实核实；裸 native ID 不自动 `ACTIVE`，不能证明归属则登记能力未闭合。同一绑定/引用复用原 Resource，不重复建立 owner/ACL；未知只核原引用，不发 CREATE。只有明确支持的 `REMOTE_ADAPTER` 原生创建才执行原 `resolve_native_scope(CREATE/LOOKUP)` 流程（DD-98）；平台 owner 不改变服务自己的 owner/ACL 或授予上游 admin。binding 转 `DISABLED` 后其 Resource 保留只读（§2.4）。

上游应用不必原生具有 Kailo Tenant/Workspace。Adapter 必须根据固定 binding 把平台 scope 解析为该实现已证明的 native tenant、namespace、resource filter、dedicated instance 或 resource instance：内置参考实现以 `02` 的 SOURCE_FACT/SOURCE_SEAM 证明，外部实现以准入时声明、经一致性测试套件验证并由平台管理员批准的隔离模式证明（§2.5）。解析失败必须拒绝，不得回退到默认实例。

### 2.3 共享对象与不可混合的对象

```text
ComponentDefinition       稳定组件类型（PLATFORM | APPLICATION）
  └─ ComponentRelease    不可变契约和 artifact 快照
       └─ ComponentPackage  manifest 与 Web artifact 交付包

PlatformProviderBinding  只引用 PLATFORM release
ApplicationBinding       只引用 APPLICATION release
ComponentRuntimeProjection(binding kind + id + release + generation)
```

`ComponentBinding` 只是文档中对两种 binding 的总称，不是一张混合两种 scope 的业务表。

Huddle 语音推理进程（DD-125(3)）不是 Platform Component 或 Application Component：它不实现平台端口或能力类别契约，没有 ComponentDefinition、release 或 binding，不登记 Resource、Action、Tool 或 Route，也不出现在 Catalog 或宿主菜单中；它只是 Core 在 Web Huddle 中为本人转写与朗读调用的无状态内部计算服务，部署登记只有内网地址与并发上界。

### 2.4 能力类别与能力契约

业务能力以能力类别加版本化能力契约接入（DD-88）。能力类别与契约是 Platform Catalog 的运行时数据（DD-102）：下表三类是随平台构建交付的预置种子，Catalog 启用时由部署引导一次性登记为 `ACTIVE`（DD-108）；只使用固定 permission 与通用 Resource/Action/Tool 语义的新类别或新契约版本由平台管理员经受审批的 Governed Action 登记，不需要发版；需要新 ProtocolSession kind、Workflow kind、能力声明、前端交付模式或 permission 的类别只能随 Core 发版加入。预置种子为：

| 能力类别 | 为人与 Agent 提供 | `type_key` 命名空间 |
|---|---|---|
| `FILE_STORAGE` | 文件目录、字节、版本与分享；实现可另声明条件能力 `online_editing=SUPPORTED`，对本实现自己的 ContentReference 提供查看与协同编辑，以 DocumentLaunchDescriptor 启动（DD-90/95/103） | `file_storage.<kind>` |
| `KNOWLEDGE` | 企业知识的检索、问答与受控导入 | `knowledge.<kind>` |
| `DATA_QUERY` | 受控数据查询（text2sql 等） | `data_query.<kind>` |

每份能力契约由平台定义，内容固定为：

- 标准 ResourceType 族与 `type_key` 命名空间 `<category>.<kind>`，`type_key` 不含产品名；
- Action/Tool 契约键 `<category>.<verb>@vN`（如 `knowledge.search@v1`）及其参数/结果 schema；
- 每个契约键到固定 SpiceDB permission（`discover/read/consume/export/update/execute/manage/audit` 等 `03` 已有 canonical permission）的映射；
- ContentReference 语义：`native_object_ref`、`native_revision` 与授权目标的判定规则（DD-90）；返回 ContentReference 的结果（如 `KNOWLEDGE` 检索的 citation）由实现的 adapter 按契约直接给出，BFF 只做授权与解析，不调用实现的原生接口重建；
- 协议会话类能力的启动描述：`file_storage.v1` 为声明 `online_editing=SUPPORTED` 的实现定义与产品无关的 `DocumentLaunchDescriptor(method[GET|POST], action_url, form_fields{string→string}, editor_origin, expires_at)`。launch 请求携带 Buzz 已解析的 theme 与 locale（主题语义值与 `en/zh-CN`），descriptor 由目标 ContentReference 所属 ApplicationBinding 的 adapter 生成，实现私有的参数映射、协议发现与 action 选择（如 WOPI discovery）全在 adapter 内；Core 只校验 `editor_origin` 属于该 release 登记的 `editor_origins[]` 且等于该 binding 固定的实例 origin（release 以 host 通配登记时也逐 binding 精确比对）、`action_url` 的 origin 等于 `editor_origin`、字段均为字符串且未过期，再原样下发（DD-95/103）；
- 观测、计量、取消、revision 查询、版本化模型（`versioned_model`）、在线编辑（`online_editing`）、服务读取边（`read_edge`，§8.2）与 Tenant 删除能力声明，缺失字段不等于 `NONE` 或 `UNSUPPORTED`；revision 查询指按 `native_object_ref` 查询当前 revision（Adapter Protocol `query_revision`），`FILE_STORAGE` 实现未声明 `revision_query=SUPPORTED` 时不得声明 `online_editing=SUPPORTED`（DD-90/103）；
- 一致性测试套件：在 Adapter Protocol 或所声明的标准协议线上验证契约语义、终态、幂等、取消、错误映射、redaction 与 ContentReference 往返。

预置种子各类别的 v1 契约键与 permission 映射固定如下；种子的参数与结果 schema、错误映射和一致性套件以 `contracts/adapter/<category>.v1` 为唯一权威。运行时登记的契约，其 schema 与一致性套件测试向量以 digest 固定在 Catalog 中，由平台发布的通用一致性套件运行器执行（DD-102）。内置参考实现对这些键的逐项映射在 `08`：

| 能力类别 | v1 契约键 → permission |
|---|---|
| `FILE_STORAGE` | `file_storage.list@v1`→`discover`；`file_storage.read@v1`、`file_storage.list_revisions@v1`→`read`；`file_storage.export@v1`→`export`；`file_storage.write@v1`→`update`；`file_storage.delete@v1`→`delete`；`file_storage.share@v1`→`share`；条件键 `file_storage.open_view@v1`→目标 ContentReference 的 `read`、`file_storage.open_edit@v1`→`update`（会话内下载、复制、打印→`export`），仅 `online_editing=SUPPORTED` 的实现实现并暴露，ProtocolSession kind 为 `file_storage.edit_session`（DD-103） |
| `KNOWLEDGE` | `knowledge.search@v1`→`consume`；`knowledge.read@v1`→`read`；`knowledge.export@v1`→`export`；`knowledge.ingest@v1`→`update`；`knowledge.delete@v1`→`delete` |
| `DATA_QUERY` | `data_query.query@v1`、`data_query.dry_run@v1`→`execute`；`data_query.describe@v1`→`read`；条件键 `data_query.publish_version@v1`→`update`，仅 `versioned_model=SUPPORTED` 的实现实现并暴露，经 `CAPABILITY_VERSION_PUBLISH` 收敛该版本的运行时与工具端点（DD-90） |

契约键的新增、删除或语义变化只能以新契约版本（`@v2`）发布，旧版本在兼容窗口内继续有效；契约键分必选键与条件键：条件键只随实现在 release 中声明 `SUPPORTED` 的对应能力（如 `versioned_model`）一起实现，未声明即不实现、不暴露；实现声明 `implements[category@version]` 时必须实现该版本的全部必选键，以及其已声明能力所对应的条件键，不能只实现子集（DD-88）。上表未标“条件键”的均为必选键。

一致性向量的值来源、绑定与比对按 DD-124：向量格式 `V2` 只允许 `LITERAL`、`PRECONDITION`、`CAPTURE` 三种来源；契约定义为实现生成的标识（`native_revision`、`generated_refs[]` 列出的输出字段与 Core 生成的执行标识）只能以 `CAPTURE` 出现，任何实现都不能经原生入口满足的字面期望不得登记。种子 `file_storage@1` 的向量含此类字面值，现行版本为 `file_storage@2`：键、permission 映射、schema、条件键与声明同 @1，键后缀 `@v2`。`KNOWLEDGE` 的服务读取边接收方契约现行版本为 `knowledge@3`：在 v1 键之外含 `NATIVE_MANAGED` 接收方键 `knowledge.sync_apply@v3`→`update`、`knowledge.sync_retire@v3`→`delete`，ingest 经 `READ_EDGE` 消费来源 ContentReference；`knowledge@2` 的向量同样不可满足，不 approve。`DATA_QUERY` 现行版本为 `data_query@2`：键后缀 `@v2`，permission 映射、条件键与声明同 @1；`data_query@1` 的 schema 把实现生成的 `deploymentId`、`deploymentHash` 与 ContentReference `native_revision` 定型为单一实现的整数与十六进制格式，@2 只把这三个成员改为不透明非空字符串（DD-124(1)(3)）。

ComponentRelease 以 `implements[category@version]` 声明实现。`action_key`、ToolDefinition、DelegationScope、ApprovalPolicy 与 AgentVersion 能力需求只引用契约键；`component_type_key` 只记实现来源，不进入任何授权、审批或 Agent 能力判定。产品专属扩展只能位于该组件自身命名空间 `<category>.<kind>` 之下的扩展键内，不得改变契约键的语义、permission 映射或结果形状，也不得被 AgentVersion 作为能力需求引用。

同一 Tenant 或同一 Workspace 的同一能力类别同时只有一个 active ApplicationBinding。Workspace 级 binding 在该 Workspace 内覆盖 Tenant 级 binding，Workspace 未绑定该类别时解析到 Tenant 级 binding；ToolBinding 与 WorkspaceCapabilityDefault 都按这一顺序解析（DD-88）。

ComponentRelease 只声明门禁已闭合的能力类别，未闭合的类别在后续 release 中加入，不存在按类别部分激活的 binding（DD-88）。类别内切换实现是「新建 binding、旧 binding 转 `DISABLED` 只读保留」，不是在旧 binding 上换 generation：新 binding 经 `COMPONENT_BINDING` 对账到 `ACTIVE` 接管契约键，旧 binding 经 `COMPONENT_DISABLE` 转 `DISABLED`，已开始的执行固定旧 binding/generation 到终态。旧 binding 下的 Resource 转为保留只读，只可 discover 元数据、不可发起新动作；指向旧 binding Resource 的 WorkspaceCapabilityDefault 清空待重新选择；以旧 Resource 或旧 Tool 为 target 的 DelegationScope 与 ToolBinding 失效，ToolBinding 按契约键重绑到新 binding，DelegationScope 由 grantor 重新授予，AgentVersion 不重发；历史 ContentReference（含 `mem/*` citation）保留原值，解析为不可用而不报成功或失败（DD-88/92）。Workspace 在某类别下的默认 Resource 由可空的 `WorkspaceCapabilityDefault(workspace_id, category, resource_id)` 记录，它不是 Workspace `ACTIVE` 的前提（DD-90）。

平台自有能力（记忆、Buzz 消息、任务、审批等）的工具来源为 `PLATFORM_NATIVE`，不依赖任何 ApplicationBinding：它们由 Core 自托管的 Streamable HTTP MCP 端点提供，Core 经 SS-AGW-ADMIN 把该端点登记为 AgentGateway 的 MCP target，调用同样经会话级 bearer 与 ExtMcp PEP，不需要 adapter、Adapter Protocol 或 ActionToken（DD-105）；业务能力工具来源为 `APPLICATION`，经 MCP 与 AgentGateway ExtMcp PEP 调用。Workspace 内某契约键没有 active 实现时，该工具 effective 状态为 `NO_PROVIDER`，AgentInstallation 仍可 `ACTIVE`（DD-92）。

### 2.5 准入路径

ComponentRelease 登记 `APPROVED` 按来源只有两条路径（DD-88）；只提供独立服务原生页面入口、不实现任何能力契约的 release 沿其中一条来源路径，按第三行的接入范围准入（DD-127）：

| 路径 | 适用 | 准入条件 |
|---|---|---|
| 内置参考实现 | 一期随平台交付的业务能力实现（`08`） | `02` 的 SOURCE_FACT/SOURCE_SEAM 证明 native scope、API、状态与治理映射，加该能力契约的一致性测试套件全过 |
| 外部实现 | 第三方或自研实现，含闭源与 SaaS | 能力契约、一致性测试套件全过、平台管理员批准，并在 release 中以 `vendor`、`artifact_version` 与 artifact digest 标识来源、声明隔离模式与数据位置；`source_commit` 可空，不要求 `.references` 中存在其源码（DD-94(1)） |
| 原生页面入口（DD-127） | 独立服务只在 Web/Desktop 提供 `NATIVE_PAGE` 入口：`implements=[]`、ExecutionConnector `NONE`，无 Resource/Action/Tool、binding secret 与 Kailo 发起的原生动作；可声明经平台模型路由调用模型（DD-128） | 来源标识按上两行之一；声明 `native_page_category`；`adapter_build_ref` 固定所部署原生服务（接入改造后的服务 artifact）的 digest；声明 `native_page_origins[]`；登记冻结空套件计划（没有 adapter 可测，不运行 Adapter Protocol 一致性套件），另一位 Catalog Tenant admin 经 ApprovalWorkflow 批准 |

两条路径都经 `ComponentTaskWorkflow(kind=COMPONENT_RELEASE)` 与 ApprovalWorkflow，按实际接入范围校验治理、业务可观测性与隔离合同；主题/i18n 的宿主强制合同适用于 Kailo 自有页面与同窗口 module，不要求独立原生后台重写。外部实现声明的隔离模式与数据位置写入 release 的 governance 段并固定 digest；声明与一致性套件结果不符即拒绝。平台核心的 Platform Component 不走外部实现路径，仍以源码证据与 Core 已编译端口准入。本文与 `03`–`06` 中凡要求“固定 source commit/source baseline”的准入、Workflow input 与运行时注册条件，都按 `admission_path` 的来源标识解读，外部实现不因无源码被拒（DD-94(1)）。

业务能力实现的 `REMOTE_ADAPTER` 运行体一律部署在平台运维域内（`adapter_build_ref` 固定 digest、独立凭据、独立私有数据网络），外部与 SaaS 实现也不例外，其服务端点只是 adapter 的上游。ActionToken 验签公钥与 `secret_schema` 声明的凭据（含供应商签发给该 Tenant 的 API 凭据）统一经 OpenBao Agent 投递到 adapter 运行体，与 AgentGateway 的做法相同，不新增公钥或凭据分发通道。以 `PROTOCOL_PEER` 接入的实现不接收 ActionToken，不能作为服务读取边（§8.2）的来源方（DD-94）。

### 2.6 数据存储与凭据隔离

平台核心每个服务与每个自托管的业务能力实现各自使用独立数据库实例，至少独立 database，并使用独立凭据与独立私有数据网络；禁止共用 schema 与跨库访问。外部托管（SaaS）实现的数据位于供应商环境、与平台及其他实现不共享存储，其 adapter 运行体仍使用独立凭据与独立私有数据网络（DD-93/94）。约束固定为：

- Core 不持有任何业务能力服务的数据库凭据；平台对业务数据的一切访问只经能力契约暴露的 Resource/Action/Tool。
- 组件状态目录不放在 Core/Worker 运行体内；业务能力实现的增量状态、索引与缓存属于该实现自己的运行体与存储。
- 两个业务能力服务之间不直连数据面、不共用数据库；跨服务数据获取只按 §8.2。
- 接入凭据及明确选择由平台托管的密钥由 release manifest 声明 `secret_schema`：`secret_key`、类型、长度或格式、轮换类别 `SERVICE_CREDENTIAL|DATA_KEY`、投递方式、是否需重启。Core 按通用 schema 校验并经 OpenBao 托管与投递，不内置任何产品的密钥语义；未交由平台托管的服务内部密钥由服务独立管理；`DATA_KEY` 轮换后已存密文的重加密是该服务自己的数据平面职责，平台只按声明的轮换类别投递新版本；服务经 Adapter Protocol `report_rekey` 回报重加密完成后，平台才记录结果并允许销毁旧版本；未回报或结果不明时旧版本保留、该 binding 进入对账并计入度量，直到回报或平台管理员经审计处置（DD-93）。
- release 声明 `data_store_isolation[DEDICATED_INSTANCE|DEDICATED_DATABASE|VENDOR_MANAGED]` 与 `data_location`，随 release digest 固定，供平台管理员批准时核对；`VENDOR_MANAGED` 只用于外部托管（SaaS）实现，必须同时声明数据位置并经平台管理员批准（2026-09-28 按 DD-93 修订）；缺失任一声明的 release 不得 `APPROVED`。binding 不另存这两项，一律以其 pin 的 release 为准。

## 3. Component Package 与不可变 Release

Component Package 包含：

```text
manifest
manifest digest
package digest
WebArtifactSet[path, media_type, digest][]
backend_delivery = EXTERNAL_SERVICE | BUILD_BOUND | NONE
```

Package 不包含 Core 要启动的本机 executable，也不携带 credential、native access token 或临时 URL。`EXTERNAL_SERVICE` 只表示该 release 要求独立服务，服务地址属于 binding；`BUILD_BOUND` 表示可执行代码已与主体构建绑定，package 只能引用当前 registry 已有 key，且只允许 PLATFORM release 使用；APPLICATION release 只能是 `EXTERNAL_SERVICE` 或 `NONE`（SF-MAT-05、DD-58/64/87）。

`WebArtifactSet` 的 canonical 清单整体计算 `web_artifact_set_digest`。Catalog 把每个文件固定服务于 `/component-artifacts/<release_id>/<sha256>/<path>`；entry 的静态相对 import 必须解析在同一 release 根内，绝对外域、父目录越界或未列入 artifact set 的 import 一律拒绝登记。该路径位于 Buzz Web Service Worker 的 `/app/` scope 外；snapshot endpoint 固定 `Cache-Control: no-store`。Buzz Web Caddy 只提供静态 `/app/*`，单一公开 origin 由 AgentGateway 路径前缀路由组合：`/app/*` 到 Buzz Web 静态站、`/api/*` 到 BFF、`/component-artifacts/*` 到 Core artifact handler（SF-WEB-07/08、DD-60）。

Release manifest 必须完整声明：

```text
identity
  component_type_key / release_id / semantic version / manifest_schema_version
  admission_path[BUILTIN_REFERENCE|EXTERNAL]
  BUILTIN_REFERENCE: source_project / exact source_commit（必填）
  EXTERNAL: vendor / artifact_version（必填）；source_commit 可空

compatibility
  platform_port_key | NONE
  implements[category@version] | NONE
  host_api_range | NONE
  adapter_protocol_range | NONE

delivery
  FrontendDelivery（SOURCE_BOUND_PROTOCOL 含 editor_origins[] / launch_descriptor_schema_version；NATIVE_PAGE 含 native_page_origins[]）
  ExecutionConnector
  ComponentPackage digest + WebArtifactSet

domain
  ResourceTypeDefinition[] / ActionDefinition[] / ToolDefinition[]
  target_resource_type_keys[] for capability components

governance
  isolation / call identity
  data_store_isolation / data_location / secret_schema
  capability_declarations[cancel / observe / meter / revision_query / versioned_model / tenant_delete | retain_on_tenant_delete]
  Approval / Workflow / Capacity / Quota / Meter / Audit contracts
  BusinessObservabilityContract
  IncrementalContract / LLMGatewayContract(allowed_model_call_modes[])
  native status / error / cancel / idempotency / reconcile mapping
  FrontendPresentationContract
```

manifest 只写声明与上界；binding 在其中的选择（启用的 `capability_categories[]`、`model_call_mode`、`retain_on_tenant_delete`）属于 ApplicationBinding，字段以 `03` §3 为准。

原生页面入口 release（DD-127）的 `implements[]`、`capability_declarations`、domain 三类定义、`target_resource_type_keys` 与 `secret_schema` 全为空，`allowed_model_call_modes` 为 `{NONE, PLATFORM_LLM_ROUTE}` 的非空子集（DD-128），ExecutionConnector 为 `NONE`（`adapter_protocol_range`、`action_token_audience` 均为 `NONE`），FrontendDelivery 只能是 `NATIVE_PAGE` 且必须声明 `native_page_category`（`file_storage`、`knowledge`、`data_query`）；`adapter_build_ref` 槽位记录所部署原生服务的 artifact digest，作为该 release 的 artifact digest 参与来源取证。

Release 一经 `APPROVED` 不原地修改。source commit 或外部 artifact version、schema、artifact bytes/digest、`implements[]`、Resource/Action/Tool、meter、redaction、隔离声明或兼容范围改变都生成新 release。能力进入 release 的证明按 §2.5 的准入路径：内置参考实现以 `02` 的 SOURCE_FACT/SOURCE_SEAM 和 adapter 契约证明，外部实现以能力契约一致性测试套件与平台管理员批准证明；两者都无法证明的能力不进入 release。

## 4. Component Host

### 4.1 固定宿主边界

Buzz Web 与 Buzz Desktop 是两个上游代码库，共享 Buzz 原版 TypeScript 页面、组件与交互主体及 Kailo 平台包（Host API、surface registry、BFF 客户端与契约生成物），由宿主适配认证、签名与传输，Component Host 的一次性变更边界按端分别由两条接缝定位（2026-09-28 按 DD-74 修订）：

| 承载端 | 接缝 | 一次性变更边界 | 可承载的 FrontendDelivery |
|---|---|---|---|
| Buzz Web（buzz-web `web/`） | SS-WEB-COMPONENT-HOST | 在静态 routeTree 中只增加一个 `/apps/$componentKey/$` catch-all route；从 `BuzzWebApp.Workspace` 提炼 index 与 app route 共用的 `WorkspaceShell`；用 surface registry 取代封闭 `WorkspaceTool` union 和硬编码内容分支；增加同源 loader、动态 i18n source 与同源内容寻址 artifact route | `HOST_NATIVE`、`REMOTE_MODULE`、`NATIVE_PAGE`、`SOURCE_BOUND_PROTOCOL` |
| Buzz Desktop（Buzz `desktop/`） | SS-DSK-COMPONENT-HOST | 在 `src/app/routes.ts` 显式登记固定 `route("/apps/$componentKey/$", …)`，随构建进入生成的 routeTree；`AppShell` 内容区以运行时 surface registry 按 BFF 快照挂载 surface；`AppSidebar` 的业务条目由快照生成，取代其固定 props 中的逐项入口（`useAppNavigation` 只是跳转函数集合） | `HOST_NATIVE`、隔离的 `NATIVE_PAGE`、`SOURCE_BOUND_PROTOCOL`；CSP 编译在签名包内，不执行 `REMOTE_MODULE` 运行时 script，对应入口显示确定状态并指向 Web（SF-DSK-03） |

两端共同的宿主规则：

- 导航、路由子路径、图标标识、文案 key 和排序由宿主根据 projection descriptor 渲染，不由 module 注入任意 router 或 DOM。
- 宿主保留登录、协作、审批、任务、治理、主题和 i18n 控制权。

一期扩展槽只有：

| Extension slot | 作用 | 宿主准入 |
|---|---|---|
| `MANAGEMENT_PAGE` | Platform/Tenant/Workspace 管理页及受控子路径 | descriptor scope + `discover/manage/audit` |
| `RESOURCE_VIEW` | Resource/Asset 详情、查询和动作 | Resource/Asset permission + ResultExposure |
| `CHAT_ATTACHMENT_ACTION` | 频道内的 Resource/ContentReference 打开与动作 | Workspace scope + target permission |

新 slot 是 Host API 变更，不能通过 manifest 动态创建，且两个承载端必须同时实现。Desktop 对 `REMOTE_MODULE` 交付的 slot 内容显示确定状态并指向 Web，§4.2–§4.4 的 remote module 加载与 Host API 只在 Web 执行（SF-DSK-03）。

扩展槽承载 Kailo 接入管理、受权资源视图及可选的独立原生管理页面。Kailo 自有页面发起的业务数据操作（上传、导入、查询、发布、分享、删除等）与 Agent 走相同 Governed Action/Tool 链：Browser→BFF 语义命令→Admission→Adapter Protocol 或 AgentGateway MCP→实现。独立原生管理页面通过自己的会话访问自己的后端；调用 Kailo 公共服务时按对应认证与准入合同执行，不把全部内部 API 改造成 BFF 命令。`HOST_NATIVE` 只实现通用接入管理及平台资源视图，不为 Cells、WeKnora、Wren 重写后台；产品原生后台按 `NATIVE_PAGE` 提供受治理的完整原生页面入口，也可独立访问，`REMOTE_MODULE` 不是其唯一交付方式。没有 active binding 时不显示该服务的 Kailo 原生页面入口，不影响其独立入口和业务运行。

### 4.2 运行时快照、通知与 reconcile

BFF 只返回当前 PlatformSession、Tenant、Workspace 和 Principal 可发现的完整 `ComponentRuntimeProjectionSnapshot`：

```text
snapshot_generation
scope_digest
projections[
  binding_kind / binding_id / release_id / generation
  component_type_key / authorized surface descriptors
  served_entry_path / artifact digest / host_api_range
]
```

BFF session stream 只通知 `snapshot_generation` 变化，Browser 立即重取完整快照并做 set reconciliation。新增 projection 直接 load；版本变更时，新导航解析新 generation，已挂载旧 surface 保留到卸载或用户确认刷新，不能在存在未保存输入时强制 dispose；projection 消失则停止新导航并请求已打开 surface 安全关闭。断线重连、页面恢复可见或 generation 不连续时也重取完整快照。事件只是失效通知，不是授权或组件状态权威（DD-61）。Mattermost 在事件路径上把 payload 当完整状态直接 load/remove、只在重连时全量 reconcile（SF-MAT-06），是本设计明确不采用的反例。

### 4.3 前端 module 加载协议

```text
Host 按(type, release_id, generation, entry_digest)登记 pending load
→ 校验 served_entry_path 为当前 release digest 的同源内容寻址路径
→ 在现有 script-src 'self' 下注入 module script
→ module 求值期同步调用 register(descriptor)
→ Host 暂存 descriptor；script load 事件后按 pending load 全字段匹配并接受
→ module mount(host-owned root, narrow Host API)
→ snapshot 移除/变更时 dispose + unregister
```

pending load 只在 Host 内部存在，绑定 Browser session、projection、注入元素与过期时间；静态 module artifact 不携带会话 ticket。无 pending、重复 register、load 失败、字段不一致或 Host API 不兼容均拒绝。`register` 在 module 求值期只暂存 descriptor，必须等对应注入元素的 load 事件发生后才 commit，避免把无关脚本的全局调用接受为该 projection。

Host 以 try/catch 包住 `mount()` 与 `dispose()`，并监听 `window.error`/`unhandledrejection`；当 `ErrorEvent.filename` 或可解析 stack URL 命中该 generation 的 artifact 根前缀时，尽力 dispose，将 Host 侧 generation 置 `ERROR`，并在槽位显示本地化 fallback。React error boundary 不作为 remote module 隔离承诺；事件 handler、timer 与 promise 错误也走上述全局归因。该错误只改变浏览器 Host generation，不改 ApplicationBinding、native task 或后端 projection 状态。

`dispose()` 的强制合同是：清空 Host 分配的 DOM root，移除 module 自有 style、全局 listener 与 timer，注销其 i18n namespace；CSS selector 必须以 Host 注入的 `data-platform-component=<type>` 与 `data-platform-generation=<generation>` 双属性作用域化。ES module 代码本身不会从同一 window 卸载，因此旧 generation 不得再次 mount；无法履行 dispose 的 release 在 Catalog 登记时拒绝。

`source_entry_url` 只供 Catalog 登记流程取件。批准前按密码学 digest 固定 bytes，Browser 只请求同源 immutable `served_entry_path`，不请求外域 script，不放宽承载端当前 `script-src 'self'`（SF-WEB-06、SF-MAT-01/03、DD-60）。

Remote module 是平台管理员批准的同窗口信任代码，不是安全沙箱。Tenant 管理员只能启用已批准 release，不能上传或替换 JavaScript。

### 4.4 窄 Host API

Host API 只提供：

- 当前受限 scope 和 FrontendPresentationContext 读取；
- BFF Resource query；
- action preview 与 semantic command；
- Task/Approval/operation 状态订阅；
- 受权导航、`subscribePresentation(cb)` 与 namespaced `hostI18n.t(namespace,key)` 注册。

Module 不获得完整宿主 store、Relay signer、ActionToken signing key、native credential 或 SpiceDB/Temporal/OpenMeter/AgentGateway 管理凭据。即使 module 自行发起同源 BFF 请求，BFF 仍对每个 query/action 重做 session、scope、SpiceDB、Approval、Quota 和 Audit 准入；前端代码不是授权边界。

### 4.5 主题与 i18n

- `HOST_NATIVE` 直接使用 Buzz CSS variables（取值为 `20` 的 Kailo 视觉设计系统，DD-141）、`MessageKey/t/getLocale`。
- `REMOTE_MODULE` 通过 `subscribePresentation(cb)` 持续接收 resolved `LIGHT/DARK` 与 `EN/ZH_CN`，使用 Buzz tokens；不得只在 mount 时读取一次。Catalog 登记时校验 namespaced `en` 与 `zh-CN` catalog 的 key 集完全一致且覆盖 manifest 声明的全部 key，不一致即拒绝 release；remote key 不进入 Buzz 封闭的 `MessageKey` 类型或本地 `check-i18n` 扫描面（SF-WEB-03/08、SS-WEB-COMPONENT-HOST）。
- `SOURCE_BOUND_PROTOCOL` 的 launch 请求携带 Buzz 已解析的 theme 与 locale，由实现的 adapter 映射为其私有参数并写入 DocumentLaunchDescriptor，每次 launch 固定；surface 与 Core 不理解这些参数；内置参考实现的映射见 `18`（SF-WEB-03、DD-95）。
- `NATIVE_PAGE` 声明 `NONE` 时保留服务自身呈现，支持原生参数时传递 theme/locale，不要求 Host API、双语 catalog 或重写原生后台；声明 `KAILO_EMBED` 时按 §4.7 以 Kailo 令牌呈现，经启动参数与 wire v1 postMessage 跟随宿主明暗与语言。平台自身状态使用宿主稳定 code 和 i18n key，组件页面自身错误由组件呈现。

独立管理页面的隔离打开按 §4.6；在线编辑仍使用独立的 `SOURCE_BOUND_PROTOCOL` 合同，不以管理页面入口替代文档编辑准入。release 固定 editor origin 与 DocumentLaunchDescriptor schema 版本、并按 §2.5 准入路径取得 `APPROVED` 后，承载端只有一个通用 `SOURCE_BOUND_PROTOCOL` surface `ProtocolDocumentSurface`，按 `FILE_STORAGE` 契约的在线编辑条件能力消费 adapter 生成、经 Core 校验后下发的 DocumentLaunchDescriptor，不含产品专名分支，WOPI 只是内置参考实现的一种取值（DD-95）。在线编辑所需的 Web CSP `frame-src`/`form-action` 来源取自部署级 editor origin 许可集合；独立管理页面的许可来源另按 §4.6 校验并加入 `frame-src`，不加入宿主 `form-action`：该集合等于平台管理员批准的 release 所登记 `editor_origins[]` 的并集，Tenant 与 binding 不能扩大，不随会话变化。BFF 在运行时持有该集合并据此决定各端编辑入口：Web 端由同一份部署配置同时投影出 Web 静态服务 CSP 与 BFF 读取的 Web 已生效集合，变更时重启 Web 静态服务、不重建镜像，Web 有效集合是许可集合与 Web 已生效集合的交集；Desktop 主窗口 CSP 编译在签名包内且不放宽，编辑器不嵌入主窗口，而在独立 `platform-editor-*` WebviewWindow 中打开，其 `on_navigation` 钩子按 BFF 运行时下发的许可集合逐次校验，Desktop 有效集合就是该运行时许可集合，新增 origin 不需要发布 Desktop 包（DD-104、SS-DSK-EDITOR-WINDOW）。Desktop 在线编辑当前为 `BLOCKED: GAP-DSK-EDITOR-01`，上述窗口与动态许可集合是阻断解除后的合同，当前不注册该端编辑 Route 或 Action；不阻断 Web 编辑与普通 Desktop 功能。某端有效集合未包含该 origin 时，该端编辑入口按 REQ-21 显示确定状态，不回落为隐藏或报错。`script-src 'self'` 不因任何 release 放宽（DD-60/95/104、SF-WEB-06、SF-DSK-03）。文件所属的 `FILE_STORAGE` 实现未声明 `online_editing=SUPPORTED` 时，该文件只显示元数据与受权下载（REQ-07、DD-90/103）。

### 4.6 独立原生管理页面

`NATIVE_PAGE` 复用各独立服务经过 Kailo 接入改造的完整前端与后端，保留其上游页面和功能；内置实现源码在 `apps` 对应服务目录维护、构建与发布，不以未经改造的原版镜像替代已接入交付物，也不把后台重写进 Kailo 主体。release 以 `native_page_origins[]` 声明允许来源，binding 配置实际页面入口；BFF 只向有权发现该 binding 的用户返回入口，核对 URL origin 同时属于 release 和部署许可集合。URL 不携带平台 service credential、管理令牌或长期密钥，不接受用户提供的任意跳转地址。

接入改造包含实际业务请求中的身份、资源归属、授权与公共服务调用。原产品缺少用户或作用域概念时，在该产品自己的后端与持久模型中补齐必要的主体引用、资源归属和执行者关联；身份关联使用统一身份的稳定引用，不能创建另一套平台用户或密码权威。实例登录许可不等于全部项目、数据源、查询结果或管理动作的权限。原产品已有账号、成员、角色与资源模型时，复用其原模型和映射，不无条件重写数据库；原生业务数据仍由独立服务持有。

按 2026-10-07 用户纠正，Web/Desktop 将完整原生页面作为与 Inbox、Projects 同级的左侧导航项，点击后在同一主窗口右侧内容区的跨 origin iframe 中显示，保留 Kailo 侧边栏和当前导航状态。两端复用同一个 TypeScript 菜单、路由内容与 iframe 主体，不以打开独立浏览器页、独立桌面窗口或入口弹窗代替内容区集成；不重写或精简服务原生后台。Mobile 不渲染该入口，不用 WebView 绕过。iframe 加载完成仅证明页面载入，不证明 SSO、当前 scope 或业务执行成功。

iframe 的地址只取经 fresh 授权的 ApplicationBinding descriptor；只允许 release 与部署许可集合交集内的独立服务 origin，禁止宿主同源、任意地址和 URL 凭据。sandbox 允许原生界面所需的脚本、自身 origin、表单、下载及用户触发的认证弹窗，不允许导航或访问 Kailo 顶层页面，不授予 Tauri IPC。Web `frame-src` 从部署配置投递许可集合；Desktop 的编译期 `frame-src` 支持 HTTP(S) 子页面，实际入口仍逐 binding 精确校验，`script-src` 与远端 IPC 权限不放宽。服务端以显式宿主 origin 配置生成 `frame-ancestors`，保留独立登录与授权；不通过删除所有嵌入限制、共享管理员凭据或关闭第三方 Cookie 策略来绕通。需顶层浏览器完成的 OIDC 认证可使用用户触发的认证窗口，完成后回到原内容区；该窗口不作为原生应用的日常承载方式。声明 `KAILO_EMBED` 的页面在 iframe 内以 `prompt=none` 静默登录，需要交互时请求宿主在顶层登录（§4.7.2），不显示自身登录页或按钮。

服务原生页内嵌的第三方内容仍是该服务的原生页内容（例如 DD-132 中 Cells 页内的 DocumentServer 编辑器）：它的 `frame-ancestors` 必须精确列出自身、该服务 origin 与 Kailo 宿主 origin，不因多层嵌套放宽 sandbox，不授予 Tauri IPC，也不构成平台的编辑 Route 或 Action；它的授权仍是该服务自己的 ACL。

入口的标签与图标按呈现类别决定（DD-127）：`NATIVE_PAGE` release 可在 FrontendDelivery 声明 `native_page_category`（`file_storage`、`knowledge`、`data_query`，分别呈现为云盘、知识库、问数）；原生页面入口 release 必须声明，带能力的 release 可不声明，声明时必须属于其 `implements[]`。ApplicationBinding 视图从其 pin 的 `APPROVED` release 投影该值，侧边栏取 binding `capability_categories[]` 与 `native_page_category` 的并集决定标签与图标，二者都没有时才显示 `component_type_key` 与通用图标。呈现类别不授予任何能力、不参与类别解析或同类别唯一 binding。

入口与能力接入解耦（DD-127）：显示原生页面只要求一个 `ACTIVE` 的 ApplicationBinding，不要求该服务已接入 adapter、工具或能力契约。只提供入口的服务以 §2.5 第三行的原生页面入口 release 准入，binding 激活只核对 release `APPROVED`、入口 origin 属于 release 与部署许可集合的交集、Tenant/Workspace `ACTIVE`；入口发现、descriptor 校验、iframe sandbox 与 CSP 不因此放宽。能力与工具接入仍以实现能力契约的新 release 版本走原准入，入口 release 不被原地改写。

页面用服务自己的用户会话访问自己的后端，可对接公共身份服务实现统一登录；统一登录不等于共享平台管理员或机器凭据。Kailo 管理 API 仍经 BFF，工具仍经 AgentGateway，公共工作流/审批/额度等调用仍由各自权威准入。页面承载不要求每次组件内部操作都建立 Kailo ActionExecution，也不把组件内部任务、数据库、模型配置或账单复制到 Core。

入口拓扑（DD-164(10)）：生产部署对外只开放 Kailo 入口（Kailo 网关的浏览器、原生与 webhook 入口，IdP，Relay）。组件部署单元不向宿主公开端口，运维探测只可绑定回环地址；组件加入 Kailo 网关所在的组件网络，由 Kailo 网关为每个组件 origin 开设一个专用 listener：监听原组件端口、转发到组件内部地址，因此组件 origin、IdP 回调与 back-channel 地址、`NATIVE_PAGE_ORIGINS`、`frame-ancestors` 都不改变。listener 规则：带 `Sec-Fetch-Dest: document` 的顶层导航一律 `302` 到 `<PUBLIC_ORIGIN>/app/applications/open?origin=<组件 origin>&path=<原路径与查询>`，Kailo 在当前用户可发现的 `ACTIVE` 原生页面 binding 中按 origin 找到入口并在内容区以该路径打开，找不到时显示确定状态而不跳回组件；iframe 内导航、子资源、XHR、WebSocket 与 IdP 的服务端 back-channel 请求照常转发，请求头与响应头不被改写；文档编辑服务（云盘页内的编辑器）只转发编辑器浏览器所需的路径，`/healthcheck`、`/info`、`/example`、命令与转换接口对外一律 `404`，云盘经内部地址调用它们。部署检查拒绝任何组件 compose 向非回环地址公开端口。迁移：① 发布带组件 listener 声明的网关配置，listener 在对应组件仍公开端口时不启用；② 维护窗口内逐个组件以不公开端口的声明重建，随即启用该组件的 listener；③ 每个组件逐项验证 iframe 静默登录、上传下载、文档编辑、back-channel 退出、顶层访问跳转与运维接口 `404`；④ 回退为恢复组件端口声明并停用该 listener，origin 与 IdP 配置无须变更。

端能力不支持或入口校验失败时，在内容区显示确定状态，不自动跳出主窗口；不因此关闭独立服务、禁止它提供工具，或重写其后台。binding 停用或用户被撤销平台接入权时撤去 Kailo 入口、卸载对应 iframe 并撤销公共服务调用权；组件自身的会话和内部权限由其身份/权限集成处理，不宣称关闭页面已注销外部服务。切换菜单、返回、刷新与登录恢复须验证页面状态、上传下载、内部跳转和原生业务操作，不能用 iframe 元素存在代替功能验收。

### 4.7 组件一体化呈现（DD-133）

侧栏云盘、知识库、问数的原生页（以及之后任何声明 `KAILO_EMBED` 的 `NATIVE_PAGE` 组件）对用户就是 Kailo 本身：没有上游品牌、没有第二次登录、用户与组织就是 Kailo 的用户与组织、样式与 Kailo 主体一致。改造在组件自己的 fork 与部署单元内完成；平台只提供本节的令牌、运行时、身份声明、头像解析与退出联动，§4.6 的隔离、来源与授权边界不变。

#### 4.7.1 呈现合同与构建输入

- release 的 FrontendPresentationContract 取 `KAILO_EMBED` 时必须同时满足：FrontendDelivery 为 `NATIVE_PAGE`；`theme_change_policy=LIVE`；`locale_resolution_policy=BROWSER_RESOLVED`；`theme_mapping` 的键恰为 `LIGHT`、`DARK`，`locale_mapping` 的键恰为 `ZH_CN`、`EN`，值为该组件原生主题或语言标识（1–64 个字母、数字、`.`、`_`、`-`）。Core 登记时拒绝其他组合；`NONE` 保持原义。未完成 DD-133 (1)–(5) 的 artifact 必须声明 `NONE`。
- 组件页面产物的构建输入包含 `client-kit/embed/kailo-theme-tokens.css`、`client-kit/embed/kailo-embed.js` 与 `web-client/web/public/app-icon.png`：三者列入该 artifact 的 `inputs`，按仓库相对路径进入构建上下文并参与 `source_digest`，构建时复制进产物、由组件自身 origin 提供。任一文件变化都使已记录的 `source_digest` 失效，组件须重建；运行时不从 Kailo 取用任何样式、脚本或图片。
- 令牌文件由 client-kit 的主题源生成：DD-141 起唯一来源是 `kailo-tokens.ts`（Kailo 视觉设计系统，`20`），连同 `typography.css` 与 `tailwind.config.js`；生成结果与提交文件逐字节一致是检查项。浅色在 `:root`，深色在 `:root[data-kailo-theme="dark"]`；颜色以 `--kailo-color-<名>` 给出完整颜色、以 `--kailo-hsl-<名>` 给出 `H S% L%` 三元组，另有 `--kailo-font-sans`、`--kailo-font-mono`、`--kailo-font-size-*`、`--kailo-radius*`、`--kailo-shadow-*`（含 `xl`）、`--kailo-duration-*`、`--kailo-ease-*`、`--kailo-gradient-brand`，以及 DD-141 新增的品牌色阶 `--kailo-color-brand-<50…950>` 与语义色 `--kailo-color-{success,warning,danger,info}`（各带 `-text`、`-soft`）。既有名称保持不变，取值随 `20` 变化。深色的 `background` 是 Kailo 内容区画布。组件以一层覆盖把原生主题变量映射到这些令牌，不逐页硬编码颜色，也不保留上游品牌色（`20` §11）。
- 页面头部依次放置 `<meta name="kailo-web-origin">`（值取组件部署单元的 `KAILO_FRAME_ANCESTORS`，与其 `frame-ancestors` 同一事实）、favicon、令牌样式表与 `kailo-embed.js`，均在组件自身样式与脚本之前。
- 运行时在 iframe 内为 `<html>` 加 `data-kailo-embedded`；组件据此隐藏与 Kailo 重复的全局外壳（产品顶栏、个人设置、退出、帮助、切换组织），只保留业务导航。顶层访问保持同一品牌与令牌。各表面的唯一归属与组件在 Kailo 模式下（嵌入与顶层）不得出现的入口见 §4.8（DD-138）。
- 产品名是 `PLATFORM_DISPLAY_NAME` 加呈现类别名（云盘、知识库、问数；Files、Knowledge、Data Q&A），用于 `<title>`、加载页、错误页、空态与邮件模板。

#### 4.7.2 主题与语言协议（wire v1）

| 方向 | 消息 | 时机 |
|---|---|---|
| Kailo → 组件 | 启动 URL 查询参数 `kailo_theme=light\|dark`、`kailo_locale=zh-CN\|en`，加在 descriptor 批准的 URL 上，origin 不变；载入管理面时另带 `kailo_admin_surface=<管理面标识>`（DD-138(6)，§4.8.5），它只选择呈现哪一项管理功能，不构成授权 | 每次装载 iframe 文档；之后的切换不重载 iframe |
| 组件 → Kailo | `{source:"kailo-embed", version:1, type:"ready"}` | 运行时装载完成 |
| 组件 → Kailo | `{source:"kailo-embed", version:1, type:"auth-required"}` | 静默 OIDC 需要交互（DD-133(2)） |
| 组件 → Kailo | `{source:"kailo-embed", version:1, type:"share", intentId}`（DD-164(4)，`intentId` 为 UUID） | 用户在组件页点“分享”、组件服务端已取得 ComponentShareIntent；宿主打开 Kailo 分享对话框，`intentId` 不是凭据，读取意图仍按会话校验 |
| Kailo → 组件 | `{source:"kailo-host", version:1, type:"presentation", theme, locale}` | 收到 `ready` 时与每次 Kailo 切换主题或语言时 |
| Kailo → 组件 | `{source:"kailo-host", version:1, type:"preferences", values}`（DD-138，§4.8.2） | 收到 `ready` 时紧随 `presentation`，与该页面已声明偏好的值每次变化时 |

- 本表之外，DD-157 的页头、Toast、确认与快捷键消息见 §4.8.7。
- 发送方只以单一精确 origin 为 `targetOrigin`，不用 `*`。组件只接受 `event.origin` 属于 `kailo-web-origin` 且 `event.source` 是父窗口的消息；Kailo 只接受 `event.origin` 等于 descriptor `origin` 且 `event.source` 是该 iframe 窗口的消息；其余形状、版本或取值一律忽略。消息不携带令牌、身份、URL 或用户数据。
- Kailo 的 `theme` 取宿主根元素实际应用的明暗（任何 Kailo 主题按其明暗映射为 `light`/`dark`），`locale` 取设备本地语言（REQ-08）。组件初值依次取启动参数、本标签页已收到的 Kailo 值（OIDC 跳转会丢掉查询串，运行时以 sessionStorage 保留）、设备默认；只有 Kailo 提供的值被保留。顶层访问时组件可用 OIDC `locale` claim 作初值，Kailo 给出语言后不再采用。
- 运行时向组件暴露 `getState`、`onChange`、`onThemeChange`、`onLocaleChange`、`useIdentityLocale` 与 `requestTopLevelSignIn`，并派发 `kailo:presentation` 事件；组件把它们接到自己的主题与 i18n 上，不提供自己的主题或语言切换入口。
- Kailo 宿主收到 `ready` 后不再显示“登录服务”按钮与 DD-127 边界说明；收到 `auth-required` 时在内容区显示需要重新登录的确定状态与按钮，由用户触发顶层登录（Web 结束本次 Kailo 会话后在顶层重新进入当前路由，Desktop 用原生认证窗口，窗口行为见 §4.7.5「Desktop」），不自动跳出、不在 iframe 内登录。

#### 4.7.3 身份声明与头像

组件专属 browser client（当前部署：Cells `kailo-cells-native-browser`、WeKnora `kailo-knowledge-native`、Wren `platform-local-wren-native-browser`，以部署 env 为准）由部署引导声明式配置，读回一致即不变，已有同名而不一致的 mapper 被拒绝而不覆写：

| claim | 来源 | IdP 配置 | 组件用途 |
|---|---|---|---|
| `sub`（与 `iss`） | IdP 用户 ID | 标准 | 唯一身份键（DD-127(9)），首次登录即时开户 |
| `name`、`preferred_username` | IdP 用户资料 | client 默认 scope 含 `profile` | 显示名与登录名，每次登录刷新 |
| `email`、`email_verified` | IdP 用户资料 | client 默认 scope 含 `email` | 只作资料，`email_verified=true` 才写入，不参与关联 |
| `picture` | realm 用户资料属性 `picture`（管理员可写、本人可读，URI） | client mapper `kailo-picture`：用户属性 `picture` 写入 ID token、access token 与 userinfo | 头像 URL，每次登录刷新 |
| `locale` | realm 用户属性 `locale`（IdP 登录语言） | client mapper `kailo-locale` | 只作顶层访问的语言初值 |

`picture` 的值固定为 `<PUBLIC_ORIGIN>/api/v1/identity/avatars/<sub>`，由部署引导对 realm 全部用户写入并回读；它标识人，不标识某张图片。BFF 路由 `GET /api/v1/identity/avatars/{subject}` 只对已登录 Kailo 的请求者解析（未登录、会话已失效或请求者在会话 Tenant 内已无 ACTIVE 成员身份时同样 404，不以 401/403 区分人或会话是否存在；只有依赖不可用如实返回不可用）：在请求者当前会话 Tenant 内找到该 subject 的 ACTIVE 成员与 SERVER HUMAN Buzz 身份，读取其 kind:0 `picture`，属于本社区媒体时 302 到 `/api/v1/profile/media/<sha256>`，否则 404。组件把它作为普通图片地址使用（同站请求携带 Kailo 会话）；不缓存成本地副本，不向 Tenant 外的人披露。kind:0 `picture` 为内联 `data:image/{png,jpeg,gif,webp,svg+xml}` 且解码后不超过 256 KiB 时，路由在同一授权判断后直接以该媒体类型返回图片字节（`Cache-Control: private, max-age=300`、`X-Content-Type-Options: nosniff`、`Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`），不再 404；Buzz 默认头像即此形式（DD-164(9)）。组件显示名以已应用目录快照的 `displayName` 为准，IdP `name` 只在此人尚无目录资料时使用，登录不覆盖目录值。

#### 4.7.4 组织映射与成员目录

组件部署单元服务单个 Tenant（`DEDICATED_INSTANCE`）。每个组件登记一张映射表，列固定如下；表中每一格写组件原生对象、建立与撤销的触发、以及读取的成员目录字段：

| Kailo 概念 | 组件原生对象 | 自动建立 | 成员加入/移出 | 角色派生 | 成员目录未交付时 |
|---|---|---|---|---|---|

成员目录读取是平台交付的只读接口：组件实例以其专属服务 client 的 client-credentials 令牌（audience 为 Core service audience，`azp` 等于该入口 binding 配置登记的目录 client）读取该 binding 所属 Tenant（及 Workspace）的成员：`iss`、`sub`、Kailo 显示名、`picture`、Tenant 角色（`ADMIN`/`MEMBER`，由 SpiceDB 的 Tenant `manage` 判定）与其 ACTIVE Workspace 成员关系，附目录版本；组件按目录增删成员与角色，撤员在下一次读取后生效。组件周期读取：`directoryVersion` 与上次完整应用的版本相同即不改动，不同则把快照幂等收敛到组件（预开户、加入与移出、角色、Workspace 对应对象），全部成功后才记下新版本；读取被拒、暂不可用（含 503）或回应不符合同（含 `bindingId` 或 Tenant 与部署声明不符）时保持上次已应用的状态，不做部分同步、不视为空目录。已应用的快照跨组件重启保留；目录交付后不在快照中的 `iss`+`sub` 不能登录或访问组件，登录不再把角色回退为成员。目录只读、不授予 Kailo 侧任何权限，组件不从 IdP groups、email 或显示名推导组织与角色。目录读取交付前组件只即时开户为成员，不在组件内授予管理员。

读取合同：

- **入口**：Core 服务监听面 `GET /service/v1/component-directory/bindings/{bindingId}/members`，与 adapter 回调同一服务认证器，不挂在网关的浏览器路由上；读取不建立 ActionExecution，回应 `Cache-Control: no-store`。
- **调用身份**：令牌由部署 IdP 签名，`iss` 为部署 issuer，`aud` 含 Core service audience，`azp` 等于该 binding `normalizedConfig.directoryClientId`。该 client 是组件部署单元的部署事实，与 §4.7.5 的退出属性同由部署的 IdP 声明式配置登记（随平台发布的部署阶段在配置摘要变化时执行、回读阶段只读核对）：声明逐项为「组件部署单元 → 目录 client ID」，client ID 互不相同，且不得是平台自身任一 client、任一组件专属 browser client 或 binding 的 adapter `client_id`；client 不存在时以机密 client 创建：只启用 service account（client-credentials），不启用授权码、隐式、口令与设备授权流程，不登记回调与来源，不授予任何 realm 或 client 角色，唯一的协议 mapper 把 Core service audience 写入访问令牌的 `aud`；已有同名 client 的这些属性或 mapper 与声明不一致时整体拒绝而不覆写。凭据以 IdP 中的 client secret 为准，只写入部署运行目录中该组件部署单元专属的 0600 secret 文件，由组件部署单元以只读文件挂载消费，不进入 `.env`、日志、命令输出或 Core；文件缺失时按 IdP 当前值补写，与 IdP 不一致时以 IdP 值原子替换，回读核对文件与 IdP 一致。Core 只核对 `azp`，不建立、不持有、不投递它的凭据（§6.2 原生页面入口仍不建立 IdP service client）。`directoryClientId` 在非 `DISABLED` binding 中唯一，不得等于任何 binding 的 adapter `client_id`、Worker 或平台自身 client；令牌不成立与 binding 不满足前提一律拒绝，不区分原因。
- **前提**：binding `ACTIVE` 且 active generation 投影 `ACTIVE`、release `APPROVED` 且 FrontendDelivery 为 `NATIVE_PAGE`、Tenant（及 Workspace）`ACTIVE`。
- **范围**：binding 无 Workspace 时为该 Tenant 全部 ACTIVE HUMAN 成员（TenantMembership、HumanIdentity 与 Principal 均 `ACTIVE`）；binding 属于 Workspace 时只取其中对该 Workspace 有 `discover` 的成员（SpiceDB，fully consistent）。不含 Agent、SERVICE 主体、他 Tenant 与已撤员的人。
- **成员项**：`principalId`；`identities[]`，该人每个 `ACTIVE` ExternalIdentity 一项 `issuer`、`subject` 与 `picture`（`<PUBLIC_ORIGIN>/api/v1/identity/avatars/<subject>`，与 §4.7.3 的 claim 同值）；`displayName` 为 Kailo 显示名：该成员 SERVER HUMAN Buzz 身份当前 kind:0 的 `display_name`（缺省取 `name`），没有资料时取 HumanIdentity 的 `display_name`；`tenantRole`：SpiceDB Tenant `manage` 为 `ADMIN`，否则 `MEMBER`；`workspaces[]`：其 `ACTIVE` WorkspaceMembership 所在、属于本范围的 `ACTIVE` Workspace，每项 `workspaceId` 与 `role`（Workspace `manage` 为 `ADMIN`，否则 `MEMBER`）。不含邮箱：Core 不持有邮箱，组件按 §4.7.3 只从 `email` claim 且 `email_verified=true` 时取得；也不含 Buzz 公钥、会话或任何凭据。
- **快照与版本**：回应另含 `bindingId`、`tenant`（`tenantId`、`name`）、`workspaces[]`（范围内全部 `ACTIVE` Workspace 的 `workspaceId`、`name`，组件按映射表建立对应对象）与 `directoryVersion`（回应其余内容规范 JSON 的 SHA-256，内容不变则不变）。回应是完整快照、不分页；组件以快照替换上次结果：不在快照中的人从组件组织撤出，角色与 Workspace 成员关系按快照改写。数据库、SpiceDB 或 Relay 任一不可读时整体拒绝为暂不可用，不返回部分目录。

- **schema 2（DD-164(2)(4)(6)）**：带查询参数 `schema=2` 的读取在上述内容之外返回顶层 `schema: 2`、成员项 `tenantCreate`（Tenant `create`）、成员 `workspaces[]` 每项 `create`（Workspace `create`）与顶层 `shares[]`；不带参数或 `schema=1` 时回应与上述合同逐字节相同。`shares[]` 每项为该 binding 一个 ACTIVE `component.shared_object` Resource：`resourceId`、`nativeType`（第一阶段 `folder`、`knowledge_base`）、`nativeId`、`ownerPrincipalId` 与 `grants[]`（每项 `subject` 为 `{kind: PRINCIPAL, principalId}`、`{kind: WORKSPACE, workspaceId}` 或 `{kind: TENANT}`，`access` 为 `READ`/`WRITE`；owner 恒有一项 `WRITE`；主体不在本快照成员或 Workspace 中时省略），按 `resourceId` 排序，逐 Resource fully consistent 读取 SpiceDB 的 `owner`、`reader`、`editor`。
- **分享意图**：`POST /service/v1/component-directory/bindings/{bindingId}/share-intents`，同一服务认证器与前提；请求 `nativeType`、`nativeId`（1–255 个可见字符）、`name`（1–200 字符）、`initiator{issuer, subject}`、`workspaceId | null`；Core 核对发起人是本 binding 目录范围内的 ACTIVE 成员、`nativeType` 属于该 binding 呈现类别的可分享表、`workspaceId` 属于范围内 ACTIVE Workspace，写入 10 分钟有效的 ComponentShareIntent 并返回 `intentId`。组件只在原生上发起人可分享该对象时调用；意图不授予权限。
- **收敛回执**：`PUT /service/v1/component-directory/bindings/{bindingId}/receipt`，同一服务认证器与前提；请求 `schema`、`directoryVersion`、`appliedAt`、`outcome`（`APPLIED`/`FAILED`）与至多 100 项 `failures[]`（`kind`、`ref`、`reasonCode`，不含个人资料）；Core 以 binding 为键覆盖保存 ComponentDirectoryReceipt。binding 管理视图比较当前目录版本与回执：不同且超过两个读取周期显示“成员与分享未同步”，回执中的失败项按类别列出。回执不改变目录、不授予权限。
- **撤员时的原生令牌**：组件在快照中撤去一个人时，除登录锁与结束会话外，吊销其在组件内持有的原生令牌（云盘文档编辑 PAT、知识库 API key）。

#### 4.7.5 退出联动（OIDC Back-Channel Logout）

Kailo Web 退出先撤销 Core PlatformSession，再经网关 logout 以 RP-Initiated Logout 结束 IdP 会话（SS-AGW-END-SESSION）；Desktop 退出按下文「Desktop」结束其 WebView 中的 IdP 会话；IdP 随后对该 SSO 会话中出现过的每个 client 以服务端请求投递 `logout_token`。组件专属 browser client 的 IdP 配置：`frontchannelLogout=false`；`backchannel.logout.url` 为组件自身 origin 上的固定路径；`backchannel.logout.session.required=true`；`backchannel.logout.revoke.offline.tokens=false`。Kailo browser client 登记 `post.logout.redirect.uris` 为 `<PUBLIC_ORIGIN>/app/`。这些退出属性与 §4.7.3 的 claim 同由部署引导声明式配置，并随平台发布的部署阶段在配置摘要变化时自动执行、在回读阶段只读核对：每个组件专属 client 只登记 client ID 与其 back-channel 地址，地址必须在该组件自身 origin（属于部署 `NATIVE_PAGE_ORIGINS`）且路径是下表之一，否则整体拒绝；已有 client 的 `frontchannelLogout`、`backchannel.logout.url`、`backchannel.logout.session.required`、`backchannel.logout.revoke.offline.tokens` 与声明不一致时以声明值收敛并回读确认（这四项完全由部署声明决定，不承载组件或管理员的自定义；同名 mapper 不一致仍按 §4.7.3 拒绝而不覆写），client 不存在时拒绝而不创建（client 由组件部署建立）。固定接收路径：

| 组件 | 接收路径 |
|---|---|
| Cells | `<Cells origin>/auth/kailo/backchannel-logout` |
| WeKnora | `<WeKnora origin>/api/v1/auth/oidc/backchannel-logout` |
| Wren | `<Wren origin>/oauth/backchannel-logout` |

接收端规格（每个组件实现）：

- 只接受 `POST`、`Content-Type: application/x-www-form-urlencoded`、表单字段 `logout_token`；不读取 cookie，不跟随跳转，不要求浏览器会话。
- `logout_token` 是 IdP 签名的 JWT：以该 issuer 的 JWKS 验签（拒绝 `none` 与对称算法）；`iss` 等于部署的 OIDC issuer；`aud` 含该组件 client ID；`iat` 在允许时钟偏差内且不过旧；`events` 含键 `http://schemas.openid.net/event/backchannel-logout`；不得含 `nonce`；至少含 `sid` 或 `sub`；`jti` 在令牌有效窗口内去重，重放拒绝。
- 登录时组件把 ID token 的 `sid` 与 `iss`+`sub` 记入其会话。收到有效令牌时结束该 `sid` 的全部组件会话；缺少 `sid` 时结束该 `iss`+`sub` 的全部会话。结束即服务端失效（删除或标记会话、撤销其持有的令牌），下一次请求按 DD-133(2) 重新静默登录或请求顶层登录。
- 成功返回 `200` 与 `Cache-Control: no-store`，令牌无效返回 `400`（不说明原因细节），内部处理失败返回 5xx 供 IdP 记录；重复投递幂等。日志只记 `sid`/`sub` 摘要与结果，不记令牌原文。
- 组件会话的最长寿命不超过 IdP SSO 会话最长寿命；会话续期依赖静默 OIDC 而非长期本地会话。

撤权（DD-164(6)）：Tenant 成员撤销的 `MEMBERSHIP_REVOCATION` 在撤销 PlatformSession 与 SpiceDB relationship 之后，由 Worker 以部署声明的专用会话终止 client（只启用 service account、只授予 realm 角色 `manage-users`，凭据只在 Worker 的 0600 secret 文件）对此人每个 `ACTIVE` ExternalIdentity 调用 IdP 用户退出接口（Keycloak `POST /admin/realms/<realm>/users/<subject>/logout`）：IdP 结束该用户全部会话、设置令牌不早于时间，并对会话中出现过的每个 client 投递上表的 back-channel `logout_token`。该 client 与目录 client 同由部署的 IdP 声明式步骤登记与回读（client 不存在时以机密 client 创建，已有同名而属性不一致时拒绝而不覆写）。该步骤幂等、按 Activity 重试，确定成功前成员不进入 `REVOKED`；结果写入 Workflow 历史与审计。Workspace 撤员不结束 IdP 会话。

Desktop：Desktop 以系统浏览器登录（RFC 8252），那里的 IdP 会话不在应用 WebView 中；组件 iframe 静默登录所依赖的 IdP 会话只由原生认证窗口（§4.7.2）在应用 WebView 中建立。

- 原生认证窗口经 fresh 授权取得该 binding 的 descriptor 后，以 Desktop 原生 public client 在窗口内完成授权码 + PKCE S256（`state` 校验），`redirect_uri` 为回环地址 `http://127.0.0.1/kailo/embedded-sign-in`：窗口导航到该地址时被拦截、取出授权码后关闭，不加载该地址、不起本机监听；窗口只允许导航到 IdP issuer origin。换得的访问令牌与刷新令牌立即丢弃，只把该次 ID token 作为「WebView IdP 会话退出提示」存入 OS keyring（与刷新令牌同一 secret store），新的一次覆盖旧值。窗口关闭后宿主重新装载 iframe，组件以 `prompt=none` 静默登录。
- Desktop 退出依次：撤销 Core PlatformSession、请 IdP 作废刷新令牌（既有），再以一个不可见、不可交互的窗口导航到 IdP `end_session_endpoint`，带 `id_token_hint`（上述退出提示）、`client_id`（原生 client）与 `post_logout_redirect_uri=http://127.0.0.1/kailo/signed-out`（同样被拦截；原生 client 登记该地址为 `post.logout.redirect.uris`）。到达该地址即确认 IdP 已结束该会话，IdP 随即对其中出现过的组件 client 投递 back-channel `logout_token`。退出提示随之从 keyring 删除，不论确认与否。
- 没有退出提示时视为应用 WebView 中没有 IdP 会话；窗口被导航到 issuer origin 与该回跳地址以外、IdP 停在确认页或在部署时限内未到达回跳地址时，关闭窗口并如实报告 IdP 会话未确认结束，不宣称组件会话已失效，也不改为自动确认。

### 4.8 产品一体化呈现（DD-138）

用户与管理员看到的是一个产品：Kailo。云盘、知识库、问数与其中的文档编辑（以及之后任何声明 `KAILO_EMBED` 的组件）只在核心功能与负载上松耦合——独立部署、独立数据与凭据、各自承担业务负载、可替换（DD-87、DD-127(7)）；所有面向人的表面由 Kailo 唯一提供，组件只向这些表面贡献内容，不提供第二个外壳。本节扩展 §4.7（DD-133）：§4.7 让组件页“看起来是 Kailo”，本节规定“每个表面只有 Kailo 一个入口”。

#### 4.8.1 表面归属

| 表面 | Kailo 的唯一入口 | 组件贡献方式 | 禁止出现的形态 |
|---|---|---|---|
| 用户设置 | Kailo 设置页，分类为 Kailo 的功能分类：个人资料、外观（语言、主题）、通知、文档与文件、问答、快捷键等 | release 在 FrontendPresentationContract 声明偏好项（§4.8.2），由 Kailo 设置页在对应功能分类中与 Kailo 自有项混排渲染，值经 wire v1 `preferences` 下发 | 按组件分区或以组件命名的设置页、分组或标题；“已连接的服务/外部服务/集成”列表作为个人设置；组件页内的个人设置、资料、语言、主题、字体、密码、通知偏好、个人凭据入口；在 Kailo 中嵌入组件原生设置页 |
| 导航 | Kailo 侧栏一套导航；组件入口是其中的普通条目（云盘、知识库、问数） | ApplicationBinding 的呈现类别决定条目标签与图标（DD-127(4)）；组件页内只保留业务导航 | “外部服务连接”等接入语义分组；按 Tenant 级/Workspace 级分列同一类别；条目提示显示 `component_type_key`；内容区再套“服务工作区”、返回、刷新、“登录服务”等宿主外壳；组件自己的产品顶栏、产品切换、组织切换 |
| 通知与收件箱 | Kailo 收件箱与 Kailo 设置「通知」分类 | 组件通知投递（§4.8.3） | 组件内通知中心、铃铛、活动收件箱、邮件通知偏好；组件直接向用户发送邮件通知 |
| 搜索入口 | Kailo「搜索全部」 | 组件内容作为搜索来源（§4.8.4） | 组件内跨产品的全局搜索或命令面板；命令面板中的设置、引导、帮助命令。组件业务范围内的检索（在云盘目录中找文件、在知识库中检索）保留为业务功能 |
| 管理后台 | Kailo 管理区（治理组） | 管理面贡献（§4.8.5），按 Kailo 管理分类呈现 | 组件原生管理控制台作为单独产品出现（对最终用户与管理员均不出现）；业务页中的管理入口；组件内成员、角色、邀请、空间与组织管理（成员与角色只来自 Kailo，DD-133(4)） |
| 帮助、关于 | Kailo 帮助与关于 | 不贡献 | 组件的关于、版本、致谢、帮助、反馈、新手引导、升级与上游链接（DD-133(1)） |
| 错误页、空态、加载态 | Kailo 内容区状态：加载由宿主显示到页面握手（`ready`）；需要重新登录、入口不可用与读取失败用 Kailo 文案与样式 | 组件自身的错误页与空态使用 Kailo 令牌与部署显示名加呈现类别名（DD-133(1)） | 上游默认错误页（如未本地化的 404）；宿主与组件各显示一层状态或边界说明 |
| 个人数据与审计 | Kailo 个人数据与审计页 | 个人数据与活动来源（§4.8.6） | 组件内的个人数据导出、删除或活动审计入口 |

判定规则：任一表面上，用户不能据页面内容判断“这里是另一个产品”。组件在 Kailo 模式（部署声明 `KAILO_EMBED` 的实例）下，上表“禁止出现的形态”在嵌入与顶层访问中都不出现；顶层访问只用于登录跳转与直接链接，不因此恢复组件外壳。组件对禁止入口的处理是删除或在 Kailo 模式下不渲染，服务端同时拒绝与 Kailo 权威冲突的写入（例如 DD-133(4) 已关闭的成员与组织接口）；仅前端隐藏不构成授权边界。

#### 4.8.2 偏好贡献

声明：FrontendPresentationContract 的 `preference_declarations[]`（manifest 字段 `preferences`）只能与 `integration_mode=KAILO_EMBED` 同时出现，省略即为空。每项：

| 字段 | 规则 |
|---|---|
| `key` | 1–64 字符，`小写字母开头的段` 以 `.` 连接 2–4 段（如 `documents.measurementUnit`），release 内唯一；是 Kailo 侧的偏好键，不含组件名 |
| `settingsCategory` | `APPEARANCE`（外观）、`NOTIFICATIONS`（通知）、`DOCUMENTS`（文档与文件）、`ANSWERS`（问答）之一；Kailo 按此放入设置页对应分类 |
| `valueType` | `BOOLEAN` 或 `ENUM`；不接受自由文本、数字区间、URL、凭据或任何用户数据 |
| `options[]` | `ENUM` 时 2–12 项、取值互不相同，每项 `value`（1–32 个字母、数字、`.`、`_`、`-`）与 `label`；`BOOLEAN` 时为空 |
| `defaultValue` | 字符串：`BOOLEAN` 为 `true`/`false`，`ENUM` 为 `options[].value` 之一 |
| `label`、`description` | 键恰为 `ZH_CN`、`EN` 的文案（`label` 1–60 字符必填，`description` 1–200 字符可选） |

Core 登记 release 时按上表校验，任一项不符整体拒绝（与 §4.7.1 同一拒绝），最多 16 项；ApplicationBindingView 与原生页面 descriptor 从 pin 的 `APPROVED` release 投影该列表，Core 不保存偏好的值。

呈现：Kailo 设置页读取当前用户可发现的 `ACTIVE` 原生页面 binding（Tenant 级与当前 Workspace 级）的声明，把每项放入 `settingsCategory` 对应分类，与 Kailo 自有项混排，标题与说明只用声明文案，不出现组件名、呈现类别名或分区；`DOCUMENTS`、`ANSWERS` 分类在没有任何项时不出现。同一 `key` 在多个 release 中声明完全一致（类型、选项、默认值）时只呈现一个控件、共享一个值；不一致时该键不呈现，各组件取自己的默认值。

存放（DD-164(7)）：值是账号偏好，与主题、语言一同保存在 Core 的 AccountPreferences（每个 HumanIdentity 一份，`GET/PUT /api/v1/account/preferences`，按 `version` 比较并交换），Kailo 宿主 origin 的本机存储只作缓存与首屏初值；登录后与窗口重新获得焦点时以 Core 值为准，本机改动先应用再写入 Core，冲突时取 Core 当前值后重放这一项。宿主读取时按该 binding 的声明校验，不合法或缺失的值以声明默认值代替。

下发（wire v1 附加消息，`version` 仍为 1，旧运行时按 §4.7.2 忽略未知 `type`）：

| 方向 | 消息 | 时机 |
|---|---|---|
| Kailo → 组件 | `{source:"kailo-host", version:1, type:"preferences", values}` | 收到 `ready` 时（紧随 `presentation`）与该页面任一已声明偏好的值变化时 |

`values` 恰含该 binding 的 release 声明的全部键，值为 `BOOLEAN` 的 JSON 布尔或 `ENUM` 的取值字符串；宿主只以 descriptor `origin` 为 `targetOrigin`。运行时按 §4.7.2 的来源规则接收，键或值形状不符时整条忽略；接受后存入本标签页 sessionStorage（随 OIDC 跳转保留），暴露 `getPreferences()`、`onPreferencesChange(listener)` 并派发 `kailo:preferences` 事件。组件对未收到的键使用自己声明的默认值，忽略未知键。偏好值只是枚举或布尔，不构成令牌、身份或用户数据，§4.7.2 的消息边界不变。

组件义务：已声明的偏好只经此路径生效，组件页内不再提供同义入口；组件需要但未声明的个人偏好不得以组件内设置页补齐，要么声明为偏好项，要么固定为 Kailo 模式下的确定行为。文档编辑（DD-132）的偏好由承载它的云盘 release 声明，作用于编辑器启动配置，编辑器内的“高级设置”在 Kailo 模式下不出现。

#### 4.8.3 组件通知并入 Kailo 收件箱

组件需要通知某人的事件只投递给 Kailo，由 Kailo 收件箱呈现，并按 Kailo「通知」分类的偏好提醒。这类事件包括：分享给你、提及你、评论、访问申请、任务完成和内容更新。组件不自建通知中心、铃铛、活动收件箱或邮件通知。持久形态是 `03` §3 的 ComponentNotification，权威在 Core，不投影到 Relay。

投递合同：

- **入口**：Core 服务监听面 `POST /service/v1/component-notifications/bindings/{bindingId}/notifications`。
  - 与 §4.7.4 成员目录使用同一服务认证器、同一调用身份：`azp` 等于该 binding 的 `normalizedConfig.directoryClientId`，且该 client 在非 `DISABLED` binding 中唯一。
  - 前提与成员目录相同：binding、active generation 投影均 `ACTIVE`，release `APPROVED` 且为 `NATIVE_PAGE`，Tenant 与 Workspace `ACTIVE`。另要求 release 的 FrontendPresentationContract 为 `KAILO_EMBED`。
  - 不挂在网关的浏览器路由上，不建立 ActionExecution，不授予任何权限。回应带 `Cache-Control: no-store`。
- **请求体**：一次一条，类型为 `ComponentNotificationDelivery`。未知字段整体拒绝。
  - `idempotencyKey`：1–128 个字符，取字母、数字、`.`、`_`、`:`、`-`，在该 binding 内唯一。
  - `recipient`：接收人的 `issuer` 与 `subject`。
  - `actor`（可选）：触发者的 `issuer` 与 `subject`。
  - `category`：封闭枚举。`SHARED` 分享给你；`MENTIONED` 提及你；`COMMENTED` 评论了你的对象；`ACCESS_REQUESTED` 访问申请；`TASK_COMPLETED` 任务完成；`CONTENT_UPDATED` 你关注的内容有更新。
  - `title` 与可选的 `summary`：键恰为 `ZH_CN`、`EN` 的文案，不含控制字符。标题 1–120 字符，摘要 1–280 字符。
  - `path`：该组件页面 origin 内的相对路径，1–1024 字符，规则如下：
    - 以单个 `/` 开头，不含反斜杠、空白或控制字符；
    - 按 descriptor origin 解析后 origin 不变；
    - 查询参数名不得是 `token`、`access_token`、`id_token`、`refresh_token`、`code`、`secret`、`password`、`api_key`、`key`、`signature` 或 `sig`，不区分大小写。
  - `occurredAt`（可选）：RFC3339，不晚于 Core 当前时刻 5 分钟。
- **接收人与触发者**：`recipient` 必须在该 binding 当前目录范围内（§4.7.4「范围」），即同时满足：
  - `issuer`+`subject` 是 `ACTIVE` 的 ExternalIdentity；
  - 其 HumanIdentity、该 Tenant 的 TenantMembership 与 HUMAN Principal 均为 `ACTIVE`；
  - Workspace binding 另要求该 Principal 对该 Workspace 有 `discover`（SpiceDB fully consistent）。

  `actor` 按同样规则核对，且不得是接收人本人。任一项不满足即整条拒绝。
- **幂等与限流**：
  - 同一 binding 与 `idempotencyKey` 的重复投递按内容摘要（请求体规范 JSON 的 SHA-256）判断：摘要相同返回首次结果，不同返回 `409`。
  - 按 binding 统计最近 60 秒内新建的条目数，超过部署上限（默认 600）返回 `429`，不写入。
- **回应**：
  - 新建返回 `201`，重复返回 `200`。回应体为 `notificationId` 与 `duplicate`。
  - 令牌不成立、binding 不满足前提、接收人或触发者不在范围内，一律返回 `403`，不区分原因。
  - 形状或取值不合返回 `400`；数据库或 SpiceDB 不可读返回 `503`。
  - 组件遇到 `503` 或 `429` 时以同一幂等键退避重试；遇到 `400`、`403`、`409` 不重试。
  - 日志只记 binding、类别与结果，不记标题、摘要或路径。

呈现：

- **读取范围**：Kailo 收件箱经 BFF 读取当前会话 Principal 在会话 Tenant 内收到的条目，按 `received_at` 倒序分页。只列出同时满足两项条件的条目：所属 binding 仍为 `ACTIVE`；本人对其 Workspace（Workspace binding）或 Tenant（Tenant binding）仍有 `discover`。
- **展示**：条目不显示组件名、`component_type_key` 或 binding ID，来源只标注呈现类别名（云盘、知识库、问数）。触发者以 Kailo 显示名与头像呈现。
- **分类**：全部条目进入「全部」。`ACCESS_REQUESTED` 另进入「需要处理」，`MENTIONED` 另进入「提及」。
- **打开**：打开条目即把它标记为已读，并在 Kailo 内容区打开该 binding 的组件页。iframe 地址由 descriptor `origin` 与 `path` 组成，再附 §4.7.2 启动参数；解析结果离开该 origin 时不打开，只显示条目。打开后可见的内容仍由组件自身 ACL 决定。
- **已读**：已读状态是接收人本人的个人状态，与 Channel 已读位置同类。BFF 只允许本人把自己的条目标记为已读，不建立 ActionExecution。
- **提醒**：Kailo 设置「通知」分类按上述每个类别各设一个开关，默认开启。关闭某类别只停止它的桌面通知、提示音与未读角标计数，条目仍进入收件箱。组件不得声明与这些开关同义的偏好（§4.8.2）。
- **保留**：条目自 `received_at` 起保留 90 天，之后由 Core 删除；Tenant 删除时一并删除。binding 停用后，条目不再列出，也不再接受新投递。

组件义务：Kailo 模式下，组件的通知中心、铃铛、活动收件箱、邀请提醒与邮件通知偏好都不出现，组件也不直接向用户发送通知邮件。原本触发这些提醒的事件改按本节投递；投递失败时不回退为组件内提醒或邮件。

#### 4.8.4 组件内容作为 Kailo 搜索来源

Kailo「搜索全部」是唯一的全局搜索入口。组件内容只能以能力契约接入成为搜索来源，条件是同时满足：

- release 的 ExecutionConnector 为 `REMOTE_ADAPTER`；
- release 声明 `search_source=SUPPORTED`（manifest 字段 `executionConnector.searchSource`，省略即为 `NONE`；其他 connector 不得声明该字段）。

满足条件的 release，其 adapter 必须实现 §5.2 的 `search` 操作。只提供原生页面入口（`ExecutionConnector=NONE`）的 release 不被 Core 调用，因此不贡献搜索结果；组件页内只保留其业务范围内的检索。

- **准入与授权**：
  - BFF 以当前 HUMAN 的 ExecutionContext 准入。
  - 候选 binding 须在会话 Tenant 内，binding 与 active generation 投影均为 `ACTIVE`，release `APPROVED` 且声明 `searchSource=SUPPORTED`。Workspace binding 另须经该 Workspace 的成员准入。
  - 对每个候选，Core 取该 binding 下 `ACTIVE` 的 Resource，逐个对当前 Principal 做 fresh `read` Check（SpiceDB fully consistent）。没有可读 Resource 的 binding 不被调用。
  - 查询不建立 ActionExecution，不消耗 Quota。
- **调用**：Core 经 binding 的 adapter 端点调用 `search`。
  - 请求体字段：
    - `idempotencyKey`；
    - `query`：去掉首尾空白后 1–200 字符；
    - `limit`：1–20；
    - `locale`：`ZH_CN` 或 `EN`；
    - `resources[]`：本次可读 Resource 的 `resourceId`、`nativeType`、`nativeId`，至多 50 个。
  - 以 Search Token 认证：
    - 与 ActionToken 使用同一签名密钥与 JWKS，算法 ES256；`aud` 为 release 的 `actionTokenAudience`；
    - `token_use=COMPONENT_SEARCH`；
    - 含 `tenant_id`、`binding_id`、`projection_generation`、`actor_principal_id`、`authorization_min_zed_token`，Workspace binding 另含 `workspace_id`；
    - `normalized_parameter_hash` 为请求体规范 JSON 的 SHA-256；
    - 有效期不超过 60 秒；
    - 不含 Delegation、Agent 或结果暴露授权。
  - Adapter 验签，并核对 Tenant、Workspace、binding 与摘要，之后只在 `resources[]` 指定的 native 对象内检索。
- **结果**：
  - 每项包含 `title`（1–200 字符）、可选的 `summary`（至多 400 字符）、`kind`（`FILE`、`FOLDER`、`DOCUMENT`、`KNOWLEDGE_BASE`、`QUESTION`、`DASHBOARD`）、`path`（与 §4.8.3 同一相对路径规则）和可选的 `updatedAt`，至多 `limit` 项。
  - 任一项不合规，就丢弃该 binding 的全部结果，并把该来源标为不可用；不截断，也不部分采信。
  - Core 不保存结果。
- **扇出**：
  - 各 binding 并行调用。单次超时取 binding adapter 配置与 5 秒中的较小值。
  - 回应列出每个来源的状态（可用或不可用），一个来源失败不影响其他来源。
- **呈现与打开**：
  - 结果按来源的呈现类别（云盘、知识库、问数）分组标注，不显示组件名或 binding。
  - 打开时，在 Kailo 内容区载入同一 Tenant（与 Workspace）中该呈现类别生效的原生页面入口，解析方式与侧栏相同，地址由其 descriptor `origin` 与 `path` 组成。
  - 没有可打开入口的来源不贡献结果。

#### 4.8.5 组件管理能力并入 Kailo 管理区

组件的管理能力只以**管理面**贡献给 Kailo 管理区；组件原生管理控制台在 Kailo 模式下不作为任何人可达的产品存在（DD-138(6)）。本节不新增实体、动作键、Workflow kind、SpiceDB 关系、授权权威或计量：管理面声明是随 release 固定的值对象，打开管理面是读取；组件内的写仍由组件按成员目录派生的角色在服务端判定（DD-133(4)），Kailo 的显示不替代该判定。

**声明**：FrontendPresentationContract 的 `admin_surface_declarations[]`（manifest 字段 `adminSurfaces`）只能与 `integration_mode=KAILO_EMBED`、FrontendDelivery `NATIVE_PAGE` 同时出现，省略即为空，至多 12 项。每项：

| 字段 | 规则 |
|---|---|
| `key` | 管理面标识，格式同 §4.8.2 偏好键（2–4 个小写字母开头的段以 `.` 连接，≤ 64 字符），release 内唯一，不含组件名；首段不得为 `members`、`roles`、`invitations`、`users`、`groups`、`spaces`、`organizations`、`tenants`、`workspaces`——成员、角色、邀请、空间与组织只在 Kailo 成员与角色管理中，不作为管理面贡献 |
| `adminCategory` | Kailo 管理分类：`MODELS`（模型）、`DATA_SOURCES`（数据源）、`STORAGE`（存储）、`INDEXING`（索引与解析）、`INTEGRATIONS`（集成）、`SYSTEM`（系统）之一 |
| `path` | 组件 origin 内的固定路径：以单个 `/` 开头，1–256 字符，每段只含字母、数字与 `.`、`_`、`~`、`-`，没有空段、`.` 或 `..` 段、查询、片段、百分号编码与反斜杠；多个管理面可共用同一路径，以管理面标识区分 |
| `requiredPermission` | 所需 Kailo 权限：`BINDING_MANAGE` 为 binding 所属 scope 的 `manage`（Workspace 级 binding 即该 Workspace 的 `manage`，Tenant admin 经 `tenant->manage` 同样持有；Tenant 级 binding 即 Tenant `manage`）；`TENANT_MANAGE` 为 Tenant `manage`，用于作用于整个组件实例、超出单个 Workspace 的设置 |
| `access` | `EDITABLE`：组件自有、在该页内可改的设置；`READ_ONLY`：由 Kailo 派生或由部署声明、组件内只读展示的设置，组件服务端在 Kailo 模式下拒绝对应写接口（见下文归属表） |
| `title`、`description` | 键恰为 `ZH_CN`、`EN` 的文案（`title` 1–60 字符必填，`description` 1–200 字符可选），不含组件名 |

Core 登记 release 时按上表校验，任一项不符整体拒绝（与 §4.7.1 同一拒绝），不保存任何管理面的状态。

**列出**：BFF `GET /api/v1/admin-surfaces?workspaceId=` 返回当前 HUMAN 可管理的管理面。只取当前 Tenant 级与所给 Workspace 级（先经 Workspace 准入）`ACTIVE` binding 的 pin `APPROVED` release 所声明的项，逐项对 `requiredPermission` 对应对象做 FullyConsistent 的 fresh `manage` 检查，不通过的项不返回，也不区分“无权”与“不存在”。每项只含 binding ID、Workspace、呈现类别（DD-127(4)）与声明本身，不含 URL、`component_type_key`、配置或凭据。ApplicationBindingView 不投影管理面：它对持有 `discover` 的成员可见。

**管理区呈现**：Kailo 管理区（治理组；Web 与 Desktop 共用同一共享页面）在 Kailo 自有的成员与角色、邀请等项之后，按固定顺序模型、数据源、存储、索引与解析、集成、系统分组列出管理面。条目只显示声明的标题与说明、来源的呈现类别名（云盘、知识库、问数；与收件箱、搜索同一来源标注规则）和 `READ_ONLY` 时的“由 Kailo 管理 · 只读”标记；没有项的分类不出现，没有任何项时整组不出现。不按组件分组，不显示 `component_type_key`，不出现“已连接的服务”。

**载入**：打开条目时宿主请求 `GET /api/v1/application-bindings/{id}/native-page?adminSurface=<key>`。Core 在 §4.6 descriptor 的全部校验之外确认该 key 属于 pin release 的声明，并以 `requiredPermission` 对应对象的 fresh `manage` 代替 `discover`；任一不成立按 `PERMISSION_DENIED` 拒绝。descriptor 的 `url` 为 descriptor `origin` 加声明的 `path`（不取 binding 入口路径），另附 `adminSurface`（该项声明）。宿主沿用原生页面的嵌入方式在 Kailo 内容区载入（§4.6 iframe 与 CSP、§4.7.2 握手、§4.8.7 页头与骨架）：启动 URL 在 `kailo_theme`、`kailo_locale` 之外附 `kailo_admin_surface=<key>`，运行时与主题、语言同样把它存入本标签页 sessionStorage（随 OIDC 跳转保留）并暴露 `adminSurface()`。页头由 Kailo 绘制为“管理 › 分类名 › 标题”（`20` §13.2）；组件经 `page` 只可追加面包屑与操作，宿主忽略管理面页中的 `tabs`。

**组件义务**：

1. **单项呈现**：带管理面标识打开的页面只渲染该项管理功能，不渲染自己的管理导航、侧栏、个人菜单、产品外壳或通往其他管理功能的链接；标识未知、与路径不匹配或缺失时显示 Kailo 空态，不渲染任何管理功能。
2. **服务端判定**：管理权限仍由组件服务端按成员目录派生的角色判定（DD-133(4)），`kailo_admin_surface` 参数与 Kailo 管理区的显示都不是授权；`READ_ONLY` 管理面对应的写接口在 Kailo 模式下由组件服务端拒绝，不只在页面上禁用控件。
3. **原生控制台关闭**：Kailo 模式下，组件原生管理控制台、“全部设置”与“系统管理”等管理对话框，以及业务页中的管理入口（菜单项、齿轮、管理快捷方式）全部删除；直接请求原生控制台或管理路由时，组件服务端在返回任何管理页面之前重定向到业务首页或以 `403` 拒绝。只有声明的管理面路径在携带匹配的 `kailo_admin_surface` 时以单项形态返回。前端隐藏不作为关闭的证据（V-SCN-270）。
4. **首次接入例外**：组件尚无可用业务配置时（如问数尚未连接数据源）业务页只显示“请管理员在 Kailo 管理区完成设置”的 Kailo 空态，不在业务页内打开管理流程；首次配置同样经对应管理面完成。

**系统级设置归属**（Kailo 模式）：

| 设置 | 归属与来源 | 组件内 |
|---|---|---|
| 模型：供应商、模型、端点、密钥、本地模型下载 | Kailo 模型路由（DD-128）：Tenant admin 在 binding 的 `modelGateway` 选定 `llm_route`，Core 投影组件专属 key 与原生模型集合 | 只读展示已投影的模型（`MODELS`，`READ_ONLY`）；新增、编辑、删除模型与拉取本地模型在服务端拒绝。业务对象内“选用哪一个已投影模型”（如知识库使用的对话或向量模型）是业务设置，保留在业务页 |
| 成员、角色、邀请、空间、组织、个人账号 | Kailo 成员与角色（DD-133(4)），经目录同步派生 | 不是管理面；组件内只读，写接口拒绝 |
| 存储：数据源、存储后端、向量库与数据存放位置 | 部署声明（组件部署单元与 binding config），在部署时生效 | 只读展示（`STORAGE`，`READ_ONLY`），写在服务端拒绝 |
| 索引与解析：解析引擎、分块与索引默认参数 | 部署声明 | 只读展示（`INDEXING`，`READ_ONLY`），写在服务端拒绝 |
| 认证与单点登录、邮件、升级与更新、运行队列、服务与调度、实例级 API key、系统审计与活动日志 | Kailo（身份 DD-133、通知 §4.8.3、个人数据与审计 §4.8.6、可观测性 `14`、凭据只以 SecretRef 出现）或部署 | 不呈现、不是管理面；入口删除、路由与写接口拒绝 |
| 问数的数据源连接、语义建模与项目设置 | 组件自有业务配置：模型与数据留在组件，Kailo 不建立第二份模型权威（DD-87、`08` §9.2）；连接凭据只在组件内保存 | 管理面（`DATA_SOURCES` / `SYSTEM`，`EDITABLE`），写仍需 binding `manage`（问数的 Core `manage` 判定） |
| 知识库的联网搜索 | 组件自有的问答能力配置，只作用于组件内的快速问答 | 管理面（`INTEGRATIONS`，`EDITABLE`）。问答技能（及其沙箱）与 MCP 服务只服务于 Kailo 模式下已关闭的 Agent 模式，不是管理面，写接口在服务端拒绝（DD-163、§4.8.8） |
| 云盘的元数据字段 | 组件自有业务配置 | 管理面（`SYSTEM`，`EDITABLE`） |

保留在组件内的只有两类：只有组件理解其语义的业务配置（语义模型、数据源连接、联网搜索、元数据字段），以及业务对象内对已由 Kailo 提供之物的选择（选用哪个已投影模型）。把它们复制进 Core 会形成第二份权威，并违背业务能力只经能力契约接入、平台不复制组件内部配置的原则（DD-87、§4.6）；它们以管理面在 Kailo 管理区呈现，因此对管理员仍只有一个产品。

文档编辑（DD-132）不贡献管理面：它的原生管理面板已在打包时移除（DD-35），编辑器的个人设置由承载它的云盘 release 按 §4.8.2 声明，服务级设置（连接、令牌、字体与格式支持）是部署声明，不在任何页面中可改。

#### 4.8.6 个人数据与审计

用户在 Kailo 个人数据页查看与导出本人数据、在 Kailo 审计页查看与本人相关的记录。组件数据作为来源接入：能力 release 经 `REMOTE_ADAPTER` 提供本人数据导出与活动查询，原生页面入口 release 按 §4.8.3 同一服务身份投递本人相关的活动摘要；组件内不提供个人数据或活动审计入口。具体来源合同在该阶段的设计增量中登记。

#### 4.8.7 组件页外壳与交互（DD-157）

§4.7 让组件页取 Kailo 的令牌，§4.8.1–4.8.6 让每个表面只有 Kailo 一个入口；本节让组件页的**外壳与交互**也由 Kailo 提供：页头（产品名、面包屑、标题、操作）、分区标签、Toast、确认对话框、全局快捷键与首屏骨架由 Kailo 绘制，组件只渲染内容区。视觉与交互规格见 `20` §13；本节规定线协议与双方义务。不新增实体、动作键、Workflow kind、授权权威或计量；§4.6 的隔离、来源与授权边界不变。

**声明**：组件页在 `kailo-embed.js` 之前放置 `<meta name="kailo-embed-features" content="page toast confirm shortcuts">`，取值为构建事实（与 `kailo-web-origin` 同类，不从 URL 读取），只认识这四项，未知项忽略。运行时在 `ready` 中附带已声明的子集 `features`；旧宿主忽略该字段。

**线协议**（wire v1 附加消息，`version` 仍为 1；旧运行时与旧宿主按 §4.7.2 忽略未知 `type`；来源校验同 §4.7.2：精确 origin、父窗口或该 iframe 窗口）：

| 方向 | 消息 | 规则 |
|---|---|---|
| 组件 → Kailo | `{type:"page", page}`；`page` 为 `null` 时清除 | `title` 1–120 字符；`breadcrumbs[]` ≤ 8（祖先，外到内，不含当前标题）、`tabs[]` ≤ 8，各项 `id`（1–256 字符的不透明串）与 `label`（面包屑 ≤ 80、标签 ≤ 40）；`activeTab` 须为某个 `tabs[].id`；`actions[]` ≤ 8，各项 `id`、`label` ≤ 40、`variant` ∈ `primary\|secondary\|menu`（`primary` 至多一个）、可选 `icon`（闭集：upload、plus、folder-plus、share、download、rocket、refresh、settings、message-square-plus、play、trash、pencil、filter、search、more）、`disabled`、`busy`；`id` 在 `actions` 内唯一；需要用户选择文件的操作另声明 `files:{accept?, multiple?, directory?}`（`accept` 为 1–200 个字母、数字、`.+-/*,` 或空格） |
| 组件 → Kailo | `{type:"toast", toast:{tone, title, description?}}` | `tone` ∈ `success\|info\|warning\|error`；标题 1–120、说明 ≤ 280 字符 |
| 组件 → Kailo | `{type:"confirm", confirm:{id, tone, title, description?, confirmLabel?, cancelLabel?, option?}}` | `id` 为 1–64 个字母、数字或 `-`；`tone` ∈ `default\|danger`；标题 ≤ 120、说明 ≤ 400、按钮文字 ≤ 24 字符；`option:{label, warning?}` 为对话框内唯一一个默认未勾选的选择（如“永久删除”），`label` 1–80、`warning` ≤ 200 字符，只发往宣告了 `confirm-option` 的宿主 |
| 组件 → Kailo | `{type:"shortcut", shortcut}` | 闭集 `search\|settings\|back\|forward`，由运行时在捕获阶段识别 Kailo 的全局组合键后发送 |
| Kailo → 组件 | `{type:"navigate", target:{kind:"tab"\|"breadcrumb", id}}` | 只回传组件当前页头中声明过的 `id`；运行时再校验一次 |
| Kailo → 组件 | `{type:"action", id, files?, paths?}` | 同上，且该操作未禁用；只有声明了 `files` 的操作才携带用户在 Kailo 文件选择器中选中的 `File`（≤ 1000 个）与等长的相对路径（≤ 1024 字符），运行时逐项校验 |
| Kailo → 组件 | `{type:"confirm-result", id, confirmed, option?}` | `confirmed` 为布尔；`option` 只回答带 `option` 的请求，为该选择的勾选状态，`confirmed:false` 时恒为 `false` |

所有文本字段不得含控制字符，空白折叠后计长；任一字段不合规时整条消息丢弃，不部分采用。

**文件选择通道**：浏览器只把用户激活交给发生点击的文档及其祖先，跨 origin 的 iframe 收不到宿主点击带来的激活，组件因此不能在页头操作的回调里打开自己的文件选择器。声明了 `files` 的操作由 Kailo 在用户点击的同一手势内打开系统文件选择器，选中的 `File` 以结构化克隆随 `action` 消息只投递给该 iframe 的 origin；取消选择不发送任何消息。Kailo 不读取、不保存、不上传文件内容，上传仍由组件以自身认证与授权完成（§4.6）；组件内的拖放与自身上传按钮保持不变。

**宿主能力宣告**：支持本节的 Kailo 在每条 `presentation` 中附带 `features`（同一闭集中宿主实际处理的项，另加宿主能力 `files`（页头操作的文件选择通道）与 `confirm-option`（确认中的单项选择））；运行时据此提供 `hostSupports(feature)` 并在 `<html>` 上写 `data-kailo-host-features`。宿主应答之前，声明 `page` 的页面由 Kailo 骨架遮盖；应答中不含某项时，运行时对该项返回 `false`/`null`，组件保留自己的页头、提示或对话框（按 `20` §13 样式），不会因宿主较旧而失去导航。带 `option` 的确认在宿主未宣告 `confirm-option` 时由运行时返回 `null`，组件保留自己的对话框，不把选择静默丢弃。

**数据边界**：页头、Toast 与确认中的文字是组件在当前用户浏览器中呈现给同一用户的显示文本（目录名、知识库名、文件名等），因此本节是 §4.7.2“消息不携带用户数据”的唯一例外，且限定为：Kailo 只以纯文本渲染（不解释为 HTML、Markdown 或链接），只保存在该页面的内存状态中，不写入存储、日志、遥测、Inbox、搜索或任何服务端请求，iframe 卸载即丢弃；消息仍不携带令牌、身份、URL 或凭据。`id` 对 Kailo 不透明，只原样回传。

**宿主义务**：

1. **页头**：Kailo 为每个组件页绘制页头（`20` §13.2）。产品名与类别图标取侧栏条目的呈现类别（DD-127(4)），与组件声明无关；组件声明的标题与面包屑跟在其后，操作按 `variant` 排列。组件未声明 `page` 或尚未发送时只显示产品名。
2. **首屏**：声明了 `page` 的组件在收到第一条 `page` 消息前 iframe 不可见，Kailo 显示与页头一致的骨架；超过 §4.7.2 的握手宽限（8 秒）仍未收到则直接揭开，不阻断使用。未声明 `page` 的组件以 `ready` 为界，行为同 §4.7.2。
3. **Toast**：以 Kailo 的通知面显示（`20` §9）；同一 iframe 10 秒内至多 5 条，相同内容 3 秒内合并。
4. **确认**：以 Kailo 对话框显示，同一时刻只有一个；已有对话框时新的请求立即以 `confirmed:false` 回答。关闭（含 Esc 与遮罩点击）即 `false`。带 `option` 时以默认未勾选的复选框显示，勾选后才显示 `warning`；选择与确认一起回传，同样不构成授权。结束后把焦点交回 iframe。确认结果只回传给该组件，Kailo 不据此执行任何动作；组件的写操作仍由组件自身认证与授权（§4.6），对话框不构成授权。
5. **快捷键**：收到 `shortcut` 时在宿主窗口重放对应的 Kailo 组合键，由宿主既有处理器执行（搜索全部、设置、前进后退），与在 Kailo 中按下等效。
6. **嵌入**：iframe 无边框，元素背景为内容区 surface，`color-scheme` 随当前明暗；令牌文件附带基础层（画布、滚动条、选区、焦点环、主题切换时关闭过渡，`20` §13.5），宿主使用同一滚动条规格。

**组件义务**：

1. 声明 `page` 的组件在内容可显示时首次 `setPage`，此后每次路由或上下文变化重新声明；`setPage` 返回 `true` 时不渲染自己的页标题、面包屑、产品顶栏和与标签同义的导航（`20` §13.2）；返回 `false`（顶层访问）时保留自己的页头，但样式按 `20` §13。
2. 声明 `toast` / `confirm` 的组件把用户可见的提示与破坏性确认交给 `KailoEmbed.toast()` / `KailoEmbed.confirm()`；二者在没有 Kailo 宿主时分别返回 `false` / `null`，组件此时自绘，样式同 `20` §9。
3. 声明 `shortcuts` 的组件不再响应 Kailo 的全局组合键（运行时已在捕获阶段拦截），也不显示“⌘K 全局搜索”一类提示；业务内检索保留。
4. 控件、密度、图标与文案按 `20` §13.3–13.6；Esc 只关闭本文档最上层浮层，不用于页面导航。

**兼容**：旧运行时不发送新消息，宿主按 §4.7.2 行为不变；旧宿主忽略新消息，组件的 `setPage` 仍返回 `true` 但没有页头——因此组件声明 `page` 的 release 须与支持本节的 Kailo Web/Desktop 版本同批发布（`kailo-embed.js` 与令牌文件变化本身已使组件 `source_digest` 失效，§4.7.1）。

#### 4.8.8 协作与 AI 的单一体系（DD-163）

#### 4.8.9 组件用量上报与额度准入（DD-165）

组件的业务用量进入 Kailo 统一的计量、额度与用量视图。OpenMeter 是唯一计量与额度权威；Core 只登记随 Core 固定的平台 meter、接收上报、写 UsageEvent 并代组件读取 entitlement，不保存余额或用量副本（DD-07）。组件不自建额度、计费或用量页面。

meter 目录（一期）：

| meter | 聚合 | 采集点 | 成员维度 | 呈现类别 | 额度项 |
|---|---|---|---|---|---|
| `component_model_tokens` | sum | Gateway durable usage（SS-AGW-USAGE），不可上报 | 无 | 任意（模型调用的 binding） | `component_tokens` |
| `knowledge_answer_count` | count | 本节上报：一轮问答的原生完成终态写入后一次 | 有 | `knowledge` | `knowledge_answers` |
| `data_query_count` | count | 本节上报：原生问数任务建立后一次 | 有 | `data_query` | `data_queries` |
| `file_storage_bytes` | latest | 本节上报：每小时一次本实例用户内容总字节快照 | 无 | `file_storage` | `file_storage` |

上报合同：

- **入口**：Core 服务监听面 `POST /service/v1/component-usage/bindings/{bindingId}/reports`。调用身份、前提与 §4.8.3 相同：binding 的目录 client 令牌；binding 与 active generation `ACTIVE`，release `APPROVED`、`NATIVE_PAGE`、`KAILO_EMBED`，Tenant 与 Workspace `ACTIVE`。另要求请求的 meter 与 release 的 `native_page_category` 按上表对应。不建立 ActionExecution、不授予权限，回应带 `Cache-Control: no-store`。
- **请求体**：一次一条，类型 `ComponentUsageReport`，未知字段整体拒绝：
  - `idempotencyKey`：规则同 §4.8.3，在该 binding 内唯一；内置实现以原生持久记录 ID（问答消息、问数 query）或 UTC 小时（存储快照）派生。
  - `meterKey`：上表可上报的三项之一。
  - `quantity`：非负整数；count meter 恰为 1，存储快照为字节数，不超过 10^15。
  - `occurredAt`：RFC3339，不晚于 Core 当前时刻 5 分钟，不早于 7 天前。
  - `member`：count meter 必填、存储快照不得出现；为 `issuer`+`subject`，必须在该 binding 当前目录范围内（§4.8.3「接收人」同一规则）。
- **入账**：Core 以 `(bindingId, idempotencyKey)` 派生稳定 `source_id`，写入来源类型 `COMPONENT_REPORT` 的 UsageEvent：operation 为该 binding 当前 generation 的用量归集 operation（attribution `BINDING`），Customer 为 Tenant，subject 为该 Customer 的原生 key（Tenant ID，按 key 原生归属，不逐 binding 登记 subject），维度为 `workspace_id`（Tenant 级 binding 不上送）、binding、release、generation 及 count meter 的 `member_principal_id`。随后由既有 outbox 投递 OpenMeter，202 只到 `ACCEPTED`，查到 `stored_at` 才 `COMMITTED`（`11` §4）。
- **幂等、限流与回应**：同键同内容（请求体规范 JSON 的 SHA-256）返回首次结果 `200`，同键异内容 `409`；新建 `201`，回应体为 `usageEventId` 与 `duplicate`。按 binding 统计最近 60 秒新建的上报，超过部署上限（默认 1200）`429`。令牌、前提、meter 类别或成员范围不成立一律 `403` 不区分原因；形状或取值不合 `400`；数据库、SpiceDB 不可读 `503`。组件遇 `503`/`429`/网络失败以同一幂等键退避重投，遇 `400`/`403`/`409` 不重投。上报是已发生用量，额度耗尽时照常入账。日志只记 binding、meter 与结果，不记成员身份。

准入合同：

- **入口**：`POST /service/v1/component-usage/bindings/{bindingId}/admission`，身份、前提与 meter 类别规则同上报；请求体 `ComponentUsageAdmissionRequest{meterKey, member?}`，`member` 规则同上报。
- **判定**：读该 Tenant Customer 对应额度项的 entitlement（硬限制）。无访问为 `TENANT_QUOTA_EXHAUSTED`；entitlement metadata 带成员上限 `kailo_member_limit` 且 OpenMeter 在当前周期按 Customer 与 `member_principal_id` 过滤的 committed usage 不小于它为 `MEMBER_QUOTA_EXHAUSTED`；否则 `ALLOWED`。回应体 `ComponentUsageAdmission{decision, periodResetAt?}`。OpenMeter 不可读或映射不唯一 `503`，组件不得放行。判定是 CHECK：不预留、不扣减，组件可把 `ALLOWED` 缓存至多 60 秒。
- **组件行为**：动作开始前询问；`TENANT_QUOTA_EXHAUSTED`、`MEMBER_QUOTA_EXHAUSTED` 与 `503`/不可达都拒绝该动作且不产生原生副作用，并在组件原位以 Kailo 文案提示（组织额度用完请联系管理员／本人额度用完／用量服务暂不可用）；已开始的动作允许完成并照常上报。

模型调用的额度由 DD-128(2) 的 ExtAuthz 逐调用 CHECK `component_tokens`，不经本节入口。二期 meter（知识检索次数、云盘传输字节、文档转换次数、云盘个人空间存储）按同一目录、上报与准入规则登记，采集点闭合前不登记（DD-165(6)）。

## 5. Component Adapter Protocol

### 5.1 与上游项目形态解耦

| Connector | 适用条件 | 边界 |
|---|---|---|
| `PLATFORM_PORT_CLIENT` | Platform Component 实现已知 port | Core typed client 通过 Port Router 调 provider；不再套 application adapter |
| `REMOTE_ADAPTER` | Application Component 默认形态 | Core/Worker 调独立 adapter，adapter 调 native API |
| `EMBEDDED_DRIVER` | 仅平台自身，上游明确提供 library runtime | 代码与 Core/Worker 构建绑定；业务能力服务不得使用（DD-64/87） |
| `PROTOCOL_PEER` | Application Component 只经 AgentGateway 的 MCP Tool 传输接入（DD-12/58） | 端点属于 binding 配置，不写死产品配对；Gateway 双相 PEP/Core 执行完整统一准入、fresh 授权、审批、Quota 与审计，不要求原生 peer 接受 ActionToken 或实现 Adapter API；不用于两个业务服务之间的数据面直连。需要上游 Adapter Protocol、ActionToken、ProtocolSession 或该协议 revision 查询的能力（含在线编辑与服务读取边来源）必须经 `REMOTE_ADAPTER`（DD-94/103） |
| `NONE` | 仅 `class=APPLICATION` 的原生页面入口 release（DD-127）：`implements=[]`、FrontendDelivery `NATIVE_PAGE` | 无 adapter、无工具、无 ActionToken、无 binding secret；Core/Worker 不向该服务发起任何调用，页面由服务自身会话访问自己的后端 |
| `INTERNAL` | Core 自身领域，仅 `class=PLATFORM` 且 `platform_port_key=CORE_INTERNAL` | 不生成网络 adapter 或自签 token 循环；`class=APPLICATION` 不得使用 |

不变式：`class=APPLICATION` release 的 `execution_connector.mode` 只取 `REMOTE_ADAPTER` 或 `PROTOCOL_PEER`，或在原生页面入口 release 取 `NONE`（DD-127），`PLATFORM_PORT_CLIENT`、`EMBEDDED_DRIVER` 与 `INTERNAL` 只属 `class=PLATFORM`（DD-58/64）；ApplicationBinding 的 `call_identity_mode` 不含 `INTERNAL`。业务能力服务只使用 `REMOTE_ADAPTER`，或仅为 MCP Tool 传输使用经 binding 配置的 `PROTOCOL_PEER`；`PROTOCOL_PEER` 的平台 Resource 引用登记依 DD-98 核实原生协议或可信运行投递证据，不为此强加 Adapter 创建接口；证据未闭合时该入口保持关闭。`SOURCE_BOUND_PROTOCOL` 前端交付的 launch 由该实现的 `REMOTE_ADAPTER` 生成 descriptor，不属于 `PROTOCOL_PEER`（DD-58/95）。一个能力组件内部为实现其契约而使用的协议（如内置参考实现中 Cells 与 ONLYOFFICE 之间的 WOPI）属于该组件内部集成，对平台仍是一个 ApplicationBinding，不构成两个服务之间的平台级连接（DD-90）。

业务能力实现可保持原 monolith/service，不需要为 Buzz 强拆前后端。Remote adapter 只在稳定 native API 上实现能力契约；原生后台继续独立存在，Buzz 用 `NATIVE_PAGE` 在 Web/Desktop 共同的右侧内容区以跨 origin iframe 承载完整原生页面，不要求重写或强拆；`HOST_NATIVE` 仅处理平台接入与通用资源视图，`REMOTE_MODULE` 是可选呈现方式。内置参考实现的 native API 证据见 `08`（SF-CEL-01/03、SF-WEK-01/03、SF-WRN-01、DD-58）。

### 5.2 版本化深接口

Adapter Protocol 只包含以下逻辑操作，传输编码由 release 的协议版本固定。出站操作由 Core/Worker 发起、adapter 应答：

```text
handshake(protocol range, component/release identity, capabilities)
validate_binding(binding ref/version, normalized config digest, secret ref versions)
resolve_native_scope(binding ref, platform resource ref, mode[CREATE|LOOKUP], ActionToken)  // 仅明确 REMOTE_ADAPTER 原生创建分支
execute(action key/version, normalized args, ActionToken)
observe(external execution ref, ActionToken)
cancel(external execution ref, ActionToken)
reconcile(binding or execution ref, ActionToken)
query_revision(native_object_ref, ActionToken)
search(query, limit, locale, readable resource refs, SearchToken)  // 仅 search_source=SUPPORTED 的 REMOTE_ADAPTER（DD-138）
extract_usage(native evidence ref)
map_native_status_error(native status/error)
```

入站操作由业务能力实现以其 binding 的 ServicePrincipal 发起、Core 应答，与 `09` ServicePrincipal 表的「业务能力实现 → Core PEP（入站 service 边）」和「服务读取边」两行一致：

```text
pep_check(binding ref, protocol session ref | action token ref, target ContentReference, requested operation)
request_native_execution_admission(binding ref, frozen action/external execution ref, native intent ref, current HUMAN identity)
request_native_task_execution_admission(binding ref, frozen action/external execution ref, retained native task ref)
report_rekey(binding ref, secret_key, new secret version, result[COMPLETED|FAILED])
request_read_grant(receiver binding ref, source resource ref, batch parameters)
```

- `resolve_native_scope` 的 `mode=CREATE` 在 binding 固定的 native scope 内按 platform resource ref 幂等创建或取回 native 对象，返回 native type/ref 或确定的 `REFUSED`；`mode=LOOKUP` 只查不建，返回 `FOUND`（native type/ref）或 `ABSENT_FENCED`——确认该 ref 没有 native 对象，并在同一原子步骤为该 ref 写入拒绝标记，此后该 ref 的 `CREATE` 一律返回 `REFUSED`。`ComponentTaskWorkflow(kind=RESOURCE_PROVISION)` 结果不明时只以同一 Resource ref 调 `LOOKUP` 对账，不以 `CREATE` 重放；一致性套件验证幂等、`REFUSED` 与 `ABSENT_FENCED` 之后的拒绝（DD-98）。
- 登记服务既有对象不是 `resolve_native_scope(CREATE)` 的别名，不要求原生 peer 实现 Adapter Protocol。Core 复用 `resource.create`/`RESOURCE_PROVISION` 核实冻结 binding/native scope、native type/ref 与来源证据，再完成原 SpiceDB 投影；证据只来自固定原生协议或可信运行投递事实，不新增假定存在的查询 API。记录及对账不保存正文、临时 URL 或凭据；未知只重核同一引用，不发 CREATE。必要归属证据不能闭合时，对应引用登记能力未闭合，不生成入口。原 CREATE/LOOKUP/ABSENT_FENCED 一致性向量只适用于明确原生创建；既有引用向量验证已有对象、重复绑定、证据不足、scope 不一致、撤权与 UNKNOWN 收敛（DD-98）。
- `query_revision` 按 `native_object_ref` 返回当前 revision，是声明 revision 查询能力的实现必须提供的操作；ProtocolSession `UNKNOWN` 对账与 EDIT admission 的 head 查证都只经它进行（DD-90）。
- `search` 是只读检索：只在请求列出的、当前 HUMAN 已经 fresh `read` 的 Resource 对应 native 对象内返回标题、摘要、类别与组件页面相对路径，不返回正文、ContentReference 或凭据，不建立 ActionExecution 或 ExternalExecution；请求、Search Token 与结果规则见 §4.8.4（DD-138(5)）。
- `pep_check` 是协议会话内每个读写入口的 fresh Check，继承父 operation，不新建 Action/Workflow/Quota；Core 不可达或超时一律拒绝。
- `request_native_execution_admission` 只为原生 writer 消费已经 dispatch 的同一 APPLICATION ActionExecution/ExternalExecution；它不是 `execute` 重试、Action 创建、observe 授权写或通用续签。Core 从持久事实核对原 HUMAN、Tenant/Workspace、target、action/version、参数摘要、审批消费、quota reservation 与原 AE/EE 冻结的 binding/release/generation，再核对该冻结版本的绑定 SERVICE 和当次独立 HUMAN 凭据；引用不全、终态、取消、安全撤权、停用、过期或该执行所需 projection 未对账均拒绝。合法升级保留原在途执行冻结的版本与代次，不改用当前 active generation，也不只因当前代次变化而拒绝；停用及安全撤销仍阻止新字节。返回的短期 ActionToken 只在当次 writer 请求内使用，audience 固定原 binding，不能持久化或延长原生意图的截止时间。原生服务在读取请求体前以原任务/存储事务唯一领取该意图下的写入位置，重复或并发请求只能观察同一原生事实，不因另取令牌而重复写入；Multipart 只继续该原生上传中尚未消费的步骤，不能换 upload ID、目标或重新开始。写入中 fresh 拒绝后停止后续写入，已有字节及 ACK 不明保持 UNKNOWN；不可变 native revision ACK 与完整用量证据经原 observe/extract_usage 才能终结 ExternalExecution。该接缝必须连同对应能力输入、writer、幂等栅栏及终态映射一起通过一致性验证，否则对应 release/binding 不激活（REQ-03/11、DD-09/11/87、`03` §6）。
- `request_native_task_execution_admission` 只供绑定 SERVICE 在原 `ComponentTaskWorkflow(kind=COMPONENT_ACTION)` 已派发的同一 HUMAN APPLICATION 动作内，授权原生持久任务尚未消费的步骤；不接受 HUMAN writer 请求替代、不创建 ActionExecution/ExternalExecution、不调用第二次 `execute`。请求以原 AE、EE、幂等键及已由原 observe 核实的 native type/id 定位；Core 从原持久事实核对 Tenant/Workspace、原 initiator 当前权限与暂停/撤权、审批消费、quota、target/action/参数、Workflow 仍运行且未取消、冻结 binding/release/generation 和投影，绑定 SERVICE 不能凭任意 native ref 创建或领用任务。合法升级沿原冻结代次继续，停用及安全撤销拒绝；缺引用、缺执行期限、终态或原任务领取/副作用结果不明时不以本接口重派。执行期限在首次 dispatch 前按受控执行配置冻结在原执行引用，原生任务同步保存并执行；后续请求不得延长。短期票据只在当次原任务执行上下文中使用，每个后续外部副作用仍 fresh 校验，不持久化票据。原生任务存储负责同任务及其原子步骤的一次领取，重复消息、进程恢复和 ACK 丢失仅观察已有领取与原 ACK；未证实尚未消费的步骤保持 UNKNOWN，不能靠再领票重做。该接口不改变 `request_native_execution_admission` 所要求的当次独立 HUMAN 身份，也不允许 observe/extract_usage 票据执行写入；一致性证据闭合前对应异步能力不激活（REQ-03/11、DD-09/11/48/87、`03` §6）。
- `report_rekey` 回报 `DATA_KEY` 轮换后的重加密结果；只有 `COMPLETED` 回报使平台记录结果并允许销毁旧版本，其他情形旧版本保留、binding 进入对账（DD-93）。
- `request_read_grant` 是服务读取边的申请入口：Core 以接收方 ServicePrincipal 为 SERVICE actor 做 Governed Action 准入，通过后为该批建立 operation 并返回短期 ActionToken（audience 为来源实现的契约端点，target 为来源 Resource），规则见 §8.2（DD-89）。来源方 PEP 即来源实现在平台运维域内的 adapter，其验签公钥经 OpenBao Agent 投递；`PROTOCOL_PEER` 实现不接收 ActionToken，不能作为来源方（DD-94）。

Handshake 成功只证明协议兼容，不表示 binding active。Binding 只在 service identity、config digest、SecretRef audience/version、native scope、隔离方式、capability 和全部 projection 对账后 active。

Core 在 dispatch 前完成准入。Core→adapter 的 ActionToken 由 adapter 运行体校验，验签公钥（JWKS）与 `secret_schema` 声明的凭据经 OpenBao Agent 投递到 adapter，不另设分发通道（DD-94）。ActionToken 固定 issuer/audience、Tenant/Workspace、actor、delegation、action/version、target、operation、parameter hash、ResultExposure 和短 expiry。Adapter 校验 token 后仍按 `03` 的 PEP 合同将请求收窄到 binding 已固定 native scope。Adapter 不接受 payload 自报 Tenant/Workspace、不自行扩大权限、不回退默认实例（DD-63）。

ResultExposure 由确切 ActionDefinition 决定：固定 `NONE` 且只返回平台 ID 与状态的管理动作，其 ActionToken 内容策略 ID 与版本按 `03` §6 成对为 `NONE`；协议操作名或管理父动作不构成该例外。实际业务内容访问与返回内容的子动作仍需其有效内容策略及 fresh 授权，不以 `NONE` token 执行业务读取，也不以自造 `CONSUME_ONLY` 策略填充管理调用。

真实副作用在 dispatch 前建立 ExternalExecution 和稳定 operation/idempotency key。超时且无 native query/dedupe 接缝时进入 `UNKNOWN`，不自动重发。Adapter 只映射源码存在的 progress/cancel/terminal；HTTP 200/202、queued 或 cancel accepted 都不等于业务完成。`observe` 的终态应答必须携带据以判定终态的原生状态原值，`native_status=NONE` 只允许于尚无原生事实的 `PENDING_DISPATCH`、`RUNNING` 与 `UNKNOWN`；缺失即终态证据不完整，Core 与 Worker 不受理（DD-124(5)）。

Kailo HUMAN 经平台发起、需要 native task 或 ExternalExecution 对账的 APPLICATION 能力契约动作，必须声明 `TEMPORAL` 并由原 `ComponentTaskWorkflow(kind=COMPONENT_ACTION)` 承接（`05` §2.7、`06` §5）；不能为省略真实 WorkflowRef 把带 native history 的执行伪装为 `SYNC`。确实同请求完成且无 native task、无需 ExternalExecution 对账的动作保留原 `SYNC` AE/audit 路径。两者均消费同一已批准的 ActionDefinition、原准入与 fresh PEP，不新增组件专名 Workflow、权限或注册表，也不把独立原生 UI 的内部 API 改作平台治理入口。

## 6. 两类 Binding 的生命周期

### 6.1 PlatformProviderBinding

```text
approved PLATFORM release
→ create/upgrade provider binding for exact known port
→ PENDING projection generation
→ validate connector/target registry/service identity/config/secret/readiness/governance
→ Port Router atomically selects ACTIVE generation for new calls
```

变更由 Platform Catalog Tenant 的 `ComponentTaskWorkflow(kind=COMPONENT_BINDING, binding_kind=PLATFORM_PROVIDER)` 承接。旧 generation 保留给已开始调用；新 generation 校验失败不切流。安全撤销导致 provider fail closed，不静默切换未批准实现。

### 6.2 ApplicationBinding

```text
approved APPLICATION release
→ Tenant/Workspace creates or upgrades exact binding
→ PENDING projection generation
→ validate adapter handshake/config/secret/native scope/isolation/governance/Web artifact
→ reconcile Resource/Action/Tool/Gateway/route/observability projections
→ atomically select ACTIVE generation
```

变更由业务 Tenant/Workspace 的 `ComponentTaskWorkflow(kind=COMPONENT_BINDING, binding_kind=APPLICATION)` 承接。同一 binding 升级到同一实现的新 release 时生成新 generation：已开始的 ActionExecution/Workflow/ExternalExecution 继续使用旧 generation；新 Action 只解析 active generation。Rollback 也创建新 generation，不改写旧 release 或历史执行。换成另一实现不走 generation 切换，而是 §2.4 的「新建 binding、旧 binding 转 `DISABLED` 只读保留」。切换 `model_call_mode` 是需要审批的 Governed Action，同样经本 Workflow 生成新 generation（DD-92）。

原生页面入口 release（ExecutionConnector `NONE`，DD-127）的 binding 由 Tenant admin 以同一 `application_binding.create` 建立：`capability_categories=[]`、`adapter_service_ref=NONE`、`secret_refs=[]`、`model_call_mode=NONE`、`retain_on_tenant_delete=false`，配置只含入口 `nativePageUrl`，组件读取成员目录时另含 `directoryClientId`（§4.7.4，Core 只用它核对目录令牌的 `azp`）；release 允许且 binding 选定 `model_call_mode=PLATFORM_LLM_ROUTE` 时配置另含 `modelGateway`，激活按 DD-128 增加 route 授权、OpenBao 写入、Gateway key 与以该 key 的模型发现核验，其余不变。同一 Workflow 中 PENDING generation 的校验由 Core 自身完成：release 仍 `APPROVED`、入口 origin 属于 release `native_page_origins[]` 与部署 `NATIVE_PAGE_ORIGINS` 的交集且不是平台 origin、Tenant（及 Workspace）`ACTIVE`；不读取 ApplicationAdapterDirectory，不调用 handshake/validate_binding，不写 OpenBao，不建立 IdP service client，不生成 Resource/Tool/route/类别投影；只有选定 `PLATFORM_LLM_ROUTE` 的入口 binding 按 DD-128 写 OpenBao 并生成模型计量主体。binding 自己的 SERVICE 主体照常生成但无任何凭据。校验通过即原子选中 `ACTIVE` generation；停用按 §6.3，没有原生对账。

### 6.3 Disable

两类 binding 的停用都使用 `ComponentTaskWorkflow(kind=COMPONENT_DISABLE, binding_kind=...)`。Core 先置 `DISABLING` 并停止新 discovery/action/call，再暂停该 binding 的 Kailo Schedule、撤平台授权/AgentGateway route/tool/Web projection、观察 Kailo 发起的在途 execution 并对账 usage/audit。不停止外部服务进程、不暂停组件自有工作流，不因平台 binding 停用而删除原生后台入口。Disable 不删除 Resource/Asset/native data；`DISABLED` binding 下的 Resource 保留只读，只可 discover 元数据，其 ContentReference 解析为不可用；该 binding ServicePrincipal 的全部 `reader` 关系随之撤销；保留或不明 ref 存在时不伪造已收敛。业务能力 binding 停用只影响它提供的契约键：对应 `APPLICATION` 工具 effective 变为 `NO_PROVIDER`（该类别无其他 active 实现）或 `DISABLED`，AgentInstallation、协作、记忆与 `PLATFORM_NATIVE` 工具不受影响（DD-92）。

## 7. 全局治理契约

每个经 Kailo 或调用其公共服务的用户、Agent、Schedule、callback 或 Workflow action 必须声明；外部服务独立入口的内部动作不自动纳入本表：

| 贯穿项 | Release 声明 | 运行时强制点 |
|---|---|---|
| Tenant | scope rule、binding isolation、native scope derivation | Core 从 session/parent action 构造；adapter 不接受自报 |
| Workspace | WorkspaceRule 与 binding scope | scope guard 先于 Resource permission；execution 固定 scope |
| Authorization | canonical permission、target、ResultExposure | SpiceDB fresh Check；Agent 另与 Delegation/ToolBinding 求交 |
| Approval | confirmation mode、ApprovalPolicy、owner rule | Temporal Approval 固定 exact action/parameter/owner/policy version，消费前重检 |
| Workflow | `SYNC/PROTOCOL/TEMPORAL`、kind、idempotency/UNKNOWN/cancel | Temporal 持有持久生命周期；native task 是 ExternalExecution |
| Capacity/Quota/Billing | capacity/quota mode、meter、strict upper bound | CapacityLease/QuotaReservation/OpenMeter；actual usage 只有一个 source |
| Operation Audit | intent/decision/dispatch/outcome/revoke/reconcile 与 redaction | 外部副作用前先持久 intent；结果沿同一 operation 追加 |
| Business Observability | correlation、terminal/progress/usage/cost source 和 redaction | operation→release/binding generation→native evidence→usage/cost 的受权联合视图 |

`NONE` 只能是明确策略值，缺失字段不等于 `NONE`。平台 provider 的内部 RPC 继承父 operation，不递归创建 Governed Action；任何用户可达的 provider 管理动作仍完整经过上表。

## 8. Resource 附加合同

### 8.1 IncrementalContract

每个 ResourceType 至少登记一份合同：

```text
NATIVE_INTERNAL / NATIVE
VERSIONED_PUBLICATION / VERSIONED_REPUBLISH
```

`NATIVE_INTERNAL` 表示新增、修改、删除与处理逻辑变更的增量、对账和就绪全部在该实现内部完成。实现必须经 Adapter Protocol 暴露：

- 跨调用稳定、同一 Resource 内唯一的 native object ref；
- 内容 revision，而非仅修改时间；
- 删除是否可观察，以及删除后的 native ref 状态；
- ready/failed/cancelled/unknown 的判定与 query/reconcile 接缝；
- 处理逻辑变更（如重新解析、重新索引）的触发方式与进度。

`VERSIONED_PUBLICATION` 表示以完整不可变版本发布替换，不对版本内部项做差异；业务能力实现的版本发布与下线收敛由通用 `ComponentTaskWorkflow(kind=CAPABILITY_VERSION_PUBLISH)` 承接，Workflow 只依能力契约与 binding 固定的版本 Resource/Asset 工作，不含产品专属步骤（DD-90）。

只提供 mtime、只 create 无 delete/readiness、或要求平台直写组件数据库、vector store、图数据库的类型不得登记为 active。平台与其他服务禁止直写任何业务能力实现的数据库；实现内部的派生索引由该实现自己维护。

平台不接管组件内部索引，不持有逐项增量状态，不为业务数据建立跨 Resource 的派生副本；平台不存在物化端口、物化 binding 或物化 Workflow kind（DD-89）。平台不持有的内容固定为：任何业务能力实现内部的增量状态、索引、队列或游标；两个业务能力服务之间的逐项映射、去重表或同步游标；任何业务能力服务的数据库凭据（DD-93）。平台自有的持久流仍各归原权威：Buzz event 消费游标与 AgentGateway log tail 游标是已有持久流的 `IngressCheckpoint`。

平台核心 ResourceType 的合同固定为：

| ResourceType | 合同 | 结论 |
|---|---|---|
| Buzz Community/Channel | `NATIVE_INTERNAL` | Relay event 是 native 权威；Core 以稳定 event ID+cursor 消费 |
| AgentGateway LLM Route | `VERSIONED_PUBLICATION` | ConfigResource version/reload 是 native 配置投影（SF-AGW-01） |
| AgentGateway request log | 观测流 checkpoint | logging database 中已成功持久化的稳定 log ID+tail cursor 供业务观测；不承担完整计费（SF-AGW-06/09） |

内置业务能力参考实现的合同见 `13` §3。

### 8.2 跨服务数据获取

服务读取边是 release 可声明的可选能力：release 以能力声明 `read_edge[SOURCE|RECEIVER|BOTH|NONE]` 声明本实现可作来源方、接收方、两者或都不作，未声明 `SOURCE` 的实现不接受读取令牌，未声明 `RECEIVER` 的实现不得调用 `request_read_grant`。没有这条边时，两个服务各自仍完整可用，只是彼此不取数；平台不因缺少读取边降级任一服务（DD-87/89）。一个业务能力服务需要另一服务的数据时只有两条路径（DD-89）：

1. **接收方自拉**：接收方在自己的管理面（独立访问或经 Component Host 打开）配置数据源连接器，指向来源方的一个 Resource。平台以既有机制授权：一个 Governed Action（按 ApprovalPolicy 可含来源 Resource owner 审批）为接收方 binding 的 ServicePrincipal 写入来源 Resource 的 `reader` 关系；授予要求发起者对来源 Resource 持有 `share`、对接收方 Resource 持有 `update`。接收方每批拉取经**服务读取边**完成，经来源方公开的能力契约读取。增量、状态、去重与删除收敛全在接收方内部，Core 不感知其状态。
2. **人或 Agent 显式读写**：人或 Agent 经两边各自暴露的 Tool 显式读取一侧、写入另一侧，每一步都是独立 Governed Action，各自授权、审批、计量与审计。

**服务读取边。** 接收方 binding 经 Adapter Protocol `request_read_grant` 向 Core 申请读取来源 Resource；Core 以接收方 ServicePrincipal 为 SERVICE actor 做 Governed Action 准入：scope guard 要求接收方 binding 与来源 Resource 同 Tenant，Workspace 级接收方还须与来源 home Workspace 一致或来源为 Tenant 级 Resource；对来源 Resource fresh `read` Check；Quota。通过后 Core 为该批建立 operation，签发短期 ActionToken（audience 为来源实现的契约端点，target 为来源 Resource，携带该批 operation）；来源实现的 PEP 按 `03` §6 的通用 ActionToken 规则校验并再做 fresh `read` Check。来源方 PEP 即来源实现在平台运维域内的 adapter 运行体，外部与 SaaS 实现也不例外；验签公钥与其凭据经 OpenBao Agent 投递到该 adapter；以 `PROTOCOL_PEER` 接入的实现不接收 ActionToken，不能作为服务读取边的来源方（§2.5、DD-94）。接收方不持有来源实现的 native 凭据；平台为接收方 binding 投递的 SecretRef 只是其自身服务凭据，用于认证 Adapter Protocol，不能直接访问来源。经平台签发令牌访问来源的契约端点不是服务间数据面直连（§5.1、DD-89）。

授予、撤销与每批读取都按八项贯穿执行：

| 能力 | 规则 |
|---|---|
| Tenant | 来源 Resource、接收方 binding 与其 ServicePrincipal 必须同 Tenant；跨 Tenant 数据只走 REQ-09 两段导出/导入 |
| Workspace | 授予按来源 Resource 的 home Workspace 做 scope/permission；每批读取按 `03` §2 的 SERVICE scope guard，执行 Workspace 取接收方 binding 的 Workspace（Tenant 级为 NONE）；授权不产生隐式跨 Workspace 共享 |
| Authorization | 授予要求发起者对来源 Resource 持有 `share`、对接收方 Resource 持有 `update`；每批读取在 Core 准入与来源 PEP 各做一次对接收方 ServicePrincipal 的 fresh `read` Check；Agent 发起授予时另与 Delegation/ToolBinding 求交 |
| Approval | 授予的 ApprovalPolicy 绑定来源 Resource、接收方 binding 与 parameter hash；发起者不是来源 Resource owner 时，来源 owner 必须批准；Approval 不能补 permission。每批读取不再审批 |
| Workflow | 授予与撤销是一次关系写入，结果不明按既有 ActionExecution/UNKNOWN 规则对账；每批读取是 `SYNC` 准入与令牌签发；接收方的拉取运行不是平台 Workflow |
| Capacity/Quota/Billing | 每批读取在准入时做 Quota；来源方按其 meter 对该批读取计量、接收方按其 meter 对导入处理计量，UsageEvent 都归属该批 operation；模型 usage 按 §8.3 |
| Operation Audit | 授予/撤销记录 actor、来源 Resource、接收方 binding、ServicePrincipal 与 Approval；每批读取记录 SERVICE actor、来源 Resource、ActionToken `jti` 与该批 operation，来源方的 native execution evidence 归属同一 operation |
| Business Observability | 平台视图展示授权关系状态、每批读取 operation 与双方各自暴露的 native 进度/错误；不展示逐项同步状态 |

**撤权收敛。** 撤销 `reader` 关系即收回读取权：Core 对后续 `request_read_grant` 拒绝，来源方 PEP 对已签发未过期令牌的后续读取 fresh 拒绝。接收方已取得数据的处置由接收方按其能力契约声明的删除语义负责；平台不代为删除接收方数据，也不宣称撤权使已导入内容消失。接收方 binding 停用时，平台撤其 ServicePrincipal 的全部 `reader` 关系；来源方 binding 停用时，接收方后续申请失败，接收方按自身规则保留或标记失效，不得把拉取失败解释为来源内容已删除。

暂停导入、撤销读取授权、停用 binding 与删除派生内容是四个不同动作，UI 与 Agent tool 不得合并按钮或复用 action key。暂停导入属于接收方管理面上的本组件动作，不是平台 Workflow 状态。

平台只治理授权与动作，不经手数据、不持有同步状态、不以 Schedule 或 Workflow 编排跨服务同步。

### 8.3 LLMGatewayContract

Kailo 接入范围内的模型调用模式由 release 声明允许的集合 `allowed_model_call_modes[]`，binding 在其中选定一种 `model_call_mode`；切换模式是需要审批的 Governed Action。`model_call_mode≠NONE` 的 binding，其 release 对所启用类别的 meter 能力必须为 `SUPPORTED`（DD-92）：

| `model_call_mode` | 合同 | 计量 |
|---|---|---|
| `PLATFORM_LLM_ROUTE` | 服务的模型 base URL 经 binding 配置指向 AgentGateway `llm_route`；协议必须属于 AgentGateway 已实现的 Chat/Responses/Embeddings/Messages/Gemini/Rerank，provider credential 只存在 Gateway SecretRef（SF-AGW-04/05） | Actual token/cost 只取 SS-AGW-USAGE 闭合后的 durable usage 并写 OpenMeter；经网关路由的调用，组件自报 token 不形成计费事件，也不形成第二份账 |
| `SELF_MANAGED_MODEL` | 服务自管模型与凭据，平台不向服务数据写入模型配置 | 服务经 Adapter Protocol `extract_usage` 上报的 usage 是 actual usage source，Core 按稳定 source identity 去重写入 OpenMeter 并标注来源模式；平台照常执行 Quota 与审计 |
| `NONE` | 当前接入能力不调用模型，不代表独立服务内部没有模型 | 无本接入模型 usage |

逐调用关联以标准 W3C `traceparent` 与 operation 头为可选增强：存在时把模型调用归因到平台 operation；缺失时按 gateway identity（`PLATFORM_LLM_ROUTE`）或 Adapter Protocol 上报身份（`SELF_MANAGED_MODEL`）解析出的 binding scope 入账，只降低到 operation 的归因精度，不阻断 binding `ACTIVE`，也不免于计量（DD-20/92）。平台自有 Agent 的模型调用始终经 AgentGateway，不受本节模式选择影响。原生页面入口 binding 只能选 `PLATFORM_LLM_ROUTE` 或 `NONE`，没有 Kailo operation 可关联，服务自带 `traceparent` 不参与归因，一律按 binding scope 入账；其 key 投影、投递、轮换与吊销按 DD-128。

业务能力 binding 的模型 usage（两种非 `NONE` 模式）只计入随 Core 固定、由部署引导幂等登记的平台 meter `component_model_tokens`，binding 的模型 meter 引用只能是它；它计入 Tenant 额度项 `component_tokens`，由 ExtAuthz 逐调用 CHECK（2026-10-30 按 DD-165 修订）。组件的其他业务用量经 §4.8.9 上报入账，meter 同样随 Core 固定而不由 manifest 声明，APPLICATION release 的 ActionDefinition 仍一律 `meters=[]`、`quota_policy=NONE`（DD-123/124(6)/163）。

### 8.4 Transfer 与 Tenant delete

`transfer_formats[]` 必须同时证明 export、import/create、format/version、digest、terminal 和错误语义；缺任一端则不注册跨 Tenant Action。组件停用不等于删除 native data。

Tenant 销毁以平台自有事实为前提（DD-91）。平台核心自有 ResourceType（Agent、Skill、Tool、`llm_route` 等）的删除由 `ComponentTaskWorkflow(kind=TENANT_LIFECYCLE)` 按平台核心销毁链执行，不适用保留；Tenant delete Action 在注册时已存在的每个平台事实类别都有经验证的销毁处理器后注册，之后新增的平台核心 ResourceType 或平台存储面必须与其处理器同一构建登记，snapshot 中出现没有处理器的类别时准入拒绝（DD-99）；业务能力实现的删除缺口不阻断注册。每个 ApplicationBinding 的 native 删除是 Tenant 删除中独立的子流程（`03` TenantDeleteSubprocess），由能力契约的 Tenant 删除能力声明决定：

- 声明支持删除的实现必须提供稳定 native ref、幂等 delete、terminal query 和 retained-error 语义，登记 `tenant_delete_action_key`；该子流程失败或结果不明时按 fail closed 持续对账，其他子流程照常推进；
- 不具备的实现在准入时声明 `retain_on_tenant_delete`：Tenant 删除时撤该 binding、撤凭据、保留审计，并把该 binding 的 native 数据登记为待人工处置项，子流程进入 `RETAINED_DECLARED`，不阻断平台 Tenant 状态机；
- 已声明删除能力的子流程停在 `UNKNOWN` 时，只有该业务 Tenant 的 admin 经 owner 审批的 Governed Action 可把它处置为 `RETAINED_BY_DECISION`；处置不改写 binding 或 release 的声明字段，处置与理由进入审计。

Tenant 只在全部子流程到达终态后进入 `DELETED`。任何业务能力实现的删除缺口只影响该实现自身的删除子流程，不阻断平台 Tenant 生命周期。

## 8A. 第三方接入面

`REQ-11` 保证组件可在运行时注册，`REQ-22` 保证第三方能在开发期独立做出组件。后者的交付物固定为六件，与 Component Host 同 Stage 交付（`DD-76`）：

| 接入面 | 内容 | 来源 |
|---|---|---|
| Component SDK | TypeScript 包：Host API 类型与调用封装、Adapter Protocol 客户端/服务端骨架、错误六分类与 reason code 常量、slot descriptor 构造 | 由 `contracts/` 生成或派生，不手写 |
| manifest schema 与校验器 | 可本地运行的 manifest 校验，错误信息指向具体字段与允许取值 | 本文 §3 的 manifest 定义 |
| 脚手架 | 生成含前端 module、后端 adapter、manifest 与一致性测试配置的最小可运行组件 | — |
| 本地开发环境 | 不接真实平台即可加载 module、应答 Adapter Protocol、模拟 binding 与 presentation context | — |
| 一致性测试套件 | 在 Adapter Protocol 线协议层验证 handshake、终态语义、幂等、取消、错误映射与 redaction；按 `implements[]` 叠加对应能力契约的契约键语义、permission 映射与 ContentReference 往返 | 本文 §2.4、§5 与 `03-领域模型与权限模型.md` 的状态约束 |

约束：

- SDK 是 `contracts/` 的消费者，不是第二权威；两者冲突以 `contracts/` 为准，`contracts/` 与本文冲突以本文为准。
- 前端 remote module 只能是 TypeScript，由承载端运行时决定；后端 adapter 的契约是线协议，因此首方不承诺多语言 SDK，任意语言实现以一致性套件自证。
- 接入面随 Host API 与 Adapter Protocol 的 range 一起版本化。新增扩展槽或 Host API 不兼容变更时，接入面必须同步发布，否则第三方拿到的类型与真实宿主不一致。
- 一致性套件通过是登记 release 的必要条件，不是充分条件；平台管理员批准、digest 固定、隔离与数据位置声明核对和全局治理校验仍然独立执行。外部实现（含闭源与 SaaS）以该套件作为源码证据的替代，按 §2.5 准入。
- 接入面不暴露平台内部实体、SpiceDB schema、Core 数据库结构或任何 service credential。
- `NATIVE_MANAGED` 接收方同步能力的一致性验证沿原接收方发起方向执行，不转换成普通 `execute`。套件只驱动一次原生批次并观察该批次；原生调度、逐项状态、解析及删除收敛仍归组件，既有一致性 Workflow 只记录验证步骤，不成为业务同步 Workflow。
- 此方向的隔离环境运行与生产相同的 Core `request_read_grant`、receiver 准入、PEP 与 `read_receipt` 消费者。模拟身份、binding、资源及授权事实只在独立验证部署内引导，使用独立数据库和凭据；不得连接生产库、修改生产 `ACTIVE` 条件、给生产入口增加可选绕过开关，或把预填的 SOURCE/receiver 执行引用当成真实准入。模拟引导属于平台维护的验证环境，不向第三方暴露内部表结构或凭据。该证据必须标注隔离模拟范围，不能替代生产绑定的审批、激活与真实业务验收。
- 原一致性 plan 固定接收方方向、输入引用及幂等键；首次原生发起之前，原 Temporal history 必须已有对应 dispatch 事实。组件 adapter 将该键关联到同一个原生批次的持久事实，丢失 ACK 后只对账同一批次，不重发非幂等启动。任务或回执消失、关联不完整、超过原生保留期限时为 `UNKNOWN`，不得重新启动来补造通过证据。
- step evidence 只保存实际生成的批次引用、SOURCE 与 receiver 执行/operation 引用、双方回执及结果摘要，不保存正文、token 或逐项同步状态。观察须核对同一批次、绑定代次和原回执；已受理、HTTP 成功或管理员填入结果均不构成终态。通用 Core/Worker 不含产品名或原生路由分支，原生启动和观察差异留在对应 adapter/二开实现；不得引入任意 HTTP 脚本执行器或第二执行账本。
- 原生 MCP peer（`PROTOCOL_PEER`）的隔离套件只投递 environment，其 `initializeResultJson`、`listResultJson` 按 DD-136(3) 经与生产同一 Gateway 构建实际取得、两次会话一致后登记，不手填；交付目录 `protocolPeers` 与该 environment 是随源码版本化的部署声明，由发布入口渲染进以 artifactDigest 寻址的候选集合，Core 与 Worker 每次使用时按 release 的 adapter digest 选取（DD-136(2)）。
- `REMOTE_ADAPTER` 候选与 `PROTOCOL_PEER` 候选并存；它由组件部署入口在隔离运行全部阶段成功后写入，运行中的原生凭据与原生 onboarding 由运行器经隔离实例的原生 API 完成，凭据只在该次运行的隔离 OpenBao 或 0600 文件中，不需要人在阶段之间介入；登记窗口结束后由同一入口撤下候选并拆除隔离环境（DD-136(5)）。
- `PROTOCOL_PEER` 套件步骤是同步 MCP 调用，没有原生任务、去重键或结果查询。Core 在发出调用前为该步骤写 `DISPATCH`，收到应答并按冻结向量核对后在同一 operation 写 `OUTCOME`（`14` §4）；`DISPATCH` 已写而 `OUTCOME` 缺失，或 `OUTCOME` 已写而观察未回到原 Workflow，该步骤结果不明，不重放。原 Workflow 对账该步骤时，Core 为它追加一条 `RECONCILIATION`（`NOT_DISPATCHED`、`DISPATCH_RESULT_UNKNOWN` 或 `OBSERVATION_UNAVAILABLE`）并确定答复套件无法认证本次登记，原 `component_release.register` 以 `FAILED` 终止且不写 release；需要时由 Catalog 管理员重新提交 `component_release.register`（新 ActionExecution、新 Workflow、新一轮套件），不续用、不改写原尝试（DD-124、DD-136，2026-10-23 生产验收裁决）。
- 向量值按 DD-124(1)(2) 代入：fixture 只提供 `PRECONDITION` 取值，且只能是候选实现原生入口实际返回的标识；`CAPTURE` 只取本次运行的线上应答或接收方向隔离 Core 的准入；占位与绑定由已登记向量固定，运行器不接受额外映射，也不以 fixture 改写期望。
- 接收方向 case 的隔离部署按 DD-124(4)：平台运维逐次建立，Core/Worker 与生产同一构建（PlatformBuildInfo），来源方为生产 Catalog 中已 `APPROVED`、声明 `read_edge` 为 `SOURCE` 或 `BOTH` 的来源类别 release；授予经真实 `resource.grant_read`，接收方动作由隔离 Core 以真实 APPLICATION ActionExecution 准入与派发，`request_read_grant` 锚定该执行。生产 Core 只从原 `COMPONENT_RELEASE` plan 的 `receiver_start`/`receiver_observe` 观察受理证据：plan identity digest 固定隔离 Core 构建与来源 release digest，观察中的执行与 operation 标识必须由隔离 Core 本次生成、未出现在 plan 或 fixture 中，并与双方 `read_receipt` 一致；带外报告或管理员填写结果不受理。
- 本地开发环境的模拟 PEP 应答 `pep_check`，并按 DD-124(7) 应答套件自身 FORWARD 探针的原生任务执行准入：对候选 release 声明 `nativeTaskExecutionTimeoutSeconds` 的动作，首次准许的 `execute` `pep_check` 按该时刻加声明秒数冻结该探针的 `nativeTaskDeadline`；准入在见到该探针的 `pep_check` 前为 `PENDING_REFERENCE`，之后只原样交回生产 Core 为该探针签名的未过期 ActionToken、其规范化参数、不晚于期限的该 token 到期时间与冻结期限。模拟 PEP 不持有私钥、不签名、不延长 token 或期限、不创建或预填执行引用，引用、幂等键、原生类型或期限不符即拒绝；它不应答 `request_read_grant`、`read_receipt` 或协议会话回调。
- 示例组件以 `implements=[]` 登记，是唯一允许带 Resource/Action/Tool 的该形态 Application release（DD-127 的原生页面入口 release 不含任何定义，不受本条约束）：它不是业务能力服务，不获得契约键；其 ResourceType `type_key` 固定为 `component.<component_type_key>.<kind>`，ActionDefinition 与 ToolDefinition 的 `action_key` 固定为 `component.<component_type_key>.<verb>`、`capability_contract_key=NONE`，归类为组件自有动作（既非平台核心动作也非能力契约动作，`capacity_policy=NATIVE`，其余策略逐项声明），`component.` 前缀保留、能力类别登记不得使用（DD-102）；其 binding 配置 `refuse_create_type_keys[]`（只用于验证部署，进入 `config_digest`）列入的 `type_key` 在 `resolve_native_scope(mode=CREATE)` 时确定返回 `REFUSED`，作为 DD-98 确定拒绝分支的注入点；其 Tool 不能被 AgentVersion 作为能力需求引用，不作服务读取边任一方（`read_edge=NONE`）；零业务能力 binding 部署与生产 Catalog 不登记其 release（DD-101）。

## 8B. 用户自助连接器与平台认证通道

第三方 MCP 服务器进入 Kailo 有两条互不替代的通道（DD-149）：

| 通道 | 谁来做 | 信任等级 | 必经 | 产物 |
|---|---|---|---|---|
| 平台认证（DD-134(5)、DD-136） | 平台管理员与运维 | `APPLICATION`（`PROTOCOL_PEER`） | 交付目录与一致性环境、能力契约、一致性套件、Catalog 双人审批、ApplicationBinding | 契约键工具，可作为能力需求，按 release 治理 |
| 用户自助连接器（DD-149） | Tenant 管理员与按策略允许的成员 | `USER_REGISTERED_EXTERNAL` | 出站校验、探测、逐工具定级与调用策略确认 | `mcp.connection` 及其 ToolDefinition，只能按 Tool Resource 选用 |

约束：

- 自助通道不登记、不修改任何能力契约、ComponentRelease、ApplicationBinding、交付目录 `protocolPeers` 条目或一致性环境；连接器不能原地转为 `PROTOCOL_PEER`，平台认证仍从 DD-134(5) 向导开始，认证后的工具以 `APPLICATION` 另行出现，两者并存时各自独立治理。
- 自助连接器的端点不属于平台运维域，AgentGateway 不直连它：Gateway 的 MCP target 是 Core 私有服务网络上的外部 MCP 中继，出站校验、凭据注入、OAuth 刷新与结果标注都在中继完成（DD-149(5)(6)(9)）。§2.5 中“MCP target 只指向平台运维域内运行体”的要求因此对本通道依然成立。
- 自助连接器不实现 Adapter Protocol、不接收 ActionToken、不承载 ProtocolSession、不作服务读取边任一方，不能贡献 Kailo 的 Resource、搜索来源、通知或管理面（`07` §4.8 的贡献只经认证通道）。

## 9. 无需重发 Core/承载端的精确边界

| 变化 | Core/承载端重发 | 原因 |
|---|---|---|
| 新增/升级兼容 Application release | 不需要 | 使用已有 manifest、Adapter Protocol、Resource/Action/Tool 和 slot |
| release 引入部署级许可集合尚未包含的 editor origin | Web 重启静态服务（不重建镜像）；Desktop 的不重发合同仅在 GAP-DSK-EDITOR-01 闭合后成立 | Web CSP 的 `frame-src`/`form-action` 只为部署级许可集合放宽（DD-95、SF-WEB-06）；Desktop 主窗口 CSP 不变，编辑器在独立 editor 窗口中按 BFF 运行时下发的许可集合校验导航（DD-104、SS-DSK-EDITOR-WINDOW）。Desktop 在线编辑当前不注册（`BLOCKED: GAP-DSK-EDITOR-01`）；某端有效集合未包含该 origin 时，编辑入口显示确定状态 |
| 启用/停用/回滚 ApplicationBinding | 不需要 | 只切换运行时 projection generation |
| 为已有 platform port 更换兼容远程 provider | 不需要 | Port Router 只切换 PlatformProviderBinding generation；指同一端口已登记产品的实例、版本或配置，平台核心组件产品不可替换（DD-64/87） |
| 新增或升级 embedded/internal provider 代码（仅平台自身） | 需要 Core/Worker | 可执行代码与主体构建绑定，manifest 只能引用已有 registry key |
| 同一能力类别内切换实现 | 不需要 | 契约键不变；新建 ApplicationBinding、旧 binding 转 `DISABLED` 只读保留，ToolBinding 按契约键重绑（§2.4） |
| 只使用固定 permission 与通用 Resource/Action/Tool 语义的新能力类别或新契约版本 | 不需要 | 平台管理员经受审批的 Governed Action 在 Catalog 登记，schema 与测试向量以 digest 固定（DD-102） |
| 需要新 ProtocolSession kind、Workflow kind、能力声明、前端交付模式或 permission 的能力类别 | 需要 Core | 改变平台能力语义（DD-102） |
| 一致性向量格式版本（如 DD-124 的 `V2`） | 需要 Core | 通用一致性套件运行器的代入与比对语义改变（DD-102(4)、DD-124）；以已支持格式登记的新契约版本不需要 |
| 新 canonical permission、SpiceDB object type、Workflow 语义或 platform port | 需要 Core | 改变 Core 权威契约 |
| 新 extension slot；两端共用部分的 Host API 不兼容变更 | 需要 Buzz Web 与 Buzz Desktop | 宿主需理解新界面语义，两端契约必须同版本；两端是两个代码库，各自按 SS-WEB-COMPONENT-HOST、SS-DSK-COMPONENT-HOST 发布 |
| 只属于 remote module 的 Host API 变更（module 加载、`subscribePresentation`、namespaced i18n 注册等） | 只需要 Buzz Web | Desktop 不执行 `REMOTE_MODULE`（SF-DSK-03），不消费这部分 Host API |
| Adapter Protocol 不兼容变更 | 需要 Core/adapter | Dispatcher 与 adapter 协议契约改变 |

运行时注册必须同时满足：manifest schema 可解析；只使用已有 port/permission/Workflow kind/slot 与已有能力契约版本；Host API 或 Adapter Protocol range 相交；按 `admission_path` 取证的来源标识（DD-94(1)）、artifact digest、全局治理、业务可观测性、主题+i18n 和隔离合同全部通过；binding 完成 projection reconcile。任一项不成立都 fail closed，manifest 不得绕过边界。

## 10. `.references` 差异与 Release 演进

`.references/UPDATE_TASKS.json` 只告知 upstream diff，只作用于内置参考实现与平台核心。差异命中 release 引用的 SOURCE_FACT/SOURCE_SEAM 时，重验 native scope、API、状态、增量、LLM、治理和前端合同，通过后形成新 immutable release。旧 binding 继续 pin 旧 release；源码新增 endpoint、UI、Resource、Tool 或 meter 不自动进入 manifest，不自动扩大 relationship、Delegation、route 或 quota。新 release 只在 Catalog 批准、binding 变更和新 generation 对账后对新调用可见。外部实现的新 artifact version 同样形成新 immutable release，按 §2.5 重跑一致性测试套件并经平台管理员批准。
