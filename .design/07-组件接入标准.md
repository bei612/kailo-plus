# 组件接入标准

本文件是平台级组件、应用级组件、Component Package、Component Host 和 Component Adapter Protocol 的设计权威。Component Host 由 Buzz Web 与 Buzz Desktop 两端承载同一份契约，Buzz Mobile 不是组件宿主（REQ-11/21、DD-74）。组件保留自身数据面，但不取得 Kailo 的 Tenant、Workspace、owner、授权、审批、Workflow、Quota/Billing 或 Audit 权威。

## 1. Buzz 的确定起点

承载端当前没有运行时组件系统：routeTree、router、导航、`WorkspaceTool` 和内容分支均是构建期静态源码，i18n catalog 也是静态的（SF-WEB-02、SS-WEB-COMPONENT-HOST）。因此运行时注册不是 Buzz 上游现成能力，而是一次性 Buzz 二开后形成的固定产品边界。

Mattermost 只证明四个可复用机制：manifest、active manifest 快照、同源 script registration、版本 reconcile/unload（SF-MAT-01/03）；其事件路径把 payload 当完整状态，是 §4.2 明确不采用的反例（SF-MAT-06）。不复用其全局 enable、完整 Redux store、宽 PluginAPI 或本机 executable plugin：这些边界分别不满足 Tenant/Workspace 绑定、最小权限和独立服务交付（SF-MAT-02/04/05）。

一次性二开后的稳定结构为：

```text
Component Host（Buzz Web + Buzz Desktop）
        ↕ authorized runtime projection
Platform Core Catalog
        ├─ Platform Port Router → PlatformProviderBinding → platform service
        └─ Application Adapter Dispatcher → ApplicationBinding → adapter → native app
```

兼容发布在后端为独立远程服务、无后端或只引用当前主体已编译 key 时，可在运行时注册、升级、回滚和停用，无需重发 Core 或任一承载端。这不等于组件零交付：组件后端服务仍独立部署，Web artifact 仍需交付、校验和批准；新 embedded/internal 代码仍须重发对应主体（DD-59/64）。

## 2. 两类组件与两种绑定

| 分类 | 作用 | 绑定 | 当前对应 |
|---|---|---|---|
| Platform Component | 实现 Core 已知的平台端口 | `PlatformProviderBinding` | AgentGateway（`IDENTITY_EDGE` 与 `AI_GATEWAY` 两个 Definition）、SpiceDB（`AUTHORIZATION`）、Temporal（`APPROVAL_WORKFLOW`）、OpenMeter（`METERING_BILLING`）、OpenBao（`SECRET_STORE`）、CocoIndex（`MATERIALIZATION`）、Buzz Relay（`COLLABORATION_RELAY`） |
| Application Component | 提供用户可见的 Resource、Action、Tool 和 Web surface | `ApplicationBinding` | Cells、WeKnora、Wren、ONLYOFFICE |

### 2.1 Platform Component

Platform release 只能实现 Core 已编译的 `platform_port_key`。`PlatformProviderBinding` 属于 Platform Catalog scope，固定 port、release、provider target、config/secret reference 和 active generation。Provider target 只能是独立远程服务、当前主体已编译 driver key 或 Core internal key。它不属于业务 Tenant/Workspace，不挂到 Resource/Asset，不拥有业务数据。

每个 port 同时只选一个 active provider generation。新调用解析 active generation；已开始的 ActionExecution、Workflow 和 ExternalExecution 固定旧 generation 到终态。同一 port 下的兼容远程 provider 可运行时切换。Embedded/internal binding 只能选当前 Core/Worker registry 已有代码；新 driver 或 driver 代码升级必须重发 Core/Worker（SF-CIX-01/04、DD-64）。新 platform port、新 canonical permission 或新 Workflow 语义也必须改变 Core 契约。

### 2.2 Application Component

Application release 在已有 Resource/Action/Tool 和宿主扩展槽内登记业务能力。`ApplicationBinding` 属于业务 Tenant，可进一步限定 Workspace，固定 release、adapter service、native instance/scope、isolation mode、config/secret reference 和 active generation。应用 Resource 只能指向同 Tenant 的 active ApplicationBinding。

上游应用不必原生具有 Kailo Tenant/Workspace。Adapter 必须根据固定 binding 把平台 scope 解析为源码已证明的 native tenant、namespace、resource filter、dedicated instance 或 resource instance。解析失败必须拒绝，不得回退到默认实例。

### 2.3 共享对象与不可混合的对象

```text
ComponentDefinition       稳定组件类型（PLATFORM | APPLICATION）
  └─ ComponentRelease    不可变契约和 artifact 快照
       └─ ComponentPackage  manifest 与 Web artifact 交付包

PlatformProviderBinding  只引用 PLATFORM release
ApplicationBinding       只引用 APPLICATION release
ComponentRuntimeProjection(binding kind + id + release + generation)
```

`ComponentBinding` 只是文档中对两种 binding 的总称，不是一张混合两种 scope 的业务表。

## 3. Component Package 与不可变 Release

Component Package 包含：

```text
manifest
manifest digest
package digest
WebArtifactSet[path, media_type, digest][]
backend_delivery = EXTERNAL_SERVICE | BUILD_BOUND | NONE
```

Package 不包含 Core 要启动的本机 executable，也不携带 credential、native access token 或临时 URL。`EXTERNAL_SERVICE` 只表示该 release 要求独立服务，服务地址属于 binding；`BUILD_BOUND` 表示可执行代码已与主体构建绑定，package 只能引用当前 registry 已有 key（SF-MAT-05、DD-58/64）。

`WebArtifactSet` 的 canonical 清单整体计算 `web_artifact_set_digest`。Catalog 把每个文件固定服务于 `/component-artifacts/<release_id>/<sha256>/<path>`；entry 的静态相对 import 必须解析在同一 release 根内，绝对外域、父目录越界或未列入 artifact set 的 import 一律拒绝登记。该路径位于 Buzz Web Service Worker 的 `/app/` scope 外；snapshot endpoint 固定 `Cache-Control: no-store`。Buzz Web Caddy 只提供静态 `/app/*`，单一公开 origin 由 AgentGateway 路径前缀路由组合：`/app/*` 到 Buzz Web 静态站、`/api/*` 到 BFF、`/component-artifacts/*` 到 Core artifact handler（SF-WEB-07/08、DD-60）。

Release manifest 必须完整声明：

```text
identity
  component_type_key / release_id / semantic version
  source_project / exact source_commit / manifest_schema_version

compatibility
  platform_port_key | NONE
  host_api_range | NONE
  adapter_protocol_range | NONE

delivery
  FrontendDelivery
  ExecutionConnector
  ComponentPackage digest + WebArtifactSet

domain
  ResourceTypeDefinition[] / ActionDefinition[] / ToolDefinition[]
  target_resource_type_keys[] for capability components

governance
  isolation / call identity
  Approval / Workflow / Capacity / Quota / Meter / Audit contracts
  BusinessObservabilityContract
  IncrementalContract / LLMGatewayContract
  native status / error / cancel / idempotency / reconcile mapping
  FrontendPresentationContract
```

Release 一经 `APPROVED` 不原地修改。source commit、schema、artifact bytes/digest、Resource/Action/Tool、meter、redaction 或兼容范围改变都生成新 release。不能由 `02` 的 SOURCE_FACT/SOURCE_SEAM 和 adapter 契约证明的能力，不进入 release。

## 4. Component Host

### 4.1 固定宿主边界

Component Host 对承载端的一次性变更边界已由 SS-WEB-COMPONENT-HOST 定位（该接缝在 buzz-web 上取证，Buzz Desktop 因与 Web 共用同一 TypeScript 主体而适用同一改造面，SF-MOB-02）：

- 在静态 routeTree 中只增加一个 `/apps/$componentKey/$` catch-all route。
- 从 `BuzzWebApp.Workspace` 提炼 index 与 app route 共用的 `WorkspaceShell`。
- 用 surface registry 取代封闭 `WorkspaceTool` union 和硬编码内容分支。
- 导航、路由子路径、图标标识、文案 key 和排序由宿主根据 projection descriptor 渲染，不由 module 注入任意 router 或 DOM。
- 宿主保留登录、协作、审批、任务、治理、主题和 i18n 控制权。

一期扩展槽只有：

| Extension slot | 作用 | 宿主准入 |
|---|---|---|
| `MANAGEMENT_PAGE` | Platform/Tenant/Workspace 管理页及受控子路径 | descriptor scope + `discover/manage/audit` |
| `RESOURCE_VIEW` | Resource/Asset 详情、查询和动作 | Resource/Asset permission + ResultExposure |
| `CHAT_ATTACHMENT_ACTION` | 频道内的 Resource/FileReference 打开与动作 | Workspace scope + target permission |

新 slot 是 Host API 变更，不能通过 manifest 动态创建，且两个承载端必须同时实现。

### 4.2 运行时快照、通知与 reconcile

BFF 只返回当前 PlatformSession、Tenant、Workspace 和 Principal 可发现的完整 `ComponentRuntimeProjectionSnapshot`：

```text
snapshot_generation
scope_digest
projections[
  binding_kind / binding_id / release_id / generation
  component_type_key / authorized surface descriptors
  served_entry_path / artifact digest / host_api_range
]
```

BFF session stream 只通知 `snapshot_generation` 变化，Browser 立即重取完整快照并做 set reconciliation。新增 projection 直接 load；版本变更时，新导航解析新 generation，已挂载旧 surface 保留到卸载或用户确认刷新，不能在存在未保存输入时强制 dispose；projection 消失则停止新导航并请求已打开 surface 安全关闭。断线重连、页面恢复可见或 generation 不连续时也重取完整快照。事件只是失效通知，不是授权或组件状态权威（DD-61）。Mattermost 在事件路径上把 payload 当完整状态直接 load/remove、只在重连时全量 reconcile（SF-MAT-06），是本设计明确不采用的反例。

### 4.3 前端 module 加载协议

```text
Host 按(type, release_id, generation, entry_digest)登记 pending load
→ 校验 served_entry_path 为当前 release digest 的同源内容寻址路径
→ 在现有 script-src 'self' 下注入 module script
→ module 求值期同步调用 register(descriptor)
→ Host 暂存 descriptor；script load 事件后按 pending load 全字段匹配并接受
→ module mount(host-owned root, narrow Host API)
→ snapshot 移除/变更时 dispose + unregister
```

pending load 只在 Host 内部存在，绑定 Browser session、projection、注入元素与过期时间；静态 module artifact 不携带会话 ticket。无 pending、重复 register、load 失败、字段不一致或 Host API 不兼容均拒绝。`register` 在 module 求值期只暂存 descriptor，必须等对应注入元素的 load 事件发生后才 commit，避免把无关脚本的全局调用接受为该 projection。

Host 以 try/catch 包住 `mount()` 与 `dispose()`，并监听 `window.error`/`unhandledrejection`；当 `ErrorEvent.filename` 或可解析 stack URL 命中该 generation 的 artifact 根前缀时，尽力 dispose，将 Host 侧 generation 置 `ERROR`，并在槽位显示本地化 fallback。React error boundary 不作为 remote module 隔离承诺；事件 handler、timer 与 promise 错误也走上述全局归因。该错误只改变浏览器 Host generation，不改 ApplicationBinding、native task 或后端 projection 状态。

`dispose()` 的强制合同是：清空 Host 分配的 DOM root，移除 module 自有 style、全局 listener 与 timer，注销其 i18n namespace；CSS selector 必须以 Host 注入的 `data-kailo-component=<type>` 与 `data-kailo-generation=<generation>` 双属性作用域化。ES module 代码本身不会从同一 window 卸载，因此旧 generation 不得再次 mount；无法履行 dispose 的 release 在 Catalog 登记时拒绝。

`source_entry_url` 只供 Catalog 登记流程取件。批准前按密码学 digest 固定 bytes，Browser 只请求同源 immutable `served_entry_path`，不请求外域 script，不放宽承载端当前 `script-src 'self'`（SF-WEB-06、SF-MAT-01/03、DD-60）。

Remote module 是平台管理员批准的同窗口信任代码，不是安全沙箱。Tenant 管理员只能启用已批准 release，不能上传或替换 JavaScript。

### 4.4 窄 Host API

Host API 只提供：

- 当前受限 scope 和 FrontendPresentationContext 读取；
- BFF Resource query；
- action preview 与 semantic command；
- Task/Approval/operation 状态订阅；
- 受权导航、`subscribePresentation(cb)` 与 namespaced `hostI18n.t(namespace,key)` 注册。

Module 不获得完整宿主 store、Relay signer、ActionToken signing key、native credential 或 SpiceDB/Temporal/OpenMeter/AgentGateway 管理凭据。即使 module 自行发起同源 BFF 请求，BFF 仍对每个 query/action 重做 session、scope、SpiceDB、Approval、Quota 和 Audit 准入；前端代码不是授权边界。

### 4.5 主题与 i18n

- `HOST_NATIVE` 直接使用 Buzz CSS variables、`MessageKey/t/getLocale`。
- `REMOTE_MODULE` 通过 `subscribePresentation(cb)` 持续接收 resolved `LIGHT/DARK` 与 `EN/ZH_CN`，使用 Buzz tokens；不得只在 mount 时读取一次。Catalog 登记时校验 namespaced `en` 与 `zh-CN` catalog 的 key 集完全一致且覆盖 manifest 声明的全部 key，不一致即拒绝 release；remote key 不进入 Buzz 封闭的 `MessageKey` 类型或本地 `check-i18n` 扫描面（SF-WEB-03/08、SS-WEB-COMPONENT-HOST）。
- `SOURCE_BOUND_PROTOCOL` 只使用源码已证明的 launch 映射；ONLYOFFICE 每次 launch 固定 theme/locale（SF-WEB-03、SF-OFF-07）。
- 不能接受 presentation contract 的原生 UI 不嵌入任一承载端。native error 原文只作受权 evidence，用户界面使用宿主稳定 code 和 i18n key。

Iframe 不是常规组件形态，因为它无法保证 Host API、主题、i18n 和逐动作治理。只有像 ONLYOFFICE WOPI 这样两端固定协议已被源码证明的 `SOURCE_BOUND_PROTOCOL` 才能使用隔离页面。

## 5. Component Adapter Protocol

### 5.1 与上游项目形态解耦

| Connector | 适用条件 | 边界 |
|---|---|---|
| `PLATFORM_PORT_CLIENT` | Platform Component 实现已知 port | Core typed client 通过 Port Router 调 provider；不再套 application adapter |
| `REMOTE_ADAPTER` | Application Component 默认形态 | Core/Worker 调独立 adapter，adapter 调 native API |
| `EMBEDDED_DRIVER` | 上游明确提供 library runtime | CocoIndex Rust SDK（SF-CIX-01/04） |
| `PROTOCOL_PEER` | 双方存在已证明的固定协议 | ONLYOFFICE↔Cells WOPI（SF-CEL-05、SF-OFF-03） |
| `INTERNAL` | Core 自身领域 | 不生成网络 adapter 或自签 token 循环 |

Cells、WeKnora 和 Wren 可保持原 monolith/service，不需要为 Buzz 强拆前后端。Remote adapter 只在稳定 native API 上实现平台契约；Buzz 端使用 `HOST_NATIVE` 或获批准 `REMOTE_MODULE`，不嵌入原生管理后台（SF-CEL-01/03、SF-WEK-01/03、SF-WRN-01、DD-58）。

### 5.2 版本化深接口

Adapter Protocol 只包含以下逻辑操作，传输编码由 release 的协议版本固定：

```text
handshake(protocol range, component/release identity, capabilities)
validate_binding(binding ref/version, normalized config digest, secret ref versions)
resolve_native_scope(binding ref, platform resource ref)
execute(action key/version, normalized args, ActionToken)
observe(external execution ref, ActionToken)
cancel(external execution ref, ActionToken)
reconcile(binding or execution ref, ActionToken)
extract_usage(native evidence ref)
map_native_status_error(native status/error)
```

Handshake 成功只证明协议兼容，不表示 binding active。Binding 只在 service identity、config digest、SecretRef audience/version、native scope、隔离方式、capability 和全部 projection 对账后 active。

Core 在 dispatch 前完成准入。ActionToken 固定 issuer/audience、Tenant/Workspace、actor、delegation、action/version、target、operation、parameter hash、ResultExposure 和短 expiry。Adapter 校验 token 后仍按 `03` 的 PEP 合同将请求收窄到 binding 已固定 native scope。Adapter 不接受 payload 自报 Tenant/Workspace、不自行扩大权限、不回退默认实例（DD-63）。

真实副作用在 dispatch 前建立 ExternalExecution 和稳定 operation/idempotency key。超时且无 native query/dedupe 接缝时进入 `UNKNOWN`，不自动重发。Adapter 只映射源码存在的 progress/cancel/terminal；HTTP 200/202、queued 或 cancel accepted 都不等于业务完成。

## 6. 两类 Binding 的生命周期

### 6.1 PlatformProviderBinding

```text
approved PLATFORM release
→ create/upgrade provider binding for exact known port
→ PENDING projection generation
→ validate connector/target registry/service identity/config/secret/readiness/governance
→ Port Router atomically selects ACTIVE generation for new calls
```

变更由 Platform Catalog Tenant 的 `ComponentTaskWorkflow(kind=COMPONENT_BINDING, binding_kind=PLATFORM_PROVIDER)` 承接。旧 generation 保留给已开始调用；新 generation 校验失败不切流。安全撤销导致 provider fail closed，不静默切换未批准实现。

### 6.2 ApplicationBinding

```text
approved APPLICATION release
→ Tenant/Workspace creates or upgrades exact binding
→ PENDING projection generation
→ validate adapter handshake/config/secret/native scope/isolation/governance/Web artifact
→ reconcile Resource/Action/Tool/Gateway/route/observability projections
→ atomically select ACTIVE generation
```

变更由业务 Tenant/Workspace 的 `ComponentTaskWorkflow(kind=COMPONENT_BINDING, binding_kind=APPLICATION)` 承接。已开始的 ActionExecution/Workflow/ExternalExecution 继续使用旧 generation；新 Action 只解析 active generation。Rollback 也创建新 generation，不改写旧 release 或历史执行。

### 6.3 Disable

两类 binding 的停用都使用 `ComponentTaskWorkflow(kind=COMPONENT_DISABLE, binding_kind=...)`。Core 先置 `DISABLING` 并停止新 discovery/action/call，再暂停 Schedule、撤授权/route/tool/Web projection、观察已运行 execution 并对账 usage/audit。Disable 不删除 Resource/Asset/native data；保留或不明 ref 存在时不伪造已收敛。

## 7. 全局治理契约

每个用户、Agent、Schedule、callback 或 Workflow 可达 action 必须声明：

| 贯穿项 | Release 声明 | 运行时强制点 |
|---|---|---|
| Tenant | scope rule、binding isolation、native scope derivation | Core 从 session/parent action 构造；adapter 不接受自报 |
| Workspace | WorkspaceRule 与 binding scope | scope guard 先于 Resource permission；execution 固定 scope |
| Authorization | canonical permission、target、ResultExposure | SpiceDB fresh Check；Agent 另与 Delegation/ToolBinding 求交 |
| Approval | confirmation mode、ApprovalPolicy、owner rule | Temporal Approval 固定 exact action/parameter/owner/policy version，消费前重检 |
| Workflow | `SYNC/PROTOCOL/TEMPORAL`、kind、idempotency/UNKNOWN/cancel | Temporal 持有持久生命周期；native task 是 ExternalExecution |
| Capacity/Quota/Billing | capacity/quota mode、meter、strict upper bound | CapacityLease/QuotaReservation/OpenMeter；actual usage 只有一个 source |
| Operation Audit | intent/decision/dispatch/outcome/revoke/reconcile 与 redaction | 外部副作用前先持久 intent；结果沿同一 operation 追加 |
| Business Observability | correlation、terminal/progress/usage/cost source 和 redaction | operation→release/binding generation→native evidence→usage/cost 的受权联合视图 |

`NONE` 只能是明确策略值，缺失字段不等于 `NONE`。平台 provider 的内部 RPC 继承父 operation，不递归创建 Governed Action；任何用户可达的 provider 管理动作仍完整经过上表。

## 8. Resource 附加合同

### 8.1 IncrementalContract

每个 ResourceType 至少登记 `NATIVE_INTERNAL` 或 `VERSIONED_PUBLICATION`；参与跨 Resource 物化时再登记成对 `MATERIALIZATION_SOURCE/TARGET`，包含稳定 key、revision、缺失/删除、reconcile trigger、readiness 和目标 ownership。CocoIndex 只拥有逐项 previous/desired/pending/owner/generation 状态；Core 只拥有 MaterializationBinding 和 run/usage/audit refs（SF-CIX-02/03/04）。

只提供 mtime、只 create 无 delete/readiness、要求直写组件数据库或状态目录不可稳定恢复的类型不得物化。native 内部索引继续由组件维护，跨 Resource endpoint 才使用 CocoIndex；完整规则以 `13` 为准。

### 8.2 LLMGatewayContract

`REQUIRED` release 必须证明协议属于 AgentGateway 已实现的 Chat/Responses/Embeddings/Messages/Gemini/Rerank；active base URL 指向内部 Gateway route，provider credential 只存在 Gateway SecretRef，逐调用 trace context 能关联 operation（SF-AGW-04/05、SS-WEK-LLM-CTX）。Actual token/cost 只取 SS-AGW-USAGE 闭合后的 durable usage 并写 OpenMeter，组件自报 token 不形成第二份账。

### 8.3 Transfer 与 Tenant delete

`transfer_formats[]` 必须同时证明 export、import/create、format/version、digest、terminal 和错误语义；缺任一端则不注册跨 Tenant Action。`tenant_delete_action_key` 必须有稳定 native ref、幂等 delete、terminal query 和 retained-error 语义。组件停用不等于删除 native data。当前首批 release 受 GAP-LCM-01 阻断，全部 `tenant_delete_action_key=NONE`。

## 8.1 第三方接入面

`REQ-11` 保证组件可在运行时注册，`REQ-22` 保证第三方能在开发期独立做出组件。后者的交付物固定为六件，与 Component Host 同 Stage 交付（`DD-76`）：

| 接入面 | 内容 | 来源 |
|---|---|---|
| Component SDK | TypeScript 包：Host API 类型与调用封装、Adapter Protocol 客户端/服务端骨架、错误六分类与 reason code 常量、slot descriptor 构造 | 由 `contracts/` 生成或派生，不手写 |
| manifest schema 与校验器 | 可本地运行的 manifest 校验，错误信息指向具体字段与允许取值 | 本文 §3 的 manifest 定义 |
| 脚手架 | 生成含前端 module、后端 adapter、manifest 与一致性测试配置的最小可运行组件 | — |
| 本地开发环境 | 不接真实平台即可加载 module、应答 Adapter Protocol、模拟 binding 与 presentation context | — |
| 一致性测试套件 | 在 Adapter Protocol 线协议层验证 handshake、终态语义、幂等、取消、错误映射与 redaction | 本文 §5 与 `03-领域模型与权限模型.md` 的状态约束 |
| 示例组件 | 一个端到端参考实现，覆盖三个扩展槽中至少一个与一条 Tool 路径 | — |

约束：

- SDK 是 `contracts/` 的消费者，不是第二权威；两者冲突以 `contracts/` 为准，`contracts/` 与本文冲突以本文为准。
- 前端 remote module 只能是 TypeScript，由承载端运行时决定；后端 adapter 的契约是线协议，因此首方不承诺多语言 SDK，任意语言实现以一致性套件自证。
- 接入面随 Host API 与 Adapter Protocol 的 range 一起版本化。新增扩展槽或 Host API 不兼容变更时，接入面必须同步发布，否则第三方拿到的类型与真实宿主不一致。
- 一致性套件通过是登记 release 的必要条件，不是充分条件；平台管理员批准、digest 固定与全局治理校验仍然独立执行。
- 接入面不暴露平台内部实体、SpiceDB schema、Core 数据库结构或任何 service credential。

## 9. 无需重发 Core/承载端的精确边界

| 变化 | Core/承载端重发 | 原因 |
|---|---|---|
| 新增/升级兼容 Application release | 不需要 | 使用已有 manifest、Adapter Protocol、Resource/Action/Tool 和 slot |
| 启用/停用/回滚 ApplicationBinding | 不需要 | 只切换运行时 projection generation |
| 为已有 platform port 更换兼容远程 provider | 不需要 | Port Router 只切换 PlatformProviderBinding generation |
| 新增或升级 embedded/internal provider 代码 | 需要 Core/Worker | 可执行代码与主体构建绑定，manifest 只能引用已有 registry key |
| 新 canonical permission、SpiceDB object type、Workflow 语义或 platform port | 需要 Core | 改变 Core 权威契约 |
| 新 extension slot、Host API 不兼容变更 | 需要 Buzz Web 与 Buzz Desktop | 宿主需理解新界面语义，两端契约必须同版本 |
| Adapter Protocol 不兼容变更 | 需要 Core/adapter | Dispatcher 与 adapter 协议契约改变 |

运行时注册必须同时满足：manifest schema 可解析；只使用已有 port/permission/Workflow kind/slot；Host API 或 Adapter Protocol range 相交；source baseline、artifact digest、全局治理、业务可观测性、主题+i18n 和隔离合同全部通过；binding 完成 projection reconcile。任一项不成立都 fail closed，manifest 不得绕过边界。

## 10. `.references` 差异与 Release 演进

`.references/UPDATE_TASKS.json` 只告知 upstream diff。差异命中 release 引用的 SOURCE_FACT/SOURCE_SEAM 时，重验 native scope、API、状态、增量、LLM、治理和前端合同，通过后形成新 immutable release。旧 binding 继续 pin 旧 release；源码新增 endpoint、UI、Resource、Tool 或 meter 不自动进入 manifest，不自动扩大 relationship、Delegation、route 或 quota。新 release 只在 Catalog 批准、binding 变更和新 generation 对账后对新调用可见。
