# 领域模型与权限模型

本文是平台实体、关系、状态与权限表达的唯一来源。它描述逻辑数据，不指定物理表、数据库或代码目录。

## 1. 权威矩阵

| 事实 | 唯一权威 | 其他系统中的形态 |
|---|---|---|
| OIDC browser authentication session | AgentGateway | 加密 HttpOnly cookie；Core 不读取 ID token |
| Human identity、platform session | Platform Core | OIDC subject 投影 |
| Tenant/Workspace membership 与收敛状态 | Platform Core | SpiceDB tenant/workspace relationships 与 Buzz relay/Channel roster 投影 |
| HUMAN 的 Workspace 收藏/静音与 Channel/Message/Thread 已读位置 | Platform Core | Browser 只有会话缓存；Relay kind:30078 不是一期权威 |
| Tenant、Workspace、Resource、Asset、owner | Platform Core | Buzz/组件 binding、SpiceDB relationships |
| 访问允许/拒绝 | SpiceDB | ActionDecision 中的 ZedToken 与 evidence |
| Approval/Workflow lifecycle | Temporal | Core TaskProjection 只读视图 |
| Buzz Community/Channel/message/thread/event | Buzz Relay | Core binding、AuditEvent 与 AgentInvocation 引用 |
| Agent Definition、Version、Installation、Skill 与有效配置投影 | Platform Core | Buzz Persona/identity、Codex config/skill/MCP、AgentGateway ConfigResource 投影 |
| Agent Installation 的 core/cold 长期记忆 head | Buzz Relay NIP-AE | AgentMemoryBinding 与 AgentSession 只保存 binding/event ref，不复制正文 |
| Agent session thread/turn/item | Codex ThreadStore/Rollout | AgentSession/AgentInvocation 固定 thread、version、projection generation 与 core event 快照 |
| Tool transport/route | AgentGateway | Core ToolDefinition 的运行投影 |
| Entitlement、credit、committed usage、billing | OpenMeter | Core QuotaReservation/UsageOutbox |
| 平台 runtime slot | Platform Core | CapacityLease |
| 能力类别与版本化能力契约 | Platform Core Catalog | CapabilityCategory/CapabilityContract；ComponentRelease 以 `implements[]` 引用 |
| 组件业务正文、native 对象与版本、native task、协议会话运行状态 | 对应业务能力实现 | Resource/Asset、ApplicationBinding、ExternalExecution；ContentReference、ProtocolSession 与 Buzz event 只存稳定引用与门禁 evidence |
| Platform AuditEvent | Platform Core | Buzz/Temporal/SpiceDB/OpenMeter/native IDs 作 evidence |

不变式：

- `(provider_id, issuer, subject)` 只映射一个 HumanIdentity。
- HumanIdentity 在每个 Tenant 至多一个非 `REVOKED` TenantMembership/HUMAN Principal。TenantMembership `ACTIVE` 只在 Core membership、SpiceDB tenant relationship 与 Buzz `relay_members` 全部对账后成立；`INVITED/PROVISIONING/REVOKING/REVOKED/ERROR` 均不能建立 PlatformSession 或发起新动作（DD-45）。Tenant 为 `ACTIVE` 时会话为 `access_mode=FULL`；Tenant 处于 `SUSPENDING/SUSPENDED/DELETING` 时，只有 DD-96 受限会话的资格者（该 Tenant admin，及已冻结 snapshot 中的 HUMAN owner）可建立 `access_mode=LIFECYCLE_RESTRICTED` 会话，它只被 DD-96 列出的生命周期入口接受，其余入口一律拒绝；受限会话随 Tenant delete Action 注册，此前暂停中的 Tenant 不建立任何会话。
- TenantMembership 只经 DD-83 的邀请兑换进入 `INVITED`（部署引导的首位成员直接 `PROVISIONING`）；`INVITED` 只有两条出路：`tenant.member.admit` 获批并重新准入后进入 `PROVISIONING`，或准入/审批以任何方式终结而未派发时进入 `REVOKED`。
- TenantInvitation 只保存一次性凭据的摘要，`credential_digest` 全局唯一；明文凭据不属于任何实体。`ISSUED` 只可进入 `REDEEMED`（兑换，同时写入兑换者、membership、兑换时刻与 admit ActionExecution）或 `REVOKED`；`expires_at` 已过的 `ISSUED` 邀请按查询时判定为过期，既不能兑换也不能撤回。`invitee_label` 是邀请人写给审批人看的称呼，不参与寻址与判定（DD-83）。
- WorkspaceMembership 引用的 Workspace 与 HUMAN Principal 必须同 Tenant；同一 `(workspace_id, tenant_principal_id)` 至多一个 active membership。`ACTIVE` 只在 Core membership、SpiceDB relationship 与 Buzz Channel roster 全部对账后成立；`REVOKING/REVOKED/ERROR` 均拒绝新 scope（DD-41）。
- 一个 HumanIdentity 可在多个 Tenant 各有一条 `ACTIVE` TenantMembership，但一期不提供登录时选择 Tenant 的入口。此时身份解析以 `BLOCKED/TENANT_SELECTION_NOT_AVAILABLE` 拒绝并留审计，不按任何顺序任取其一——任取即回退默认租户。非 `ACTIVE` 的 membership 不参与选择，也不得遮住唯一 `ACTIVE` 的那一条。
- TenantMembership 进入 `REVOKING` 时立即撤销其 PlatformSession、关闭全部 Workspace stream 并拒绝新动作；HUMAN Principal 在收敛期间仅作为历史责任与 owner 转移标识，不能执行。除 Tenant 销毁外，其所有 active Resource/Asset 必须先由 Tenant admin 的受治理 owner-transfer Action 转给另一 active HUMAN，才能在 SpiceDB tenant relationship 与 Buzz relay roster 均已撤销后进入 `REVOKED`（DD-45）。
- Principal 只属于一个 Tenant；OIDC claim 只认证 HumanIdentity，不产生业务授权。
- ApplicationBinding 的 ServicePrincipal 以 `component_binding_ref` 指向该 binding，只在服务读取边（DD-89）作为 SERVICE actor；它不是 Resource/Asset owner，不能发起审批决定，其读取权只来自经 Governed Action 写入的来源 Resource `reader` relationship。binding 转 `DISABLED` 时其 ServicePrincipal 同步停用。
- TenantBuzzBinding 与 WorkspaceBuzzBinding 一对一；任一侧不一致时 scope 不可用。
- `TenantBuzzBinding` 与 `WorkspaceBuzzBinding` 的正常建立路径固定为 `UNBOUND → PROVISIONING → RECONCILING → ACTIVE`，停用进入 `DISABLED`；`BuzzIdentityBinding` 固定为 `PENDING_SECRET → RECONCILING → ACTIVE → REVOKING → REVOKED`。`RECONCILING` 必须核对 Relay roster；启用 `pubkey_allowlist` 时还必须写入并查证 allowlist 行。`ACTIVE` 的 Tenant binding 固定保存当前 NIP-11 文档的 canonical digest、查证时刻与 Relay 的 `self` 公钥，运行连接不得使用超出该快照声明值的订阅、filter、limit 或 frame 合同。Tenant binding 另有一条漂移路径 `ACTIVE → RECONCILING → ACTIVE`：只由 Core 治理对账器在以 `normalized_host` 抓到摘要不同的文档时进入，按 DD-114 的比对规则重新查证后回到 `ACTIVE`；BFF 请求路径不迁移状态。
- 每个可在 Buzz 产生 event 的 HUMAN/AGENT 都有独立 BuzzIdentityBinding；不共享 pubkey。BuzzIdentityBinding 以 `pubkey` 为身份：一个 HUMAN Principal 在其 Tenant 内至多一条非 `REVOKED` 的 `custody=SERVER` binding（Buzz Web），另有每台原生设备一条 `custody=CLIENT` binding，设备数以部署登记的上界为限（DD-77）。一个人同时使用 Web 与原生端时，Relay 看到的是同一 Principal 名下的多个 pubkey；审计与作者显示按 pubkey 归因到该 Principal。
- 成员投影与撤权对该 Principal 的**全部**非 `REVOKED` binding 生效：建立时每个 pubkey 都进入 relay 与 Channel roster，撤权时全部移出，任一 pubkey 未收敛即整体未收敛（DD-77）。单台设备的 CLIENT binding 可单独撤销，只影响该 pubkey。
- `custody` 按 `09-统一身份与Buzz协议投影.md` 的托管表取值：Buzz Web 的 HUMAN、全部 AGENT 与 CONTROL 为 `SERVER`，`private_key_secret_ref` 必须非空；Buzz Desktop 与 Buzz Mobile 的 HUMAN 为 `CLIENT`，`private_key_secret_ref` 必须为空。`custody=CLIENT` 的 binding 跳过 `PENDING_SECRET`，自 `RECONCILING` 起始，其 `RECONCILING` 只核对 Relay roster 而不核对 secret 可读性。
- `custody` 不改变任何授权、审批、额度或审计判定；撤权对两种取值都以 SpiceDB relationship 与 Buzz roster 为执行点（`10` §4）。`custody=CLIENT` 时平台不具备停止该 pubkey 签名的手段，轮换语义相应收窄为 roster 移除加已知连接关闭。
- CONTROL 身份是 Buzz Community 的协议级 SERVICE owner，只作 Community/roster 投影与该 Tenant 的 NIP-AE Memory Counterparty/解密边界，不得成为 Resource/Asset owner 或业务 actor。
- ConversationBuzzBinding 是 REQ-24 的原生私聊投影绑定，不是 Workspace、Resource 或第二套聊天权威；正文、消息、线程及私聊频道仍在 Buzz Relay。参与者是同 Tenant 的 HUMAN Principal，按排序去重后的不可变集合寻址；增加人得到另一场私聊，不能让新人读到旧会话。一个用户的 SERVER/CLIENT 多把钥匙只改变 roster 投影，不改变参与者集合或会话标识。1v1 与群组参与人数沿固定 Buzz 上游的 2–9 人语义，设备钥匙不计为额外用户。
- 创建、重开与扩展私聊经 BFF，发起者必须属于参与者集合，所有参与者须为 ACTIVE HUMAN 且 TenantMembership ACTIVE；按 Tenant 的 fresh `discover` 加参与者事实共同准入，不以 Tenant/Workspace admin 代替私聊参与资格。执行 scope 为 Tenant，Workspace 为 NONE；CONTROL 只签发原生 DM 投影命令，不进入 DM roster。非参与者不得读列表、正文、元数据、搜索结果或订阅事件，管理角色不构成例外。
- 私聊 binding 从 PROVISIONING 经 RECONCILING 到 ACTIVE，仅当原 Relay private DM、原生引用及全部允许的钥匙投影查证一致才开放。投影使用单调 generation；旧 generation 不能覆盖新 roster，同 generation 的不同 payload 拒绝。结果不明保留原 binding、operation 和 generation 继续对账，不另建会话；超过部署已有投影对账时限告警。停用进入 DISABLED，历史引用与正文不因此被复制或伪造删除。
- 私聊设备增补、撤销与 Tenant 成员撤权复用原 BUZZ_IDENTITY_PROJECTION/MEMBERSHIP_REVOCATION 收敛：进入 REVOKING 即拒绝新的 BFF 私聊访问，并在 Relay 移出对应全部或单台设备的公钥。参与者集合保留作历史引用，不自动授予恢复身份访问；只有当前 ACTIVE membership、identity 与已查证投影同时成立才恢复。Tenant 暂停沿原 Community 归档与 session/stream 关闭覆盖私聊，不增加独立暂停权威。
- `RelayOperatorIdentity` 是唯一部署级 Buzz operator signer，归 Platform Catalog Tenant 而不属于任一业务 Tenant。它只允许 audience `buzz-relay-operator`，SecretRef 与任一 Tenant CONTROL key 分离，签名目标必须精确等于登记的 `relay_operator_api_origin` 加 operator route。Tenant lifecycle 只能借此 identity 创建、列出、归档与解档 Community（后两者只用于 Tenant 暂停与恢复，owner 为该 Tenant CONTROL，DD-96），Community 内的业务管理一律使用该 Tenant CONTROL identity（SS-BUZ-OPERATOR）。
- `private_key_secret_ref` 只存 locator，不存私钥明文或平台自制 ciphertext；locator 指向该 Tenant OpenBao namespace 内 KV v2 的具体版本，签名只在 Core signer 内存中完成（DD-72）。
- `ServerKeyProvisionIntent` 冻结 HUMAN、CONTROL、OPERATOR 三类平台自持私钥的一次写入目标，不复制私钥、公钥或 OpenBao metadata。`finished_at=NONE` 且 `fenced_at=NONE` 为 OPEN；`fenced_at` 已记录而 `finished_at=NONE` 为 FENCED；binding 与 `finished_at` 同事务提交且 `destroyed_at=NONE`、`retired_at=NONE` 为 BOUND；仅在 OpenBao metadata 查证版本 1 已销毁后，同事务记录 `destroyed_at` 与 `finished_at` 为 DESTROYED。FENCED 禁止两条建钥入口提交 binding；当前 metadata 版本 0、超时或传输失败都不能终结意图。BOUND 与 DESTROYED 互斥；DESTROYED 不改变成员投影 Workflow 的终态（DD-86）。按 DD-113，意图覆盖三类平台自持私钥：`key_kind=HUMAN` 由 Governed Action 发起（`action_execution_id` 必填），`CONTROL` 由 Tenant 建立的 operation 发起、`principal_id` 为该 Tenant 的 CONTROL SERVICE Principal，`OPERATOR` 由部署引导或轮换命令的 operation 发起、`tenant_id` 为 Platform Catalog Tenant、`principal_id=NONE`；同一 HUMAN Principal、同一 Tenant 的 CONTROL、同一 Catalog 的 OPERATOR 各至多一条未完成意图。`action_execution_id` 只对 HUMAN 唯一（其 locator 由该 ActionExecution 派生，同一动作的重试续用同一意图）；CONTROL 同一 operation 的重试在 fence 并销毁不可续用的写入后，为同一 operation 冻结新 key 的新意图（DD-113 (2)）。每个 `target_locator` 只有一把 key、只写版本 1：CONTROL 与 OPERATOR 由 pubkey 派生，HUMAN 由原 ActionExecution 派生（DD-86）。`origin=PROVISIONED` 的意图 `operation_id` 必填；`origin=BACKFILLED` 是 DD-115 为存量补建的行，`operation_id` 与 `action_execution_id` 为空，只能是 BOUND 或 RETIRED。`origin=PROVISIONED` 的 OPERATOR 意图必有 `commit_deadline_at`，绑定只在截止前提交，过期未绑定即终态（DD-115）。进入退役到期时同事务冻结 `retire_operation_id`，退役审计追加到它；孤儿审计追加到 `operation_id`。BOUND 的意图在其 key 退役时（HUMAN binding 到 `REVOKED`，或 operator 轮换已确认旧 key 被拒）执行 `destroy`，仅在 metadata 查证版本 1 `destroyed=true` 后记录 `retired_at`；`finished_at` 与 `retired_at` 均已记录且 `fenced_at=NONE`、`destroyed_at=NONE` 为 RETIRED，RETIRED 只能由 BOUND 进入。
- Resource `home_workspace_id` 与 ActionExecution `workspace_id` 是不同维度。Tenant/成员/全局 Catalog 等 `workspace_rule=TENANT_ONLY` 的管理动作显式使用 `workspace_id=NONE`；Workspace 顶层动作使用受校验 Workspace；Workspace 内工具/模型 child action 继承父 operation 的 Workspace，即使目标 Resource 是 `home_workspace_id=NONE`。不能从 Resource home、模型名或字段缺失推断执行 scope（DD-54）。
- Workspace scoped Action 先要求 Workspace `ACTIVE`，再按 actor kind 执行 scope guard：HUMAN 必须有 active WorkspaceMembership，或 fresh SpiceDB Check 证明 workspace `manage`；AGENT 必须同时匹配 active AgentInstallation/AgentPrincipal、fresh workspace `discover`、Buzz Channel roster 与 active ChannelAgentBinding；SERVICE 只在服务读取边（DD-89）作为 actor，必须是 active ApplicationBinding 的 ServicePrincipal，该 binding 与来源 Resource 同 Tenant，Workspace 级接收方 binding 还须与来源 `home_workspace_id` 一致或来源为 Tenant 级 Resource，执行 Workspace 取接收方 binding 的 `workspace_id`（Tenant 级接收方为 NONE），SERVICE 不经 WorkspaceMembership 或 Agent 路径取得 scope。该 guard 在 Resource/Asset permission Check 之前执行；因此 owner/Resource permission、频道 event 或 ToolBinding 都不能单独绕过 Workspace 边界。暂停/恢复等生命周期 Action 从 Tenant scope 指向 Workspace，不借用被暂停的 Workspace scope（DD-46/50）；业务 Tenant 的暂停/恢复同理从平台 Catalog scope 指向该 Tenant（DD-96）。
- CollaborationUserState 只属于一个 active HUMAN Principal。`workspace_preferences` 的 key 必须是同 Tenant 且该 HUMAN 可发现的 Workspace；`conversation_preferences` 的 key 必须是该 HUMAN 当前参与、投影已闭合的 ConversationBuzzBinding。`read_contexts` 接受上述可读 Workspace 或私聊的原生 Channel ID、`msg:<Buzz event id>` 或 `thread:<Buzz root event id>`，消息/线程以本人 SERVER 身份经 Relay 查证，再核验当前参与资格与绑定。BFF 每次写入从 PlatformSession 取 principal/scope，不接受 Browser 自报 Principal。撤销成员或参与资格后立即禁止读写该 scope，保留偏好仅用于恢复资格后继续使用；私聊不借 Workspace ID 或管理权限准入。私聊隐藏/恢复仍属于 Relay 的原生 channel_members.hidden_at 与 NIP-DV 可见性快照，不复制到 CollaborationUserState。
- buzz-web 原有 kind:30078 NIP-44 self-encryption 需要浏览器 signer（SF-WEB-05）；一期 Browser 无 Nostr 私钥，因此该路径固定停用。CollaborationUserState 是平台用户状态，不伪装为服务端 NIP-44 兼容层（DD-40）。

### ExecutionContext

```text
ExecutionContext(
  tenant_id,
  workspace_id | NONE,
  authenticated_principal_id,
  acting_principal_id,
  initiating_human_principal_id | NONE,
  session_id | NONE,
  agent_invocation_id | NONE,
```

ExecutionContext 只能由 Platform Core 从 session、route、Resource、binding kind/ID/generation 与 runtime identity 构造。浏览器、prompt、Agent 参数与 callback 中的 scope 只是待校验输入。

### Frontend Presentation Context

```text
FrontendPresentationContext(
  theme_preference[LIGHT|DARK|SYSTEM],
  resolved_theme[LIGHT|DARK],
  locale[EN|ZH_CN]
)
```

- `theme_preference` 与 `resolved_theme` 由 Buzz `ThemeProvider` 产生；组件只能消费 `resolved_theme`，不能再解析系统主题或持久化第二份偏好。
- `locale` 由共用 i18n 解析：设备未选择语言时默认 `ZH_CN`，显式选择英文时取 `EN`；已选语言不被浏览器/系统语言覆盖。一期只允许这两个正式 locale；新增 locale 必须先进入 Buzz `AppLocale + messages`，再供组件映射。
- `theme_preference` 是当前设备 Buzz ThemeProvider 解析出的明暗模式，不宣称跨设备同步。Web/Desktop 的原版主题样式、强调色与跟随系统偏好沿用 `buzz-theme`、`buzz-accent-color`、`buzz-follow-system`；这些是同一 ThemeProvider 的本地外观输入，不是第二份组件偏好。兼容现有 Web 的 `buzz-web-theme`：仅在原版偏好尚不存在时一次迁移其有效明暗模式，成功持久化后移除旧键与旧读取路径；已有 Desktop 原版偏好不得被覆盖。跨端/组件合同的 `theme_preference[LIGHT|DARK|SYSTEM]`、`resolved_theme[LIGHT|DARK]` 不扩展为主题样式名称，Mobile 保留原生明暗控制，不加载 TypeScript 主题或组件页面。`locale` 仅有设备本地偏好，设置页提供 `en/zh-CN` 切换；共享 TypeScript 与 Dart 消费同一消息表和中文默认规则，不新增后端偏好字段。React App 内的登录回跳、无 Tenant、加载和错误状态仍在同一 ThemeProvider/AppLocale 下；外部 IdP 页面不属于 Buzz Web surface（DD-53）。
- 所有 Buzz host-native 业务页、管理页、弹窗、空状态、错误、审批和任务状态都使用 Buzz CSS variables 与 `MessageKey/t`；remote module 使用 Host API presentation context 与 namespaced catalog；后端只返回稳定状态码和结构化参数，不返回最终界面文案。
- 平台自有日期、时间、数字与相对时间使用 `getLocale()`；用户输入的消息、Resource 名称、文件名、Agent 输出和组件业务正文保持原文，不送入 `t()` 也不自动翻译。native error 原文只作为受权 evidence，UI 状态使用稳定 code 对应的 MessageKey（DD-53）。
- source-bound surface 只接收其固定协议能够证明的 theme/locale 映射。独立原生管理页面不要求实现 Host API 或完全继承 FrontendPresentationContext，按 `07` §4.6 隔离承载，支持时传递偏好。

- Digest 规则全局统一，所有 `*_digest` 字段与 `integrity` 值都用它：字节流直接 `sha256`；结构化对象先按 canonical JSON（键排序、无无意义空白、UTF-8）序列化再 `sha256`。路径中使用十六进制表示，浏览器 `integrity` 属性使用 `sha256-<base64>`。没有该规则就无法复算 `config_digest`/`normalized_manifest_digest`，也无法做 Subresource Integrity。
- `PlatformBuildInfo` 是当前已部署主体的能力事实，兼容性判定的"当前一侧"只从它读取：Catalog 批准 release 要求 `host_api_range` 与已部署 Buzz Web 的 `host_api_version` 相交、`adapter_protocol_range` 与 Core/Worker 的 `adapter_protocol_versions` 相交、`EMBEDDED_DRIVER`/`INTERNAL` 的键在 `driver_registry_keys` 内、`platform_port_key` 在 `platform_port_keys` 内；BFF 返回 Component 快照时按请求方自报并经校验的 `host_api_version` 过滤，滚动发布期间不同版本的 Browser 各自只看到自己能加载的 generation。缺少 `PlatformBuildInfo` 时 release 不得批准、快照不得下发。
- `adapter_build_ref` 固定 `REMOTE_ADAPTER` 实现的构建产物 digest。adapter 在 handshake 中必须出示与 release 登记值一致的 `adapter_build_ref`；`source_commit` 只固定上游项目，不能证明 Kailo 自建 adapter 的字节。不一致时 binding 停在 `PENDING/ERROR`。
- Resource 是平台持久化的治理根；Application Resource 表示对外部对象的 Core 授权引用，不表示 Core 拥有或创建了服务原生对象。native ID 永不作为平台 API 的裸标识，引用登记及核实按 DD-98，不新增第二资源系统。
- Resource `state` 转移固定：平台核心 ResourceType 由各自领域动作写入 Core 事实并完成 SpiceDB relationship 投影后进入 `ACTIVE`（投影闭合前按该领域动作自己的状态机 fail closed），native 字段为 Core 自身 ID；应用 Resource 只经 `resource.create` 取 `PROVISIONING → ACTIVE | FAILED | UNKNOWN`，既有引用的 `UNKNOWN` 只经同一冻结引用/证据核对转 `ACTIVE | FAILED`；明确 `REMOTE_ADAPTER` 原生创建分支的 `UNKNOWN` 只经原 `LOOKUP` 对账转出（DD-98）；所属 ApplicationBinding 转 `DISABLED` 时 `ACTIVE → RETAINED_READ_ONLY`，只可 discover 元数据（DD-88）；按能力契约的删除键或 Tenant 销毁链删除时 `ACTIVE | RETAINED_READ_ONLY → DELETING → DELETED`，删除结果不明保持 `DELETING` 并按该删除的 ExternalExecution 或平台核心销毁链对账。只有 `ACTIVE` 接受新动作；`FAILED` 与 `DELETED` 为终态，保留 Core 事实与审计。
- Resource 和每个已登记 Asset 都显式保存一个 active HUMAN owner，不使用条件性 `owner_override`。
- Resource、home Workspace、ApplicationBinding、owner 及所有 relationship subject 必须同 Tenant；Asset、父 Resource、owner/producer 也必须同 Tenant。Core 在写业务事实和 SpiceDB relationship 前同时校验，不依赖 schema 自动推断这个不变式。Core 原生 Resource 的 `application_binding_id=NONE`；Application Component 所属 Resource 创建时必须指向同 Tenant 的 active ApplicationBinding；该 binding 因类别内切换转 `DISABLED` 后，Resource 保留原指向并转为保留只读，只可 discover 元数据、不可发起新动作（DD-88）。
- Application Component 的 Core 授权引用只经 `resource.create` 首次登记（DD-98）：发起 HUMAN（Agent 代发起时为 initiating HUMAN）是平台 accountable owner，不是自动取得上游 owner/admin。Core 先写 `PROVISIONING` Resource、ActionExecution 与 WorkflowRef，原 `RESOURCE_PROVISION` 写 SpiceDB relationship 并复检；已有外部对象须由冻结 binding/native scope 的可复核原生协议证据或可信运行投递事实核实，用户裸 native ID 不能直接转 `ACTIVE`，证据未闭合不生成入口。同 Tenant 的相同绑定/native 引用复用原 Resource；不得跨 Tenant 共享或重复建立绕过原 owner/ACL 的治理根。既有引用未知只查原引用/证据，不能调用原生 CREATE；只有明确 `REMOTE_ADAPTER` 原生创建才经原 `resolve_native_scope(CREATE)` 与 `LOOKUP/ABSENT_FENCED` 流程。引用或关系确定拒绝转 `FAILED` 并撤其未完成投影，未知保持 `UNKNOWN`；非 `ACTIVE` 不接受其他动作、不作 ContentReference 或 WorkspaceCapabilityDefault 目标。平台核心 ResourceType 仍由各自领域动作创建。
- `home_workspace_id=NONE` 只表示 Tenant-level Resource；非空时 Workspace 必须同 Tenant。Workspace 暂停保留 Resource/Asset、owner 与 relationships，但 scope guard 拒绝普通读写、Agent trigger、Tool discovery 和新 Workflow；恢复完成后重新开放。当前 Workspace 不含 `DELETING/DELETED` 状态，也不注册 delete Action（DD-46）。
- 任何 SpiceDB relationship、ApplicationBinding、WorkspaceCapabilityDefault、ContentReference、ProtocolSession、ToolBinding 或 native object 引用都不得跨 Tenant。PlatformProviderBinding 不引用业务 Resource/Asset。跨 Tenant 不是 `share` permission 的一种变体；它只能通过 DD-42 的两段 export/upload/import 边界生成新对象。
- 未持久登记的 native 子项（文件子项、知识块、临时查询结果行等）留在 native Resource 内，不是 Platform Asset。
- Agent/service 只能是 producer；新 Asset 的 owner 由 initiating HUMAN 或已批准的 owner-transfer action 确定。
- ExportPackage 是源 Tenant 内的 Asset 扩展，必须与 source Resource/Asset、export operation 及 HUMAN owner 同 Tenant。package 只在 `READY` 时可下载；导入时目标 Tenant 只信任新 session 上传的 bytes、已登记 `format_key/version` 与重算 digest，不信任 package 内的 Tenant、owner、ACL、native ID、URL 或 token。目标 Resource/Asset 由目标 Tenant `create` 准入重新创建；不建立到源对象的平台外键或授权关系。
- 应用不必原生具有 Kailo Tenant/Workspace；ApplicationBinding 必须固定一种源码可证明的隔离方式，解析失败时拒绝而不是回退默认实例。`RESOURCE_INSTANCE` 表示一个平台 Resource/不可变版本独占一个固定 native runtime context；是否采用由实现的 release manifest 声明并在准入时校验。
- 每个部署只有一个 `catalog_tenant_id`，它引用正常受治理的 Platform Catalog Tenant。ComponentDefinition/Release 是该 Tenant 管理的全局技术元数据，不是可跨 Tenant 共享的业务 Resource；release 登记、批准、撤销与 artifact 访问均以该 Tenant 的 platform-admin Principal 进入 Governed Action。业务 Tenant 的 Binding 只能引用 `APPROVED` release，不能修改 release 或上传代码。
- ComponentDefinition 只表达稳定类型与分类。`class=PLATFORM` 时 `platform_port_key` 必须是 Core 已登记端口；`class=APPLICATION` 时必须为 `NONE`。ComponentRelease 发布后不可变；来源标识按 `admission_path` 任一变化——`BUILTIN_REFERENCE` 的 `source_commit`，`EXTERNAL` 的 `artifact_version`（供应商服务或 API 版本）、`component_package_digest` 或 `adapter_build_ref`——以及 manifest schema、Host/Adapter Protocol range、Resource/Action/Tool、治理合同、Web artifact 任一变化，都创建新 release（DD-94(1)/(6)）。ComponentPackage 只携带 manifest 与 digest 固定的 Web artifacts，不包含后端 executable；远程服务独立交付，`BUILD_BOUND` 代码必须已存在于当前 Core/Worker 构建。
- `class=APPLICATION` release 的 `execution_connector.mode` 只能取 `REMOTE_ADAPTER` 或 `PROTOCOL_PEER`；`INTERNAL`、`EMBEDDED_DRIVER` 与 `PLATFORM_PORT_CLIENT` 只属 `class=PLATFORM`，因此 ApplicationBinding 的 `call_identity_mode` 不含 `INTERNAL`，Core 在 release 登记与 binding 建立时各自校验（DD-58/64）。
- CapabilityCategory 与 CapabilityContract 是 Platform Catalog Tenant 管理的平台 Catalog 实体，是运行时数据，不是业务 Resource，也不属于任何 ComponentRelease（DD-102）。`origin=PLATFORM_SEED` 的 `FILE_STORAGE`、`KNOWLEDGE`、`DATA_QUERY` 与其 v1 契约随平台构建交付，Catalog 启用时由部署引导一次性登记为 `ACTIVE`（DD-108）；`origin=CATALOG_REGISTERED` 的类别与契约版本由平台管理员经 `capability_contract.register` 登记为 `DRAFT`，经另一位 Catalog Tenant admin 批准的 `capability_contract.approve` 转 `ACTIVE`（`05` §2.8）。运行时登记的契约只能使用 §5 的固定 permission、通用 Resource/Action/Tool 与 ContentReference 语义、`required_declarations` 的封闭取值，`protocol_session_kinds[]` 只能引用当前 Core 已编译的 kind；需要新 ProtocolSession kind、Workflow kind、能力声明、前端交付模式或 permission 的类别只能随 Core 发版加入。每个类别的 ResourceType `type_key` 固定为 `<category>.<kind>` 命名空间（类别键的小写形式），不含产品名，不得使用保留前缀 `component.`（DD-88/101）。
- CapabilityContract 以 `(category_key, contract_version)` 唯一，`ACTIVE` 后不可变，语义变化创建新版本。`operation_contracts[].contract_key` 固定为 `<category>.<verb>@vN`，`permission` 只取 §5 固定 permission；`required_declarations` 列出实现必须在 release 中逐项声明的取消、观测、计量与 Tenant 删除能力；`schema_set_digest` 固定该版本全部参数与结果 schema，`conformance_suite_digest` 固定该版本的一致性测试向量，由平台发布的通用一致性套件运行器执行；种子契约的 schema 权威是 `contracts/adapter/<category>.v1`。
- ComponentRelease 只放声明与上界，ApplicationBinding 只放上界内的选择。release 声明 `admission_path`、`implements[]`、来源标识、`data_store_isolation` 与 `data_location`、`allowed_model_call_modes[]`、`secret_schema` 与 `capability_declarations`；binding 选择 `capability_categories[]`（`implements[]` 的非空子集，即该 binding 实际启用的能力类别）、`model_call_mode`（必须属于 `allowed_model_call_modes[]`）与 `retain_on_tenant_delete`。binding 不另存隔离模式之外的数据存储或数据位置声明，一律以其 pin 的 release 为准。来源标识按 `admission_path` 取值：`BUILTIN_REFERENCE` 必填 `source_project` 与 `source_commit`；`EXTERNAL` 必填 `vendor` 与 `artifact_version`，`source_commit` 可空，来源以 `vendor`、`artifact_version` 与 artifact digest 取证；凡要求固定 source commit 或 source baseline 的准入、Workflow input 与运行时注册条件都按此解读（DD-88/94）。
- `class=APPLICATION` 的业务能力 release 以 `implements[category@version]` 声明实现，每项必须引用 `ACTIVE` CapabilityContract，且 release 必须同时满足：为契约 ResourceType 族登记 `capability_category/capability_contract_version` 与之相等的 ResourceTypeDefinition；为每个必选 operation contract，以及其已声明 `SUPPORTED` 的能力（如 `revision_query`、`versioned_model`）所对应的条件 operation contract，登记 schema digest 一致的 ActionDefinition 或 ToolDefinition，未声明的条件键不实现、不暴露；逐项给出 `capability_declarations`。release 只声明门禁已闭合的能力类别，未闭合的类别在后续 release 中加入，因此 binding 对每个启用类别只有一个状态。对 `FILE_STORAGE` 声明 `online_editing=SUPPORTED` 的 release 必须同时声明 `revision_query=SUPPORTED`（按 `native_object_ref` 查询当前 revision），缺失者不得声明在线编辑（DD-90/103）。`read_edge` 声明该实现能否作为服务读取边的来源方或接收方，`NONE` 时该实现不参与 `resource.grant_read` 的 ServicePrincipal 授予与 `request_read_grant`，自身能力完整可用（DD-89）。产品专属扩展只能位于该组件命名空间内且不得改变契约语义。`class=PLATFORM` release 的 `implements` 必须为空。准入两条路径：内置参考实现以 SF/SS 源码证据加一致性套件；外部实现以能力契约、一致性套件、平台管理员批准与其声明的隔离模式和数据位置准入，不要求 `.references` 源码（DD-88）。
- `implements=[]` 的 `class=APPLICATION` release 只允许 REQ-22 示例组件（DD-101）：它不是业务能力服务，其 ResourceType 的 `type_key` 为 `component.<component_type_key>.<kind>`，Action/Tool 的 `action_key` 为 `component.<component_type_key>.<verb>`，只在该命名空间登记，不获得契约键，不参与类别解析、WorkspaceCapabilityDefault 与 ContentReference，其 Tool 不能被 AgentVersion/SkillVersion 作为能力需求引用，不作服务读取边任一方，`model_call_mode=NONE`；零业务能力 binding 部署与生产 Catalog 不登记其 release。
- 同一 Tenant 或 Workspace 的同一能力类别同时只有一个 active ApplicationBinding。解析顺序固定：Workspace 级 binding 在该 Workspace 内覆盖 Tenant 级 binding，Workspace 未绑定该类别时解析到 Tenant 级 binding；两者都没有即该类别在该 Workspace 无实现。零业务能力 binding 时，平台核心实体、流程与 Workflow kind 全部可用（DD-87/88）。
- 类别内切换实现是「新建 binding、旧 binding 转 `DISABLED` 只读保留」，不是在旧 binding 上换 generation：新 binding 按 `COMPONENT_BINDING` 对账到 `ACTIVE` 后，旧 binding 经 `COMPONENT_DISABLE` 转 `DISABLED`，已开始的执行固定旧 binding/generation 到终态。旧 binding 下的 Resource/Asset 保留只读，只可 discover 元数据；指向旧 binding Resource 的 WorkspaceCapabilityDefault 清空待重新选择；以旧 Resource 或旧 Tool 为 target 的 DelegationScope 与 ToolBinding 失效，ToolBinding 按契约键重绑到新 binding 的 ToolDefinition，DelegationScope 由 grantor 以新 target 重新授予；历史 ContentReference（含 `mem/*` citation）保留原值，解析为不可用，不报成功或失败（DD-88）。
- PlatformProviderBinding 只能 pin `class=PLATFORM` 的 approved release，且 `platform_port_key` 必须与 Definition 一致；它属于 Platform Catalog scope，不建立业务 native scope、Resource 或 Asset。`REMOTE_SERVICE` 固定独立 service ref；`BUILD_BOUND_DRIVER|CORE_INTERNAL` 的 ref 必须出现在当前主体已编译 registry，否则拒绝 binding。每个 port 同时只有一个 active generation，新调用使用新 generation，已开始的 Action/Workflow 保持旧 generation。
- ApplicationBinding 只代表独立服务在 Kailo 的接入，不代表该服务自身运行或管理状态；停用只撤平台投影及平台调用，保留服务原生后台和独立业务。ApplicationBinding 必须 pin `class=APPLICATION` 的 approved release。`ACTIVE` 要求 native scope 已对账、七项治理投影与 Business Observability 已闭合；有 Web surface 时按其 delivery mode 校验呈现合同：module 校验 artifact digest，`NATIVE_PAGE` 校验批准的来源与 binding 页面地址，不下载或复制原生站点为平台 artifact。`REVOKED` release 拒绝新 binding/upgrade，并触发既有 binding fail-closed 停用，不静默切换到其他版本。
- `model_call_mode` 是 binding 在 release `allowed_model_call_modes[]` 内选定的模型调用方式：`PLATFORM_LLM_ROUTE` 由服务配置指向 AgentGateway `llm_route` 端点，平台计量；`SELF_MANAGED_MODEL` 由服务自管模型，经 Adapter Protocol 上报 usage，该上报是其 actual usage source，平台照常执行 Quota 与审计；不调用模型的实现为 `NONE`。`model_call_mode≠NONE` 的 binding，其 release 对所启用类别的 `meter` 必须为 `SUPPORTED`。切换 `model_call_mode` 是需要审批的 Governed Action。平台不向服务数据写入模型配置；trace 以标准 `traceparent`/operation 头关联，缺失时按 gateway identity 解析出的 binding scope 入账，只降低到 operation 的归因精度，不阻断 binding，也不免于计量。平台自有 Agent 的模型调用始终经 AgentGateway（DD-20/92）。
- release 的 `data_store_isolation` 声明该实现使用独立数据库实例（`DEDICATED_INSTANCE`）或至少独立 database（`DEDICATED_DATABASE`），并同时使用独立凭据与独立私有数据网络；外部托管（SaaS）实现声明 `VENDOR_MANAGED`，数据位于供应商环境、与平台及其他实现不共享存储，必须同时声明 `data_location` 并经平台管理员批准，其 adapter 运行体仍按 DD-94 使用独立凭据与独立私有数据网络；`data_location` 记录其声明的数据位置；`class=APPLICATION` release 缺失任一声明不得 `APPROVED`（2026-09-28 按 DD-93/94 修订）。禁止与平台核心或其他实现共用 schema 与跨库访问；Core 不持有任何业务能力服务的数据库凭据，组件状态目录不放在 Core/Worker 运行体内（DD-93）。
- `retain_on_tenant_delete=TRUE` 只在 release 对该 binding 启用的某个能力声明 `tenant_delete=RETAIN_ON_TENANT_DELETE` 时成立；全部启用能力都声明 `SUPPORTED` 时必须为 `FALSE`。每个 ApplicationBinding 的 native 删除是 Tenant 销毁的独立子流程（TenantDeleteSubprocess）；`TRUE` 的 binding 在 Tenant 删除时撤 binding、撤凭据、保留审计并登记待人工处置，不阻断平台 Tenant 状态机（DD-91）。
- release manifest 的 `secret_schema` 声明该服务每个密钥的类型、长度或格式、轮换类别、投递方式与是否需重启；Core 按通用 schema 校验并经 OpenBao 托管与投递，不内置任何产品的密钥语义。`DATA_KEY` 轮换后的已存密文重加密是该服务自己的数据平面职责，平台只按声明投递新版本；服务经 Adapter Protocol 的 `report_rekey` 回报重加密完成后，平台才记录结果并允许旧版本转 `REVOKED`；未回报或结果不明时旧版本保持 `SUPERSEDED`，该 binding 进入对账并计入度量，直到回报或平台管理员经审计处置（DD-93）。
- Binding 的 `normalized_config` 只保存按该 release 固定 schema 规范化后的非敏感值，`config_digest` 参与 projection generation；credential、provider key、PAT 与 cookie key 只能成为具名 `SecretRef`。Upgrade 时新 schema 不能验证旧 config 或 SecretRef audience 就保持旧 generation 或 fail closed，不在 Core 执行 manifest 提供的任意迁移代码。
- ComponentRuntimeProjection 是 PlatformProviderBinding 或 ApplicationBinding 的可执行快照。升级先生成新 `PENDING` generation，校验 port/adapter、native scope、Action/Tool/route 与 Web artifact 后原子切换 `active_projection_generation`；新调用只取新 generation，已开始的 ActionExecution/Workflow 固定旧 release/generation。回滚同样生成新 generation，不改写历史执行。
- 普通 Application Component 至少声明一个 ResourceType。能力型 Application Component 只有在“不产生自己的长期 ownable 数据、所有 action 都指向 `target_resource_type_keys[]` 中既有类型、短期 session 不升格为 Resource”三个条件同时成立时，才允许 `resource_type_definitions=[]`；是否适用由 release manifest 声明并在准入时校验。
- 前端交付与 native 项目是否前后端分离无绑定关系。`HOST_NATIVE` 使用随 Component Host 发布的通用资源/表单/任务视图；`REMOTE_MODULE` 的 source URL只在 Catalog 登记时取件，运行时从 digest 固定的同源 `served_entry_path` 加载；`SOURCE_BOUND_PROTOCOL` 只以 release 固定的 editor origin 与 DocumentLaunchDescriptor schema 版本 launch（DD-95）；`NONE` 不提供组件页面。`NATIVE_PAGE` 嵌入独立服务已有的管理页面，具体入口由 binding 配置，origin 必须在 release 的 `native_page_origins[]` 与部署许可集合内；不向主窗口注入第三方脚本，不共享平台管理凭据。独立服务保留自己的访问入口，不要求拆前后端或重写后台（DD-87、`07` §4.6）。
- `REMOTE_MODULE` 与宿主同窗口运行，属于平台管理员批准的宿主信任代码，不是权限或故障隔离边界。它只能通过 versioned Host API 登记 `MANAGEMENT_PAGE / RESOURCE_VIEW / CHAT_ATTACHMENT_ACTION` 三个一期扩展槽；BFF 对每次 query/action 仍按当前 session fresh准入，模块不能取得 native management credential、ActionToken signing key、SpiceDB/OpenMeter/Temporal/AgentGateway admin credential 或完整宿主 store。
- `SOURCE_BOUND_PROTOCOL` 只允许固定 editor origin（`editor_origins[]`）与固定 DocumentLaunchDescriptor schema 版本（`launch_descriptor_schema_version`）的协议 surface，由 release manifest 声明，来源证据按 `admission_path` 取证（DD-94(1)）；其他 delivery mode 的 `editor_origins[]` 为空。launch 请求携带 Buzz 已解析的 theme/locale，descriptor 由目标 ContentReference 所属 ApplicationBinding 的 adapter 生成（实现私有参数映射在 adapter 内），Core 只校验其 `editor_origin` 属于该 release 的 `editor_origins[]` 且等于该 binding 固定的实例 origin（release 以 host 通配登记时也逐 binding 精确比对）、`action_url` 的 origin 等于 `editor_origin`、字段均为字符串且未过期后原样下发；editor origin 许可集合是部署级配置，等于平台管理员批准的 release 所登记 `editor_origins[]` 的并集，Tenant 与 binding 不能扩大；BFF 在运行时持有该集合：Web 的有效集合是它与 Web 由部署配置投影的已生效集合之交集，Desktop 以独立 editor 窗口承载编辑器，其有效集合就是运行时下发的许可集合，BFF 据此决定各端编辑入口（2026-09-28 按 DD-95/104 修订）。内置参考实现的实例见 `18`。`PLATFORM_PORT_CLIENT` 只允许 `class=PLATFORM` 且绑定 Core 已知 port；`EMBEDDED_DRIVER` 只允许源码本身提供 library runtime且没有外部管理 API，业务能力实现不得使用（DD-87）；`PROTOCOL_PEER` 只允许双方固定协议已相交，且只用于经 AgentGateway 的 MCP Tool 传输；需要上游实现 Adapter Protocol、接收 ActionToken、承载 ProtocolSession 或提供该协议 revision 查询的能力（含在线编辑与服务读取边来源）必须用 `REMOTE_ADAPTER`。`PROTOCOL_PEER` 仍接受 Gateway 双相 PEP/Core 完整统一准入，不因平台侧 Governed Action 而要求原生 peer 接受 ActionToken 或 Adapter API（DD-12/58/94/103、`12` §4）；其他 Application Component 统一使用独立 `REMOTE_ADAPTER`，禁止上传本机 executable 给 Core 启动。
- 每个 FrontendDelivery 必须明确 FrontendPresentationContract；`NATIVE_PAGE` 可声明 `NONE`，表示保留独立页面呈现而非没有页面，不要求平台语言 catalog 或主题 token。既有线协议值 `BROWSER_RESOLVED` 表示宿主解析最终语言，按本节的设备偏好/默认中文规则解析，不再从浏览器首选语言取默认值；保留该值避免无必要的协议迁移。Host-native 固定 `BUZZ_NATIVE + theme LIVE + locale BROWSER_RESOLVED`；remote module 固定 `HOST_API_REMOTE + theme LIVE + locale BROWSER_RESOLVED`并同时提供 `en/zh-CN` namespaced messages；`SOURCE_BOUND_PROTOCOL` surface 固定 `LAUNCH_MAPPED + theme/locale NEXT_LAUNCH`。语言 catalog、主题 token 与错误 code 映射的完整性约束作用于 Kailo 自有页面与同窗口 module，不作为独立原生页面接入的前提。
- `incremental_contracts[]` 至少含一个 `NATIVE_INTERNAL` 或 `VERSIONED_PUBLICATION` 合同，只描述该组件自身的增量与发布语义；不存在跨组件的增量角色或引擎（DD-89）。`NATIVE_INTERNAL` 的派生、状态与删除收敛全在实现内部；`VERSIONED_PUBLICATION` 以 `VERSIONED_REPUBLISH` 整体换代，发布与下线的收敛由 `ComponentTaskWorkflow(kind=CAPABILITY_VERSION_PUBLISH)` 执行，不原地改写已发布版本（DD-90）。
- `transfer_formats[]` 默认为空，表示该 ResourceType 不支持跨 Tenant 转移。每个条目必须把一个固定 format/version/digest rule 同时绑定已注册的 `RESOURCE_EXPORT` 和 `RESOURCE_IMPORT` ActionDefinition；缺任一端时不能注册为可转移格式。平台核心自有 ResourceType（Agent、Skill、Tool、`llm_route` 等）必须登记由 `ComponentTaskWorkflow(kind=TENANT_LIFECYCLE)` 按平台核心销毁链执行的删除，不适用保留；其销毁处理器与该 ResourceTypeDefinition 在同一构建中登记，缺处理器的 ResourceTypeDefinition 不得 active（DD-99）。`tenant_delete_action_key=NONE` 只允许业务能力实现的 ResourceType，表示其 native 对象不能由该 Workflow 证明删除，按其 ApplicationBinding 的 `retain_on_tenant_delete=TRUE` 处理；`NONE` 与保留声明都不适用于平台核心 ResourceType（DD-91）。
- 当前固定基线下，全部首批 ResourceType 的 `transfer_formats=[]`，因为 `02` 没有登记成对 TransferFormat SOURCE_SEAM；内置业务能力参考实现的 ResourceType 另为 `tenant_delete_action_key=NONE`，其 binding 按 DD-91 在准入时声明 `retain_on_tenant_delete`，GAP-LCM-01 只阻断实现自身的删除能力声明，不阻断平台 Tenant 销毁。平台核心 ResourceType 的删除由平台核心销毁链登记，不属于此项。这是当前 Catalog 的确定注册结果；不将“未注册”改写成“上游全项目永久不具备”。
- 平台不编排跨服务数据同步，不登记跨组件数据关系或同步状态（DD-89）。一个业务能力服务需要另一服务的数据时只有两条路：(a) 接收方在自己的管理面配置数据源连接器，经 Governed Action（含审批）为接收方 binding 的 ServicePrincipal 写入来源 Resource 的 `reader` relationship；授予要求发起者对来源 Resource 持有 `share`、对接收方 Resource 持有 `update`。接收方经来源方公开的能力契约自行拉取，增量、状态、去重与删除收敛全在接收方内部，Core 不感知；撤销该 relationship 即收回读取权；(b) 人或 Agent 经两边各自暴露的 Tool 显式读写，每步都是 Governed Action。
- 路径 (a) 的每批拉取经**服务读取边**完成：接收方 binding 经 Adapter Protocol `request_read_grant` 向 Core 申请读取来源 Resource；Core 以该 binding 的 ServicePrincipal 为 SERVICE actor 做 Governed Action 准入（§2 SERVICE scope guard、对来源 Resource 的 fresh `read` Check、Quota），为该批建立 operation，签发短期 ActionToken（audience 为来源实现的契约端点，target 为来源 Resource，携带该批 operation）；来源实现的 PEP 按通用 ActionToken 规则校验并再做 fresh `read` Check。该批的 AuditEvent、UsageEvent 与观测都归属这一 operation。接收方不持有来源实现的 native 凭据；平台投递给接收方的 SecretRef 只是其自身 binding 的服务凭据，用于认证 Adapter Protocol，不能直接访问来源。经平台签发令牌访问来源契约端点不是服务间数据面直连（DD-89）。业务能力实现的 `REMOTE_ADAPTER` 运行体一律部署在平台运维域内，外部与 SaaS 实现也不例外，其服务端点只是 adapter 的上游；因此来源方 PEP 即来源实现的 adapter，ActionToken 验签公钥与 `secret_schema` 声明的凭据统一经 OpenBao Agent 投递到 adapter 运行体。以 `PROTOCOL_PEER` 接入的实现不接收 ActionToken，不能作为服务读取边的来源方（2026-09-28 按 DD-94 修订）。
- ComponentProjection 只记录平台 Resource 到平台核心运行时的受控投影，`target_platform_runtime` 只取 `CODEX` 或 `AGENTGATEWAY`；例如 `llm_route` 的 AgentGateway ConfigResource 是原生权威，Codex provider 配置是其投影。平台不向任何业务能力服务写入数据或配置投影；业务能力服务只以 `model_call_mode=PLATFORM_LLM_ROUTE` 在自身配置中指向 AgentGateway `llm_route` 端点（DD-92）。
- Core 不含数据查询模型实体。数据查询的可查询模型由 `DATA_QUERY` 实现按能力契约注册为 Resource，具有 HUMAN owner。只有在 release 中声明 `versioned_model=SUPPORTED` 的实现才把发布版本注册为不可变 Asset、实现 `data_query.publish_version` 条件键并走 `VERSIONED_PUBLICATION` 合同，发布新版本不改写旧版本或旧查询 evidence；未声明者没有版本 Asset，也不进入 `CAPABILITY_VERSION_PUBLISH`（2026-09-28 按 DD-88/90 修订）。
- IngressCheckpoint 只保存外部持久流的恢复游标。重复读取仍由源稳定 ID 的业务唯一约束去重，不能把游标当成 exactly-once 保证。
- `llm_route` 是 `PLATFORM` ResourceType：具有 HUMAN owner、可选 home Workspace、`discover/execute/manage/audit` 权限和 AgentGateway native ID；组件不得把上游 URL/API key 另建为业务 Asset。
- WorkspaceCapabilityDefault 可空，每个 `(workspace_id, category)` 至多一条，只选择该能力类别在该 Workspace 的默认 Resource，不复制 native 结构。`resource_id` 必须同 Tenant，其 `type_key` 属于该类别的 ResourceType 族，并指向按本节解析顺序（Workspace 级 binding 优先，其次 Tenant 级）得到的该类别 active ApplicationBinding。所指 binding 转 `DISABLED` 或被 Workspace 级 binding 覆盖时该条清空，待重新选择。它不是 Workspace `ACTIVE` 的前提；缺失时平台核心能力不受影响（DD-88/90）。
- ContentReference 是审批附件、任务产物、聊天引用与 citation 指向业务内容的唯一平台形态；没有文件能力 binding 时退回 Relay media。`native_object_ref` 与 `native_revision` 的语义由目标 ResourceType 所属 CapabilityContract 的 `content_reference_semantics` 定义，Core 只保存、比较并纳入 parameter hash，不解释其内部结构。ContentReference 必须解析到同 Tenant、同 Workspace 可访问的 Resource 和确定 `native_revision`；`asset_id` 非空时该 Asset 是细粒度授权目标，否则授权目标是父 Resource。所属 binding 已 `DISABLED` 时 ContentReference 保留原值，解析结果为不可用，不报成功或失败（DD-88）。native 子项默认只是 Resource 的 native child，不另建 ResourceType。聊天 event、审批、任务与 citation 均不得携带临时下载 URL、协议会话 token 或 launch config（DD-90）。
- ProtocolSession 是 `execution_mode=PROTOCOL` 动作的短期记录，不拥有 owner；owner 仍取 `target` 授权目标 Resource/Asset 的 active HUMAN。`kind` 取能力契约登记的协议会话类型。请求 `VIEW` 检查 `read`，请求 `EDIT` 检查 `update`；EDIT admission 还要求实现按能力契约 fresh 查证 `target.native_revision` 为当前 head，历史 revision 只能 VIEW。实现的协议 PEP 始终按 `base_revision` 提供内容，不静默换 latest；EDIT 只写同一 `native_object_ref`。`native_session_ref` 与 `token_revocation_key` 绑定同一 session。`SAVED` 只有实现按能力契约返回写入已被接受且确认 `result_revision` 时成立；写入结果不明进入 `UNKNOWN`，由 `ComponentTaskWorkflow(kind=PROTOCOL_SESSION_RECONCILE)` 以实现登记的 revision 查询（Adapter Protocol `query_revision`）对账。在线编辑（`kind=file_storage.edit_session`）的 `target` 只能是该 ProtocolSession 所属 ApplicationBinding 自己实现的 `FILE_STORAGE` ContentReference；平台不在编辑器与文件存储之间建立数据通道（DD-90/103）。在线编辑的 ProtocolSession admission 成功后，BFF 返回目标 ContentReference 所属 ApplicationBinding 的 adapter 生成、经 Core 校验的 DocumentLaunchDescriptor；descriptor 只用于本次 launch，不持久化进 ProtocolSession 之外的任何事实，也不进入聊天、审批、任务或 citation（DD-95）。
- ProtocolSession 状态转移固定：`ADMITTED → OPENING → OPEN`；`OPEN → DIRTY`（实现报告首次写入迹象）；`SAVED → DIRTY`（实现报告新的实际写入迹象）；`DIRTY → SAVED | CONFLICT | UNKNOWN`；`OPEN|DIRTY|SAVED → READ_ONLY`（降级只读）；任一非终态 `→ REVOKED`（撤权或 token 吊销）、`→ FAILED`（确定失败）；`SAVED|READ_ONLY|OPEN → CLOSED`（正常关闭且无未确认写入）。终态为 `CLOSED/EXPIRED/REVOKED/FAILED`，`UNKNOWN` 只由对账转为 `SAVED/CONFLICT/FAILED`。未在 `expires_at` 前到达终态时：没有未确认写入的 `ADMITTED/OPENING/OPEN/READ_ONLY` 会话，以及已确定 `SAVED` 且之后无新写入迹象的会话，转 `EXPIRED`；`DIRTY` 或任何仍有未确认写入回报的会话转 `UNKNOWN` 并按 `query_revision` 对账到 `SAVED`（回填 `result_revision`）、`CONFLICT` 或 `FAILED`，查不到确定结果时保持 `UNKNOWN` 并告警。历史上曾写入不等于当前结果不明；重复保存不改写冻结 `base_revision`，后续写入沿实现的原生 marker 链使用已核验的 `result_revision` 对应事实，不静默改用 latest（DD-90，文件存储参考实现见 `18` §5.4）。
- 同一 ProtocolSession 首次进入 `UNKNOWN` 时，原 ActionExecution 只启动一条 `PROTOCOL_SESSION_RECONCILE` Workflow，沿该 Session 生命周期继续运行；`SAVED` 只结束本轮 revision 对账，不终结 Workflow，不建立新的 ActionExecution、WorkflowRef 或 workflow ID。初始 session ID/version、binding refs、base revision 与 correlation 保持冻结；后续轮次从原 Session 已持久化的 version、correlation 和写入 evidence 取证，经 Activity 结果写入 Temporal history 后固定本轮查询目标，再查证相同引用。Session 到达 `CLOSED/EXPIRED/REVOKED/FAILED` 且没有未确认写入时才允许 Workflow 终结；正常 TTL 处理继续生效，不以等待新写入延长 Session 或 token（DD-90，`06` §6）。
- launch theme/locale 是该 session 的稳定快照，不因宿主切换而静默重载。协议细节属于实现该能力的组件，内置参考实现见 `18`（DD-90）。

- 每个治理入口都有 `operation_id` 和 ActionDecision。
- 组件动作在准入时从 active ComponentRuntimeProjection 固定 `binding_kind + binding_id + release_id + generation`；dispatch、Workflow、ExternalExecution、UsageEvent 与 AuditEvent 沿用同一快照。运行中 upgrade/rollback 不改变该动作解析到的 schema、adapter、meter 或 redaction。

- ActionExecution 只保存门禁/调度状态；Temporal 运行终态只在 Temporal/TaskProjection。
- 任务取消/重跑的控制 ActionDefinition 以原 `ActionExecution` 为 `target_type=ACTION_EXECUTION`，控制 ActionExecution 的 `target_id` 固定为原动作 ID；它不是新的 SpiceDB object type。Core 从原动作及其确切 ActionDefinition 解析原 target、Tenant/Workspace 与 permission object，控制定义必须与原动作的 Tenant/Workspace rule、permission/object type 一致。只有原动作的 active HUMAN 发起者可经 BFF 控制本人任务，且必须在准入和派发前重新做 scope 与 FullyConsistent Check；缺失或不一致即拒绝。控制动作与原动作各有独立的 operation、准入、批准、调度和审计事实；原动作的 WorkflowRef 与 TaskProjection 不受控制动作直接改写（DD-84）。
- 取消控制动作的 `cancel_first_run_id` 在第一次向 Temporal 发请求前与 `dispatch_state=UNKNOWN` 同事务冻结，之后不可改；它只给该控制动作定位原 Workflow 的 execution chain，不是原任务终态。`UNKNOWN` 对账先查询固定链的 history：匹配控制动作 ID 的取消事件可使控制动作转 `DISPATCHED`；缺事件不证明未发出，只有原执行仍 OPEN 且首次 run ID 未变时才能以同一控制 ID 重发。原执行已关闭又无肯定证据时保持 `UNKNOWN`，由对账年龄告警与 RB-07 接手（DD-84、SF-TMP-11）。
- TenantLifecycleSnapshot 是 Tenant 销毁 Workflow 的不可变 Core 清单，只保存 Resource/Asset/owner/binding ID+version 与 digest，不保存业务正文。Tenant 进入 `SUSPENDING` 后禁止创建新 Resource/Asset，snapshot 在 Tenant delete 准入时从已停写的 `SUSPENDED` Tenant 冻结，删除子流程随之建立，暂停本身不冻结 snapshot；Workflow 恢复时以 snapshot 和 ExternalExecution refs 继续，不重新从可变列表计算已批准对象。
- TenantDeleteSubprocess 是 Tenant 销毁中每个删除子流程的记录，随 snapshot 冻结时逐一建立：平台核心销毁链一条（`subject=PLATFORM_CORE`、`mode=PLATFORM_CORE_CHAIN`），snapshot 中每个 ApplicationBinding 一条（`mode` 取自该 binding 的 `retain_on_tenant_delete`：`FALSE` 为 `NATIVE_DELETE`，`TRUE` 为 `RETAIN_ON_TENANT_DELETE`）。`NATIVE_DELETE` 与 `PLATFORM_CORE_CHAIN` 走 `PENDING → RUNNING → DELETED`，失败或结果不明进入 `UNKNOWN` 并按 fail closed 持续对账；`RETAIN_ON_TENANT_DELETE` 在撤 binding、撤凭据并保留审计后进入 `RETAINED_DECLARED`，其 native 数据登记为待人工处置项。`NATIVE_DELETE` 子流程停在 `UNKNOWN` 时，只有该业务 Tenant 的 admin 经 owner 审批的 Governed Action 可把它处置为 `RETAINED_BY_DECISION`，`disposition_action_execution_id` 记录该动作，处置与理由进入审计；该处置不改写 binding 的 `retain_on_tenant_delete` 或 release 声明，也不适用于 `PLATFORM_CORE_CHAIN`。终态为 `DELETED/RETAINED_DECLARED/RETAINED_BY_DECISION`；Tenant 只在全部子流程到达终态后进入 `DELETED`（DD-91）。
- `tenant.delete` 的注册按平台事实增量成立（DD-99）：注册时已存在的每个平台事实类别（平台核心 ResourceType 与 Core 事实、SpiceDB、Buzz Community 与 roster、OpenBao Tenant namespace、OpenMeter Customer 数据、AgentGateway 投影等平台存储面）都有经验证的销毁处理器；之后新增的类别必须与其处理器同一构建登记。snapshot 冻结时记录其中出现的平台事实类别，任一类别在当前构建没有处理器时 delete 准入拒绝、Tenant 保持 `SUSPENDED`；准入后才出现缺失时 `PLATFORM_CORE_CHAIN` 停在 `UNKNOWN` 并 fail closed，Tenant 不进入 `DELETED`。
- `PLATFORM_CORE_CHAIN` 中「Buzz Community 与 roster」类别的处理器以上游整 Community 删除引擎真实删除（DD-109、SF-BUZ-46），不以 Community 或 Channel 归档、DELETE_GROUP、NIP-09 代替：处理器在 `irreversible_dispatch_started=TRUE` 持久化之后才提交删除请求，只有上游请求到达 `retention_pending`、且 operator 回读不再列出该 Community 时该类别才算完成；`blocked`、不可达或结果不明时 `PLATFORM_CORE_CHAIN` 停在 `UNKNOWN`。上游不删除的 Community 墓碑行、删除证据与未物理回收的共享 CAS 字节作为平台保留项登记在完成审计中，不改变子流程状态集合，也不适用 `RETAINED_BY_DECISION`。
- 业务能力动作的 `capability_contract_key` 必填，且 `action_key` 等于该契约键；`component_type_key` 只记实现来源。ToolDefinition、DelegationScope、ApprovalPolicy 与 AgentVersion 能力需求对业务能力动作只引用契约键，因此在类别内切换实现不改变 `action_key` 与审批策略的寻址；以旧 binding 的 Resource 或 Tool 为 target 的 DelegationScope 仍随旧 binding `DISABLED` 失效（§3、§6）。每次准入固定实际解析到的 binding、release 与 generation。平台核心动作的 `capability_contract_key=NONE`（DD-88）。示例组件的组件自有动作同样 `capability_contract_key=NONE`，`action_key` 以 `component.<component_type_key>.` 开头，`capacity_policy=NATIVE`（DD-101）。
- 业务能力动作的 `capacity_policy` 固定为 `NATIVE`；`PLATFORM_SLOT` 只用于平台自有 Agent runner。
- 每个 ActionDefinition 必须显式给出 Tenant rule、Workspace rule、permission、execution、approval、capacity、quota/meter、result exposure、audit schema 和 observability policy，缺任一项不得 active。progress/usage/cost 可显式 `NONE`，但 correlation、terminal source 与 redaction 不得缺失。`GATEWAY_DURABLE_USAGE` 只有 SS-AGW-USAGE 已闭合且写入获得持久确认时可登记；原始 AgentGateway request log 只能作为 native observability evidence。
- `TENANT_ONLY` 只用于 Tenant 自身、TenantMembership 和 Tenant 级管理意图；`WORKSPACE_REQUIRED` 使用当前 active Workspace；`TARGET_HOME_WORKSPACE` 还要求执行 Workspace 等于目标 home Workspace；`DECLARED_WORKSPACE` 用于 ApplicationBinding 动作与 `resource.create`：取 target binding 的 `workspace_id` 或创建参数 `home_workspace_id`（进入 parameter hash），非 NONE 时执行 Workspace 必须等于它并以该 Workspace 为 permission 对象，NONE 时以 Tenant 为 permission 对象（DD-100(2)）；`INHERIT_PARENT` 只用于同一 operation 的内部 child action，并复制父 Workspace（含 NONE）。任何规则都要校验 target/binding 与 execution Tenant 相同；唯一例外是 DD-96 的业务 Tenant 暂停与恢复：它以 `tenant_rule=SESSION_TENANT` 在 Platform Catalog Tenant 中执行、`target_type=TENANT` 指向业务 Tenant，业务 Tenant 一侧由其自己的 `TENANT_LIFECYCLE` operation、WorkflowRef 与审计承接，两侧不共享 operation。Tenant-level Resource 被 Workspace Agent消费时，child action 使用 `INHERIT_PARENT`，不因 `home_workspace_id=NONE` 丢弃 Workspace（DD-54）。

## 5. 固定 SpiceDB schema

平台 schema 只含 `principal/tenant/workspace/resource/asset`。组件注册不新增 object type。

```zed

  relation member: principal
  relation admin: principal
  relation creator: principal
  relation auditor: principal
  permission discover = member + admin
  permission create = creator + admin
  permission manage = admin
  permission audit = auditor + admin
}
```

规则：

- 规范 permission 只是 `discover/consume/read/export/create/update/delete/share/manage/execute/approve/delegate/transfer_owner/audit`。Asset 不有 `create`，创建检查父 Resource 的 `create`。
- 尚不存在的顶层 Resource 无法成为 Check 对象；创建顶层 Resource 检查所在 Workspace 的 `create`，Tenant-level Resource 检查 Tenant `create`，创建后再写 Resource owner 与其他 relationships。
- `consume` 只允许 Agent 返回收窄 answer、citation、aggregate 或 derived Asset；原文、文件下载、raw SQL 行和模型定义需要 `read/export`。
- RoleTemplate 只是 Platform Core Catalog 中从角色名到上述关系写入集合的版本化模板，不是第二授权引擎或第二套 assignment 表。角色的授予与撤销、有效 Tenant admin 不得为空，以及部署引导只能 0→1 写入首位 Tenant admin，按 DD-82。
- Resource/Asset owner 是 Core 业务事实，SpiceDB owner 是授权投影；未对账时 owner 审批和 owner-only 高风险动作拒绝。
- WriteRelationships 返回的 ZedToken 传入同一因果链的 `AtLeastAsFresh`检查；无因果 token 且即将发生不可逆外部副作用时使用 `FullyConsistent`。列表可使用低延迟 consistency，但不可代替最终 admission Check。
- `LookupResources` 只用于有明确 resource type、permission、有限 `OptionalLimit` 与 cursor 的发现路径；limit 不得超过服务端 `MaxLookupResourcesLimit`，cursor 只在原请求与原授权 revision 内继续，不跨 revision 复用。Tenant 管理页不以管理员的 `tenant->manage` 展开全 Tenant stream，而先对 Core 自有索引分页，再用 `CheckBulkPermissions` 过滤当前页；最终动作仍单独 fresh Check（SF-SPZ-05）。

- Agent 允许是 `AgentPrincipal permission ∩ grantor 当前可委托 permission ∩ DelegationScope ∩ Agent/Tool binding ∩ ResultExposurePolicy`。
- DelegationGrant、Installation、AgentPrincipal 和 Workspace 必须同 Tenant/Workspace，grantor 必须是该 Tenant 的 active HUMAN。DelegationScope 不含通配：`action_key` 必填；操作既有对象时 `target_id` 必填且 `create_workspace_id=NONE`，创建动作时 `target_id=NONE` 且 `create_workspace_id` 必须等于 Grant 的 Workspace。Tool 存在时 `tool_resource_id` 也固定。任何不满足这一互斥结构的 scope 拒绝持久化。`target_id` 或 `tool_resource_id` 指向的 Resource 所属 ApplicationBinding 转 `DISABLED` 时，该 DelegationScope 失效并拒绝新 dispatch；它不自动改指新 binding 的对象，需由 grantor 以新 target 重新授予（DD-88）。
- `max_uses` 在真实首次 dispatch 前以 `(delegation_id, operation_id)` 唯一 DelegationUse 原子消费；同 operation retry 不重复计数。达到上限、过期或 `REVOKING` 后新 dispatch 立即拒绝，已发生的 DelegationUse/Audit 保留。
- ResultExposurePolicy 是最大暴露边界：`CONSUME_ONLY` 只允许 answer/citation/aggregate/derived Asset，`READ` 仍要求目标 `read`，`EXPORT` 仍要求目标 `export`；三者还与 ToolDefinition `output_schema_hash` 和 ActionDefinition redaction 求交，不能扩大 permission。
- ActionTokenClaims 的两项 ResultExposurePolicy 引用只在已登记的确切 ActionDefinition 固定 `ResultExposure=NONE`、且结果仅为平台 ID 与状态时成对为 `NONE`，不为此建立 `NONE` 或伪 `CONSUME_ONLY` 策略。这里的结果限定向用户或 Agent 暴露的管理动作结果；Adapter Protocol 用于治理的结构化非正文元数据（scope 映射、native 引用/revision、能力与终态证据）仍按既有 schema 核验，不因 `NONE` 禁止，但不得包含业务正文或检索结果。其余动作两项均必填并核验同一有效策略版本；只缺一项、未知 exposure、由调用方自报 `NONE` 或以管理父动作的 `NONE` 代替业务子动作的内容策略均拒绝。`NONE` 不允许返回业务内容，也不省略 ActionToken 的身份、scope、action/version、target、operation、参数 hash、签名及 fresh 授权校验。
- ActionTokenClaims 只用于跨网络/进程边界，不持久化为授权权威。接收 PEP 必须校验签名、issuer、精确 audience、短 expiry、scope/actor/delegation/action/target/operation，重新规范化参数并比对 hash，再以 `authorization_min_zed_token` 至少同样新鲜或 `FullyConsistent` 做 scope/permission/delegation fresh Check。ActionToken 固定使用非对称签名（`ES256` 或 `EdDSA`，算法白名单固定，拒绝 `none` 与 HMAC 家族）：私钥以 KV v2 版本托管于 OpenBao `platform/` namespace、只由 Core 读取并只在内存签名；公钥集合由 Core 导出为 JWKS，经 OpenBao Agent template 渲染成文件供 AgentGateway 与业务能力实现的 adapter 运行体（Core→adapter 与服务读取边的接收 PEP，均在平台运维域内，DD-94）以文件引用加载（文件被 watch，轮换无需重启），不另设公钥分发通道。`kid` 取该 KV v2 版本号；轮换用重叠窗口——新 `kid` 先进 JWKS 并确认网关与 adapter 已 reload，再切换签名密钥，旧 `kid` 保留不少于 ActionToken 最大有效期后移除。对称密钥方案不可行：验签方在 AgentGateway 与 adapter 进程内，"只由 Core 读取"与"PEP 校验签名"无法同时成立（DD-49/70/71/94）。
- Approval 不能补足缺失的 permission、Delegation、scope、binding、capacity 或 quota。
- 一个 ActionExecution 最多绑定一个 ApprovalWorkflow。Workflow 中间步需要独立批准时，创建 child ActionExecution 和 child ApprovalWorkflow。
- ApprovalProjection 只由 Temporal history 投影，不接受 CRUD 改状态。`affected_owner_refs` 在请求时从 Core Resource/Asset 的 `owner_principal_id + version` 与已对账 SpiceDB owner relationship 冻结；两者不一致时请求不启动。`ALL_AFFECTED_OWNERS` 要求列表中每个不同 active HUMAN owner 各有 APPROVE，`TARGET_OWNER` 要求目标 active HUMAN owner APPROVE；`role_requirements` 的每项分别满足其 `min_distinct`。同一 HUMAN 在多个要求中可同时计数，但只产生一个决定。
- approver 必须是 active HUMAN。每个 approver 对同一 workflow 只能写一个不可变决定；决定以 Temporal Update 提交（Update ID = `<approval_workflow_id>:<approver_principal_id>`，Server 侧去重）：Validator 只做确定性状态判断（已终结、重复/冲突决定、过期、approver 在冻结名单内），权限类检查由 handler 体内的 Activity 完成（SF-TSDK-09）；重复同值 Update 幂等，冲突值拒绝。任何通过当前 selector/owner 校验的 `DENY` 使 Workflow 进入 `DENIED`。Agent、SERVICE、过期/失权 Human 的 Update 不形成决定。批准后的主动作只执行一次，进入 `CONSUMED` 后不能复用（DD-47）。
- WorkflowRef 在调用 Temporal Start 前持久化，`workflow_id` 对 ActionExecution 唯一；Start 响应不明时保持 `PENDING_START|UNKNOWN` 并按同一 ID Describe/History，不生成第二个 ID。`run_id` 只从 Temporal observation 回填。TaskProjection 只由 Temporal/history、ExternalExecution 和引用事实生成，控制命令不能直接改 projection（DD-48）。
- Kailo HUMAN 发起的 APPLICATION 能力契约动作，确实在同请求完成且无 native task、无需 ExternalExecution 对账时，沿原 `SYNC` ActionExecution/audit；需要 native task 或 ExternalExecution 对账时，固定 `execution_mode=TEMPORAL`、`workflow_type=ComponentTaskWorkflow`、`kind=COMPONENT_ACTION`。它复用原 ActionExecution、WorkflowRef、ExternalExecution 与 TaskProjection，不新增业务实体或执行权威。Agent 工具动作仍归原 AgentTaskWorkflow，不为同一工具执行再建一个组件动作 Workflow。
- ExternalExecution 必须和 Workflow/ActionExecution 的 binding ref 一致；ApplicationBinding 调用还必须同 Tenant/Workspace。binding version 与 request digest 在首次 dispatch 前冻结。每个真实副作用先写稳定 idempotency key；超时且没有 native ID 时进入 `UNKNOWN`，仅按该 ActionDefinition 已登记的 native query/dedupe rule 对账。callback 只能用 ExternalExecution ID 或已绑定 native ID 定位 scope，callback payload 的 Tenant/Workspace 不具权威性。

- `RuntimeProfile` 是随平台发布的 Catalog 合同，不是用户 Resource。第一期只定义 `SERVER_CODEX`；其源码投影接缝成立，AgentTaskWorkflow 与凭据链按 DD-69/70/71 定义；二者实现并对账前不能标记运行 active。`LOCAL_ACP/REMOTE_PROVIDER` 只保留可识别类型，`web_availability=DISABLED`，不得被 Installation 选择。
- `AgentRuntimeProjection` 是静态运行投影，不是授权权威。其字段来自 `AgentVersion requested ∩ Workspace/Channel/Tool/Skill/LLM bindings ∩ AgentPrincipal permission ∩ Gateway projection ∩ RuntimeProfile capability`；任一层只能收窄，不能放宽。Delegation、Approval、Capacity 与 Quota 属于具体 Invocation/ActionDecision 的动态准入，不写入 projection config hash。
- 固定 reason code 为 `NOT_BOUND / NO_PROVIDER / NO_PERMISSION / NO_DELEGATION / WAITING_APPROVAL / QUOTA_BLOCKED / CAPACITY_BLOCKED / PROJECTION_FAILED / RUNTIME_NOT_READY / NOT_AVAILABLE_ON_WEB / NOT_SUPPORTED_BY_RUNTIME / DISABLED`。管理页按字段展示 requested、effective、source 和 reason；不以“配置未生效”笼统代替确定原因。
- 工具来源分两类（DD-92）。`PLATFORM_NATIVE` 工具（记忆、Buzz 消息、任务、审批等）由 Core 原生提供，`capability_contract_key=NONE`，不依赖任何 ApplicationBinding；AgentVersion 的 `declared_tool_resource_ids[]` 只引用此类工具。`APPLICATION` 工具由业务能力实现按契约登记，`capability_contract_key` 必填，经 MCP 与 AgentGateway ExtMcp PEP 调用；AgentVersion 只以 `capability_requirements[]` 声明契约键与版本，不引用具体实现的 Tool Resource。
- Installation 在 Workspace 内把每个能力需求解析为一条 ToolBinding：`tool_resource_id` 指向该类别 active ApplicationBinding 所登记、契约键与版本相符的 ToolDefinition，binding 按 §3 的顺序解析——该 Workspace 的 Workspace 级 binding 优先，其次 Tenant 级 binding。没有 active 实现时 `tool_resource_id=NONE`，该工具 effective 为 `NO_PROVIDER`，Installation 仍可 `ACTIVE`。类别内切换实现时，指向旧 binding ToolDefinition 的 ToolBinding 随旧 binding `DISABLED` 失效，再按契约键重绑到新 binding 的 ToolDefinition 并生成新的 AgentRuntimeProjection generation；已开始的 Invocation 固定旧 generation，AgentVersion 不重发（DD-88/92）。
- SkillVersion 只提供指令和能力需求声明（契约键与版本，DD-92），不引用任何具体实现的 Tool Resource。能力需求不能创建 ToolBinding、Delegation 或 Resource permission；Installation 在 Workspace 内把需求解析到 active 实现的 Tool，缺实现时 skill 的有效状态为 `NO_PROVIDER`，缺授权时为 `NOT_BOUND/NO_PERMISSION`。
- 配置升级先生成新的 PENDING projection，验证 Gateway、Skill root 与 runtime 能力后切 ACTIVE。已开始的 Invocation 固定旧 version/generation 并自然结束；新触发只取新 ACTIVE generation。授权撤销不是配置升级，按 `10` 立即阻止后续副作用并终止已知旧连接。
- rollback 与 upgrade 使用同一动作，只把 Installation 指回一个仍可用的旧 PUBLISHED version，并生成新的 projection generation；历史 Invocation/Audit 不改写。
- ToolBinding 与 ChannelAgentBinding 都是 Installation 的受控子配置，继承 Installation Resource 的 HUMAN owner；它们只控制可见性/触发，不授予业务 Resource permission。
- AgentMemoryBinding 是 Installation Resource 的一对一 native child binding，不是新 Resource/Asset。`agent_buzz_identity_binding_id` 必须指向该 Installation 的 AGENT identity，`memory_counterparty_buzz_identity_binding_id` 必须指向同 Tenant 的 CONTROL identity；两者构成唯一 NIP-AE `(agent, counterparty)` namespace。该 counterparty 只是 NIP-AE `p` 加密对手，不是 Resource HUMAN owner；owner 转移不重绑或重加密记忆（DD-66）。
- NIP-AE head 是内容权威。`core_head_event_id/created_at` 只是可对账的最新观测引用，不是 Core 正文副本；冷记忆 listing 只有复合游标完整走到末尾时为 `COMPLETE`，超过显式 10000 条上界为 `BOUND_EXCEEDED`，传输、验签或解密失败为 `UNKNOWN`（SF-BUZ-07/16/19）。若观测 head 超前 Relay 当前时间准入窗口，`head_state=HEAD_AHEAD_OF_RELAY` 并拒绝新写入；不得改写 created_at 或删除 head，恢复只等待时钟窗口重新成立。所有 signer 副本必须使用同步时钟（SF-BUZ-29）。
- AgentSession 必须使用非 ephemeral Codex thread，`runtime_thread_id` 是会话恢复键。创建 Session 时固定当时的 `core_memory_state`与成功读取的 `core_memory_event_id`；活跃 Session 不追随新 core head，新 Session 才取新 head。`UNREADABLE` 时 event ID 为 NONE，不等于 `ABSENT`（DD-67）。
- `memory_policy` 是 immutable AgentVersion 的最大写入边界：HUMAN owner 可通过受治理 Action 管理 core/cold memory；Agent 只在该 Installation 的 active Invocation 中获得内部 core/cold read，只在 `INVOCATION_SCOPED` 时可写 cold memory，只在 `AGENT_WITH_APPROVAL` 且 Temporal Approval 已消费时可写 core。该策略不授予任何业务 Resource permission。
- 唯一 Agent 触发键为 `(tenant_id, source_event_id, installation_resource_id)`；自动化运行的唯一键为 `(tenant_id, trigger_source_id, automation_resource_id)`（DD-107）。
- `AutomationDefinition` 是平台核心 ResourceType `automation` 的一对一 Resource 扩展，`home_workspace_id` 必填且等于 `workspace_id`，`AutomationVersion` 是其下的不可变 Asset，二者都有显式 HUMAN owner。`executor_installation_resource_id` 必须是同一 Workspace 的 AgentInstallation，`delegation_id` 是 owner 授予该 Installation、范围覆盖 `automation.run` 与该版本动作的 DelegationGrant。`ENABLED` 要求 pin 一个 `PUBLISHED` 版本；`SCHEDULE` 触发的 Temporal Schedule 与 `WEBHOOK` 触发的 SecretRef 只在 `ENABLED` 时存在，`PAUSED` 暂停 Schedule 并拒绝 webhook，`DISABLED` 删除两者。每次运行是 Governed Action `automation.run`，执行只经 `AgentTaskWorkflow`（审批关卡为其 child ApprovalWorkflow），对应 AgentInvocation 的 `automation_version_asset_id` 固定所用版本；AGENT 与 CONTROL 身份发布的事件不匹配任何触发（DD-107）。AgentSession/Invocation 固定 exact version 与 projection generation，不能从当前 installation pointer 反推历史配置。
- 复制自动化沿同一 `automation.create` 创建新的 Resource 与 DRAFT 版本，来源仅限当前有权读取的定义配置；目标为当前授权 Workspace，新 owner 为发起 HUMAN。源 Resource/Asset ID、pin、state、Schedule、SecretRef、DelegationGrant、运行与审批历史均不继承。执行 Installation 与委托须在目标 scope 重新选择并查证；复制不授予来源 owner 的权限。表单与 YAML 共同读写上述 AutomationVersion 字段，解析后按同一合同验证，未知字段、无效枚举或不可表示的结构拒绝，不静默丢字段；不把 YAML 文本另存为配置或执行权威。
- `AutomationDefinition.DELETED` 是删除定义的不可恢复墓碑，不等同于可再次启用的 `DISABLED`。删除沿原管理动作的版本 fence 先拒绝新准入，经原 Schedule/SecretRef 清理对账后进入 `DELETED`；清理结果不明时不宣称删除完成。定义不再出现在活动定义列表，不能编辑、发布、启用或新运行；Resource 仅保留现有授权与历史引用，不物理删除版本、Invocation、WorkflowRef、用量与审计。已经准入的运行继续使用冻结版本到终态，仍逐次检查 owner、Workspace、Installation、Delegation 与权限；删除定义本身不伪造运行取消，也不释放在途 Capacity。历史读取沿原授权链，不因墓碑获得新访问权。
- 手动运行是 owner 对已启用定义的显式一次性命令，不增加第五类自动触发配置，不修改 pin。Core 从已认证 owner、同一请求幂等键与目标定义形成带 `manual:` 命名空间的稳定触发引用；客户端不能指定其他人的 initiator、Agent actor、Delegation、版本或触发来源。重复请求只读回同一运行；结果不明查原执行，不换键重发。手动运行无 Relay 事件正文，结果回到该 Workspace Channel；沿原 `automation.run` 的 AgentInvocation、审批、计量与任务历史，不增设运行实体。
- 自动化 Invocation 的结果位置由已冻结 AutomationVersion 与运行来源共同确定：消息触发使用原 Thread，定时、webhook 与 owner 手动命令使用同一 Workspace Channel。该结果位置不修改 AgentVersion 的 reply policy 或 Installation 投影；后者仍决定普通 Agent 触发的回复位置。自动化结果发布仍受原 ResultExposurePolicy、Delegation 和当前 Channel 权限约束，不因手动命令扩大可披露内容或跨 Workspace 输出。
- Core 原生的 Agent/Skill/Installation/Tool/automation Resource 的 `application_binding_id=NONE`，Core 是其 native 数据权威，不经任何 ComponentRelease 或 binding。

- CapacityLease 只用于平台自有 Agent（Codex）runner pool；业务能力服务一律 `capacity_policy=NATIVE`，只保留组件真实 429/health/job 结果，不伪造通用 lease。
- OpenMeter 开源 server 只解析一个固定 default namespace（SF-OMT-06）。全部 Tenant 共用这个 namespace，每个 Tenant 映射唯一 Customer；Workspace/Resource/Agent/operation 使用带 Tenant 前缀、且归属于该 Customer 的 subject key/dimension。OpenMeterBinding 的 `namespace` 必须等于平台固定值，Core 同时校验 `tenant_id→customer_id`，不接受请求参数替换 namespace/customer（DD-38）。
- UsageEvent 的 Tenant、Workspace、Customer、subject、Resource/Agent dimensions 只从 ActionExecution/Resource/OpenMeterBinding 构造；native payload 与 Agent 参数不能覆盖。Core 唯一键是 `(tenant_id, source_type, source_id, meter_key)`；`openmeter_event_id` 在首次 outbox 前由同一组字段确定，重试不得改变。OpenMeter 返回 202 只进入 `ACCEPTED`；按 ID/source 查到事件带 `stored_at` 才 `COMMITTED`。`validation_errors` 与 `customer` 由 OpenMeter 在每次查询时按当时的 meter 集合与 subject→Customer 映射重算，不落库、随配置变化而变化，Core 只把首次读取结果作为配置正确性告警，不作为 `COMMITTED` 的判据。这只确认 metering event 已持久，不等同 invoice finalized；结算侧的稳定结论以 charge/invoice 落库的 `validation_issues` 为准（SF-OMT-07/08、DD-51）。
- STRICT_RESERVATION 只适用于 ActionDefinition 证明最坏上界、且该 Tenant+subject+meter 的全部 usage producer 都经 Core 的路径。Core 对该键串行，把 OpenMeter committed credit snapshot 减去尚未被该快照吸收的 UsageEvent 与 active QuotaReservation 后再创建 reservation（减法项按快照时间点切分，避免重复扣减）；没有外部分流保证、snapshot/query 不可用或上界不成立时不得使用 STRICT。Reservation 不成为 plan/balance/usage 账本（DD-51）。
- CapacityLease 由持有 slot 的 Temporal Activity heartbeat 续租，`renewed_at` 取成功 `RecordHeartbeat` 对应时间，且 Activity `HeartbeatTimeout` 必须小于 lease expiry 间隔。heartbeat 超时只把 lease 置为 `UNKNOWN`，不直接置 `EXPIRED` 或回池；`RELEASED` 只接受对应 Activity 终态作为 holder terminal evidence。Activity retry 的新 `attempt` 更新同一 holder_ref 并复用原 lease，不创建第二份 units。
- `STRICT_RESERVATION` 保存可证明的最坏上界，不保存乐观 estimate。无法给出上界的动作不得使用严格额度准入。
- QuotaReservation 只防止 OpenMeter 202 异步计量期间的并发超卖，不复制 plan、balance 或 committed usage。
- ApplicationBinding 每个 generation 激活时，Core 为其建立一条用量归集 operation；该 binding 经 `PLATFORM_LLM_ROUTE` 缺 trace 的模型调用与无法关联到具体 operation 的 `SELF_MANAGED_MODEL` 上报，按 binding scope 记入该 operation（DD-20/92），UsageEvent 的 `operation_id` 始终非空。
- UsageEvent 以 `(tenant_id, source_type, source_id, meter_key)` 唯一；OpenMeter CloudEvent 固定映射为：namespace=`OpenMeterBinding.namespace`，source=`urn:platform:core:usage`，id=`openmeter_event_id`，subject=`subject_key_prefix + subject_key`，operation_id 只放入 data 的受控 dimension。source 不含 operation，重试保持同一 namespace/source/id/body（SF-OMT-04）。
- AuditEvent 追加写入；`event_key` 对同一 operation/阶段/native attempt 稳定，重试不得复制同一审计事实。它不保存 Secret、正文、完整 prompt/response、原始 SQL、结果行或工具 raw body。
- 所有 Governed Action 的 AuditEvent 必有 `tenant_id`；`workspace_id` 必须与 ActionDefinition 的 WorkspaceRule 解析结果一致。只有 `TENANT_ONLY` 或继承自 NONE 的 child action 才为 NONE，Workspace 内消费 Tenant-level Resource 仍记录实际 Workspace。`tenant_id=NONE` 只允许 `AUTHENTICATION|SESSION` 且发生在 AgentGateway OIDC callback 后、Core 尚未解析可用 TenantMembership 的边界，此时 `human_identity_id` 或不可逆外部 subject hash EvidenceRef 必有一个，Principal/业务 target 必为空（DD-52/54）。
- EvidenceRef 只能保存源码权威中的稳定 ID、version/digest 和敏感级别，不保存原始 payload、临时 URL、cookie、ActionToken、协议会话 token、Nostr 私钥或 SecretRef locator。BFF 每次 dereference 都以 AuditEvent scope、当前 `audit`/ResultExposure permission 和目标组件 binding fresh授权；原证据已删除或无权时只显示不可用状态，不回退展示 ref 内容。
- `initiator_principal_id` 表示提出业务意图的人或服务，`actor_principal_id` 表示实际执行身份。用户委托 Agent 时两者不同，Delegation/Approval/Tool/Gateway refs 留在 evidence 中，不能只记录 Agent 而丢失用户责任链。
- Business Observability 不另建事实权威表：BFF 以 ActionExecution/TaskProjection、Temporal/native/Gateway/OpenMeter/Audit refs 组成只读 operation view。普通发起者/Resource owner 只看受 ResultExposurePolicy 允许的状态与自身用量；Tenant/Workspace 聚合、错误 evidence 和成本需要目标 `audit` 权限。
- 业务观测的计费原因码固定为 `AVAILABLE` 或 `BILLING_UNAVAILABLE`，usage attribution 固定为确定 operation ref 或 `NONE`。平台自有 Agent（Codex）链上 SS-AGW-USAGE 未闭合、durable usage 缺失或 SS-COD-TRACE 未闭合任一成立时均显示 `BILLING_UNAVAILABLE + NONE`，不创建无法归属的 UsageEvent，也不显示零用量。业务能力 binding 的模型调用不适用这一处理：缺 trace 时按 gateway identity（`PLATFORM_LLM_ROUTE`）或 Adapter Protocol 上报身份（`SELF_MANAGED_MODEL`）解析出的 binding scope 创建 UsageEvent（`component_binding_ref` 为该 binding），只把归因精度降到 binding，不免于计量（DD-20/92）。
- SecretRef 只是外部 secret 版本 locator：`provider=OPENBAO`，`locator=<namespace>/<mount>/<path>`，`version` 为 KV v2 版本号，`audience` 为允许取用的 service identity；Core 从不把 secret 值写入数据库、日志或磁盘。任何 binding 在其全部 SecretRef 指向的版本可读、且该次读取已被 OpenBao audit 记录前不得 active（DD-70）。
- secret 的写入、轮换与撤销是受治理动作，不是运维旁路。Tenant admin 通过 Buzz Web 的 binding 配置界面提交 secret 值，BFF 在同一 Governed Action 内用 Core 的 service token 写入该 Tenant 的 OpenBao namespace 并只把返回的版本号记成 SecretRef；secret 值不进入 Core 数据库、日志、Workflow history 或 AuditEvent，AuditEvent 只记 `(locator, version, audience, 动作, 结果)`。Tenant admin 与任何用户都不直接持有 OpenBao 凭据。
- SecretRef 的状态随持有它的实体一起持久（binding、identity 或 SecretRefRehome 上的 ref），不另设 SecretRef 表。平台自持 Nostr 私钥的撤销与退役按 DD-113：HUMAN binding 进入 `REVOKING` 时绑定版本先 `delete`、ref 转 `SUPERSEDED`，binding `REVOKED` 后 `destroy` 并经 metadata 查证才转 `REVOKED`；身份私钥在 `REVOKING` 起没有读取者，不适用下述等待旧 generation 执行终态的规则。
- SecretRef 状态机固定为 `PENDING → ACTIVE → SUPERSEDED → REVOKED`：写入新版本得到 `PENDING`；binding 的新 projection generation 对账通过后该版本转 `ACTIVE`、旧版本转 `SUPERSEDED`；`SUPERSEDED` 版本必须保留到所有固定旧 generation 的在途 ActionExecution/Workflow/ExternalExecution 到达终态之后才允许 `destroy` 并转 `REVOKED`。禁止在旧 generation 仍有在途执行时销毁其 secret 版本——那会让无法重试的执行永久失败。
- `SecretRefRehome` 只处理业务 Tenant 的 SERVER `BuzzIdentityBinding` 遗留 `platform/` locator（DD-85），不生成新私钥、不更换 pubkey、不改变 Relay roster。Tenant admin 的受治理动作以该 binding/pubkey 为目标；同一 pubkey 至多一条非终态归位。Core 在任何 OpenBao 写入前持久化 ActionExecution、WorkflowRef 和 `INTENT`，冻结原 ref、binding version 与由 ActionExecution ID 确定的独立目标 locator。目标 namespace 必须精确等于该业务 Tenant 的 `tenants/<tenant_id>`；请求不接受 locator、version 或 secret 值。`COPY_UNKNOWN` 只按该目标 locator 查证并核对派生 pubkey，不盲写新版本；确定读回后登记 `COPIED`、新 ref 为 `PENDING`。同一 pubkey 仍有固定旧 binding version 的 `BUZZ_IDENTITY_PROJECTION` 时不切换；其余在切换前已提交、尚未终态的本 Tenant ActionExecution/Workflow/ExternalExecution 作为保守的 `old_generation_consumer_refs[]` 与切换事实同事务冻结，排除本次归位动作及其 Workflow。原 binding version 的 CAS 切换同时推进 binding generation 与 `SWITCHED`，新 ref 转 `ACTIVE`、旧 ref 转 `SUPERSEDED`；CAS 失败不得把新 ref 当成 active；COPIED 后切换被确定拒绝（发起者新鲜 `manage` 为否或 binding 已偏离冻结值）时销毁目标 locator 版本 1，metadata 确认后进入 `FAILED`、新 ref `DISCARDED`，销毁不明保持 `COPIED` 并告警（DD-85）。冻结清单全部到达权威终态后才销毁旧版本并进入 `RETIRED`；查证缺失、OpenBao 不可达或销毁结果不明保持 `SWITCHED` 并在任务工作台显示对账缺口。确定的写前拒绝才进入 `FAILED`，且 binding 保持原 ref。任一非终态须由固定 Workflow ID 的对账继续收敛；超出部署登记的对账时限进入运维告警，不能静默遗留。
- Core 自身访问 OpenBao 的引导凭据不由 OpenBao 托管：部署以 response wrapping 一次性投递 AppRole `secret_id`（或在 Kubernetes 部署下改用 Kubernetes auth，由 ServiceAccount token 换取），Core 启动后按 lease 续期；该引导路径与其审计是部署前置条件，不是平台内的 Governed Action。
- 平台权威组件 API 只接受 Core/Worker service identity：SpiceDB 使用 bearer PSK，Temporal 使用 JWT system/namespace role，OpenBao 使用 AppRole/Kubernetes auth 换取的短 TTL service token（DD-70），AgentGateway admin 与 OpenMeter 分别使用 SS-AGW-ADMIN/SS-OMT-AUTH 的 Core-only 接缝。native credential 只认证服务，不把其角色当作 HUMAN/AGENT 业务授权；每个用户可达动作仍以 ExecutionContext 做 SpiceDB Check（DD-37）。
