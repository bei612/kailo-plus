# 业务能力实现的增量更新与跨服务数据获取

本文定义两件事：业务能力实现如何对自身数据负责增量、对账与就绪；一个业务能力服务需要另一服务的数据时，如何按 DD-89 经授权由接收方自行获取。平台不编排跨服务数据同步，不接管组件内部索引，不持有逐项增量状态，也不把“定时全量重建”命名为增量。本文是内置参考实现文档（README 权威规则），不给平台新增实体、权限、Workflow kind、端口或门禁；平台通用规则以 `07` §8 为准，本文全部内容只约束一期内置参考实现。

## 1. 权威与边界

平台通用规则不在本文：IncrementalContract 的通用语义、平台不持有的内容与平台核心 ResourceType 合同以 `07` §8.1 为准；跨服务数据获取的两条路径、服务读取边、八项治理与撤权收敛以 `07` §8.2 与 `03` §3 为准；模型调用模式与计量以 `07` §8.3 为准。本文只说明一期内置参考实现如何满足这些规则。

| 事实 | 权威 |
|---|---|
| 业务正文、native 对象与版本、派生索引（chunk/vector/graph 等）、native task | 对应内置参考实现 |
| 接收方从来源方拉取的逐项状态、去重、删除跟踪与调度 | 接收方内置参考实现（本文为 WeKnora 能力组件内的导入器） |
| 模型 billable usage source | WeKnora binding 选定 `PLATFORM_LLM_ROUTE`，为 SS-AGW-USAGE 闭合后的 durable Gateway usage（DD-92） |

## 2. IncrementalContract 的适用

IncrementalContract 的两类合同、`NATIVE_INTERNAL` 必须经 Adapter Protocol 暴露的五项事实与不得登记为 active 的情形，以及平台核心 ResourceType（Buzz Community/Channel、AgentGateway LLM Route、AgentGateway request log）的合同，均以 `07` §8.1 为准，本文不重复登记。内置参考实现只按下表登记，并同样禁止平台或其他服务直写其数据库、vector store 或图数据库。

## 3. 一期内置参考实现的 ResourceType 合同

| 能力类别 / 实现 | 合同 | 结论 |
|---|---|---|
| `FILE_STORAGE` / Cells 空间 | `NATIVE_INTERNAL` | node/version/job 留在 Cells；完整目录列举与按 revision 读取经 `FILE_STORAGE` 契约供接收方经服务读取边自拉（SF-CEL-01/03、SS-CEL-MATERIALIZATION） |
| `KNOWLEDGE` / WeKnora KnowledgeBase | `NATIVE_INTERNAL` | parse/chunk/vector/graph 与导入状态全在 WeKnora 能力组件内（SF-WEK-03/05/07） |
| `DATA_QUERY` / Wren GenBI 语义模型 | `NATIVE_INTERNAL` | 模型与 deployment 保留在 GenBI；Resource 引用固定实例/project，单次查询冻结原生 deployment ref/hash。本基线不声明平台不可变版本查询，不创建版本 Asset（SF-WRN-08、DD-12） |

在线编辑不出现在 ResourceType 表：它是 `FILE_STORAGE` 契约的条件能力，只作用于声明它的实现自己的 ContentReference，不拥有增量合同、文件目录或第二内容副本（DD-90/103）。内置参考实现中，编辑保存只有在 WOPI PutFile 已写回 Cells 且 NodeVersions 确认新 head revision 后，才成为 Cells 空间的普通 revision 变化（SF-CEL-05/06/07、DD-32）。

## 4. 内置实现之间的数据获取

### 4.1 适用路径

内置 `KNOWLEDGE` 实现需要 `FILE_STORAGE` 实现的文件时，只走 `07` §8.2 的路径 1（接收方自拉）：授予由 Governed Action 为 WeKnora binding 的 ServicePrincipal 写入来源 Cells Resource 的 `reader` 关系，发起者须对来源持有 `share`、对接收方知识库 Resource 持有 `update`（DD-89）；每批拉取由导入器经 Adapter Protocol `request_read_grant` 申请，凭 Core 签发的短期 ActionToken 访问 `FILE_STORAGE` 契约端点，Cells 侧 PEP 按通用 ActionToken 规则校验并再做 fresh `read` Check。导入器不持有 Cells 的 native 凭据。

### 4.2 撤权在本实现中的表现

撤销 `reader` 关系后，导入器下一批 `request_read_grant` 被拒绝，本次导入失败，不提交删除 desired state；已导入的 Knowledge 由 WeKnora 按 `KNOWLEDGE` 契约声明的删除语义处置，平台不代删。

### 4.3 与平台的分工

导入器的逐项状态、去重、删除跟踪与调度只属于 WeKnora 能力组件；平台只看到授予/撤销动作与每批读取 operation（`07` §8.2）。

### 4.4 内置 `KNOWLEDGE` 实现从 `FILE_STORAGE` 自拉

本节只约束一期内置参考实现：WeKnora 能力组件内部的导入器从 `FILE_STORAGE`（内置实现为 Cells）拉取文件。导入器属于知识能力组件，运行于其自身运行体；如使用 CocoIndex，它只作为导入器内部的增量引擎，状态目录属于该组件自身存储，Core 不感知（`08` §8、DD-89/93）。

**来源身份。**

```text
item_key = ContentReference.native_object_ref（Cells node UUID）
revision = ContentReference.native_revision（Cells VersionId）+ streamed content hash
```

Node UUID 提供稳定身份；版本用于快速候选比较，受权读取流计算的内容 hash 决定正文是否改变。仅路径、文件名、大小或 mtime 不构成 revision。移动/重命名保持 item key，不重复创建正文。只有一次完整、成功的列举才允许把“上次存在、本次缺失”解释为删除；分页、授权或读取失败使本次导入失败，不提交不完整 desired set。导入器每批经服务读取边取得短期 ActionToken 后按 `FILE_STORAGE` 契约读取，不能通过 presigned URL 绕过下一次 scope/expiry 校验（SS-CEL-MATERIALIZATION）。

**写入 WeKnora 的内部规则。**

| 来源状态 | 导入器动作 |
|---|---|
| 新内容 | 上传 Knowledge，记录 native ref，观察 parse 到 ready |
| 相同 key/revision | 无正文动作；只处理允许的 metadata 差异 |
| 相同 key、新 revision | 创建新 Knowledge，等待 ready；成功后在旧 hash 无引用时删除旧 ref |
| key 从完整列举消失 | 删除本导入配置拥有且已无引用的 target ref |
| target ref 丢失或状态不一致 | 进入导入器内部 reconcile，按来源 desired state 重建或确认已删除 |
| 写/删/reparse 返回 409 且响应体顶层无 `code`（跨 KB 移动中；`ErrConflict` 的数值 code 嵌在 `error` 对象下） | 该项保留 pending 并在下次导入重试，本次导入计为失败；不得吞掉该 409 并记为已应用。使用 CocoIndex 时，sink 返回错误使引擎保留 pending 多态并以 `prev_may_be_missing` 重试（SF-CIX-03/06） |
| 创建返回 409、响应体 `code` 以 `duplicate_` 开头且 `data` 携带既有 Knowledge（`*DuplicateKnowledgeError`，SF-WEK-07） | 视为幂等成功，把 `data` 中的 Knowledge ID 绑定为该 item 的 target ref 并继续观察 parse；两类 409 只能按响应体区分 |
| 创建超时 | 先依 WeKnora dedupe/query 接缝确认 native ref；结果未知时标 `UNKNOWN`，不盲目重复副作用 |
| 新 target ready、旧 delete 失败 | 新版本可服务，旧 ref 留 pending delete；后续 reconcile 回收 |

WeKnora 创建按 `(tenant, knowledge_base, type=file, file_hash, file_type)` 去重并返回已存在 Knowledge——文件名与大小不参与；公开写入面没有 idempotency key、external-ID、按外部 ID 删除或文件替换 route（SF-WEK-07/11）。因此导入器的 desired item key 固定为去重元组中随内容变化的部分 `(file_hash, file_type)`：同 hash 的多个 node 先归并为一个 item，item 值携带引用它的全部 node UUID 集合，只有集合变空时才删除。禁止以 node UUID 作 target key 后把同一 Knowledge ID 绑给多个 item——WeKnora 按 Knowledge ID 删除且没有引用计数（SF-WEK-07/11、SF-CIX-02）。服务层 `ReplaceKnowledgeFile` 不用于被多个 node 共享的 Knowledge，replace 固定为 create-new → ready → delete-old（SS-WEK-MATERIALIZATION）。本实现不承诺跨 Cells/WeKnora 原子事务或 exactly-once。

WeKnora 的 chunk、embedding、实体/关系图谱继续由 native parse 生成。导入器只调用上传、任务观察/取消和删除 API，禁止直写 WeKnora DB、vector store 或 Neo4j。使用 CocoIndex 时另受 `08` §8 的状态目录约束：`db_path` 显式绝对路径、每个导入配置独立 LMDB environment、run 成功判据含各组件 `num_errors == 0`、清除前先跑空 desired set 再 `drop_state`（SF-CIX-04/06/07）。

## 5. ContentReference 回链与编辑保存

检索与问答结果的 citation 以 ContentReference 回链来源内容，不保存临时 URL、token 或编辑器 config。内置参考实现中，导入器在 WeKnora 上传请求的 `metadata` 写入 `source_resource_id/source_asset_id/source_native_object_ref/source_native_revision/import_config_ref`；固定源码证明 multipart route 将 JSON 解析为 `map[string]string`，创建服务持久化到内部 `Knowledge.Metadata`，且该字段与用户描述性 `CustomMetadata` 分离（SF-WEK-08）。citation 由本实现的 adapter 按 `KNOWLEDGE` 契约直接给出 ContentReference：adapter 以检索引用中的 `knowledge_id` 经受 KB read guard 的知识详情接口读取 Metadata 并组装 ContentReference（SF-WEK-09）；BFF 只对该 ContentReference 做授权与解析，不调用 WeKnora 原生接口重建（2026-09-28 按 DD-90 修订）。用户打开 citation 时按 `FILE_STORAGE` 目标 Resource 当前权限重新授权；来源 binding 已停用或无权时只显示不可用状态。

编辑保存不直接触发知识实现。内置参考实现中，WOPI PutFile 成功写回 Cells 并确认新 revision 后，只成为 Cells 的普通 revision 变化；导入器下一次自拉时以既有 node UUID 和新 revision 识别差异。DocumentServer、Cells、WeKnora 各自只有一个权威职责。

## 6. 模型调用与计量关联

业务能力实现内部的模型调用模式与计量规则以 `07` §8.3 为准（DD-20/92）：缺 trace 时按 gateway identity 解析出的 binding scope 入账，只降低到 operation 的归因精度，不按时间窗口猜 operation，也不免于计量。

内置参考实现 WeKnora 采用 `PLATFORM_LLM_ROUTE`。其精确归因链为：

```text
知识导入或检索 operation
→ WeKnora upload/query request
→ DocumentProcessPayload trace carrier
→ Asynq worker context
→ Chat/Embedding/Rerank HTTP traceparent
→ AgentGateway StoredRequestLog.trace_id（业务观测）
→ durable Gateway usage（计费；仅 SS-AGW-USAGE 闭合后）
→ Platform operation / OpenMeter UsageEvent
```

WeKnora 已有 Asynq `TracingContext` 注入/恢复接缝，但当前受 Langfuse enabled 门控（SS-WEK-ASYNC-TRACE）；出站模型请求已携带 context，但当前只应用静态 ModelParameters headers（SS-WEK-LLM-CTX）。本实现的二开固定为：trace carrier 不依赖可选观测产品开关，并由模型 HTTP transport 从当前 context 注入 W3C `traceparent`。该二开不改变 WeKnora 业务 task、模型接口或 provider 协议；未闭合时本实现 binding 仍可 `ACTIVE`，模型 usage 按 binding scope 入账而不归属到单次 operation。

Gateway identity 的 user/group 来自 apiKey/JWT 认证属性（SF-AGW-08），用于验证 Tenant/Workspace binding。Core 以 `IngressCheckpoint` 读取 durable usage tail，以稳定 request-log ID 去重；原始 log tail 只供业务观测，其 writer 丢批次边界由 SF-AGW-09 证明。缺 tenant/workspace identity 或 token/cost 不完整的 durable usage 进入 reconcile。

## 7. 停用、撤权、删除与恢复

通用语义以 `07` §6.3、§8.2、§8.4 为准；下表只写内置参考实现的表现：

| 命令/故障 | 内置参考实现中的确定语义 |
|---|---|
| 撤销 WeKnora ServicePrincipal 对 Cells Resource 的 `reader` 关系 | 导入器后续 `request_read_grant` 被拒绝；已导入 Knowledge 按 `KNOWLEDGE` 删除语义处置，平台不代删 |
| 停用 WeKnora binding | `COMPONENT_DISABLE` 撤其 ServicePrincipal 的 `reader` 关系、凭据、route 与 Tool；不删除 Cells 数据 |
| 停用 Cells binding | 导入器后续申请失败；失败不得解释为来源内容删除 |
| Cells 不可用或列举不完整 | 本次导入失败；不提交删除 desired state |
| WeKnora 内部 reindex/reparse | 该实现内部的处理逻辑变更，经 Adapter Protocol 暴露进度与终态；平台不重建 |
| 删除 Cells 条目 | 仅在导入器完整列举中缺失才删除 WeKnora 自己拥有的派生内容 |
| Tenant 删除 | 三个内置实现均声明 `retain_on_tenant_delete`，其删除子流程进入 `RETAINED_DECLARED`：撤 binding、撤凭据、保留审计并登记待人工处置，不阻断平台 Tenant 状态机（DD-91、GAP-LCM-01） |
| Durable usage cursor 重放 | 稳定 log ID/CloudEvent key 去重；cursor 只优化恢复，不提供 exactly-once；原始 log writer 未闭合时不产生计费事件 |

## 8. 上游升级闭环

`.references/UPDATE_TASKS.json` 只告知 source/manual 差异，只作用于内置参考实现与平台核心。涉及 Cells node/version/data/WOPI API、DocumentServer WOPI client、WeKnora upload/metadata/delete/task/model transport、CocoIndex update/target state、AgentGateway log schema 的差异，必须先重验本文引用的 SF/SS，再更新对应 IncrementalContract 与该参考实现的 release。

新上游能力不会自动扩大来源读取范围、导入动作、文件类型、图谱链或 meter。只有能力契约、owner/permission、Workflow、quota 和审计验证全部闭合的新 ComponentRelease 才能获批；旧 binding 继续固定旧 release/generation，直到受治理升级完成。外部实现的演进按 `07` §2.5 与 §10 重跑一致性测试套件。
