# 最终源码可行性分析

## 1. 总结论

Kailo 的目标设计不是“条件可行”。固定源码给出的确定结论是：

- 组件原语与已定位改动接缝分别为 `UPSTREAM_SUPPORTED` 或 `ADAPTER_REQUIRED`；两者均有固定 commit、文件和 symbol 依据。
- 统一 Secret 与 Temporal application Worker 的源码门禁（GAP-SEC-01、GAP-TMP-01）已于 2026-09-13 闭合：OpenBao 以固定 commit 进入 `.references`，其 namespace/KV v2/lease/audit/Agent 为上游能力（SF-OBA-01..09），Core 集成与投递为 `DESIGN_DEFINED`（DD-70/71/72）；`temporal-sdk-go` 以固定 commit 进入 `.references`，Kailo Worker 选用 `v1.48.0`，Server 自身 `go.mod` 依赖 `v1.44.0`，二者不以版本号相同为兼容依据（SF-TMP-04、SF-TSDK-01..08），Application Worker 为 Kailo 自建代码（DD-69）。门禁按 DD-91 分两层：平台 Stage 退出门禁与一期生产门禁只含平台核心的接缝与阻断项，由 SS-AGW-ADMIN、SS-AGW-USAGE、SS-AGW-OIDC、SS-OMT-AUTH 的适配闭合与 GAP-AGW-01 决定；业务能力实现的接缝缺口与限制（SS-CEL-*、SS-OFF-*、SS-WEK-*、GAP-WRN-01、GAP-LCM-01）只阻断该实现的 ComponentRelease `APPROVED` 或 ApplicationBinding `ACTIVE`，不阻断平台。Tenant 销毁以平台自有事实为前提；内置参考实现未闭合 native 删除契约（GAP-LCM-01），因此声明 `retain_on_tenant_delete`，不阻断平台 Tenant 状态机。“零业务能力 binding”部署必须能通过全部平台门禁（§4.1）。
- `ADAPTER_REQUIRED` 不等于已实现。对应适配闭合并完成源码重验前，Action/Route/Tool/Workflow 不得 active。
- 能力状态仅使用 README 定义的四种；一期排除项另用 `EXCLUDED`，不另造中间状态。

## 2. 主链裁决

### 2.1 Web 认证与 Buzz 协作

|---|---|---|
| AgentGateway OIDC login/session/local logout | `UPSTREAM_SUPPORTED` | authorization-code、PKCE、nonce/CSRF、issuer/audience/JWKS、加密 HttpOnly cookie、同源 POST 本地注销（SF-AGW-10） |
| claims→内网 BFF、logout 平台协同 | `ADAPTER_REQUIRED` | policy 顺序、CEL header transformation、Core PlatformSession 与 BFF stream 撤销（SS-AGW-OIDC） |

| Component Host 与运行时 release（Web + Desktop） | `ADAPTER_REQUIRED` | Buzz Web 与 Buzz Desktop 是两个上游代码库，当前 route/router/navigation/i18n 均静态；精确二开面分别为 SS-WEB-COMPONENT-HOST 与 SS-DSK-COMPONENT-HOST，两端共享 Buzz 原版 TypeScript 页面、组件与交互主体及 Kailo 平台包，不能以宿主不同裁剪基础功能；Desktop CSP 编译在签名包内，不执行 remote module（SF-DSK-03、DD-74）。Mattermost 直接证明 manifest→active fetch→script register→scoped registry→version reconcile/unload（SF-MAT-01/03/04）；其事件路径把 payload 当完整状态、只在重连时全量 reconcile（SF-MAT-06），是 DD-61 明确不采用的反例 |

AgentGateway 不产生 TenantMembership 或业务 permission；Core/BFF 只在已验证 subject 到达后解析 ExternalIdentity、邀请和 membership。Keycloak 是通用 OIDC issuer 的默认选择，不在 `.references` 内，本文不声明其内部行为或全局 logout。

Buzz Web 目前的收藏、静音和已读跨端同步依赖 Browser NIP-44 私钥（SF-WEB-05）。一期 Browser 无私钥（原生端本地持钥但按 DD-40 同样不另建第二份权威），因此 Relay kind:30078 路径明确停用；Core CollaborationUserState 是 `DESIGN_DEFINED` 的新权威，不声称 NIP-44 兼容。

Component Host 的可行性不等于 Mattermost 插件可直接移植。Mattermost 的 enable 是全局 config，初始化得到完整 store，server plugin 是本机 executable subprocess并获得宽 PluginAPI（SF-MAT-02/04/05）；这些与 Kailo 的 Tenant/Workspace、七项治理和独立 remote adapter 边界冲突，固定排除。Kailo 的 manifest、ComponentRelease/Binding 与 adapter 合同为 `DESIGN_DEFINED`；Buzz Web runtime Host 的源码改动为 `ADAPTER_REQUIRED: SS-WEB-COMPONENT-HOST`，Buzz Desktop 的为 `ADAPTER_REQUIRED: SS-DSK-COMPONENT-HOST`。

新增兼容 release 无需重发主体的结论有确定边界：它必须只使用当前 manifest schema、platform port、Host API、Adapter Protocol、canonical permission、Workflow kind 和三个 extension slot。它仍要求组件独立服务部署、Web artifact 交付/批准与 binding 对账。新增任一宿主/权威语义或 embedded/internal provider 代码仍需发布 Core/Buzz Web/Worker；release 引入部署级许可集合尚未包含的 editor origin 时，Web 重启静态服务，Desktop 只接收 BFF 运行时下发的新许可集合、不需发布新包（DD-95/104）；只使用固定 permission 与通用语义的新能力类别经 Catalog 登记与审批加入，不需发版，需要新平台语义的类别才发布 Core（DD-102）；因此本文不作“任意组件零开发热插拔”承诺（DD-56..64）。

Buzz 原生 ACP 把 core 放入其系统 prompt，但 Kailo 一期是 `SERVER_CODEX`，不直接运行该 ACP pool。确定适配是复用 SS-BUZ-ENGRAM 的验签/解密/head 语义，将 core 作为低于 AgentVersion instructions 的明确分隔 context 交给 Codex；不把 Buzz ACP 的 prompt role 排序原样搬到 Codex（DD-67）。

### 2.4 授权、审批和任务工作台

- SpiceDB 的 Check/Lookup/Write/Watch/ZedToken 与 consistency 为 `UPSTREAM_SUPPORTED`（SF-SPZ-01/02）；`03` 的固定 `principal/tenant/workspace/resource/asset` schema 能承载全部组件。
- SpiceDB serve 强制 bearer preshared key；Temporal Server 提供 JWT system/namespace role，但空 auth 配置是 no-op，必须显式选择 default mapper/authorizer（SF-SPZ-03、SF-TMP-06）。两者只认证 Core/Worker service，不替代 Kailo 用户/Agent permission。
- Application Component 无须原生复制 Kailo Tenant/Workspace 表；ApplicationBinding 必须使用按 `07` §2.5 准入路径证明的隔离模式（内置参考实现以源码证据，外部实现以一致性测试套件与批准的声明），Resource/Asset/owner/relationships 是统一授权入口。Platform Component 不伪造业务 scope，只通过 PlatformProviderBinding 实现已知 port。
- HUMAN Workspace scope 先要求 active WorkspaceMembership 或 workspace manage；AGENT scope 先要求 active Installation/Principal、workspace discover、Buzz roster 与 ChannelAgentBinding，再检查 Resource permission/Delegation。直接 owner 或 ToolBinding 不能绕过 scope（DD-46/50）。
- Resource home Workspace 与本次 Action execution Workspace 分离。Workspace Agent 调用 Tenant-level Agent/Skill/LLM Route 时继承父 Workspace，usage/audit 不丢 scope；Tenant 管理动作才固定 Workspace NONE（DD-54）。
- Delegation 不支持隐式通配；action+target/创建 Workspace 固定，首次 dispatch 以 operation 唯一计次。跨进程 ActionToken 是短期上下文，接收 PEP 仍 fresh Check（DD-49）。
- Temporal Server lifecycle 与 Schedule 为 `UPSTREAM_SUPPORTED`（SF-TMP-01/05）；Application Worker 不可省略，Nexus External target 也不能替代（SF-TMP-02/03）。
- ApprovalWorkflow、AgentTaskWorkflow、ComponentTaskWorkflow 和任务工作台为 `DESIGN_DEFINED`（GAP-TMP-01 已闭合，DD-69）；Worker 实现并通过重放回归前不得 active。Core DB、Buzz workflow 或组件 native task不得充当降级审批/Workflow 权威；Kailo 部署中 Buzz 自带 workflow 由 SS-BUZ-GOVERNANCE 的改动关闭（SF-BUZ-45、DD-106），用户可见的自动化由 Temporal 承接（DD-107）。

### 2.5 Capacity、Quota、Usage 与 Billing

- OpenMeter entitlement、credit、meter、usage、plan/subscription/invoice 与 LLM cost 为 `UPSTREAM_SUPPORTED`（SF-OMT-01）。
- OpenMeter 开源 server 只使用一个 static default namespace，v3 没有通用 API authentication（SF-OMT-06）。确定设计是同一 namespace 内一个 Tenant→一个 Customer、子 scope→subject；Core-only authentication 为 `ADAPTER_REQUIRED: SS-OMT-AUTH`，不声明 per-Tenant namespace。
- OpenMeter 无 action reserve，ingest 返回 202；Core QuotaReservation 是 `DESIGN_DEFINED` 的同步并发窗口，不复制账本（SF-OMT-02、DD-07）。STRICT_RESERVATION 只在全部该 Tenant+subject+meter producer 经 Core且动作有可证明上界时成立；它不是跨系统原子扣减（DD-51）。
- ingest/sink dedupe 默认关闭；固定 CloudEvent source/id/body 与两层 dedupe 是确定不变式（SF-OMT-03/04）。
- UsageEvent 显式固定 Tenant/Workspace/Customer/source；202 只到 ACCEPTED，按 ID/source 查到 `stored_at` 才 COMMITTED；`validation_errors` 由 OpenMeter 读时重算、不落库，只作配置告警；结算侧稳定结论读 charge/invoice 的 `validation_issues`；invoice finalized 另行查询（SF-OMT-07/08、DD-51）。CapacityLease expiry 也不等于 holder terminal，不能直接复用 slot。
- AgentGateway request log 只有配置 logging database 后可查询；DB batch 写失败后无重试并清批次（SF-AGW-06/09）。因此“查询已成功持久的 Gateway log”是 `UPSTREAM_SUPPORTED`，平台联合业务观测读模型是 `DESIGN_DEFINED`，完整 LLM billing usage 是 `ADAPTER_REQUIRED: SS-AGW-USAGE`。
- SS-AGW-USAGE 闭合前不创建 `PLATFORM_LLM_ROUTE` 模型 token/page/cost UsageEvent，不用 Codex 或业务能力服务自报值补洞，不显示零用量或已结算。`SELF_MANAGED_MODEL` 的业务能力服务经 Adapter Protocol 上报 usage，平台照常执行 Quota 与审计（DD-92）。

### 2.6 业务能力内置参考实现

本节只裁决一期内置参考实现的可行性；表中 `ADAPTER_REQUIRED`/`BLOCKED` 只阻断该实现的 ComponentRelease `APPROVED` 或 ApplicationBinding `ACTIVE`，不是平台门禁（DD-91）。外部实现按 `07` §2.5 以能力契约与一致性测试套件准入。

| 能力类别 / 实现 | `UPSTREAM_SUPPORTED` | 该实现的 binding 激活门禁与限制 |
|---|---|---|
| `FILE_STORAGE` / Cells | Node/Version/data/job/control API | 完整列举读取=`ADAPTER_REQUIRED: SS-CEL-MATERIALIZATION`；密钥=`DESIGN_DEFINED`（`secret_schema`、DD-70/71/93） |
| `FILE_STORAGE` 在线编辑条件能力 / ONLYOFFICE（与 Cells 同一能力组件，DD-103） | DocumentServer↔Cells WOPI discovery/Check/Get/Put（组件内部集成） | `ADAPTER_REQUIRED: SS-CEL-WOPI、SS-OFF-WOPI`；密钥按 DD-70/71；UNKNOWN reconcile 由通用 `PROTOCOL_SESSION_RECONCILE` 承接（DD-69/90）；Web 边缘按 DD-30 固定 CSP |
| `KNOWLEDGE` / WeKnora | native tenant/KB/Knowledge/task/cancel/实体关系图谱；`PLATFORM_LLM_ROUTE` base URL 可配 | 自拉导入写入链=`ADAPTER_REQUIRED: SS-WEK-MATERIALIZATION`；逐调用 trace=`ADAPTER_REQUIRED: SS-WEK-ASYNC-TRACE、SS-WEK-LLM-CTX`，按 DD-92 只影响成本归因精度、不阻断 `ACTIVE`；密钥=`DESIGN_DEFINED`（DD-70/71/93） |
| `DATA_QUERY` / Wren GenBI | 完整 UI、Apollo 原生 API、模型部署与 asking task（SF-WRN-07/08） | 原生身份及公共服务接入=`ADAPTER_REQUIRED: SS-WRN-IDENTITY、SS-WRN-GOVERNANCE`；独立实例与只读数据库凭据；不复用 Python v2 的 strict/行限/HTTP 结论；通用 query cancel 声明 `UNSUPPORTED` |
| 全部内置参考实现的 Tenant native 删除 | — | `BLOCKED: GAP-LCM-01` 只作用于删除能力声明；三个 release 声明 `retain_on_tenant_delete`（DD-91） |

Wren GenBI 保留完整原生后台并做身份、授权与公共服务二开；不能直接把原版镜像或配套 Engine 的 stdio 示例登记为已治理服务（SF-WRN-07/08/09）。数据库原生只读角色仍是查询写保护边界。旧 Python v2 的 SF-WRN-01–06 仅保留历史版本事实，不证明当前 GenBI 的行为（DD-12）。

WeKnora 原生个人 Memory 为 `EXCLUDED`：其 tenant+caller scope 不含 Kailo AgentInstallation；平台不把业务能力服务自带 memory 纳入 Agent 上下文或用户入口，不规定服务内部是否启用；内置参考实现 WeKnora 由其 release 自行关闭（SF-WEK-16、DD-65/92）。

### 2.7 跨服务数据获取

平台不编排跨服务数据同步：不存在物化平台端口、物化 binding、物化 Workflow kind 或平台 Schedule，平台不持有逐项同步状态（DD-89）。一个业务能力服务需要另一服务的数据时，只由接收方经授权自拉（Governed Action 为接收方 binding 的 ServicePrincipal 写入来源 Resource 的 `reader` 关系；接收方只以自身 binding 的服务凭据认证 Adapter Protocol、不持有来源凭据，每批经 Adapter Protocol 操作 `request_read_grant` 取得 Core 签发的短期 ActionToken，由来源实现在平台运维域内的 adapter 校验），或由人/Agent 经两边 Tool 显式读写；两条路径都只使用平台既有的 SpiceDB 关系、ActionToken、OpenBao 投递、Governed Action 与 Approval（DD-89/94），因此为 `DESIGN_DEFINED`，不新增平台接缝。

内置参考实现中 WeKnora 能力组件从 `FILE_STORAGE` 自拉导入，增量规则见 `13` §4.4。其内部可使用 CocoIndex 作为增量引擎；CocoIndex 的源码事实（SF-CIX-01..08）只约束该组件内部实现：状态目录在该组件自身存储并显式绝对路径、run 成功判据含 `num_errors == 0`、清除前先跑空 desired set 再 `drop_state`，Core 不感知其状态。按 hash 归并的 create-new→ready→delete-old 语义是 `ADAPTER_REQUIRED: SS-CEL-MATERIALIZATION、SS-WEK-MATERIALIZATION`，只阻断该导入能力。

WeKnora 已具有实体/关系图谱全链，EdgeQuake 会建立第二套摄取、图构建、检索和任务权威，因此不作为一期内置参考实现并行接入（SF-WEK-05、SF-EDG-01）。

### 2.8 Business Observability、Audit、主题与 i18n

- Action/Audit、Buzz event、Temporal/native status、Codex refs、已持久 Gateway log 与 OpenMeter committed usage 足以形成受权业务 operation view；这项读模型是 `DESIGN_DEFINED`，不需要基础设施 telemetry 项目。
- 原始 Gateway log 只能展示成功持久的记录，不能证明计费全集完整；计费状态必须遵守 2.4。
- 所有 Governed Action AuditEvent 必有 Tenant；Tenant NONE 只用于 OIDC callback 后、Tenant 解析前的认证/Session事件。EvidenceRef 是带 authority/type/version-or-digest/sensitivity 的稳定引用，详情 fresh授权，不能保存临时 URL/token/payload（DD-52）。
- Buzz Web 与 Buzz Desktop 共用的 ThemeProvider/CSS variables、`en/zh-CN` AppLocale/MessageKey/t/getLocale 为 `UPSTREAM_SUPPORTED`；新增管理页是 `ADAPTER_REQUIRED: SS-WEB-01、SS-WEB-PRESENTATION`。主题偏好仅设备本地，locale 由浏览器解析且一期无语言设置；平台文案本地化，用户/业务内容保持原文。独立业务能力服务保留原生后台并可按 `07` §4.6 嵌入，主题与语言差异不构成接入阻断；此处设计允许不等于客户端承载已验收（DD-53/87）。
- 通用 `SOURCE_BOUND_PROTOCOL` surface 只支持 launch-time theme/locale 映射；内置参考实现 ONLYOFFICE 的活跃 editor 不宣称实时换肤（SF-WEB-03、SF-OFF-07）。

### 2.9 Workspace 成员、跨 Tenant 转移与 Tenant 销毁

- Buzz relay/Channel roster 与 SpiceDB tenant/workspace relationship 的投影接缝已由 SF-BUZ-04/05、SF-SPZ-01/02 证明；Core TenantMembership/WorkspaceMembership 权威与 `PROVISIONING/ACTIVE/REVOKING/REVOKED/ERROR` 收敛合同为 `DESIGN_DEFINED`（DD-41/45）。建立/撤权是两个 ComponentTaskWorkflow kind，多投影运行链为 `DESIGN_DEFINED`（DD-69）；Core 的 `REVOKING` fail-closed 不等于投影已收敛。TenantMembership 终态还受 active Resource/Asset owner 转移门禁约束。
- Workspace 暂停/恢复确定映射 Buzz Channel archive/unarchive，并保留 Resource/Asset/owner；Buzz DELETE_GROUP 只软删除 Channel/discovery，故当前 Workspace 模型不含删除状态，也不注册 delete Action（SF-BUZ-15、DD-46）。
- 跨 Tenant 直接 relationship、binding、native ID 或 ExecutionContext 复用为 `EXCLUDED`。唯一合同是两段 `RESOURCE_EXPORT`/`RESOURCE_IMPORT`：源 Tenant ExportPackage Asset 经 HUMAN 下载，再在目标 Tenant 新 session 上传并创建新对象/新 owner。该领域合同与 Temporal 运行链均为 `DESIGN_DEFINED`（DD-42/69）；ResourceType 未有固定 export/import 格式与 API 源码证据时，`transfer_formats=[]` 且不暴露 Action。
- Tenant `SUSPENDING/SUSPENDED/RESTORING/DELETING/DELETED/ERROR`、TenantLifecycleSnapshot、distinct owner approvals、per-component ExternalExecution 和不可逆 dispatch 边界为 `DESIGN_DEFINED`（DD-43）。运行链为 `DESIGN_DEFINED`（DD-69）。Tenant 销毁以平台自有事实为前提（DD-91）：每个 ApplicationBinding 的 native 删除是独立子流程，由能力契约的删除能力声明决定；声明 `retain_on_tenant_delete` 的实现在 Tenant 删除时撤 binding、撤凭据、保留审计并登记待人工处置。内置参考实现尚未闭合幂等 delete 与 terminal query（GAP-LCM-01），因此全部声明 `retain_on_tenant_delete`；GAP-LCM-01 不阻断平台 `DELETING/DELETED`，Tenant delete Action 按平台门禁注册。平台核心销毁链中的 Buzz Community 与 roster 由上游整 Community 删除引擎真实删除（SF-BUZ-46、DD-109）：Community 归档只是暂停手段；删除到 `retention_pending` 后 Community 范围的行、tenant 对象前缀与缓存均已删除并经逻辑缺席验证，墓碑行、删除证据与共享 CAS 字节不删除，作为平台保留项登记；该处理器的执行面 SS-BUZ-COMMUNITY-DELETE 为 `ADAPTER_REQUIRED`。
- PlatformProviderBinding 和 ApplicationBinding 的停用合同为 `DESIGN_DEFINED`（DD-44/62）；它们必须由 `ComponentTaskWorkflow(kind=COMPONENT_DISABLE, binding_kind=...)` 收敛 Schedule/relationship/route/tool/connection/native refs/usage/audit，运行链为 `DESIGN_DEFINED`（DD-69）；Workflow 对账完成前不把 Core `DISABLING` 报成已停用。

## 4. 紧凑运行边界

### 4.1 平台核心拓扑

平台核心拓扑只包含 Buzz Client Surface 三端（Web 与 Desktop 含 Component Host）、Core/BFF（内含 Platform Port Router、Application Adapter Dispatcher 与 SS-BUZ-ENGRAM memory adapter）、Buzz Relay、AgentGateway、SpiceDB、Temporal Server+Application Worker、OpenBao、OpenMeter 和 Codex runtime。Core 内聚 Catalog/Admission/Projection/Reservation/Audit；对 SpiceDB/Temporal/OpenMeter/AgentGateway 使用固定 port client，不增加转发服务；Business Observability 是联合读模型。NIP-AE 复用现有 Buzz Relay，不新增记忆服务。Mattermost 不进入运行拓扑；也不存在独立 Agent Registry、Memory、Governance、Quota、Audit、Observability 或同步编排 control-plane 服务。

零业务能力 binding 可行性结论：协作（Relay、Channel/Thread、成员与投影）、Agent 回合与四层记忆（Relay 历史、Codex Thread、NIP-AE `core`/`mem/*`）、`PLATFORM_NATIVE` 工具、任务工作台、审批、Quota/计费、审计与业务观测只依赖上述平台核心，全部 `UPSTREAM_SUPPORTED`、`DESIGN_DEFINED` 或以具名平台 SS 为 `ADAPTER_REQUIRED`；零业务 binding 链的平台决策不以业务能力实现的 SF/SS 为依据，DD 证据列中的 SF-CEL/SF-WEK 仅为例证（`02` §7）。业务能力工具在无实现时 effective 为 `NO_PROVIDER`，AgentInstallation 仍可 `ACTIVE`；Workspace `ACTIVE` 不依赖 `WorkspaceCapabilityDefault`；审批附件、任务产物与聊天引用退回 Relay media（DD-87/90/92）。因此“零业务能力 binding”部署是不依赖任何业务能力服务的完整产品：其组合方式（上述各链不引用业务能力、缺席时的确定退化）状态为 `DESIGN_DEFINED`；其中各链自身的状态不因组合而提升，以具名平台 SS 为 `ADAPTER_REQUIRED` 的链在对应接缝闭合前不得 active，该部署也只在 §5 全部平台门禁闭合后才通过门禁。

### 4.2 可选业务能力实现

业务能力实现各自独立部署、独立数据库，可缺席、可替换：一期内置参考实现为“文件存储与在线编辑”能力组件（Cells + DocumentServer，WOPI 为组件内部集成）、WeKnora 与 Wren，各自配 remote adapter 或经 binding 配置的标准协议端点。Application Adapter 是组件 API 的松耦合边界，不取得新业务权威；CocoIndex 如使用，只在 `KNOWLEDGE` 实现内部运行，不进入平台拓扑。外部实现按同一能力契约替换，不改 Core/Worker/契约（DD-87/88）。

### 4.3 数据存储与凭据隔离

平台核心每个服务与每个自托管的业务能力实现各自使用独立数据库实例或至少独立 database、独立凭据与独立私有数据网络，禁止共用 schema 与跨库访问；外部托管（SaaS）实现声明 `VENDOR_MANAGED` 与数据位置并经平台管理员批准，其 adapter 运行体仍在平台运维域内、使用独立凭据与独立私有数据网络（DD-93/94）；Core 不持有任何业务能力服务的数据库凭据，组件状态目录不放在 Core/Worker 运行体内（DD-93）。业务能力服务的密钥由 release `secret_schema` 声明，Core 按通用 schema 校验并经 OpenBao（SF-OBA-01..09）托管与投递，不内置产品密钥语义；`DATA_KEY` 轮换后的已存密文重加密是该服务自己的数据平面职责。该隔离只使用 OpenBao 与 Catalog 的既有能力，为 `DESIGN_DEFINED`。
