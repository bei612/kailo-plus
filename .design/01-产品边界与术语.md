# 产品边界与术语

## 1. 产品目标

`REQ-01` Kailo 是以 Buzz Client Surface 为仅有用户入口的企业级多人、多 Agent 协作管理平台。Client Surface 由三端构成且不增加第四端：Buzz Desktop（Tauri 壳内的 TypeScript/React 应用）、Buzz Mobile（Flutter/Dart 应用）与 Buzz Web（浏览器内的 TypeScript/React 应用）。用户在 Channel/Thread 内协作，并在同一产品中管理 Agent、工具、任务、审批、额度、费用和审计；协作、Agent、任务、审批、额度、费用与审计是平台本体，由平台核心独立成立（DD-87）。云盘（可含在线编辑）、知识库、智能问数等是经 Catalog 接入的业务能力服务（一期提供内置参考实现），按能力类别与版本化能力契约接入（DD-88），可缺席、可被外部同类服务替换；它们是独立管理的外部服务，不属于平台本体；保留原生后台与独立访问入口，管理页面可嵌入客户端，按接入需要使用平台公共服务。工具通过 AgentGateway 注册、发现和调用，Core 不另建工具注册中心。治理语义、权限判定与审计在三端完全一致；三端的能力面按 `REQ-21` 分级，分级只减少入口，不改变任何一次操作的治理结论。

`REQ-02` 产品是一个界面下的两个平面：

- 协作数据平面：Buzz 消息、Agent 回合、工具调用证据和任务执行。业务能力服务的业务数据属于各服务自己的数据平面，平台不持有、不同步，只经能力契约协议取得受权投影（DD-87/89）。
- 管理平面：身份、Tenant、Workspace、成员、资源、owner、授权、审批、Workflow、容量、Quota/计费、审计和组件配置。

`REQ-03` Tenant、Workspace、Authorization、Approval、Workflow、Capacity/Quota/Billing、Operation Audit 和 Business Observability 必须贯穿 Kailo 发起的协作、工具、资源操作以及组件对公共服务的调用。外部服务保留独立管理，其原生 UI 可直接访问或嵌入 Web/Desktop；这些页面自己的业务请求由服务自身处理，不能以嵌入或统一登录跳过公共服务授权。Kailo 的管理 API 仍一律经 BFF，不把组件全部内部业务搬入 Core。

`REQ-04` 每个 ResourceType 必须声明资源新增、修改、删除和处理逻辑变更的增量与对账语义；每个能力实现对自身派生状态负责增量与对账，并经 Adapter Protocol 暴露就绪状态与修订。平台不维护跨服务数据副本，也不编排跨服务数据同步；一个服务需要另一服务的数据时，只按 DD-89 由接收方经授权自行获取（DD-89）。

`REQ-05` 平台自有 Agent 的远程 Chat、Responses、Embedding、Rerank 等模型调用始终经过 AgentGateway，模型路由与上游凭据不下放给 Agent runtime。接入 Kailo 的业务能力服务调用涉及模型时，由其 ApplicationBinding 声明 `PLATFORM_LLM_ROUTE`（经配置指向 AgentGateway `llm_route`，平台计量）或 `SELF_MANAGED_MODEL`（服务自管模型，经 Adapter Protocol 上报 usage）；两种模式下调用授权、Quota/计费和操作审计都由平台照常执行（DD-92）。

`REQ-06` 业务可观测性必须贯穿每个 Governed Action、Workflow、Agent turn、工具/模型调用和业务组件 native execution：按 `operation_id` 统一关联 Tenant、Workspace、发起者、实际执行者、Resource、Agent、审批、授权决策、业务状态/进度/错误、usage/cost 与 evidence。OpenMeter 承担业务用量/成本观测；Temporal、AgentGateway 和组件 native 状态保留各自业务执行权威；Platform Web 提供受权的操作时间线与 Tenant/Workspace 聚合视图。它不包含主机、容器、进程或网络的基础设施 telemetry。

`REQ-07` 在线文档是能力要求，不指定产品：在线编辑是 `FILE_STORAGE` 能力契约的条件能力（DD-103），只作用于声明它的实现自己的 ContentReference：文件所属实现声明 `online_editing=SUPPORTED` 时，其所指文档可在 Buzz Web 与 Buzz Desktop 内查看和受权编辑；未声明时只显示元数据与受权下载。可替换的单位是文件存储实现本身（带或不带在线编辑）；平台不在编辑器与文件存储之间建立数据通道，也不以一个实现的编辑器编辑另一实现的文件（DD-90/103）。编辑器以实现 adapter 生成、经 Core 校验的 DocumentLaunchDescriptor 打开，editor origin 须属于平台管理员批准的部署级许可集合（DD-95）；Web 以 iframe 承载，Desktop 以独立 editor 窗口承载、许可集合由 BFF 运行时下发（DD-104）；Buzz Mobile 按 `REQ-21` 只提供受权只读投影，不承载 editor surface。文件字节与版本权威始终属于 `FILE_STORAGE` 实现。审批附件、任务产物和聊天引用只使用 ContentReference 或 Relay media（DD-90），不依赖任何具体产品，并复用同一文档 surface，不为各页面复制编辑集成。一期内置参考实现把 Cells 与 ONLYOFFICE 作为一个声明在线编辑的 `FILE_STORAGE` 能力组件交付，二者之间的 WOPI 是该组件内部集成（`18`）。

`REQ-08` Buzz Client Surface 是 Kailo 自有页面与同窗口 module 的视觉与语言权威，这些页面使用 Buzz 的浅色/深色/跟随系统语义与 `en/zh-CN` i18n，不建立第二套宿主偏好。独立服务的原生管理页面保留自身主题、语言和功能，支持时通过原生参数继承宿主偏好；主题或语言不一致不是禁止接入或重写原生后台的理由。source-bound editor surface 继续按已声明协议映射 launch 偏好。该权威跨 TypeScript 与 Dart 两套实现成立：主题语义与 locale 取值集合、业务文案的 message key 与复数/日期规则由单一来源定义，两套实现各自渲染但不得各自定义语义或私有 key。同一 message key 在三端缺失翻译时的行为一致，并按 `REQ-21` 在缺口处显示确定状态，不回落原生英文。

`REQ-09` 一期禁止跨 Tenant 直接共享同一 Resource、Asset、native object、ApplicationBinding 或授权 relationship。跨 Tenant 转移只能由源 Tenant 的受治理导出 Workflow 产生具有独立 HUMAN owner 的 ExportPackage Asset，再由目标 Tenant 的独立导入 Workflow 创建新 Resource/Asset、新 owner 和新生命周期；源 ACL、owner、native ID 与临时 URL/token 不继承到目标 Tenant。PlatformProviderBinding 不属于业务 Tenant，因此不参与跨 Tenant 共享或转移。

`REQ-10` Tenant 暂停/删除、Workspace 成员撤权和组件停用必须是 fail-closed、可审计、可继续对账的持久收敛过程。“可恢复”固定表示：未开始不可逆 native 删除时可从 suspended 重新对账并开放；删除已分派后只保证 Workflow 重放/重试、retained native ref 与审计恢复，不承诺已删业务数据还原。

`REQ-11` Core 与承载 WebView 运行时的两端（Buzz Web、Buzz Desktop）必须一次性提供版本化组件宿主，两端共用同一份 Component Host API 与同一组前端扩展槽，不各自定义；两端是两个上游代码库，共享由 Buzz 原版提取的 TypeScript 页面、组件与交互主体，以及 Kailo 平台包与契约生成物；两端只在认证、签名、传输和宿主能力适配处区分，各自接入宿主（SS-WEB-COMPONENT-HOST、SS-DSK-COMPONENT-HOST），Desktop 不执行 remote module（SF-DSK-03、DD-74）。Buzz Mobile 不是组件宿主（`REQ-21`）。后续 ComponentRelease 只有在使用既有平台端口、治理原语、Adapter Protocol、Host API 和前端扩展槽，且后端是独立远程服务、无后端，或（仅 Platform Component）只引用当前主体已编译 driver/internal key 时，才可在运行时登记、审批、绑定、启停、升级与回滚，无需重新构建或发布 Core 与任一端。组件自己的远程服务和前端 artifact 仍须独立交付；“无需发布主体”不等于“不部署组件”。新增平台权威端口、规范 permission、Workflow 语义、前端扩展槽、不兼容 Host API/Adapter Protocol 或新 embedded/internal 代码仍须发布对应主体程序；运行时注册不是任意代码兼容承诺。

`REQ-21` 三端能力面按承载技术分级，分级依据是宿主能否执行经批准的 remote module 与 `SOURCE_BOUND_PROTOCOL` surface，不是产品偏好。Buzz Web 提供完整能力面，含 Component Host API 的全部前端扩展槽（含 remote module）、独立原生管理页面的 `NATIVE_PAGE` 嵌入与 `SOURCE_BOUND_PROTOCOL` surface。Buzz Desktop 承载 WebView 运行时，提供 `HOST_NATIVE`、隔离的 `NATIVE_PAGE` 与 `SOURCE_BOUND_PROTOCOL` surface；原生管理页面按独立来源隔离，不获得主窗口 IPC；其 CSP 编译在签名包内，不执行 remote module，以 remote module 交付的入口显示确定状态并指向 Web（SF-DSK-03、DD-74）。部署级 editor origin 许可集合由 BFF 在运行时持有：Web 的有效集合是它与 Web 由部署配置投影的已生效集合之交集，Desktop 以独立 editor 窗口承载编辑器，其有效集合就是运行时下发的许可集合（DD-104）；有效集合未包含某实现的 editor origin 时，该端编辑入口同样显示确定状态，不隐藏也不报错（DD-95）。Buzz Mobile 是 Flutter 原生应用，不加载 remote module、不承载 `SOURCE_BOUND_PROTOCOL` surface；它对业务能力数据与文档只呈现组件经协议提供、由 BFF 投影的只读投影与可降级操作入口。Mobile 不提供某个入口时，该能力在 Mobile 不可见，而不是以降级形式绕过治理；三端对同一 Governed Action 的准入、审批、额度与审计结论必须相同。

`REQ-22` 组件接入必须对第三方开发者独立可用：不读 `.design` 全文、不接触平台源码的开发者，必须能仅凭公开接入面完成一个 Application Component 的开发、自检与提交。该接入面固定为六件：`contracts/` 派生的 Component SDK（TypeScript，覆盖 Host API、Adapter Protocol、错误分类与 reason code）、manifest schema 与本地校验器、脚手架、可脱离真实平台运行的本地开发环境、语言无关的 Adapter Protocol 一致性测试套件、一个端到端示例组件。SDK 是 `contracts/` 的消费者而非第二权威；一致性套件在线协议层验证，因此后端实现语言不受限。接入面的兼容承诺以 Host API 与 Adapter Protocol 的 range 表达，SDK 版本不得引入 range 之外的能力。`REQ-11` 保证运行时可注册，`REQ-22` 保证开发期可接入；缺其一则组件机制只对平台自身可用。

`REQ-20` Agent 记忆必须分层且只有一个长期记忆权威，四层全部由平台核心承担：Buzz Relay 保存 Channel/Thread/DM 协作历史，Codex Thread/Rollout 保存一次 Agent Session 的持久对话与恢复上下文，Buzz NIP-AE `core` 与 `mem/*` 保存每个 Workspace Agent Installation 的长期核心/冷记忆。企业知识不是记忆层，而是可选的 `KNOWLEDGE` 能力：Agent 经 `APPLICATION` 来源 Tool 按 `consume` 授权访问，可缺席、可替换；平台不把业务能力服务自带的 memory、会话抽取或 prompt 注入纳入 Agent 上下文，也不规定服务内部是否启用它们（DD-92）。Agent Version instructions 与平台策略始终高于记忆；记忆不得更改权限、工具、模型路由或治理规则。

`REQ-23` 用户可在 Workspace 内定义自动化：由该 Workspace Channel 的消息、@提及、定时或外部 webhook 触发，动作是一次 Agent 回合或以 Agent 身份发送一条消息，可在副作用前设置审批关卡，结果回帖到触发消息所在 Thread 或该 Channel。自动化定义是具有 HUMAN owner 的平台事实，每次运行都是经统一准入、审批、Quota、审计与业务观测的 Governed Action，执行由 Temporal 承接（DD-107）；Buzz Relay 自带的 workflow 不作为用户能力，在 Kailo 部署中关闭（DD-106）。Web 与 Desktop 左侧导航必须提供独立的 Workflows（工作流）页面，统一管理这些定义、版本、启停与运行历史，并提供同一份定义的表单/YAML 编辑和复制创建；两端复用同一 TypeScript 页面主体，管理请求一律经 BFF。Agents 页、Tasks、Approvals 或 Temporal UI 均不能代替该入口。Mobile 按 REQ-21 只读，不提供自动化编辑与运行控制。

`REQ-24` **保留 Buzz 原版基础能力，不精简页面与功能，Web 与 Desktop 同等适用。** 固定上游基线中已有的基础协作体验是复用基线，不用重新编写的简化壳替代。保留 Inbox、Pulse、Projects、Agents、Workflows 的独立页面与导航；频道浏览、创建与管理；1v1 与群组私聊；消息、Thread、搜索、通知、附件及其原版操作；完整用户设置与资料编辑。该列举不是删除其余原版基础能力的白名单。两端共用由原版提取的 TypeScript 页面、组件、状态与交互逻辑，差异限制在宿主适配层；不得分别实现两套缩减页面。

- 完整性包含原版全部页面、布局、菜单、设置、操作与交互细节，不仅是上述基础能力列举或 API 可用。认证、权限、quota、计费、审计、Temporal、Codex 与 AgentGateway 的深度集成必须同时保留；恢复原版不能通过整体覆盖 fork 丢失 Kailo 改动，也不能另写缩减替代页。
- 统一身份、权限、工作流、审批、配额与审计只改接治理入口和执行后端，不删除用户能力。创建频道与 DM 成员变更走受治理的管理面；普通消息与读取仍按 DD-75 分端传输。私聊不是公开频道，不对非参与者开放；用户选择参与者不等于授予任意 pubkey 权限。
- Workflows 保留原版创建、编辑、复制、删除、启停、表单/YAML、手动触发、运行历史、状态和步骤轨迹；Temporal 替换持久执行引擎，不替换或取消该页面。Agent 页面改接 Codex 与平台治理，不恢复第二套 Agent/Workflow/记忆/计费权威。
- 上游开关、原生宿主要求或源码缺口必须逐项核实，不以“非核心”、开发不便、未接 BFF 或另一端尚无控件作为删减理由。没有闭合安全边界的执行路径仍不得开放；这种实现缺口计入未交付，不能通过隐藏入口、占位页或改写需求消除。明确的租户权限差异与 REQ-21 的 Mobile 宿主边界仍成立，不用于裁剪 Web/Desktop 的基础协作面。
- 基础能力的完成判据是用户能从原版对应入口完成操作并看见真实结果；只有导航、截图、静态检查、模拟返回或后台 API 不构成完成。缺页、缺操作、原版控件被删、Web/Desktop 行为不一致均是交付缺口。

## 2. 一期范围

- 同时提供 Desktop、Mobile 与 Web 三端；产品主体是 Buzz Relay 与三端客户端 fork。Desktop 与 Mobile 以 `block/buzz` 的 `desktop/` 与 `mobile/` 为受控上游基线，Web 以 `hardy4yooz/buzz-web` 的 `web/` 为受控上游基线，三者的固定 commit 与接缝登记在 `02-源码证据与设计决策.md`。
- 一个 `Tenant` 绑定一个 Buzz `Community`；一个 `Workspace` 绑定一个 Buzz `Channel`。
- Channel 是多人、多 Agent 的协作与授权作用域；Thread 只是 NIP-10 上下文，不是新 scope。
- Agent 在原 Channel/Thread 回复；一期触发方式为 mention、人工分派与自动化（`REQ-23`）。
- Codex app-server 是默认服务端 Agent runtime。
- OIDC 是可替换认证契约，Keycloak 只是默认选项；OIDC claim 不直接授予业务权限。
- **平台核心（强集成、不可替换）**：Core/BFF、Application Worker、Buzz Relay 与三端 Client Surface、Codex、AgentGateway、SpiceDB、Temporal、OpenBao、OpenMeter（DD-87）。SpiceDB 是关系授权权威；Temporal 是 Approval 与持久 Workflow 权威；OpenMeter 是 entitlement、credit、usage 与 billing 权威；AgentGateway 是 MCP/LLM 路由、模型调用网关和调用时 PEP；OpenBao 是 secret 的版本、取用、轮换与撤销权威。零业务能力 binding 时平台核心全部能力可用。
- **内置业务能力参考实现（可替换，按能力类别）**：`FILE_STORAGE`（声明在线编辑）由 Cells 与 ONLYOFFICE DocumentServer 组成的一个能力组件实现（WOPI 为组件内部集成，`18`），`KNOWLEDGE` 由 WeKnora 实现，`DATA_QUERY` 由 Wren 实现。每个实现自持数据库、凭据与执行，对自身派生状态负责增量与对账（DD-89/93）；外部同类服务按同一能力契约替换（DD-88）。
- 三端内置协作、Agent、任务工作台、审批箱、工具、用量/账单、审计与组件管理页面；业务能力服务的页面不内置，由 active ApplicationBinding 经 Component Host 露出。Buzz Mobile 上这些页面按 `REQ-21` 为受权只读视图与可降级操作入口。
- Agent 管理内置于 Platform Core/BFF 与 Buzz Client Surface：Tenant 创建 Agent，Workspace 安装一个确定版本，Channel 配置触发；不引入独立 Agent Registry 服务。
- Agent 记忆内置于同一管理面：Workspace Installation 独立绑定 Buzz NIP-AE 身份，Session 绑定可恢复的 Codex thread；不引入第二长期记忆服务。
- 三端内置按 Tenant/Workspace/Resource/operation 受权过滤的运行状态、失败、用量与成本可观测视图。

## 3. 规范术语

| 术语 | 唯一定义 |
|---|---|
| Tenant | 企业硬隔离根；一期绑定一个 Buzz Community |
| Platform Catalog Tenant | 每个部署唯一的受治理内部 Tenant；仅承载 platform-admin Principal 与全局 Component Definition/Release 登记、审批、撤销和审计，不承载业务 Resource 或跨 Tenant 数据共享 |
| Workspace | Tenant 内协作与授权作用域；一期绑定一个 Buzz Channel |
| Principal | HUMAN、AGENT 或 SERVICE 的 Tenant 内执行身份 |
| Protocol Identity | Principal 在 Buzz 中的独立 Nostr pubkey 投影 |
| Resource | 需要独立 owner、授权和生命周期的组件治理根 |
| Asset | Resource 内被平台持久登记、具有独立 owner 和授权的长期对象 |
| Owner | 对 Resource/Asset 负责的 active HUMAN Principal |
| Governed Action | 从 Web、Agent、Workflow、计划任务或 callback 进入平台的业务意图 |
| Delegation | 用户授予 Agent 的限时、限范围代办权限 |
| Approval | Temporal 管理的参数固定、一次动作级批准过程 |
| Workflow | Temporal 管理的跨请求持久业务生命周期 |
| Application Worker | Kailo 自建、以 Temporal Go SDK 执行 Approval/Workflow 逻辑的独立进程；Temporal Server 不执行应用逻辑 |
| SecretRef | 指向 OpenBao namespace/mount/path 具体 KV v2 版本的 locator；不含 secret 值 |
| ExternalExecution | Workflow 关联的组件 native task/job 执行引用 |
| Operational Capacity | 平台自有 Agent runtime（Codex）的实时并发 slot（`PLATFORM_SLOT`），或业务能力实现经 Adapter Protocol 返回的 native 容量结果；业务能力实现的 runtime 不占用平台 slot |
| Quota | OpenMeter entitlement/credit 与平台未结算 reservation 共同形成的消费准入边界 |
| Usage | 已发生并按稳定 source identity 计量的消耗 |
| Billing | OpenMeter 对 usage、plan、subscription 和 invoice 的归集 |
| AuditEvent | 平台对一个 Governed Action 或外部副作用的追加式结构化事实 |
| Business Observability | 以 `operation_id + native evidence` 关联人、Agent、Resource、审批、执行状态、用量和成本的受权业务视图；不等于基础设施监控或安全审计 |
| Incremental Contract | ResourceType 对稳定身份、修订判断、删除、重算、就绪和对账语义的固定声明 |
| LLM Route | 由 AgentGateway 承载、受 owner 与授权治理的逻辑模型入口；不向调用组件暴露上游凭据 |
| Agent Definition | Tenant 级、具有 HUMAN owner 的 Agent 治理根；表示稳定身份，不表示某次运行进程 |
| Agent Version | Agent Definition 下不可变的行为与运行声明快照；发布后不原地修改 |
| Agent Installation | Workspace 对一个确定 Agent Version 的受治理安装；拥有独立 AgentPrincipal、运行时投影和额度边界 |
| Runtime Profile | 平台预编译的运行时能力合同；一期唯一 active profile 是服务端 Codex |
| Effective Agent Config | Agent Version 声明与 Workspace/Channel/授权/委托/审批/Quota/运行时能力求交后的可执行投影 |
| Skill | 具有 HUMAN owner 和不可变版本的指令型 AI Asset；其工具依赖只声明需求，不授予工具权限 |
| Capability Component | 不拥有新的长期业务 Resource，只按能力契约向某一能力类别的标准 ResourceType 族增加受治理 Action/Web surface 的应用级组件（`resource_type_definitions=[]`，条件见 `03` §3），不绑定具体产品 |
| Platform Component | 实现一个 Core 已知平台权威端口或执行端口的组件；运行时只能更换该端口已登记产品的实例、版本或配置，平台核心组件产品本身不可替换（DD-64/87），不能从 manifest 新增权威或端口 |
| Application Component | 独立外部服务的 Kailo 接入描述：声明提供的 ResourceType、Action 和工具治理元数据，实际工具经 AgentGateway 注册；不是服务本身的管理或部署归属，业务正文、原生后台和 native task 仍由该服务负责 |
| 平台核心 | 强集成、不可替换的协作与治理本体：Core/BFF、Application Worker、Buzz Relay 与三端 Client Surface、Codex、AgentGateway、SpiceDB、Temporal、OpenBao、OpenMeter；零业务能力 binding 时全部核心能力可用（DD-87） |
| 业务能力服务 | 为人与 Agent 提供数据或工具的可缺席、可替换服务（文件存储（可含在线编辑）、知识库、数据查询及以后同类）；自持数据与执行，只经 Catalog/ApplicationBinding 配置与 Adapter Protocol、MCP 等协议接入，保留独立管理后台并可经 Component Host 嵌入（DD-87） |
| 能力类别 | Platform Catalog 中登记的业务能力分类，是运行时数据而非发版常量：预置种子为 `FILE_STORAGE`、`KNOWLEDGE`、`DATA_QUERY`，只使用固定 permission 与通用 Resource/Action/Tool 语义的新类别由平台管理员经受审批的 Governed Action 登记，需要新平台语义（如新的 ProtocolSession kind）的类别随平台发版（DD-102）。同一 Tenant 或 Workspace 的同一类别同时只有一个 active ApplicationBinding；Workspace 级 binding 在该 Workspace 内覆盖 Tenant 级 binding，ToolBinding 与 WorkspaceCapabilityDefault 按 Workspace 级优先、其次 Tenant 级解析；类别内切换实现是新建 binding、旧 binding 转 `DISABLED` 只读保留（DD-88） |
| 能力契约 | 平台为一个能力类别定义的版本化接入合同：标准 ResourceType 族与 `type_key` 命名空间 `<category>.<kind>`、契约键 `<category>.<verb>@vN`（如 `knowledge.search@v1`）及参数/结果 schema、到固定 SpiceDB permission 的映射、ContentReference 语义、观测/计量/取消/删除能力声明与一致性测试套件；ComponentRelease 以 `implements[category@version]` 声明实现（DD-88） |
| Workspace Capability Default | 可空的 `WorkspaceCapabilityDefault(workspace_id, category, resource_id)`，记录 Workspace 在某能力类别下的默认 Resource；不是 Workspace `ACTIVE` 的前提，取代旧 WorkspaceDriveBinding（DD-90） |
| Component Definition | 组件稳定身份及 `PLATFORM/APPLICATION` 分类；不包含可变运行配置 |
| Component Package | 提交给 Platform Catalog 的 release 交付包；只含 manifest、前端 artifact 清单/bytes 与 digest，不携带由 Core 启动的后端 executable。远程服务独立部署并由 Binding 引用；embedded/internal 代码已绑定主体构建版本 |
| Component Release | Component Definition 下不可变、经平台管理员批准的软件与合同快照；固定按 `admission_path` 取证的来源标识（内置参考实现为源码基线 `source_commit`，外部实现为 `vendor`、供应商 API 版本 `artifact_version` 与 `component_package_digest`/`adapter_build_ref`，DD-94(1)/(6)）、前后端交付描述、治理合同、Host API/Adapter Protocol 兼容范围和 artifact digest |
| Platform Provider Binding | Platform Catalog Tenant 对一个已知 `platform_port_key` 的部署级 provider 绑定；同一端口只选择一个 active generation，业务 Tenant 不能创建或修改 |
| Application Binding | 一个业务 Tenant、Workspace 或 Resource 对确定 Application Component Release 与 native scope 的受治理启用；管理员只能选择平台已批准的 release，并只在 release 声明的上界内选择启用的能力类别、模型调用模式与 Tenant 删除时保留（字段以 `03` 为准） |
| Platform Port Router | Platform Core 内按 `platform_port_key + active PlatformProviderBinding generation` 解析已知平台端口的调用模块；它不是独立服务或动态端口注册器 |
| Application Adapter Dispatcher | Platform Core/Worker 内按 active ApplicationBinding generation 选择 `REMOTE_ADAPTER` 或经 binding 配置的标准协议（`PROTOCOL_PEER`）的调用模块；它只派发已通过 Admission 的 Action，不加载业务能力的 `EMBEDDED_DRIVER` |
| Component Binding | `PlatformProviderBinding` 与 `ApplicationBinding` 的统称；二者作用域、权限和生命周期不同，不允许互相替代 |
| Component Runtime Projection | 某个 Binding generation 的可执行快照；固定 release、连接合同、前端 artifact、路由/Action/Tool 投影和状态，新请求只解析 active generation |
| Component Host API | Buzz Web 与 Buzz Desktop 共用的一次性窄前端 ABI，两端作为两个代码库各自实现同一份契约；新增扩展槽与两端共用部分的不兼容变更需要两端都发布，只属于 remote module 的 Host API 变更只需 Web 发布；Buzz Mobile 不实现它。remote module 只在 Web 执行，只能登记固定扩展槽并调用 BFF 语义 API，不取得组件管理凭据或授权权威 |
| Component Adapter Protocol | Core/Worker 调用应用级远程 adapter 的版本化窄协议；完成握手、binding 校验、native scope 解析，以及已准入 Action 的执行、观察、取消、对账和 usage 提取 |
| ContentReference | 指向业务能力实现中一个确定内容版本的稳定引用：`resource_id`、`asset_id\|NONE`、`native_object_ref`、`native_revision`、`display_name`、`media_type`；字段语义由对应能力契约定义（DD-90），不用 mtime 冒充 revision；不包含临时 URL、token 或编辑器 config。取代旧 FileReference |
| ProtocolSession | 一次短期协议会话执行记录（kind、binding、target ContentReference、requested/admitted mode、native_session_ref、state），关联 actor 与 operation；协议细节属于实现该能力的组件，不是 Resource 或 Asset。取代旧 DocumentSession（DD-90） |
| Frontend Presentation Context | 每端各自解析出的 `theme preference + resolved theme + locale`；三端的取值集合与解析规则同源，所有内置页面与 source-bound surface 只消费本端这一份前端上下文，不建立组件级偏好 |
| Collaboration User State | Core 按 HUMAN Principal 保存的 Workspace 收藏/静音和 Channel/Message/Thread 已读位置；一期不使用需要浏览器私钥的 Relay NIP-44 用户状态 |
| Export Package | 源 Tenant 内由受治理导出 Workflow 生成的持久 Asset；具有该 Tenant 的 HUMAN owner、格式版本和内容 digest，不是目标 Tenant 对源 Resource 的共享关系 |
| Collaboration History | Buzz Relay 中的 Channel/Thread/DM event 历史；是协作事实，不是 Agent 私有长期记忆 |
| Runtime Session History | 一个 AgentSession 对应的 Codex Thread/Rollout 持久 turn/item 历史；用于恢复会话，不作跨 Session 长期记忆权威 |
| Agent Core Memory | Buzz NIP-AE `core` head；每个 Agent Installation 的短小、每次新 Session 需要看见的长期状态 |
| Agent Cold Memory | Buzz NIP-AE `mem/*` head 集合；按 slug 按需读取的长期细节，不全量注入 prompt |
| Memory Counterparty | NIP-AE `p` 标签对应的 Tenant CONTROL 协议身份；它是加密/读取对手，不是 Resource/Asset 的 HUMAN Owner |
| Enterprise Knowledge | `KNOWLEDGE` 能力实现管理的可共享、可授权、可增量更新知识 Asset；Agent 只经 Tool 按 `consume` 访问，不是记忆层，不写入 Agent 私有 NIP-AE 记忆（DD-92） |

## 4. 贯穿边界

统一治理与业务可观测性作用于 Kailo 的 Web/BFF command、Buzz 触发的 Agent invocation、AgentGateway tool/LLM call、Temporal 外部副作用、接入管理 action、由上述调用产生的 native execution、受控 callback 和计划任务；组件自有入口的内部业务不自动变成平台 Governed Action，调用平台公共服务时仍须满足对应合同；业务能力实现内部的增量与对账不经平台编排，只以 native execution 与 Adapter Protocol 暴露的就绪/修订进入观测（DD-89）。

SpiceDB Check、OpenMeter 查询、Temporal Worker Poll、组件内部查询等已在一个 Governed Action 内发生的 RPC 只继承 `operation_id`，不递归创建 Action、Workflow、Quota 或 Audit 链。

## 5. 一期排除

- 浏览器本地 Agent、computer-use、微信/游戏客户端操作和通用桌面自动化。Buzz Desktop 与 Buzz Mobile 本身不在排除之列——它们按 `REQ-01` 与 `REQ-21` 是一期交付入口；被排除的是在这些端上执行本机自动化与操作第三方客户端的能力。
- Buzz Mobile 上的 remote module 运行时、Component Host 前端扩展槽与 `SOURCE_BOUND_PROTOCOL` editor surface；移动端不引入 WebView 组件宿主作为替代路径（`REQ-21`）。
- NIP-44 私聊与加密用户状态的服务端托管方案。
- OpenViking 等独立第二长期记忆服务、Codex 自动 Memory Pipeline。原版 Huddle/视频、Projects 与个人日历不因“非核心”标签被整体排除，按 REQ-24 核对其原生能力与治理适配。记忆一期只使用 REQ-20 的 Buzz Relay/Codex Thread/Buzz NIP-AE `core`/`mem/*` 四层；`KNOWLEDGE` 能力不是记忆层（DD-92）。
- 未登记来源或可任意导航的 iframe、未由平台管理员批准或 digest 不匹配的 remote JavaScript、Module Federation、Web Component 和通用 schema renderer。经批准的 ComponentRelease 可在 Buzz Web 的固定 Component Host API 中加载同窗口 remote module（Desktop 不执行，SF-DSK-03）；它是宿主信任代码而非安全沙箱。独立服务原生管理页面按 `07` §4.6 的 `NATIVE_PAGE` 来源与会话隔离承载，不强制改写成 module。声明在线编辑的 `FILE_STORAGE` 实现经 `SOURCE_BOUND_PROTOCOL` 前端交付、以 release 登记的固定 editor origin 与经 Core 校验的 DocumentLaunchDescriptor 约束的 Web editor iframe 与 Desktop 独立 editor 窗口仍是 REQ-07 的协议适配，不是任意 iframe；内置参考实现的具体约束见 `18`。
- 上传并在 Core/Buzz 主机启动组件后端可执行文件。Mattermost 的本机 subprocess 插件模型只作前端 manifest/registry/lifecycle 参考；平台级组件通过已知 port 的 provider binding 接入，`EMBEDDED_DRIVER` 只限平台自身；业务能力服务只使用独立远程 adapter 或经 binding 配置的标准协议（DD-58/64/87）。
- 把业务能力服务自带的 chat、AI plugin、宏、插件市场、Agent/skill/sandbox 与个人 memory 变成 Kailo 的 Agent 上下文或第二执行权威；展示独立服务原生后台不等于建立第二平台权威，平台不规定服务内部是否启用它们（内置参考实现 ONLYOFFICE 与 WeKnora 由各自 release 关闭）。Buzz 是聊天权威，平台自有 Agent 的模型调用经 AgentGateway，业务能力服务的模型调用按 REQ-05 的 binding 模式治理。
- temporal-ui 作为租户任务工作台；Temporal Nexus 应用侧接入。
- Codex host shell/process，以及任何成为平台核心第二运行链或重复管理面的集成形态：第二套 Agent 运行链、Agent Registry、Workflow、聊天、记忆或计费权威。知识、文件、数据查询类产品只能作为能力类别的实现经 Catalog 与 ApplicationBinding 接入并可替换，不因产品名被排除；同一 Tenant 或 Workspace 的同一能力类别同时只有一个 active ApplicationBinding（DD-88），因此同一 scope 不并行两套知识图谱；Agent 跨 Session 私有长期记忆仍以 Buzz NIP-AE 为唯一权威。
- Kubernetes 绑定和新的 Java 组件；Keycloak 例外且保持可替换。

## 6. 紧凑性判据

一个自研模块只在删除后会丢失明确 Requirement、且已选上游没有同一权威时保留。逻辑模块默认同进程；只有上游本来是独立服务、需要进程级隔离或拥有独立权威时才独立运行。
