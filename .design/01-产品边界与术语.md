# 产品边界与术语

## 1. 产品目标

`REQ-01` Kailo 是以 Buzz Client Surface 为仅有用户入口的企业级多人、多 Agent 协作管理平台。Client Surface 由三端构成且不增加第四端：Buzz Desktop（Tauri 壳内的 TypeScript/React 应用）、Buzz Mobile（Flutter/Dart 应用）与 Buzz Web（浏览器内的 TypeScript/React 应用）。用户在 Channel/Thread 内协作，并在同一产品中管理 Agent、工具、任务、审批、额度、费用和审计；协作、Agent、任务、审批、额度、费用与审计是平台本体，由平台核心独立成立（DD-87）。云盘、在线文档编辑、知识库、智能问数等是经 Catalog 接入的业务能力服务（一期提供内置参考实现），按能力类别与版本化能力契约接入（DD-88），可缺席、可被外部同类服务替换；它们的管理面经平台前端 Component Host 露出，认证、授权、审批、Quota/计费、审计与观测平台公用。治理语义、权限判定与审计在三端完全一致；三端的能力面按 `REQ-21` 分级，分级只减少入口，不改变任何一次操作的治理结论。

`REQ-02` 产品是一个界面下的两个平面：

- 协作数据平面：Buzz 消息、Agent 回合、工具调用证据和任务执行。业务能力服务的业务数据属于各服务自己的数据平面，平台不持有、不同步，只经能力契约协议取得受权投影（DD-87/89）。
- 管理平面：身份、Tenant、Workspace、成员、资源、owner、授权、审批、Workflow、容量、Quota/计费、审计和组件配置。

`REQ-03` Tenant、Workspace、Authorization、Approval、Workflow、Capacity/Quota/Billing、Operation Audit 和 Business Observability 必须贯穿 Buzz、平台服务与每一个配置接入的平台级或应用级组件；组件原生 UI 不是一期用户入口。

`REQ-04` 每个 ResourceType 必须声明资源新增、修改、删除和处理逻辑变更的增量与对账语义；每个能力实现对自身派生状态负责增量与对账，并经 Adapter Protocol 暴露就绪状态与修订。平台不维护跨服务数据副本，也不编排跨服务数据同步；一个服务需要另一服务的数据时，只按 DD-89 由接收方经授权自行获取（DD-89）。

`REQ-05` 平台自有 Agent 的远程 Chat、Responses、Embedding、Rerank 等模型调用始终经过 AgentGateway，模型路由与上游凭据不下放给 Agent runtime。业务能力服务的模型调用由其 ApplicationBinding 声明 `PLATFORM_LLM_ROUTE`（经配置指向 AgentGateway `llm_route`，平台计量）或 `SELF_MANAGED_MODEL`（服务自管模型，经 Adapter Protocol 上报 usage）；两种模式下调用授权、Quota/计费和操作审计都由平台照常执行（DD-92）。

`REQ-06` 业务可观测性必须贯穿每个 Governed Action、Workflow、Agent turn、工具/模型调用和业务组件 native execution：按 `operation_id` 统一关联 Tenant、Workspace、发起者、实际执行者、Resource、Agent、审批、授权决策、业务状态/进度/错误、usage/cost 与 evidence。OpenMeter 承担业务用量/成本观测；Temporal、AgentGateway 和组件 native 状态保留各自业务执行权威；Platform Web 提供受权的操作时间线与 Tenant/Workspace 聚合视图。它不包含主机、容器、进程或网络的基础设施 telemetry。

`REQ-07` 在线文档是能力类别要求，不指定产品：`DOCUMENT_EDITING` v1 只作用于同一实现（同一 ApplicationBinding）提供的 `FILE_STORAGE` ContentReference：文件所属 binding 同时启用 `DOCUMENT_EDITING` 时，其所指文档可在 Buzz Web 与 Buzz Desktop 内查看和受权编辑；未启用时只显示元数据与受权下载，不跨实现读写文件字节（DD-90）；Buzz Mobile 按 `REQ-21` 只提供受权只读投影，不承载 editor surface。文件字节与版本权威始终属于 `FILE_STORAGE` 实现。审批附件、任务产物和聊天引用只使用 ContentReference 或 Relay media（DD-90），不依赖任何具体产品，并复用同一文档 surface，不为各页面复制编辑集成。一期内置参考实现把 Cells 与 ONLYOFFICE 作为一个“文件存储与在线编辑”能力组件交付，二者之间的 WOPI 是该组件内部集成（`18`）。

`REQ-08` Buzz Client Surface 是全部前端内容的视觉与语言权威。协作数据平面、管理平面、平台级组件、应用级组件及 source-bound editor surface 必须统一继承 Buzz 的浅色/深色/跟随系统语义与 `en/zh-CN` i18n；组件不得出现独立主题开关、独立语言偏好、未翻译业务文案或与 Buzz 冲突的视觉 token。该权威跨 TypeScript 与 Dart 两套实现成立：主题语义与 locale 取值集合、业务文案的 message key 与复数/日期规则由单一来源定义，两套实现各自渲染但不得各自定义语义或私有 key。同一 message key 在三端缺失翻译时的行为一致，并按 `REQ-21` 在缺口处显示确定状态，不回落原生英文。

`REQ-09` 一期禁止跨 Tenant 直接共享同一 Resource、Asset、native object、ApplicationBinding 或授权 relationship。跨 Tenant 转移只能由源 Tenant 的受治理导出 Workflow 产生具有独立 HUMAN owner 的 ExportPackage Asset，再由目标 Tenant 的独立导入 Workflow 创建新 Resource/Asset、新 owner 和新生命周期；源 ACL、owner、native ID 与临时 URL/token 不继承到目标 Tenant。PlatformProviderBinding 不属于业务 Tenant，因此不参与跨 Tenant 共享或转移。

`REQ-10` Tenant 暂停/删除、Workspace 成员撤权和组件停用必须是 fail-closed、可审计、可继续对账的持久收敛过程。“可恢复”固定表示：未开始不可逆 native 删除时可从 suspended 重新对账并开放；删除已分派后只保证 Workflow 重放/重试、retained native ref 与审计恢复，不承诺已删业务数据还原。

`REQ-11` Core 与承载 WebView 运行时的两端（Buzz Web、Buzz Desktop）必须一次性提供版本化组件宿主，两端共用同一份 Component Host API 与同一组前端扩展槽，不各自定义。Buzz Mobile 不是组件宿主（`REQ-21`）。后续 ComponentRelease 只有在使用既有平台端口、治理原语、Adapter Protocol、Host API 和前端扩展槽，且后端是独立远程服务、无后端，或（仅 Platform Component）只引用当前主体已编译 driver/internal key 时，才可在运行时登记、审批、绑定、启停、升级与回滚，无需重新构建或发布 Core 与任一端。组件自己的远程服务和前端 artifact 仍须独立交付；“无需发布主体”不等于“不部署组件”。新增平台权威端口、规范 permission、Workflow 语义、前端扩展槽、不兼容 Host API/Adapter Protocol 或新 embedded/internal 代码仍须发布对应主体程序；运行时注册不是任意代码兼容承诺。

`REQ-21` 三端能力面按承载技术分级，分级依据是宿主能否执行经批准的 remote module 与 `SOURCE_BOUND_PROTOCOL` surface，不是产品偏好。Buzz Web 与 Buzz Desktop 承载 WebView 运行时，提供完整能力面，含 Component Host API 的前端扩展槽与 `SOURCE_BOUND_PROTOCOL` surface。Buzz Mobile 是 Flutter 原生应用，不加载 remote module、不承载 `SOURCE_BOUND_PROTOCOL` surface；它对业务能力数据与文档只呈现组件经协议提供、由 BFF 投影的只读投影与可降级操作入口。任一端不提供某个入口时，该能力在该端不可见，而不是以降级形式绕过治理；三端对同一 Governed Action 的准入、审批、额度与审计结论必须相同。

`REQ-22` 组件接入必须对第三方开发者独立可用：不读 `.design` 全文、不接触平台源码的开发者，必须能仅凭公开接入面完成一个 Application Component 的开发、自检与提交。该接入面固定为六件：`contracts/` 派生的 Component SDK（TypeScript，覆盖 Host API、Adapter Protocol、错误分类与 reason code）、manifest schema 与本地校验器、脚手架、可脱离真实平台运行的本地开发环境、语言无关的 Adapter Protocol 一致性测试套件、一个端到端示例组件。SDK 是 `contracts/` 的消费者而非第二权威；一致性套件在线协议层验证，因此后端实现语言不受限。接入面的兼容承诺以 Host API 与 Adapter Protocol 的 range 表达，SDK 版本不得引入 range 之外的能力。`REQ-11` 保证运行时可注册，`REQ-22` 保证开发期可接入；缺其一则组件机制只对平台自身可用。

`REQ-20` Agent 记忆必须分层且只有一个长期记忆权威，四层全部由平台核心承担：Buzz Relay 保存 Channel/Thread/DM 协作历史，Codex Thread/Rollout 保存一次 Agent Session 的持久对话与恢复上下文，Buzz NIP-AE `core` 与 `mem/*` 保存每个 Workspace Agent Installation 的长期核心/冷记忆。企业知识不是记忆层，而是可选的 `KNOWLEDGE` 能力：Agent 经 `APPLICATION` 来源 Tool 按 `consume` 授权访问，可缺席、可替换；业务能力服务自带的 memory、会话抽取或 prompt 注入固定关闭（DD-92）。Agent Version instructions 与平台策略始终高于记忆；记忆不得更改权限、工具、模型路由或治理规则。

## 2. 一期范围

- 同时提供 Desktop、Mobile 与 Web 三端；产品主体是 Buzz Relay 与三端客户端 fork。Desktop 与 Mobile 以 `block/buzz` 的 `desktop/` 与 `mobile/` 为受控上游基线，Web 以 `hardy4yooz/buzz-web` 的 `web/` 为受控上游基线，三者的固定 commit 与接缝登记在 `02-源码证据与设计决策.md`。
- 一个 `Tenant` 绑定一个 Buzz `Community`；一个 `Workspace` 绑定一个 Buzz `Channel`。
- Channel 是多人、多 Agent 的协作与授权作用域；Thread 只是 NIP-10 上下文，不是新 scope。
- Agent 在原 Channel/Thread 回复；一期触发方式为 mention 和人工分派。
- Codex app-server 是默认服务端 Agent runtime。
- OIDC 是可替换认证契约，Keycloak 只是默认选项；OIDC claim 不直接授予业务权限。
- **平台核心（强集成、不可替换）**：Core/BFF、Application Worker、Buzz Relay 与三端 Client Surface、Codex、AgentGateway、SpiceDB、Temporal、OpenBao、OpenMeter（DD-87）。SpiceDB 是关系授权权威；Temporal 是 Approval 与持久 Workflow 权威；OpenMeter 是 entitlement、credit、usage 与 billing 权威；AgentGateway 是 MCP/LLM 路由、模型调用网关和调用时 PEP；OpenBao 是 secret 的版本、取用、轮换与撤销权威。零业务能力 binding 时平台核心全部能力可用。
- **内置业务能力参考实现（可替换，按能力类别）**：`FILE_STORAGE` 与 `DOCUMENT_EDITING` 由 Cells 与 ONLYOFFICE DocumentServer 组成的一个能力组件实现（WOPI 为组件内部集成，`18`），`KNOWLEDGE` 由 WeKnora 实现，`DATA_QUERY` 由 Wren 实现。每个实现自持数据库、凭据与执行，对自身派生状态负责增量与对账（DD-89/93）；外部同类服务按同一能力契约替换（DD-88）。
- 三端内置协作、Agent、任务工作台、审批箱、工具、用量/账单、审计与组件管理页面；业务能力服务的页面不内置，由 active ApplicationBinding 经 Component Host 露出。Buzz Mobile 上这些页面按 `REQ-21` 为受权只读视图与可降级操作入口。
- Agent 管理内置于 Platform Core/BFF 与 Buzz Client Surface：Tenant 创建 Agent，Workspace 安装一个确定版本，Channel 配置触发；不引入独立 Agent Registry 服务。
- Agent 记忆内置于同一管理面：Workspace Installation 独立绑定 Buzz NIP-AE 身份，Session 绑定可恢复的 Codex thread；不引入第二长期记忆服务。
- 三端内置按 Tenant/Workspace/Resource/operation 受权过滤的运行状态、失败、用量与成本可观测视图。

## 3. 规范术语

| 术语 | 唯一定义 |
|---|---|
| Tenant | 企业硬隔离根；一期绑定一个 Buzz Community |
| Platform Catalog Tenant | 每个部署唯一的受治理内部 Tenant；仅承载 platform-admin Principal 与全局 Component Definition/Release 登记、审批、撤销和审计，不承载业务 Resource 或跨 Tenant 数据共享 |
| Workspace | Tenant 内协作与授权作用域；一期绑定一个 Buzz Channel |
| Principal | HUMAN、AGENT 或 SERVICE 的 Tenant 内执行身份 |
| Protocol Identity | Principal 在 Buzz 中的独立 Nostr pubkey 投影 |
| Resource | 需要独立 owner、授权和生命周期的组件治理根 |
| Asset | Resource 内被平台持久登记、具有独立 owner 和授权的长期对象 |
| Owner | 对 Resource/Asset 负责的 active HUMAN Principal |
| Governed Action | 从 Web、Agent、Workflow、计划任务或 callback 进入平台的业务意图 |
| Delegation | 用户授予 Agent 的限时、限范围代办权限 |
| Approval | Temporal 管理的参数固定、一次动作级批准过程 |
| Workflow | Temporal 管理的跨请求持久业务生命周期 |
| Application Worker | Kailo 自建、以 Temporal Go SDK 执行 Approval/Workflow 逻辑的独立进程；Temporal Server 不执行应用逻辑 |
| SecretRef | 指向 OpenBao namespace/mount/path 具体 KV v2 版本的 locator；不含 secret 值 |
| ExternalExecution | Workflow 关联的组件 native task/job 执行引用 |
| Operational Capacity | 平台自有 Agent runtime（Codex）的实时并发 slot（`PLATFORM_SLOT`），或业务能力实现经 Adapter Protocol 返回的 native 容量结果；业务能力实现的 runtime 不占用平台 slot |
| Quota | OpenMeter entitlement/credit 与平台未结算 reservation 共同形成的消费准入边界 |
| Usage | 已发生并按稳定 source identity 计量的消耗 |
| Billing | OpenMeter 对 usage、plan、subscription 和 invoice 的归集 |
| AuditEvent | 平台对一个 Governed Action 或外部副作用的追加式结构化事实 |
| Business Observability | 以 `operation_id + native evidence` 关联人、Agent、Resource、审批、执行状态、用量和成本的受权业务视图；不等于基础设施监控或安全审计 |
| Incremental Contract | ResourceType 对稳定身份、修订判断、删除、重算、就绪和对账语义的固定声明 |
| LLM Route | 由 AgentGateway 承载、受 owner 与授权治理的逻辑模型入口；不向调用组件暴露上游凭据 |
| Agent Definition | Tenant 级、具有 HUMAN owner 的 Agent 治理根；表示稳定身份，不表示某次运行进程 |
| Agent Version | Agent Definition 下不可变的行为与运行声明快照；发布后不原地修改 |
| Agent Installation | Workspace 对一个确定 Agent Version 的受治理安装；拥有独立 AgentPrincipal、运行时投影和额度边界 |
| Runtime Profile | 平台预编译的运行时能力合同；一期唯一 active profile 是服务端 Codex |
| Effective Agent Config | Agent Version 声明与 Workspace/Channel/授权/委托/审批/Quota/运行时能力求交后的可执行投影 |
| Skill | 具有 HUMAN owner 和不可变版本的指令型 AI Asset；其工具依赖只声明需求，不授予工具权限 |
| Capability Component | 不拥有新的长期业务 Resource，只按能力契约向某一能力类别的标准 ResourceType 族增加受治理 Action/Web surface 的应用级组件；例如 `DOCUMENT_EDITING` 实现作用于 `FILE_STORAGE` 的 ContentReference，不绑定具体文件产品 |
| Platform Component | 实现一个 Core 已知平台权威端口或执行端口的组件；运行时只能更换该端口的兼容 provider，不能从 manifest 新增权威或端口 |
| Application Component | 登记业务 ResourceType、Action、Tool，或作为 Capability 作用于既有 ResourceType；业务正文和 native task 仍由该组件负责 |
| 平台核心 | 强集成、不可替换的协作与治理本体：Core/BFF、Application Worker、Buzz Relay 与三端 Client Surface、Codex、AgentGateway、SpiceDB、Temporal、OpenBao、OpenMeter；零业务能力 binding 时全部核心能力可用（DD-87） |
| 业务能力服务 | 为人与 Agent 提供数据或工具的可缺席、可替换服务（文件存储、在线文档编辑、知识库、数据查询及以后同类）；自持数据与执行，只经 Catalog/ApplicationBinding 配置与 Adapter Protocol、MCP 等协议接入，管理面经 Component Host 露出（DD-87） |
| 能力类别 | 平台契约固定的业务能力分类，一期为 `FILE_STORAGE`、`DOCUMENT_EDITING`、`KNOWLEDGE`、`DATA_QUERY`；新增类别须改平台契约。同一 Tenant 或 Workspace 的同一类别同时只有一个 active ApplicationBinding；Workspace 级 binding 在该 Workspace 内覆盖 Tenant 级 binding，ToolBinding 与 WorkspaceCapabilityDefault 按 Workspace 级优先、其次 Tenant 级解析；类别内切换实现是新建 binding、旧 binding 转 `DISABLED` 只读保留（DD-88） |
| 能力契约 | 平台为一个能力类别定义的版本化接入合同：标准 ResourceType 族与 `type_key` 命名空间 `<category>.<kind>`、契约键 `<category>.<verb>@vN`（如 `knowledge.search@v1`）及参数/结果 schema、到固定 SpiceDB permission 的映射、ContentReference 语义、观测/计量/取消/删除能力声明与一致性测试套件；ComponentRelease 以 `implements[category@version]` 声明实现（DD-88） |
| Workspace Capability Default | 可空的 `WorkspaceCapabilityDefault(workspace_id, category, resource_id)`，记录 Workspace 在某能力类别下的默认 Resource；不是 Workspace `ACTIVE` 的前提，取代旧 WorkspaceDriveBinding（DD-90） |
| Component Definition | 组件稳定身份及 `PLATFORM/APPLICATION` 分类；不包含可变运行配置 |
| Component Package | 提交给 Platform Catalog 的 release 交付包；只含 manifest、前端 artifact 清单/bytes 与 digest，不携带由 Core 启动的后端 executable。远程服务独立部署并由 Binding 引用；embedded/internal 代码已绑定主体构建版本 |
| Component Release | Component Definition 下不可变、经平台管理员批准的软件与合同快照；固定源码基线、前后端交付描述、治理合同、Host API/Adapter Protocol 兼容范围和 artifact digest |
| Platform Provider Binding | Platform Catalog Tenant 对一个已知 `platform_port_key` 的部署级 provider 绑定；同一端口只选择一个 active generation，业务 Tenant 不能创建或修改 |
| Application Binding | 一个业务 Tenant、Workspace 或 Resource 对确定 Application Component Release 与 native scope 的受治理启用；管理员只能选择平台已批准的 release，并只在 release 声明的上界内选择启用的能力类别、模型调用模式与 Tenant 删除时保留（字段以 `03` 为准） |
| Platform Port Router | Platform Core 内按 `platform_port_key + active PlatformProviderBinding generation` 解析已知平台端口的调用模块；它不是独立服务或动态端口注册器 |
| Application Adapter Dispatcher | Platform Core/Worker 内按 active ApplicationBinding generation 选择 `REMOTE_ADAPTER` 或经 binding 配置的标准协议（`PROTOCOL_PEER`）的调用模块；它只派发已通过 Admission 的 Action，不加载业务能力的 `EMBEDDED_DRIVER` |
| Component Binding | `PlatformProviderBinding` 与 `ApplicationBinding` 的统称；二者作用域、权限和生命周期不同，不允许互相替代 |
| Component Runtime Projection | 某个 Binding generation 的可执行快照；固定 release、连接合同、前端 artifact、路由/Action/Tool 投影和状态，新请求只解析 active generation |
| Component Host API | Buzz Web 与 Buzz Desktop 共用的一次性窄前端 ABI，两端实现同一份契约；Buzz Mobile 不实现它。remote module 只能登记固定扩展槽并调用 BFF 语义 API，不取得组件管理凭据或授权权威 |
| Component Adapter Protocol | Core/Worker 调用应用级远程 adapter 的版本化窄协议；完成握手、binding 校验、native scope 解析，以及已准入 Action 的执行、观察、取消、对账和 usage 提取 |
| ContentReference | 指向业务能力实现中一个确定内容版本的稳定引用：`resource_id`、`asset_id\|NONE`、`native_object_ref`、`native_revision`、`display_name`、`media_type`；字段语义由对应能力契约定义（DD-90），不用 mtime 冒充 revision；不包含临时 URL、token 或编辑器 config。取代旧 FileReference |
| ProtocolSession | 一次短期协议会话执行记录（kind、binding、target ContentReference、requested/admitted mode、native_session_ref、state），关联 actor 与 operation；协议细节属于实现该能力的组件，不是 Resource 或 Asset。取代旧 DocumentSession（DD-90） |
| Frontend Presentation Context | 每端各自解析出的 `theme preference + resolved theme + locale`；三端的取值集合与解析规则同源，所有内置页面与 source-bound surface 只消费本端这一份前端上下文，不建立组件级偏好 |
| Collaboration User State | Core 按 HUMAN Principal 保存的 Workspace 收藏/静音和 Channel/Message/Thread 已读位置；一期不使用需要浏览器私钥的 Relay NIP-44 用户状态 |
| Export Package | 源 Tenant 内由受治理导出 Workflow 生成的持久 Asset；具有该 Tenant 的 HUMAN owner、格式版本和内容 digest，不是目标 Tenant 对源 Resource 的共享关系 |
| Collaboration History | Buzz Relay 中的 Channel/Thread/DM event 历史；是协作事实，不是 Agent 私有长期记忆 |
| Runtime Session History | 一个 AgentSession 对应的 Codex Thread/Rollout 持久 turn/item 历史；用于恢复会话，不作跨 Session 长期记忆权威 |
| Agent Core Memory | Buzz NIP-AE `core` head；每个 Agent Installation 的短小、每次新 Session 需要看见的长期状态 |
| Agent Cold Memory | Buzz NIP-AE `mem/*` head 集合；按 slug 按需读取的长期细节，不全量注入 prompt |
| Memory Counterparty | NIP-AE `p` 标签对应的 Tenant CONTROL 协议身份；它是加密/读取对手，不是 Resource/Asset 的 HUMAN Owner |
| Enterprise Knowledge | `KNOWLEDGE` 能力实现管理的可共享、可授权、可增量更新知识 Asset；Agent 只经 Tool 按 `consume` 访问，不是记忆层，不写入 Agent 私有 NIP-AE 记忆（DD-92） |

## 4. 贯穿边界

统一治理与业务可观测性作用于 Web/BFF command、Buzz 触发的 Agent invocation、AgentGateway tool/LLM call、Temporal 外部副作用、组件管理 action、业务能力服务 native execution、受控 callback 和计划任务；业务能力实现内部的增量与对账不经平台编排，只以 native execution 与 Adapter Protocol 暴露的就绪/修订进入观测（DD-89）。

SpiceDB Check、OpenMeter 查询、Temporal Worker Poll、组件内部查询等已在一个 Governed Action 内发生的 RPC 只继承 `operation_id`，不递归创建 Action、Workflow、Quota 或 Audit 链。

## 5. 一期排除

- 浏览器本地 Agent、computer-use、微信/游戏客户端操作和通用桌面自动化。Buzz Desktop 与 Buzz Mobile 本身不在排除之列——它们按 `REQ-01` 与 `REQ-21` 是一期交付入口；被排除的是在这些端上执行本机自动化与操作第三方客户端的能力。
- Buzz Mobile 上的 remote module 运行时、Component Host 前端扩展槽与 `SOURCE_BOUND_PROTOCOL` editor surface；移动端不引入 WebView 组件宿主作为替代路径（`REQ-21`）。
- NIP-44 私聊与加密用户状态的服务端托管方案。
- Huddle/视频、OpenViking 等独立第二长期记忆服务、Codex 自动 Memory Pipeline、个人日历、项目管理和非核心办公扩展。一期只使用 REQ-20 的 Buzz Relay/Codex Thread/Buzz NIP-AE `core`/`mem/*` 四层；`KNOWLEDGE` 能力不是记忆层（DD-92）。
- 任意 iframe、未由平台管理员批准或 digest 不匹配的 remote JavaScript、Module Federation、Web Component 和通用 schema renderer。经批准的 ComponentRelease 可在 Buzz Web 与 Buzz Desktop 的固定 Component Host API 中加载同窗口 remote module；它是宿主信任代码而非安全沙箱。`DOCUMENT_EDITING` 实现经 `SOURCE_BOUND_PROTOCOL` 前端交付、以固定 origin 与 BFF launch descriptor 约束的 editor iframe 仍是 REQ-07 的协议适配，不是任意 iframe；内置参考实现的具体约束见 `18`。
- 上传并在 Core/Buzz 主机启动组件后端可执行文件。Mattermost 的本机 subprocess 插件模型只作前端 manifest/registry/lifecycle 参考；平台级组件通过已知 port 的 provider binding 接入，`EMBEDDED_DRIVER` 只限平台自身；业务能力服务只使用独立远程 adapter 或经 binding 配置的标准协议（DD-58/64/87）。
- 业务能力服务自带的 chat、AI plugin、宏、插件市场、Agent/skill/sandbox 与个人 memory（内置参考实现中即 ONLYOFFICE 与 WeKnora 的对应能力）；Buzz 是聊天权威，平台自有 Agent 的模型调用经 AgentGateway，业务能力服务的模型调用按 REQ-05 的 binding 模式治理。
- temporal-ui 作为租户任务工作台；Temporal Nexus 应用侧接入。
- Codex host shell/process、AgentTeams、AgentRegistry、CopilotKit、Plane、RAGFlow、EdgeQuake、MinerU 等第二运行链或重复管理面。EdgeQuake 是完整第二套 GraphRAG 摄取与检索系统；`KNOWLEDGE` 能力在同一 Tenant 或 Workspace 同时只有一个 active ApplicationBinding（DD-88），一期内置参考实现为 WeKnora，EdgeQuake 不作为一期内置参考实现并行接入；Agent 跨 Session 私有长期记忆仍以 Buzz NIP-AE 为唯一权威。
- Kubernetes 绑定和新的 Java 组件；Keycloak 例外且保持可替换。

## 6. 紧凑性判据

一个自研模块只在删除后会丢失明确 Requirement、且已选上游没有同一权威时保留。逻辑模块默认同进程；只有上游本来是独立服务、需要进程级隔离或拥有独立权威时才独立运行。
