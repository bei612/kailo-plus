# ADR-02：Core 内部模块通信与 API schema 工具

- 状态：已接受
- 日期：2026-09-22
- 决策者：Kailo 实施工程负责人

## 背景

`01-工程结构与模块边界.md` §3 划定 Core 内部模块边界，`AGENTS.md` 规则 6 禁止把这些模块拆成微服务。同时 `00-实施总纲.md` Stage 0 第 2 项要求从 `.design/03` 维护一个语言无关的 contract package，并明写「生成物不得成为第二权威」。`01` §3 另有一条硬约束：Rust、Go、TypeScript 与 adapter 语言不得各自维护同名但不同义的枚举。

两个问题要一起回答：模块之间怎么通信，以及对外契约由什么描述。

## 候选方案

### 模块通信

- 进程内直接调用，边界靠 crate 划分与可见性约束：零序列化开销，事务边界天然共享，违反边界在编译期被拒。
- 进程内消息总线：解耦度更高，但把编译期可检查的边界换成运行期约定，且会诱导出实质上的微服务拆分，与规则 6 冲突。

### 契约描述

- 从 Rust 类型生成 schema（`utoipa` 一类）：写起来最省事，但让 Rust 成为事实权威，TypeScript 与 adapter 沦为下游。这直接违反「生成物不得成为第二权威」，也让非 Rust 侧无法在不读 Rust 代码的前提下实现 adapter。
- 手写 schema 为唯一来源，各语言从它生成：多一步，但唯一权威明确，枚举只有一个定义点。
- Protobuf / gRPC：schema 优先同样成立，但引入额外运行时与工具链，而 BFF 面向浏览器仍需 JSON 转换层。

## 决策

**模块通信**：Core 内部模块以进程内直接函数调用通信，模块即 crate。跨模块依赖只通过各 crate 显式导出的接口，方向在 `01-工程结构与模块边界.md` §3 固定，禁止反向依赖与循环依赖。模块之间不引入序列化、不引入网络跳、不引入消息总线。

**契约描述**：对外契约以 **JSON Schema 2020-12** 描述，手写并存放于 `contracts/`，是唯一权威。

- 覆盖范围按 `00-实施总纲.md` Stage 0 第 2 项：标识符、枚举、错误码、Action / Workflow / Adapter / Host 协议。
- 全部封闭枚举在 `contracts/enums/` 单点定义，其他 schema 以 `$ref` 引用，不允许就地重复定义枚举值。
- HTTP 表面另有一份 OpenAPI 3.1 文档，其 schema 部分全部 `$ref` 指向 `contracts/`，不自带类型定义。
- 错误体结构统一引用 `06-工程基线规范.md` §4 的六类与 reason code。

## 后果

正面：模块边界在编译期可检查；契约有唯一权威，枚举漂移在源头被消除；非 Rust 实现者只读 `contracts/` 即可实现 adapter。

负面：改契约要手写 JSON Schema，比改 Rust 结构体慢；Rust 与 TypeScript 的类型是生成物，需要 CI 保证与 schema 同步（由 ADR-03 承担）；进程内调用意味着单个模块的故障不被进程边界隔离。

锁定：Core 是单进程部署单元。放弃：模块独立扩缩容与独立发布的能力，这正是规则 6 要求放弃的。

## 替换边界

模块通信方式在 `AGENTS.md` 规则 6 被修改前不重新评估——该规则来自 `.design` 的服务边界结论，改它要走设计变更流程。

契约工具在以下条件下重新评估：出现必须由二进制协议承载的高频内部调用面；或 JSON Schema 无法表达某个 `.design` 合同所需的约束。更换需要改动 `contracts/` 全部文件与 ADR-03 的生成管线，业务代码通过生成物隔离。

## 不改变的事

本 ADR 不改变 `.design` 的任何权威划分与能力状态。`.design/03` 仍是实体、字段与状态的唯一权威，`contracts/` 是它的工程投影，两者冲突时以 `.design` 为准。
